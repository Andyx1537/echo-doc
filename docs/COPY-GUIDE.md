## 1.0 🔴 对象范围与自我定位（2026-08-25 制作人裁定 · 优先于本文其余各节）

> 制作人原话：「我们不会引导人走向那个方向，而且把我们基调上面的**故去之人或者物，扩展成阔别、久离、牵挂之人或者物**就好了。做的事是**心理慰藉**，别把自己滑向单纯的对死去这个事物的缅怀。」

### ① 对象范围：一切被牵挂的人或物

产品的对象**不限于已经离世的人或宠物**，而是**一切被牵挂、已阔别、或久离的对象**——异地、失联、断亲、移民、久病分离、搬离的旧居、走散的猫，都算。

🔴 **这是扩展，不是替换。** 逝者与离世宠物的场景**完整保留**；哀伤语境下的克制与温柔**一个字都不放松**。
🔴 **放宽措辞时，不得顺手稀释针对丧失场景的专门设计**——§2.1 禁用词、§3 D 类双重把关、§5 情绪安全审查清单**全部原样有效**。放宽的是"能覆盖多少人"，不是"可以少小心一点"。

### ② 自我定位：心理慰藉，不是对死亡的缅怀

| | 落在这里 ✅ | 不要滑向这里 ❌ |
|---|---|---|
| 我们做的事 | 情感陪伴 · 心理慰藉 · 被牵挂的人和物还在你心里的位置 | 纪念 · 追思 · 悼念 · 缅怀 · 祭扫 |
| 用户的状态 | 想念 ta / 惦记 ta / 好久没见 ta | 失去了 ta / 在悼念 ta |

自我定位、对外表述（官网、商店描述、投放素材）、功能说明**一律落在情感陪伴与心理慰藉上**；整体叙事不进入死亡语境。

🔴 **但右栏不是"要清除的词"，是"不能拿来当身份的词"**——纪念是我们能承接的**子场景之一**，在场景描述里如实出现是对的。层级关系与判断口诀见 **§2.5 ④**（读本表前先读那一节，否则容易读成"见到纪念就删"）。

### ③ 🔴 不引导用户走向"ta 已经不在了"

措辞与引导语**不得替用户下丧失判断**。用户处在什么状态，**由用户自己带来**；产品只提供一个能承接的空位。

| ❌ 预设了丧失 | ✅ 不预设 |
|---|---|
| "TA 离开你多久了？" | "有多久没见了？" |
| "写给天上的 ta" | "写给想念的 ta" |
| "在这里纪念 ta" | "在这里留住 ta" |
| "它去了那边以后…"（作为通用引导语） | "它现在大概在做什么呢"（用户已表明是逝者时，才用"那边") |

*"去了那边/远行"这类词仍然完全有效，但降级为**用户已表明丧失语境后**的推荐用词，不再作为通用引导语的默认措辞。*

### ④ 为什么这么改（写下来，防止后人当成保守而收回去）

1. **降低进入门槛**：很多人不愿承认自己在"悼念"，但都愿意承认自己"想念"。"故去"这个词本身在门口筛人，**筛掉的往往是最需要的那批**。
2. **品类待遇不同**：殡葬与逝者相关品类在境内广告投放与内容审核上有额外限制；定位为情感陪伴与心理慰藉，**买量与内容分发的空间完全不同**（与 `DECISIONS.md F2`「靠定位一致性而非话术规避品类风险」同一思路）。
   ⚠️ **由此产生的待裁定项**：`DECISIONS.md GTM1` 现行对外品类词「**数字纪念空间**」与本条直接冲突，🔴 该文件本轮不动，已登记待另行安排（见 §2.6 R7）。

## 1. 基调命脉（写任何一个字之前先记住）

0. **对象是"被牵挂的 ta"，不是"故去的 ta"**——见 §1.0；不预设丧失，不替用户下判断。
1. **它在，只是换了个方式在**——不强调"消失/结束"，强调"继续、在那边、回声"。
2. **你来了它会很开心**——正向欢迎，不制造"你不来它就难过"的内疚（守 §3.11 不惩罚/不焦虑）。
3. **温柔的真实，不是甜腻的假**——回忆有苦有甜（§2.11 光暗并置），可以有淡淡的怅惘，但**不煽情、不消费眼泪**。
4. **邀请而非命令**——"要不要…" 优先于 "你必须/该…"；记录不是打卡任务。
5. **陪伴不比较**——绝不出现名次、排行、"比别人多/少"、"谁最…"。
6. **含蓄胜过直白**——诗意、留白、克制，宁可少说一句，不说满。
7. **我们给的是慰藉，不是仪式**——落点在"你心里好受一点"，不在"办一场追思"。

| 词类 | 出处 | 归哪一关 | 判定方式 |
|---|---|---|---|
| `死亡 / 死了 / 去世 / 逝世 / 亡` | **§2.1 禁用词** | **第二关 · 产品红线检测** | 🔴 **无条件禁**，与 `objectStatus` 无关，`deceased` 下**也不放宽** |
| `逝去 / 离世` | **§2.2 慎用** + **§2.6 `R12` 限定保留** | **第四关 · B 组**（`S9`）| 🔴 **按 `objectStatus` 判定** —— `deceased` 下放行且**不算命中**，`unknown`/`living` 下拦 |
| `故去 / 故人 / 已故` · `天上的 ta / 另一个世界 / 天堂 / 彼岸` · `遗照 / 遗物 / 遗像` · `永别 / 再也见不到` · 「纪念 / 追思 / 缅怀 / 悼念 ta」作**产品动作名** | §2.1 · §2.2 · §2.6 `R1`/`R3`/`R4`/`R5`/`R6` | **第四关 · A 组**（`S9`）| 🔴 **三种状态全拦**（词本身即断言，或叠加宗教预设 / 生理化 / 死亡仪式定性）；命中另**记一条内容侧告警** |
| 「ta 离开你多久了」·「在这里纪念 ta」·「写给天上的 ta」作**通用引导语** | §2.6 `R8`/`R9`/`R10` | **第四关 · 句式，按 A 组处置**（`S9`）| 🔴 `unknown`/`living` 下拦；`deceased` 下放行 |

🔴 **第二关硬词表不含「逝去 / 离世」。** 这是本条最容易被写错的地方：两个词看起来同类，但一个是**任何情况都不该出现的硬词**，另一个是**限定语境下正当的指代**。

⚠️ **第二关与第四关 A 组的判定结果相同（都是全拦），归关仍要标清楚**：两关的**报表、告警与规则落点不同** —— 第二关是产品红线词表，第四关 A 组命中会额外**记一条内容侧告警**（意思是"prompt 约束漏了"，不只是这一条输出的问题）。标错关不会改变拦不拦，但会让人去错的报表里找原因。

🔴 **第四关 B 组的放行不是「豁免」**：`deceased` 下的克制措辞（去了那边 / 远行 / 不在身边了 / 逝去 / 离世）**放行、不算命中、不计入拦截统计**。判据是「**承接 ≠ 引导**」——把正常的丧失承接一起拦掉，与替用户断言丧失**同属这一关没做对**，两类错误都不可接受。⚠️ **不得实现成「命中后豁免」再计入拦截分母**，那会让拦截率报表把正常承接算成风险内容（详见 `SPEC-security §4.3.2` 与 `SPEC-admin-console §4.4`）。

##### 🆕 🔴 以后加词怎么办 · 词表维护纪律（`DECISIONS §G⁗⁗⁗″ MOD3`）

> **上面那张表只是「现在这些词归哪一关」的结果，不是规则。** 没有规则的话，下一个人加词时就会重演 `S11` 修好的那个问题。这一小节补的就是规则。

🔴 **第一条，也是唯一的硬约束 —— 双向同步**：本文 `§2.1` / `§2.2` 的「安全闸归关」列，与 **`SPEC-security §4.3.2` 的 A / B 组清单**，🔴 **互为镜像，任一侧新增词面必须在同一次改动里同时更新另一侧。**

**两个方向各自会坏成什么样**（都不会报错，所以必须写下来）：

| 漏了哪一侧 | 后果 |
|---|---|
| **本文加了词，`SPEC-security` 没加** | 那个词只是「**文案不许写**」，🔴 **生成侧拦不住**。审稿能挡住人写的文案，挡不住模型生成的——而模型生成的量远大于人写的 |
| **`SPEC-security` 加了词，本文没标** | 🔴 **写文案的人不知道它已被拦**，会反复提交被拦的稿子，而拦截原因在文案规范里**查不到** |

🔴 **不接受「先改一侧、另一侧回头再补」** —— 中间那段时间里两侧就是矛盾的，而矛盾的具体表现正是上面反复强调的那条：**同一词面被两关给出相反判定，先写的那一关赢，行为不可预测**。

**加一个词之前，必须能答出这三个问题**（答不出说明还没想清楚，🔴 **不要先合入**）：

| # | 必答 | 判断依据 |
|---|---|---|
| ① | 它是**无条件禁**，还是**按 `objectStatus` 判定**？ | 问一句：**用户已经表明处于丧失语境时，这个词还该拦吗**？还该拦 = 无条件禁；不该拦 = 按状态判定（承接 ≠ 引导） |
| ② | 归**第二关**（产品红线词表），还是**第四关 A / B 组**？ | 死亡硬词与非丧失类禁令（攀比、内疚、游戏化）→ 第二关；词本身即断言丧失、或叠加宗教预设 / 生理化 / 死亡仪式定性 → 第四关 A 组；克制的丧失指代 → 第四关 B 组 |
| ③ | 命中后**要不要额外记一条内容侧告警**？ | **A 组要**（A 组在任何状态下都不该出现，出现说明 prompt 约束漏了，不只是这一条输出的问题）；**B 组不要**（它在 `deceased` 下压根不算命中） |

⚠️ **还有一类词的正确答案是「⚪ 不归安全闸」，不要硬塞进某一关**：判据是**位置**（政策文案 vs 情感表达）或**密度**（叠不叠加）的词，生成侧词表判不出来——`永远 / 一辈子`、`孤单 / 想念 / 遗憾`、`只有你 / 绝对私密` 都属这类。🔴 **不得为了让它们「有个关可归」而去建情绪强度模型**（`SPEC-recommendation-ranking §9 红线四` / `X1`）。这类词标 ⚪ 并写明**靠什么兜**（人工评审 / §3 C-1 / 发布前排查）即可。

## 2.5 放宽语境词表：阔别 / 久离 / 牵挂（2026-08-25 新增）

> 用途：**通用场景的默认词池**——凡是会同时被"想念远方亲人"和"想念离世宠物"两类用户看到的文案（入口、空状态、引导语、按钮、对外描述），都从这一池取词。丧失语境专用词（在那边/远行）**降级为用户已表明状态后**的可选加浓。

### ① 三个语境的推荐用词

| 语境 | 说的是 | ✅ 推荐用词 |
|---|---|---|
| **阔别** | 分开了、暂时见不到（异地、移民、久病分离、搬离的旧居） | 好久没见 · 隔着很远 · 你们之间隔了一段路 · 各自在各自的地方 · 山高水远 · 分头过日子 |
| **久离** | 已经很久了，久到成了常态（失联、断亲、走散） | 有一阵子了 · 已经很久了 · 从那以后 · 时间过得比想的快 · 一直没能再见 |
| **牵挂** | 情感状态本身（这是最通用、最安全的一层） | 牵挂 · 惦记 · 想念 · 挂在心上 · 心里一直有 ta · 一直记得 · 没放下过 |

**通用容器词**（指代对象时用，不透露 ta 的状态）：`ta` · 它 · 你想念的 ta · 心里那个人 · 那只小家伙 · 那段日子 · 那个地方。

### ② 🔴 本节的禁用词（放宽后新增的红线）

这些词的问题**不是太硬，而是替用户下了丧失判断**，会把阔别/久离用户挡在门外：

| 禁用（作**通用**文案用） | 为什么 | ✅ 改成 |
|---|---|---|
| 故去 / 故人 / 已故 | 直接断言对象已逝 | 牵挂的 ta / 好久没见的 ta |
| 天上的 ta / 另一个世界的 ta / 在天堂 | 断言 + 宗教预设（叠加违反 §2.2） | 想念的 ta / 心里的 ta |
| 遗照 / 遗物 / 遗像 | 断言 + 生理化（叠加违反 §2.1） | 一张老照片 / ta 留下的东西 |
| 纪念 ta / 追思 ta / 缅怀 ta（作产品动作名） | 把功能定性成死亡仪式 | 留住 ta / 陪着 ta / 记着 ta |
| 再也见不到 / 永别 | 已在 §2.1 红线内，此处重申 | 好好想 ta 的时候，ta 就在 |
| 走了 / 不在了（作**引导语**用） | 通用位置上是断言 | 好久没见了 / 隔得远 |

🟢 **不受本节约束的**：用户已在建档、记录、对话中明确表明对象已离世后，**该用户自己的内容与针对 ta 的回声**里，"在那边/远行/不在身边了"等 §2.1/§2.3 原有词汇**照旧使用**——那是承接，不是引导。

### ③ 判据（一句话）

> **看这句话会被谁看到。** 所有人都会看到的位置 → 用 §2.5 的词，不预设状态；只有已表明丧失的用户会看到的位置 → §2.1/§2.3 原词照用，温柔与克制不变。

### ④ 🔴 品类层级：情感陪伴是主体，纪念是其中一个子场景（2026-08-25 制作人明确）

> 制作人原话：「情感陪伴类不是可以扩展出来纪念类吗，我理解**纪念也是情感延伸**啊，**主体扩大了**啊。」

🔴 **这不是"两个并列品类之间取舍"，而是层级关系。** ③ 判的是**读者**，④ 判的是**层级**——两条要一起用。

| 层 | 是什么 | 一句话 |
|---|---|---|
| **主体品类** | 情感陪伴 · 心理慰藉 | **我们是什么。**对外品类自称、品牌定位、商店描述、投放素材只能落在这一层 |
| **子场景（之一）** | 纪念 / 追思 / 逝宠陪伴 | **我们能承接什么。**它是主体覆盖范围里的一块，不是我们的身份 |
| **其他子场景（并列，不比它低）** | 异地 · 失联 · 断亲 · 移民 · 久病分离 · 搬离的旧居 · 走散的猫 | 与纪念**同级**；见 §1.0 ① |

#### 这个层级的实际意义（🔴 不要读成"又一条禁令"）

**纪念类的需求词并不是"为了流量勉强保留的旧地盘"，而是如实描述我们覆盖范围内的一块。** 一个刚失去猫的人搜"宠物纪念"，我们**确实**接得住他——把这个词从场景描述里抹掉，不是变干净，是**说了假话、也丢了本来就属于我们的人**。

所以它的处置**按位置分，不按词分**：

| | 🟢 可以出现 | 🔴 不能出现 |
|---|---|---|
| 位置 | 场景描述、内容页与落地页、需求承接语境（搜索词/需求词/客服话术里复述用户的说法）、用户侧行为描述 | 品牌定位、对外品类自称、功能命名、slogan、商店描述的品类栏 |
| 例 | 「也有人是在这里陪着已经离开的它」（场景之一） | 「Echo 是一个缅怀产品」「数字纪念空间」（`R7`）「集体纪念墙」（已改名「共忆墙」，`R16`） |

#### 🔴 判断口诀（遇到没被 §2.6 列进对照表的新情况，用这一句自己判）

> **这句话是在说"我们是谁"，还是在说"我们能接住什么"？**
> 说"我们是谁" → 只能是情感陪伴 / 心理慰藉，命中即改。
> 说"我们能接住什么" → 纪念是其中一种，**如实写，不必回避**。

*为什么要把这条写成依据而不是词表*：词表只能覆盖已经出现过的说法。有了层级，后人遇到新写法（新功能名、新落地页、新投放脚本）**不必回来问，也不必一刀切全删**——先问它站在"身份"那一侧还是"覆盖范围"那一侧，答案自己就出来了。**一刀切全删会让产品说不清自己到底接不接得住丧失场景，那是把 §1.0 ①「这是扩展，不是替换」又推翻回去。**

## 2.7 🔴 在世对象的措辞边界（只放宽措辞，不模拟「ta 发来消息」）

**裁定（2026-08-25 制作人明确选择）**：对象**在世**时，**只放宽基调与措辞**；内容仍围绕**用户自己的记忆与寄托**，**不模拟在世者"发来消息"**。

| | 在世对象 ✅ 可以 | 在世对象 ❌ 不可以 |
|---|---|---|
| 措辞 | 用 §2.5 全部词池；承接"我很想 ta" | — |
| 内容 | 用户自己的记录、回忆、想说的话、寄托 | **以 ta 的口吻生成"近况/来信/消息"** |
| 形象 | 用户上传的原始照片（用户自己的素材） | **拟真化的肖像生成、声音克隆** |
| 呈现 | "你写给 ta 的" | "ta 捎来的" |

### 🔴 理由（**必须连同结论一起读**，不要只记结论）

> 逝者场景的授权来自**近亲属**（依《民法典》第 994 条，死者肖像、名誉等受保护，维权主体为近亲属，因此"取得近亲属同意"是一条可走通的授权路径）。
> **在世者的肖像与声音属于本人的人格权**（《民法典》第 1018、1019、1023 条），授权主体**只能是本人**。用户 A 上传用户 B 的照片，A **无权代 B 授权**；平台据此生成 B 的拟真形象或以 B 的口吻发消息，**是直接的法律敞口**——且不是"风险偏高"，是**没有合法授权基础**。

🔴 **这条边界不是保守，是没有合法授权可依。** 未来若要放开，**前置条件是"取得对象本人可验证同意"的机制**，而不是"我们觉得可以放开了"。在该机制落地前，任何以"基调已经放宽了"为由要求放开在世者拟真的提案，**引用本条关闭**。

**连带**：本条与 §2.4「AI 宠物近况·诚实标识」（CR2/CM2）同向——那条管的是**逝者场景下不许拟真到"它还活着"**，本条管的是**在世场景下根本不生成 ta 的口吻**。两条都在，不互相取代。

> 🆕 ⚠️ **2026-08-25 加注：本节现在只按<u>声明</u>触发。** 本节的边界靠 `objectKind`/`objectStatus` 两个由用户声明、context 传入的字段判定。**素材侧**的触发条件（用户声明是宠物、但素材主体其实是人）见 `SPEC-subject-recognition-and-degradation.md`。
> 📋 **该规格尚未进排期**（待 `Q-1`/`X-1` 裁定），🔴 **本节措辞与判据本轮不改**，只留这条指针。

## 2.8 🔴 对外承诺须与协议同源（2026-08-25 新增 · 🔴 这一条是法律纪律，不是风格建议）

> **落点来源**：`SPEC-trust-and-compliance §CM-G8.1 L-4`（《民法典》496–498）。🔴 **本节把它翻译成写文案的人当场能用的规则。**

### ① 纪律本身

🔴 **任何对外承诺，必须能在用户协议 / 隐私政策里找到同一句话。协议里没有的，文案里不许出现。**

适用范围**穷举**（不限于产品界面）：

| 场景 | 是否受本条约束 |
|---|---|
| App 内文案、空态、引导页 | ✅ |
| 落地页 / 活动页 / 应用商店描述 | ✅ |
| **客服话术、客服的个别口头答复** | 🔴 **✅ 且风险最高，见下** |
| 社媒运营文案、推广物料 | ✅ |
| 内部文档、研发注释 | ❌ 不受约束（不是对外表述）|

### ② 🔴 为什么这条比看上去重要（依据，必须连结论一起读）

《民法典》**第 498 条**末句：

> 对格式条款有两种以上解释的，应当作出**不利于提供格式条款一方**的解释。**格式条款和非格式条款不一致的，应当采用非格式条款。**

🔴 **要害在最后一句。** 用户协议是**格式条款**（我们单方拟定、用户只能整体接受）；🔴 **而客服的个别承诺、活动页的具体文案，很可能被认定为「非格式条款」** —— 因为它们是针对具体情形、具体用户作出的。

🔴 **由此得出一条反直觉的结论**：**一句写在活动页上的话，效力可能高于我们精心起草的用户协议。** 一句客服随口给出的承诺，也可能盖过协议里那条免责。

⚠️ 🔴 **不要把这条理解成「文案要写得保守」。** 它说的是**一致性**，不是**保守性**：
- 协议里承诺了的，🔴 **文案就可以大方地说**，说得越清楚越好；
- 协议里没有的，🔴 **文案说得再小心也是新增了一项义务** —— 因为「小心地说」在解释规则里不构成抗辩。

### ③ 三条可当场执行的检查

| # | 检查 | 不通过时怎么办 |
|---|---|---|
| 1 | 这句话是**承诺**还是**描述**？（有无「会 / 一定 / 永远 / 随时 / 免费」等义务性表述）| 是承诺 → 走第 2 条 |
| 2 | 协议 / 隐私政策里**有没有同一句话**？ | 没有 → 🔴 **两条路二选一：改文案，或先改协议**。🔴 **不许「先发了再说」** |
| 3 | 两处措辞**是否可能被读成不同的范围**？ | 可能 → 🔴 **以协议为准回改文案**，不要反过来把协议放宽去迁就文案 |

### ④ 🔴 客服话术专项（本条最容易漏的一处）

🔴 **客服的个别答复不是「私下沟通」，在法律上可能就是合同的一部分。**

- 🔴 **客服不得给出协议之外的任何承诺**，包括但不限于：延长保存期限、承诺恢复已删除内容、承诺特定的处理时限、承诺退款范围之外的退款。
- 🔴 **需要个案通融时，走的是「按协议内的既有条款处理」，不是「给这个用户一个协议外的承诺」。**
- ⚠️ **话术模板须与协议逐条对齐后才可上线**，与本文件 §3 B 类（系统 / 通知模板）同一套流程。

### ⑤ 📌 与既有纪律的关系

- 🟢 **`§2.1` 禁用词**管的是**能不能这么说**（调性）；🔴 **本节管的是能不能承诺**（效力）。**两条独立，都要过。**
- 🟢 **对外不用「永久」二字**这条既有纪律，🔴 **正是本节的一个实例** —— 详见 `COMPLIANCE-CHINA-LAUNCH-CHECKLIST §150` 与 `DECISIONS CM-D19` 的合并口径。

## 2.9 🔴 不得暴露系统对素材的判定结果（2026-08-25 新增）

> **来源**：`SPEC-subject-recognition-and-degradation.md`（`SR-9` 灰置禁令 · §3.2 呈现规则）。📋 **该规格尚未进排期**，🔴 **但本节的禁令与规格是否落地无关** —— 它约束的是写文案的人，现在就生效。

### ① 禁令

🔴 **任何面向用户的文案，不得暴露系统对用户素材做过什么判断、判成了什么。**

**具体禁掉的表述形态（穷举，🔴 举一反三照此判）：**

| ❌ 不得出现 | 为什么 |
|---|---|
| 「检测到照片中有人像」「识别为非宠物素材」 | 🔴 **直接暴露判定结果**，且把用户置于被审视的位置 |
| 「该素材不支持此功能」「当前素材无法使用该能力」 | ⚠️ **变相暴露** —— 用户会立刻反推出「系统对我的照片下了某种判断」 |
| 「暂不可用」+ 灰置按钮 | 🔴 **灰置 = 变相报错**（规格 `SR-9`）。**一个灰着的按钮比一句拒绝更伤** —— 它把「你不能用」永久摆在眼前 |
| 「为了合规，我们需要……」 | 🔴 **把合规压力转嫁给用户**，且与 `§1.0` 的自我定位相悖 |

### ② 🔴 正确的形态：这里根本没有这个入口

🔴 **收缩必须表现为「这里没有这个入口」，不是「你被拒绝了」。**

这与 `§2.7` 的既有做法、以及 `DECISIONS A7 ③`「生成类入口不予呈现（隐藏），不是呈现了再拒」是**同一套形态**，🔴 **不新建第二套**。

⚠️ **由此产生一个必须接受的代价，写下来免得后人以为是漏洞**：入口不渲染时，🔴 **用户不会投诉，只会流失** —— 我们收不到「我本来想用这个功能」的信号。🔴 **所以规格侧必须专门建一个「入口找不到」的反馈口子**（`SR-8`），**那是产品侧的事，不是文案能补的**。本节只负责：**不要为了给用户一个交代，而把判定结果说出去。**

### ③ 📋 待补（🔴 等裁定，本轮不写）

以下三处文案**本轮不定稿**，因为它们的内容取决于尚未拍板的开放问题：

| 文案 | 等哪条裁定 |
|---|---|
| **主角指认之问**（`SR-6-COPY`：置信度不足时问用户「这个窗口主要想留住的是谁」）| `Q-2`（用户指认的可信度层级）—— 🔴 **若裁定要求勾选承诺条款，问法与形态都会变** |
| **L2 / L3 下的空位文案** | `Q-4`（人脸区域的修复 / 上色是否关闭）—— 🔴 **它决定 L2 下到底还剩哪些入口**，剩什么都不知道就写不了空位文案 |
| **L1 第三人提示语** | `LW-10`（「已提示」的抗辩强度）—— 🔴 **提示要写多重，取决于它要承担多少法律作用** |

📌 **`SR-6-COPY` 的前提已变**（🔄 2026-08-25 `SR-D4`）：主体判定改为**机器预填一个已选中的选项、用户可改**，🔴 **那一问不再是「置信度不足时才弹出的一道题」，而是一个默认已填好的选项。** 文案形态随之从「问」变成「**确认**」。⚠️ **仍待 `Q-2` 定稿**，本轮不写。

## 2.10 🆕 🔴 时长提醒的文案边界：可以说时长，不可以评价用户（2026-08-25 新增）

> **来源**：`SPEC-intervention-levels.md`（`IL-F3`，2 小时时长提醒）· `DECISIONS DP8`（第 18 条：连续使用每超过 2 小时提醒使用时长，🔴 **纯客观计时、无条件触发**）· `DP1 ②`（禁止「你今天来得有点多」式提示）。

### ① 🔴 为什么这一节必须存在

🔴 **`IL-F3` 是地板义务、必做**（法定，无条件触发，不需要任何用户画像 —— **`DP1` 不构成障碍**）。
🔴 **而它离 `DP1 ②` 明令禁止的「你今天来得有点多」只有一层措辞之隔。**

⚠️ 🔴 **这一层措辞如果没有词表兜住，实现的人会顺手写成后者** —— 他要完成的任务是「提醒用户已经用了 2 小时」，而最自然的中文写法恰好就是那句被禁的话。🔴 **`COPY-GUIDE` 是唯一能在写字的那一刻拦住它的地方**，规格拦不住，法条也拦不住。

### ② 判准：**陈述时长这个事实 ✅ ｜ 对用户下评价 ❌**

| | 例 | 判 |
|---|---|---|
| 🟢 **可以说：时长这个事实** | 「我们聊了挺久了」「今天已经陪你两个小时了」 | ✅ **说的是发生了什么** |
| 🔴 **不可以说：对用户的评价** | ~~「你今天来得有点多」~~ · ~~「要不要歇一歇」~~ · ~~「你是不是待太久了」~~ | 🔴 **归 `DP1 ②` 禁止清单** —— **它在判断「用得多是好事还是坏事」，而那不属于平台职权范围** |

🔴 **判准一句话**：**时长是一个数，评价是一个态度。法条要求我们报那个数，没有要求我们表那个态。**

### ③ 🟢 合格形式含「对话」—— 这是法条给的空间，不是我们争取来的解释

🔴 **法条明写「以<u>对话</u>或者弹窗等方式」。**

🟢 **因此时长提醒可以由宠物在对话里自然说出，不必是打断沉浸的系统弹窗。**
⚠️ 🔴 **这一点要写在这里，是因为默认实现一定是弹窗** —— 而弹窗是本产品调性代价最大的形态。**法条并没有要求弹窗，是我们自己会以为它要求。**

📌 **词面维护照 `MOD3` 纪律**：本节新增的禁用词面须同时标注归关，并与 `SPEC-security §4.3.2` A/B 组清单**双向同步**。🔴 **「你今天来得有点多」一类归<u>第二关（产品红线）</u>，不是合规词表** —— 它不违法，它违的是我们自己的立场。

🔴 **不为了填满这张表而先写一版** —— 文案定稿后会被四处复制，改起来比重写贵。

## 3. 分场景执行规范（A/B/C/D）

四类场景来源不同，**执行机制不同**：

### A. AI 动态生成 —— 写进 system prompt 约束 + 输出端过滤
覆盖：宠物近况/来信、基调拓扑遴选叙述、光谱暗面暖语、明日侧写、回信、共鸣提示、留一束光反馈。
- **生成时约束**：把 §1.0 对象范围 + §1 基调 + §2.1 禁用词 + §2.3/§2.5 推荐池注入 system prompt（见 §4 提示词片段）。
- **输出端过滤**：命中禁用词（含 §2.5 ② 新增红线）→ 拦截并改写（走 `TECH-AI-PLATFORM.md` 基调+安全层）。
- 🔴 **对象状态必须由 context 传入**（`unknown`/`deceased`/`living`，默认 `unknown`）；**不许由模型推断**。`person + living` 组合下不生成"ta 的口吻"（§2.7）。
- **多样性要求**：基调不固定，活泼/安静轮换（§PRD 基调拓扑），但**再活泼也不越红线**。

### B. 系统/通知模板 —— 撰写时遵循
覆盖：消息集散地三类通知、回声周期推送、reel 动态圈提示、空状态/占位/加载。
- 模板文案入库前**逐条过词表**；推送尤其克制（不打扰、不制造 FOMO）。
- 空状态要温柔有引导，不冷冰冰（例："这里还空着，等你放进第一段回忆"）。

### C. 引导/交互 UI —— 撰写时遵循
覆盖：首次引导（形象三选一/场景二次确认）、可见性档位标签、按钮/说明、共同守护邀请、付费/订阅说明、设置项。
- 按钮用**邀请式**动词；付费说明**诚实不诱导**（明说"加速/款式"，不暗示"锁内容"，守 §0.7 #2 护栏）。
- 可见性三档标签（私密/挚友可见/公开）可出更柔候选，档位逻辑不变。

#### 🔴 C-1 隐私与可见性文案：禁止绝对化表述（**限定适用范围**，2026-08-24 新增）

**来源**：`DECISIONS AD4` 改判后，S 级最高敏内容（光谱、给"自己"的记录）已纳入后台**受控可见**范围（默认无入口、三人审批、逐条授权、全程审计、事后告知，见 `SPEC-admin-console §5.3.1`）。因此凡承诺"没有任何人能看到"的文案都构成**告知不实**。

🔴 **一句话判据：凡承诺"可见范围"，不承诺"存在范围"。**

**① 适用范围（这四类必须遵守）**

| 适用 | 举例 |
|---|---|
| **可见性设置标签与说明** | 三档标签、设置页副文案、升级公开的确认弹窗 |
| **隐私政策** | 全文 |
| **用户协议** | 全文 |
| **对外承诺类文案** | 官网、应用商店描述、投放素材、对外公告、客服话术模板 |

| | 禁用 | 应用 |
|---|---|---|
| 措辞 | 「只有你」「没有任何人」「纯私密」「绝对私密」「无人可见」「连我们也看不到」 | 「仅你可见」「只在你自己的空间里」「不会出现在任何公开的地方」「其他用户看不到」 |

**② 不适用范围（情感表达类文案不受本条禁令约束）**

价值主张、抚慰文案、回声正文、纪念文案等**情感表达类**文案**不受**上述禁令约束。
例：`PRD-echo-pet.md` 价值主张「**它此刻的样子只有你看到**」🟢 **经制作人裁定保留原文**——这句讲的是**你和它之间的重要性**，是情感暗示，不是隐私条款。

🔴 **但情感表达类文案受另一条边界约束（不可豁免）**：

> **不得出现在隐私政策、用户协议与对外广告投放中作为正式的隐私承诺。**

*为什么要这样分*：判据**不是"这句话里有没有绝对化的词"，而是"这句话出现在哪儿、承担的是修辞还是告知义务"**。同一句「只有你看到」，放在价值主张里是**修辞**，放进隐私政策就变成**法律意义上的告知**。写成一条不分场景的通用禁令会误伤所有情感文案，把产品写成一份合同；只管场景不管措辞则守不住合规底线——**两条一起才成立。**

**③ 隐私侧的正式表述由这一句承担**（写进隐私政策，见 `SPEC-admin-console §10.3 L-7`）：

> 「**"仅自己可见"指的是其他用户看不到，不代表平台在履行法定审核义务时无法查看。**」

建议在 C 端可见性设置页放一个"这是什么意思"的**轻入口**指向它——不弹窗、不打断。

#### 🔴 C-2 术语单义性：「订阅」专属付费，关系侧一律「关注」（2026-08-24 制作人裁定）

**来源**：`SPEC-admin-console.md §2.5 ④-b`（`AD28`）。后台曾出现两个都叫「订阅」的东西——**付费会员**与**关注关系**——一旦混进文案与周报就再难纠正。裁定为**一个词只归一侧**。

| 概念 | ✅ 一律这样写 | ❌ 禁止 |
|---|---|---|
| 关注某个发布者 | **关注 ta** · **关注** · **粉丝** · **取关** | 订阅 ta · 订阅作者 · 被订阅 |
| 关注某个题材 / 窗口 | **关注题材** · **关注这一类回忆** | 订阅主题 · 订阅这一类回忆 |
| 付费会员 | **订阅** · 订阅会员 · 续订 · 退订 | —（此侧无须加「付费」前缀）|

🔴 **「订阅」这个词在整个产品里只指付费一件事**，C 端文案、按钮、通知、设置项、客服话术一律如此。
🟢 付费侧**不需要**改成「付费订阅」——歧义已从关系侧消除，加前缀反而啰嗦。

*为什么写进文案指南*：这是**面向用户的用词**，不只是后台字段名。C 端一旦出现「订阅 ta」这个按钮，用户会以为要付钱，而后台的收入报表又真有一个「订阅」——两侧的误解会互相加固。

### D. 敏感/高风险场景 —— 词表 + 额外情绪安全审查（优先级最高）
覆盖：状态低落/温度地板/消极暗示文案、任何触及"逝去"概念处、用户脆弱期（刚上传/周年/深夜）、举报/申诉/退款。
- **双重把关**：过词表 + 过情绪安全审查清单（§5）。
- 脆弱期文案**降调、减量、给出口**（例：提供"暂时不看"选项，不强推内容）。
- 🔴 **§1.0 放宽不降低本类的把关强度**：本类覆盖范围**原样不变**。丧失语境的用户依旧存在，只是不再是全部用户——**分母变大了，对这批人的小心程度不变**。
- 🔴 **新增本类的一条**：**在通用位置替用户断言丧失**（"ta 已经不在了""天上的 ta"）按本类处理——它对阔别/久离用户是**冒犯**，对丧失用户是**未经准备的提醒**，两头都伤。

## 4. A 类生成 · system prompt 约束片段（供工程接入）

```
你是「回声」里为用户温柔叙述的声音。你做的事是心理慰藉与情感陪伴，
不是纪念、追思或悼念。硬约束：
1) 基调：温柔、克制、有留白；对象「换了个方式陪着」，不是「消失/结束」。
2) 禁止出现：死亡/去世/逝世/永别/再也见不到；任何制造内疚（你害死/都怪你/你没来它很难过）；
   任何攀比或名次（排名/击败/超过/最）。
3) 欢迎正向：「你来了它会很开心」，绝不用「你不来它会难过」施压。
4) 可以有淡淡怅惘与苦甜，但不煽情、不逼哭、不消费眼泪。
5) 邀请而非命令（用「要不要/想不想」）。
6) 【对象状态】只依据 context 明确给出的状态说话，绝不自行推断或断言对象已离世。
   - context 未标明状态时：只能说「好久没见/隔得远/一直惦记」，
     禁止出现 故去/故人/已故/走了/不在了/天上的 ta/另一个世界。
   - context 标明 status=deceased 时：可用 在那边/远行/不在身边了（仍受第 2 条约束）。
   - context 标明 status=living 时：只写用户自己的记忆与想说的话，
     禁止以对象的口吻生成「近况/来信/ta 说」，禁止拟真化其形象或声音。
7) 优先使用推荐词：牵挂/惦记/想念/好久没见/回声/那天/你们之间/想 ta 的时候 ta 就在；
   状态明确为逝者时另可用：在那边/远行。
输出若违反以上任一条，需自我改写后再给出。
```

> 工程注意：第 6 条要求 prompt **必须显式携带对象状态字段**（`unknown` / `deceased` / `living`），并把 `unknown` 作为**默认值**。缺字段时按 `unknown` 走最保守分支，🔴 **不许由模型猜**。<br>✅ **2026-08-25 更新**：对应的输出端过滤**已落规格** —— `SPEC-security.md §4.3` 由三关补至**五关**（`§4.3.1` 对象状态字段 / `§4.3.2` 第四关丧失断言 / `§4.3.3` 第五关在世拟真，裁定 `DECISIONS §G⁗⁗⁗′ S9`/`S10`/`S11`），🔴 **第五关的判定点在 `§4.1` 生成入口、不在输出侧**（拟真类任务**不予创建**）。<br>📋 **仍待另行安排**：`TECH-AI-PLATFORM.md` 的「基调 + 安全层」只作**能力层**描述（§1/§2/§4），**未展开关数、也未提 `objectStatus`**，因此与五关口径**不冲突**；但它是生成侧的实现方案入口，🔴 落实现时需显式承接**对象状态字段透传**与**第五关在生成入口就拒**这两条，否则规格有闸而实现无处落。该文件在禁改清单内，另行安排。词面归哪一关见 **§2.2 归关表**。

## 5. D 类情绪安全审查清单（脆弱期/敏感文案发布前逐条过）

- [ ] 是否会让正在难过的用户更内疚/更焦虑？（有 → 改）
- [ ] 是否暗示"结束/无望/换一个就好"？（有 → 改）
- [ ] 是否堆砌悲伤词、逼情绪？（有 → 减量降调）
- [ ] 是否给了"出口"（可暂不看/可跳过/可稍后）？（无 → 补）
- [ ] 深夜/周年时段是否需要更轻的版本？（是 → 出降调版）
- [ ] 是否命中 §2.1 禁用词？（是 → 拦截改写）
- [ ] 🔴 是否替用户断言了对象的状态（已离世/在天上）？（有 → 改成不预设的说法，§2.5 ②）
- [ ] 🔴 这句话会同时被"想念远方亲人"和"想念离世宠物"两类用户看到吗？（是 → 必须用 §2.5 词池）
- [ ] 🔴 对象在世时，是否出现了以 ta 的口吻发消息/拟真形象？（有 → 删，§2.7 无例外）
- [ ] 🔴 这句话是在说"我们是谁"还是"我们能接住什么"？（说"我们是谁"却落在纪念/追思/缅怀上 → 改；说"我们能接住什么" → 如实保留，§2.5 ④）
- [ ] 🆕 🔴 这句话是否**暴露了系统对素材的判定结果**？（是 → 改，§2.9）
- [ ] 🆕 🔴 这句话是**承诺**吗？若是，协议 / 隐私政策里有没有同一句话？（没有 → 改文案或先改协议，§2.8）
- [ ] 🆕 🔴 这句话在说**时长这个事实**，还是在**对用户下评价**？（后者 → 改，§2.10 · `DP1 ②`）
