### 0.1 「温和」的判准定成 **3 + 1**（🟢 **换骨架后不变**）

🔴 **三条逐条验的文案闸（合取，缺一条即不可发）+ 一条只验一次的结构前置。** ⚠️ **这三条与频率/背压之争无关，所以 v0.2 一字未改。**

| 位置 | 判准 | 一句话机械判据 |
|---|---|---|
| **文案闸 ②** | **输入显式** | **凭什么挑中他？** 答案里出现任何「他多久没来 / 他看了多久 / 他点没点开」→ **不可发** |
| **文案闸 ③** | **内容非心理** | **把主语换成「他的内容」，还读得通吗？** 通 → 过 |
| **文案闸 ④** | 🔴 **无损可略过** | **把这次送达整个删掉，用户失去了什么？** 答「什么也没失去，晚点看到而已」→ 过 |
| **结构前置 ①** | **单一开关** | 🔴 **不进文案闸。** 见 `0.2` |

- ②③ 直接沿用 `SPEC-feed-surfaces §3.4.3` 的第 2、3 条，**一字未改**。
- ④ 采纳 `PRODUCT-SPEC-OPEN-QUESTIONS §5.1.3` 的建议并**升为本文正式判准**。🔴 **它补的是「不发行不行」这一维。**
- 🔴 **判准管不了两件事，必须另外管**：**频次**（三条全过的一条推送、一天发二十次仍是骚扰 → 🟢 **背压模型下这件事由库存上限管住了**，`§4`）与**通道**（`S8` → `§6.5`、`§6.6`）。

### 0.1b 🟢 换骨架后，判准与背压是什么关系

| | |
|---|---|
| **判准管** | **一条推送<u>能不能发</u>** |
| **背压管** | **一共<u>会有多少条</u>** |
| 🔴 **两者不重叠，也不能互相替代** | ⚠️ **上限管不住一条催促文案**（3 条里每一条都可以写得很糟）；**判准管不住总量**（每条都合规，发一百条仍是骚扰）。📌 **v0.1 那套「频次判准管不了」的诊断在 v0.2 依然成立，只是<u>补上频次的那个东西</u>从「频率配置」换成了「库存上限」** |

### 0.2 🔴 「可撤销」这一维：**从逐条判准降级为一次性结构前置**（🟢 **保留，且背压模型下更自然**）

**问题**：推送发出去物理上撤不回，而「设置里能关掉推送」形式上完全满足可撤销 —— 🔴 **于是召回式推送靠这一条就能过闸。**

**产品负责人的裁定（2026-08-27）**：「**关掉推送就是不生成了，还推什么**」—— 即**推送开关与生成开关是同一个**，不存在「生成了却推不出去」的状态。

🔴 **据此重判的结论：这条裁定消掉了「可撤销」背后的一个真实隐患，但没有救活它作为逐条判准的资格。**

- **它消掉的隐患是真的**：如果开关只关推送、生成照旧，关闭期间就会攒出一批「你没看到的东西」在后台等着，重新打开时一次性砸过来 —— 🔴 **那堆积本身就是催促的能量来源。** 开关同一个，这个隐患**结构性地不存在**。
- **但它救不了 ① 当判准**：① 问「用户能不能让它消失」，而这个问题在推送上的答案**永远是「能，去关开关」** —— 🔴 **无论那条文案是「它捎来一条近况」还是「你三天没来看它了」，两条都能过 ①。** 判准的职责是把这两条分开，① 分不开，所以它在文案闸上是**零信息量的**。

🟢 **处理方式：① 转为结构前置，验一次、验完就完，不进每条推送的闸。** 它要求四件事同时成立（`§3.2`）：**开关存在** · **与生成开关是同一个** · **关闭期间不生成、不积压** · **重新打开不补发历史**。

🟢 **背压模型下它更自然了**：🔴 **「关掉」就是把上限设为 0。** ⚠️ **开关不再是一个独立的布尔，它是上限这个量的一个取值** —— 📌 **于是「关了推送却还在生成」这个状态在<u>数据结构层面</u>就不可表示，不需要靠纪律去防。**

### 0.3 🔴 核心机制：存货 + 上限 + 背压（`§4`）

| 项 | 结论 |
|---|---|
| **控制量** | 🔴 **未读库存深度**（当前有几条已送达但未读的近况） |
| **上限** | **按档位。免费档例如 3 条未读。** ⚠️ **具体数值待定** |
| **满了怎么办** | 🔴 **停止<u>生产</u>。** 已生成的那几条**一直在那儿等着**，不撤回、不过期、不降级 |
| **怎么恢复** | 🟢 **他读了一条 → 空出一格 → <u>下一个闲时窗口</u>恢复生产。** 🔴 **不即时恢复**（理由见 `0.3b`） |
| **用户不上线** | 🟢 **就是一个满了的队列。** 不是惩罚、不是终点、无累积、无过期 |
| **内容来源** | 🔴 **只取已生成的存货，送达时不现做** |
| **主线是拉** | **用户上线才看。** 轻通知仍然存在（`B21`），🔴 **但它只是告知有新的，不是主线** |

### 0.3b 🔴 「未读」的判定口径（这一条决定生产什么时候恢复，不能含糊）

> 🟢 **「读了」= 这条近况的<u>内容</u>被展示给主人过，无论他从哪个入口进去。**
>
> 🔴 **点开即算读，<u>不看停留时长</u>** —— ⚠️ **这既是 `X8` 的硬要求，也顺手消掉了「读得够不够认真」这种判断。**

| 候选口径 | 判 |
|---|---|
| **进消息中心就算把里面的都读了** | 🔴 **否。** 一次点击清空 3 条，上限当场失效 —— **背压就不存在了** |
| 🟢 **点开那一条近况本身** | 🟢 **采纳。** 它是唯一一种「读了」真的等于「他看到了那条内容」的口径 |
| **在窗里滑过就算** | 🔴 **否。** 它读的是曝光，且是三个候选里最不诚实的一个 |

🔴 **一处必须写死的补充：入口不限。** **从消息中心进、从窗里的卡列表进、从全屏单卡层进，一律算读。** ⚠️ **否则等于强迫他走通知这一个入口，那是通道胁迫。**

### 0.3c 🔴 恢复必须等闲时窗口，不能即时（**这是硬约束，不是偏好**）

**两条理由，第一条就足以定它：**

1. 🔴 **即时恢复 = 生成挂用户点击，直接打穿裁定②。** 逐字：「**闲时从素材生成、<u>不挂用户点击</u>**」。⚠️ **「他读一条我就生一条」就是挂在点击上，只是挂得含蓄。**
2. ⚠️ **即时恢复会造出即时奖励回路。** **「我一读就又有新的」是一个学得会的因果**，而它的形状就是刷不完的信息流。📌 **闲时窗口把因果在时间上拉开，用户学不到精确的因果 —— 这是<u>有意</u>的模糊。**

### 0.6 🔴 硬禁止项（本文的红线，见 `§5.2`）

**「用户不喜欢某个题材」这个判断，必须来自用户的显式表达**（明说、划掉、设置里关某类）。

🔴 **不得由「他没点开」「停留短」「跳过了几次」推出来。** ⚠️ **那正是 `DP11` 删掉的上行传导，「停留」还直接撞 `X8`。**

⚠️ **注意这条禁令拦的是<u>看起来对用户有利</u>的做法**：「他连续 3 次没点开离别题材 → 少给他推」方向上是减频、是只减不加、感觉是在体贴用户 —— 🔴 **但它读的是行为序列，一样禁止。**

### 0.6b 🔴 队列深度撞不撞 `X8` —— 已独立核实原文，结论：**不撞**

**`X8` 逐字**（`SPEC-recommendation-ranking §4.3` 第 94 行 / `RK6` 第 2252 行）：**「停留时长 / 刷屏深度 / 完播率 / 复播率」**，在 `RK6` 的十三条禁用特征里登记为「**X8 停留参与度**」；`RK-K` 另定「**`X8` 是<u>输入侧</u>禁令 —— 只看输入读了什么，不看输出写了什么**」。

| 检验 | 结果 |
|---|---|
| **逐字比对** | 🟢 **四个量一个都不是** |
| **语义** | 🟢 **`X8` 那四个量的共同点是<u>参与强度</u>（他投入了多少）；队列深度量的是<u>平台的库存水位</u>（我们生产了多少还没被消费）。主体不同** |
| **语境** | 🟢 **`X8` 是<u>排序侧</u>禁用特征清单。队列深度不进排序，它进生产闸门** |
| **判准 ②** | 🟢 **不在「浏览 / 停留 / 完播 / 刷屏深度」四类之内** |

🔴 **但真正的危险不在 `X8`，在它<u>到 `X8` 的距离</u>** —— ⚠️ **未读数 = 已下发 − 已读，而「已读」在时间上一累积就非常接近打开率。** 所以要一条工程红线（`§4.5`）：

> 🔴 **只保留当前水位这一个瞬时值。不存历史序列、不算比率、不做时间平均。**
> ✅ 「当前未读 = 2」→ 水位，合规 · 🔴 「他最近 10 条只读了 3 条」→ 打开率，违规 · 🔴 「他平均隔几天读一条」→ 回访节律，违规

## 一、本文管什么、不管什么

### 1.1 边界

| | 归谁 |
|---|---|
| **一条近况怎么被生成出来**（素材选取、记忆锚定、文案生成、成本） | 🔴 **不归本文。** 上游裁定已把生成与送达拆开，生成侧另有方案 |
| **生成的节奏（多久攒一条存货）** | 🔴 **不归本文。** 📌 `PRODUCT-SPEC-OPEN-QUESTIONS §5.2` 在讨论（💡 那边的建议是「跟素材走不跟人走」） |
| **一条已经存好的近况，什么时候、以什么形态、送到谁面前** | 🟢 **本文** |
| **送不送、送几条、送不到怎么办、什么时候不送** | 🟢 **本文** |
| **一条推送文案能不能发** | 🟢 **本文**（`§3` 的判准） |

⚠️ **一处必须说清的依赖**：本文假定**送达时手里已经有存货**。🔴 **存货为空时本文的答案是「不送」，而不是「现做一条」** —— 见 `§6.4`。

### 1.2 送达的对象只有主人

🔴 **近况是系统 → 主人这一个方向。** 它不发给亲友、不发给陌生人、不进任何公开位。

## 三、🔴 「温和」的判准

**「温和」是形容词，不是判准。🔴 不给判准，每个人各判各的。** 这一节给出一套拿着就能判的东西。

### 3.1 结构：一条推送要过两道闸，两道闸的验法完全不同

| | **结构闸** | **文案闸** |
|---|---|---|
| **验什么** | **产品有没有把开关做对** | **这一条具体的推送能不能发** |
| **验几次** | 🔴 **一次。** 做对了就一直成立 | 🔴 **每一条都验** |
| **谁验** | 产品 + 后端，上线前一次性验收 | 🔴 **写文案的人自己就能验**（这是判准的意义） |
| **条目** | ① 单一开关（`§3.2`） | ② 输入显式 · ③ 内容非心理 · ④ 无损可略过（`§3.3`） |

🔴 **文案闸三条是合取：三条同时成立才可发，任何一条单独使用都会漏。**（这一条纪律直接继承 `SPEC-feed-surfaces §3.4.3`，那边已经吃过「只验一条就放行禁品」的教训。）

### 3.2 结构闸 ①：单一开关 —— 「可撤销」这一维的最终处置

#### 3.2.1 为什么它不能当逐条判准

`SPEC-feed-surfaces §3.4.3` 的第 1 条是「**可撤销**」：用户能让这个信号、以及由它推出的结论整体消失。

🔴 **它在推送上失效，而且失效方式很危险：**

- **推送发出去这个动作物理上不可撤销** —— 手机上那一条已经被看见了；
- ⚠️ 🔴 **而「用户可以在设置里关掉推送」<u>形式上完全满足可撤销</u>，于是这一条会给召回式推送发通行证。**

📌 **这与旧判准（「是不是用户自己按下的一个按钮」）被推翻时犯的是同一个错：一条形式成立、实质放行禁品的判准。** ⚠️ **`§3.4.3` 推翻旧判准时写的那句话在这里同样适用**：「**一条会给红线禁品发通行证的判准，不能继续留着。**」

#### 3.2.2 产品负责人的裁定，以及它改变了什么

**裁定（2026-08-27）**：「**关掉推送就是不生成了，还推什么**」

🟢 **落成规格语言**：**推送开关与生成开关是同一个开关。🔴 不存在「生成了却推不出去」的状态。**

🔴 **据此重判「可撤销」这一维，结论分两半 —— 一半被救活了，一半没有。**

| | 判断 |
|---|---|
| 🟢 **被消掉的隐患（真的）** | **两个开关分开时，会有一种状态：推送关了、生成还在跑。** 那么关闭期间就在后台攒出一批「你没看到的东西」，🔴 **重新打开的那一刻一次性砸过来。**⚠️ **那堆积本身就是催促的能量来源** —— 它让「我关掉了」变成「我欠了一笔」。**开关同一个，这个隐患结构性地不存在，不需要靠纪律去防。** |
| 🔴 **没被救活的（① 当判准的资格）** | ① 问的是「**用户能不能让它消失**」。⚠️ **这个问题在推送上的答案永远是同一个：「能，去关开关。」**<br>🔴 **所以「它捎来一条近况」和「你三天没来看它了」两条文案<u>都能过 ①</u>。** 而判准的全部职责就是把这两条分开 —— **① 分不开，它在文案闸上是零信息量的。** |

🟢 **处置：① 转为结构前置，验一次、验完就完，不进每条推送的闸。**

⚠️ **为什么必须把它挪出文案闸、而不是留着当一条弱判准**：🔴 **留着它，它就会被当成「这一条我们已经验过了」的凭据。** 一条永远返回「通过」的判准，比没有这条判准更糟 —— **它给了写文案的人一种「四条里已经过了一条」的错觉。**

#### 3.2.3 ① 的四项要求（上线前一次性验收）

| # | 要求 | 验收方式 |
|---|---|---|
| **①.1** | **开关存在**，且在设置里能找到 | 界面走查 |
| **①.2** | 🔴 **推送开关与生成开关是同一个** | **代码走查**：关闭后生成任务对该主人不再产出 |
| **①.3** | 🔴 **关闭期间不生成、不积压** | **代码走查**：关闭期间存货计数不增长 |
| **①.4** | 🔴 **重新打开不补发历史** | **测试用例**：关 → 等若干天 → 开，只按新节奏走，**不出现任何「这段时间的」补发** |

⚠️ **①.4 最容易被写成「善意的功能」**：「他关了两周，重开时把这两周的近况都给他看看，不然多可惜」—— 🔴 **那正是 ①.2 想消掉的那笔债，从生成侧被赶走、又从送达侧走回来了。**

📌 **开关的措辞已有现成的口径**，`PRODUCT-GLOSSARY §2.3` 第 ③ 条逐字：「**设置里要能说「这周先不要来信」「只保留回忆，不生成近况」**」。🟢 **注意第二句的措辞本身就是单一开关** —— 它说的是「不生成」，不是「不推送」。

### 3.3 文案闸：三条，合取

#### ② 输入显式 —— **凭什么挑中这个人、这个时刻**

> 🔴 **机械判据：把「我们为什么现在给他发这一条」写成一句话，这句话里出现了什么？**
>
> - 只出现**存货状态**（有一条已生成的近况）、**节奏状态**（距上次送达够久了）、**用户的显式设置**（他没关开关、没关这个题材）→ ✅ **通过**
> - 出现**他多久没来 / 他看了多久 / 他点没点开 / 他打开率多少 / 他活跃时段是几点** → 🔴 **不通过**

**输入白名单（本文送达侧，闭集）：**

| 允许作为送达决策输入 | 说明 |
|---|---|
| **存货是否非空** | 平台自己的库存状态，与用户行为无关 |
| **距上次送达的间隔** | 🔴 **注意这是「我们上次发是什么时候」，不是「他上次来是什么时候」。** ⚠️ **这两个量长得极像，务必分清**：前者是平台自己的下发记录，后者是对用户的行为观测 |
| **用户的显式设置** | 开关状态、静默期设置、被显式关掉的题材 |
| **主人自己填的档案数据** | 如忌日日期（建档时填的），🔴 **仅当产品决定要用**（`§6.3` 待定） |
| 🔴 **「这一条送达过没有」** | 平台自己的下发记录，用于不重复送同一条 |

🔴 **禁止作为送达决策输入（继承 `X8`，非穷举，凡属同类一律禁止）：** 打开率 · 点开与否 · 停留时长 · 完播率 · 刷屏深度 · 距上次回访天数 · 活跃时段 · 会话频次 · 任何由上述量派生的分档/评分/画像。

⚠️ **一条要写在代码注释里的区分。** 🔴 **「我们给你发过什么」（平台自己的下发记录）与「你偏好什么 / 你多久没来」（对用户的推断）观感相近、实质不同：前者允许，后者禁止。**

📌 **这个区分有现成的同型先例，逐字抄它的措辞**：`SPEC-feed-surfaces` 第 798 行（⚠️ **该处是一条<u>提案</u>的代价栏，不是定论**，引用它的措辞而非它的结论）写着 —— 「它记的是「**我们给你列过什么**」（平台自己的下发记录），不是「**你偏好什么**」（对用户的推断）—— 但这个区分**必须在实现时写在代码注释与规格里**，🔴 **否则它迟早会被顺手拿去做偏好推断**」。

🟢 **本文照办**：`§7.2` 的实现清单里把这句注释列为交付项。

#### ③ 内容非心理 —— **推送文案的主语是谁**

> 🔴 **机械判据（直接沿用 `§3.4.3`）：把结论的主语换成「他的内容」，还读得通吗？**
>
> 「**它有一条新的近况**」→ ✅ 说的是内容，**通过**
> 「**它想你了**」→ ❌ 只有主语是「它/人」才读得通，是心理状态，**不通过**

⚠️ **推送场景下的一处加严**：`§3.4.3` 原本管的是「系统对用户下的结论」，🔴 **推送文案里还有第二种主语会出问题 —— 「你」和「你们的关系」。**

| 主语 | 判 |
|---|---|
| **它 / 它的内容** | 🟢 **通过**（「它捎来一条近况」「近况里说到了去年冬天」） |
| **它的心理** | 🔴 **不通过**（「它想你了」「它在等你」「它有点孤单」） |
| 🔴 **你 / 你们的关系** | 🔴 **不通过**（「你三天没来了」「它好久没见到你了」）。⚠️ **这一类是 `§3.4.3` 字面没覆盖到的，本文补上** |

📌 **与 `PRD-echo-pet.md` 的诚实标识条款一致**：那边逐字写着「🔴 **绝不表述『它仍在现实中活动 / 在等你』**」。🟢 **③ 是这条禁令的机械形态。**

#### ④ 🔴 无损可略过 —— **不发会怎样**（新增）

> **④ 逐字**：**主人完全忽略这一次送达，不产生任何损失、不改变任何状态、下次打开时它原样还在。**
>
> 🔴 **机械判据：把这次送达整个删掉，用户失去了什么？**
> 答「**什么也没失去，晚点看到而已**」→ ✅ **通过**
> 答「**他会错过 X**」→ 🔴 **不通过** —— ⚠️ **因为「会错过」正是催促的能量来源。**

**它为什么必须存在**：📌 采纳 `PRODUCT-SPEC-OPEN-QUESTIONS §5.1.2` 的诊断 —— **原三条判准全部在问「这个东西<u>能不能用</u>」，没有一条在问「<u>不用它行不行</u>」。而温和与不温和的分界恰好在这里：**

- **温和** = **主人没看到也没有损失**，它就在那儿等着
- **不温和** = 靠「**你不看就会错过 / 它在等你**」制造**非看不可**

🟢 **它与既有条文自洽，不是新造禁令：**

| 既有条文 | 逐字 | 与 ④ 的关系 |
|---|---|---|
| `COPY-GUIDE` 基调第 2 条（第 60 行） | 「**你来了它会很开心** —— 正向欢迎，**不制造『你不来它就难过』的内疚**」 | 🟢 **④ 是它的机械形态** |
| `COPY-GUIDE` 基调第 4 条（第 62 行） | 「**邀请而非命令** —— 『要不要…』优先于『你必须/该…』；**记录不是打卡任务**」 | 🟢 **④ 是它的机械形态** |
| 🔴 `COPY-GUIDE` 禁用词表（第 82 行） | 「**你 X 天没来，它很失落/难过**」 → 判为「焦虑+内疚」，🔴 **第二关 · 无条件禁（`O-P8`）** | 🔴 **该句正是 ④ 的标准反例，且它已经是无条件禁令** —— 🟢 **④ 不是新造禁令，是给这条已有禁令一个能自己判的形态** |
| `DP1` | 产品面向成年人，自负其责 | 🟢 **同向：不替用户决定他该什么时候来** |

🔴 **④ 有一条最容易被违反的推论：任何「限时」「即将过期」「本次专属」都自动不通过。** ⚠️ **哪怕它在技术上是真的**（比如内容确实有 TTL）—— **那种情况下要改的是 TTL，不是文案。**

### 3.4 🔴 判准管不了的两件事

| # | 管不了的 | 归谁 |
|---|---|---|
| **1** | 🔴 **频次。** **三条全过的一条推送，一天发二十次仍然是骚扰。** | `§4`（节奏）。📌 **不要指望判准把频次也管了** —— ⚠️ **那会让它被拉去干它干不了的事，最后两件都判不准。** |
| **2** | 🔴 **通道。** `S8` 逐字：「消息是唯一主动推送通道，天然是骚扰放大器」，且系统消息**仅服务端可生成**。 | `§6.5`。⚠️ **近况走消息通道就落在 `S8` 管辖内，三条判准之外还要过 `S8`。**🔴 **不要为了绕开 `S8` 另开一条通道。** |

### 3.5 🔴 正例与反例

⚠️ **例子必须写成「触发条件 + 文案」的组合，不能只写文案** —— 🔴 **因为 ② 管触发、③④ 管文案，只看文案的例子无法暴露 ② 的违规。**

#### 3.5.1 正例

| # | 触发条件 | 文案 | 为什么过 |
|---|---|---|---|
| **✅ 1** | 存货里有一条已生成好的近况；距上次送达已隔一天；主人没关开关 | 「**小橘捎来一条近况。**」 | ② 输入只有存货状态 + 间隔 + 开关状态 · ③ 主语是它/内容 · ④ 删掉这次送达，主人什么也没失去，近况就在窗里等着 |
| **✅ 2** | 同上 | 「**小橘捎来一条近况，说到了去年冬天的那件事。**」 | 🟢 **内容线索属于内容属性，不是心理状态** —— 主语换成「他的内容」读得通。⚠️ **这条比 ✅ 1 更好**：它让主人**在点开之前就知道里面大概是什么**，于是「不点开」这个选择变得容易 —— **这正是 ④ 想要的效果** |
| **✅ 3** | 主人在设置里关掉了「离别」这一类题材；本次存货命中该题材 → **本次不送** | （不送，无文案） | 🟢 **不送也要过判准。** ② 的输入是显式设置 · ④ 天然满足 |
| **✅ 4** | 存货为空 → **本次不送**，也不现做 | （不送，无文案） | 🟢 **「没有就不送」永远合规。**🔴 **对照反例 🔴 8** |
| **✅ 5** | 首次送达（`B21` 的初见）：定稿后温柔过场结束 | 「**它捎来第一条消息。**」 | 🟢 **`B21` 原文，三条全过。** 触发是「定稿完成」这个显式动作 |

#### 3.5.2 反例

| # | 触发条件 | 文案 | 挂在哪一条 |
|---|---|---|---|
| 🔴 **1** | ⚠️ **主人 3 天没打开 App** | 「**小橘捎来一条近况。**」 | 🔴 **② 不过。**⚠️ 🔴 **这是本表最重要的一条**：**文案与 ✅ 1 一字不差、完全合规**，但触发读了行为序列。📌 **它单独证明了「只验文案不验触发」是不够的。** |
| 🔴 **2** | 正常节奏 | 「**它想你了。**」 | 🔴 **③ 不过。** 主语换成「他的内容」读不通 |
| 🔴 **3** | 正常节奏 | 「**你有 3 天没来看它了。**」 | 🔴 **③ 不过**（主语是「你」）**+ ④ 不过**（它的全部动力来自「你欠了三天」）。📌 **`COPY-GUIDE` 禁用词表原句** |
| 🔴 **4** | 存货里攒了 5 条 | 「**有 5 条近况在等你。**」 | 🔴 **③ 不过 + ④ 不过。**⚠️ 🔴 **这一条是最容易被写出来的「看起来合规」陷阱**：「近况」是内容、「5 条」是客观事实、句子里连一个情绪词都没有 —— **但「在等你」把主语拉回了关系，而「5 条」本身就是一笔债。** 🔴 **把这次送达删掉，主人的感觉不是「晚点看到」，是「我积压了 5 条」** → ④ 不过。📌 **处理办法见 `§6.1`：不送数量。** |
| 🔴 **5** | 正常节奏 | 「**这条近况 24 小时后就看不到了。**」 | 🔴 **④ 不过。** 人为制造损失。⚠️ **即便 TTL 技术上为真，要改的也是 TTL** |
| 🔴 **6** | ⚠️ **主人上次看近况停留了 40 秒（高于均值），判为投入度高 → 加频** | 「**小橘捎来一条近况。**」 | 🔴 **② 不过**（「停留」逐字撞 `X8`）**+ 撞「只减不加」**（加频方向不存在，`DP11`） |
| 🔴 **7** | ⚠️ **主人连续 3 次没点开「离别」题材的近况 → 该题材减频** | 「**小橘捎来一条近况。**」 | 🔴 **② 不过。**⚠️ 🔴 **这一条要单独记住**：它的**方向是减频**、符合「只减不加」、**看起来完全是在体贴用户** —— **但「没点开」是行为推断，一样禁止。** 📌 **硬禁止项全文见 `§5.2`；这正是 `DP11` 删掉的上行传导。** |
| 🔴 **8** | 到了送达时刻但存货为空 → **临时生成一条** | 「**小橘捎来一条近况。**」 | 🔴 **违反「推送时不现做」**（`§2.2`）。⚠️ **它还有一个更深的问题**：**「必须凑够节奏」这个动机本身就是催促的镜像** —— 平台在催自己，而催自己的产物最后都会落到用户头上 |
| 🔴 **9** | 正常节奏 | 「**别让它等太久。**」 | 🔴 **③ 不过 + ④ 不过。** 一句话里同时出现了心理化的它与「你不来会怎样」 |
| 🔴 **10** | 主人已关闭开关两周，今天重新打开 | 「**这两周它攒了 6 条近况，都在这儿了。**」 | 🔴 **违反结构闸 ①.4**（重新打开不补发）**+ ④ 不过**。⚠️ **它读起来很温柔，这正是它危险的地方** |

### 3.6 判准的使用方式（给写文案与写代码的人）

1. **写一条推送时，先写「我们为什么现在给他发这一条」这句话** —— 🔴 **不写这句话就没法验 ②。**
2. **再把文案的主语挑出来，做 ③ 的替换测试。**
3. **最后问 ④：把这次送达删掉，他失去了什么。**
4. 🔴 **三条任一不过，改的是触发或文案，不是判准。**

⚠️ 🔴 **一条给评审的纪律**：**「这个我觉得挺温和的」不是通过 ②③④ 的理由。** 📌 **判准的存在意义就是把「我觉得」换成「它过没过」；一旦允许用感觉覆盖判准，这一节等于没写。**

## 四、🔴 核心机制：存货 + 上限 + 背压

> 🔄 🔴 **本节在 v0.2 整节重写。** **v0.1 的「频率 + 投递时刻」骨架已推翻，原文保留在 `§4.7`。**

### 4.1 模型

**产品负责人原话（2026-08-27，本节的来源）：**

> 「**你是闲时制作的推送。用户上线才看。所以你设置一个推送产品的上限就好比如免费用就 3 条。超过 3 天就不生成了。用户不读。不上线。这个就暂停就好了啊。**」

#### 4.1.1 拆成五条

| # | 机制 | 说明 |
|---|---|---|
| **1** | **闲时生成存货** | 🟢 **裁定②，本文不管。** 逐字「闲时从素材生成、**不挂用户点击**」 |
| **2** | 🔴 **核心控制量是「未读库存深度」** | ⚠️ **不是发送频率。** **免费档例如 3 条未读** |
| **3** | 🔴 **未读堆到上限 → 停止<u>生产</u>** | ⚠️ **停的是生产，不是送达。** 📌 **这一条是整个模型的要害，也是伦理性质的来源，见 `§6.2`** |
| **4** | 🟢 **用户读了 → 库存降下来 → 自动恢复生产** | 🔴 **无需任何额外触发。不读日历、不读行为侧写、不做召回判断** |
| **5** | 🟢 **用户不上线 → 就暂停** | 🔴 **不是惩罚，也不是终点。就是一个满了的队列** |

#### 4.1.2 🟢 这个模型自带的三个好性质（都是结构性的，不靠纪律维持）

| # | 性质 | 为什么 |
|---|---|---|
| **1** | 🔴 **堆积在结构上封顶** | ⚠️ **久不来的人回来看到的是 3 条，不是 100 条。** 📌 **v0.1 要靠「只送最新 + 绝不提数量」这条纪律去压堆积；现在堆积<u>上不去</u>** |
| **2** | 🔴 **没有不可逆状态** | **满了随时可解，代价为零（读一条即可）。** ⚠️ **对照 v0.1：那套模型里「停了就不再恢复」是一个不可逆的绝对状态** |
| **3** | 🔴 **不读日历、不读行为** | **唯一输入是队列水位。** 📌 **既有那批「多久没来 / 打开率 / 活跃时段」的诱惑<u>在这个模型里没有位置可插</u>** —— **不是被禁止了，是用不上** |

#### 4.1.3 ⚠️ 本文与生成侧的接口

🔴 **背压模型让本文必须输出一个信号给生成侧**，这是 v0.2 相对 v0.1 的范围变化，要写清：

| 谁给谁 | 什么 |
|---|---|
| **送达侧 → 生成侧** | 🔴 **一个闸门信号：「这个主人的未读库存是否已达上限」。** 🟢 **只此一个，不含别的** |
| **生成侧 → 送达侧** | **存货（已生成好的近况）** |
| 🔴 **本文不管的** | **闸门打开时生成什么、怎么生成、生成得多快、成本多少** |

⚠️ **一处要避免的误读**：🔴 **「停止生产」这个动作由生成侧执行，本文只定它的触发口径。** 📌 **本文不规定生成侧的实现，也不越过闸门去管它。**

### 4.2 上限按档位，以及与三分法的对齐

#### 4.2.1 上限值

| 档 | 未读上限 | 性质 |
|---|---|---|
| **免费** | **例如 3 条** | ⚠️ **数值待定** |
| **付费各档** | **更高** | ⚠️ **数值待定，需与商业化线对齐** |
| **关闭** | 🔴 **上限 = 0** | 🟢 **这就是结构闸 ①（`§3.2`）的实现** —— **关掉 = 上限设为 0** |

🔴 **实现要求：上限必须是按档位查出来的配置，不能写成常量。**

#### 4.2.2 🔴 与「付费不解锁情感内容」的对齐关系（**必须写明，否则一定有人来质疑**）

⚠️ **可预见的质疑**：「**免费 3 条、付费更多 —— 这不就是把它对你说话的多少卖给你了吗？那『绝不设悲伤付费墙』怎么办？**」

🟢 **它不冲突，而且它落的正是既定三分法里<u>专门留给档位差异的那一格</u>。**

**现行三分口径逐字**（`DECISIONS.md` 第 65 行 / 第 452 行 · `CR-M②′`，唯一版本）：

| # | 层 | 逐字 | 性质 |
|---|---|---|---|
| **①** | **用户素材** | 🔴 **完全不受档位影响** | **`PIPL` 第 45 条，法律硬要求** |
| **②** | **已交付的服务产出** | 🔴 **不因降档或停付而减少、失效、不可访问** | **商业承诺 —— 🔴 这里才是 `CR-M②` 的真正落点** |
| **③** | **未来的生成额度** | ✅ **档位差异只体现在这里** | **本文的上限属于这一格** |

**一句话口径逐字：🔴 「已有的一样多，能新增的不一样多」。**

**逐条验本文的上限：**

| 层 | 本文的上限动了它吗 |
|---|---|
| **① 用户素材** | 🟢 **完全没动。** 上限不影响任何一张照片、一段音频的存取 |
| **② 已交付的产出** | 🟢 🔴 **完全没动，而且这是背压模型最关键的一处合规性**：**已经生成好的那几条近况，一条都不会因为满了而被撤回、过期、降级或锁起来。** ⚠️ **它们就在那儿等着，读多久之后再读都在** |
| **③ 未来的生成额度** | ✅ **只动这一格。** 上限限制的是**还没生成的那些** |

🔴🔴 **一处正面参照，同构得几乎逐字对应** —— 既有调研（`DECISIONS.md` 第 464 行 · `PRODUCT-MINDMAP` 第 785 行）为三分法找的行业参照是**百度网盘 / 阿里云盘的「不删除、只暂停写入」模型**，逐字注解：

> 「🔴 **读取权不受档位影响，写入权受档位影响**」，**与本条三分法同构**

⚠️ 🔴 **背压模型就是这个参照的逐字实现**：**满了 → 暂停写入（停生产）；已有的照旧可读（停付也不动）。** 📌 **所以这不是一个需要新论证的新设计，它是既有护栏早就点名过的那个形状。**

#### 4.2.3 ⚠️ 但有两条必须同时守住，否则对齐立刻失效

| # | 红线 | 违反了会怎样 |
|---|---|---|
| **1** | 🔴 **降档 / 停付时，已生成的存货一条都不许收回** | ⚠️ **哪怕它超出了新档位的上限。** 📌 **照阿里云盘协议 4.8 那句「已有的超过调整后容量的存储数据不会被强行删除」办** —— 🔴 **超限只影响能不能<u>新增</u>，不影响已有的** |
| **2** | 🔴 **上限不得做成「情感内容的分量」** | ⚠️ **上限限制的是<u>条数</u>，不得同时限制<u>内容的深浅</u>。** 🔴 **免费档拿到的 3 条，必须和付费档的 3 条<u>一样用心</u>** —— 📌 **`CR-M②` 逐字「任一段纪念内容本体永不锁进付费」，「本体」包括它的质量** |

### 4.3 🔴 「未读」的判定口径

**这一条直接决定生产什么时候恢复，🔴 不能含糊。**

#### 4.3.1 定义

> 🟢 **「读了」= 这条近况的<u>内容</u>被展示给主人过。**
> 🟢 **入口不限**：从消息中心进、从窗里的卡列表进、从全屏单卡层进，**一律算读**。
> 🔴 **点开即算读，<u>不看停留时长、不看看完没看完</u>。**

#### 4.3.2 三个候选口径，为什么选中间这个

| 候选 | 判 | 理由 |
|---|---|---|
| **① 进消息中心就算把里面的都读了** | 🔴 **否** | ⚠️ **一次点击清空 3 条 → 上限当场失效、背压不存在。** 📌 **它还有一个更糟的后果：它会让「进收件箱」这个动作变成清空债务的手势**，而那正是我们想避免的形态 |
| 🟢 **② 点开那一条近况本身** | 🟢 **采纳** | 🔴 **它是唯一一种「读了」真的等于「他看到了那条内容」的口径。** 而背压的整个意义就是「别生产他还没消费的东西」—— **口径必须对齐「消费」这件事本身** |
| **③ 在窗里滑过就算** | 🔴 **否** | 🔴 **它读的是曝光**，而曝光是 `X8` 家族的东西；⚠️ **且它是三个候选里最不诚实的一个** —— **滑过去了不等于看了** |

#### 4.3.3 🔴 三条附带要求

| # | 要求 | 理由 |
|---|---|---|
| **1** | 🔴 **入口不限，一律算读** | ⚠️ **否则等于强迫他走通知这一个入口 —— 那是通道胁迫。** 📌 **他在窗里自己翻到并点开，和从通知点进去，对他是同一件事，对我们也必须是同一件事** |
| **2** | 🔴 **点开即算，不加任何「读得够不够」的条件** | **① `X8` 硬要求**（停留时长禁用）· **② 它把口径往<u>宽松</u>那一侧定** —— ⚠️ **宽松即降压：他随手点开就算，不需要认真读** |
| **3** | 🔴 **已读一旦置位，不得回退** | ⚠️ **「过了 30 天没再看，算他又没读了」这种设计不许有** —— 📌 **那是给库存加了过期时间，而过期时间会把「等着他」变成「等不了他」** |

#### 4.3.4 🟢 这个口径的合规性

| 判准 | 检验 |
|---|---|
| **② 输入显式** | 🟢 **过。「点开」是显式动作**，且它就是既有白名单那一类 |
| **③ 内容非心理** | 🟢 **过。**「这条内容被展示过」是一个关于**内容**的事实，不是关于人的心理状态 |
| **`X8`** | 🟢 **不撞。** **不读停留、不读完播、不读深度**（详见 `§4.5`） |

### 4.4 🔴 恢复：等下一个闲时窗口，不即时

#### 4.4.1 结论

> 🟢 **他读了一条 → 未读水位降 1 → <u>下一个闲时窗口</u>检查到有空位 → 生产恢复。**
> 🔴 **不即时生成。**

#### 4.4.2 两条理由，第一条就足以定它

| # | 理由 |
|---|---|
| **1** | 🔴🔴 **即时恢复 = 生成挂用户点击，直接打穿裁定②。** 裁定②逐字：「**闲时从素材生成、<u>不挂用户点击</u>**」。⚠️ **「他读一条我就生一条」就是挂在点击上，只是挂得含蓄** —— 📌 **所以这不是一个偏好问题，是一条已有裁定的直接推论。** |
| **2** | ⚠️ 🔴 **即时恢复会造出即时奖励回路。**「**我一读就又有新的**」是一个学得会的因果，而它的形状就是**刷不完的信息流**。🟢 **闲时窗口把因果在时间上拉开，用户学不到精确的因果 —— 这是<u>有意</u>的模糊，不是实现偷懒。** |

#### 4.4.3 ⚠️ 一处实现上容易走偏的地方

🔴 **「闲时窗口」不得由用户的动作触发，哪怕是延迟触发。**

| 实现 | 判 |
|---|---|
| 🟢 **定时扫描：闲时窗口到了 → 检查所有主人的队列水位 → 有空位就补** | 🟢 **正确。** 触发源是**时钟**，与用户无关 |
| 🔴 **他读了 → 埋一个「30 分钟后生成」的延迟任务** | 🔴 **错。** ⚠️ **它仍然是挂在点击上的，只是加了个延迟** —— 📌 **延迟不改变因果，只是把它藏起来** |

### 4.5 🔴 队列深度算不算「读行为」—— 独立核实 `X8` 原文后的结论

> ⚠️ **产品负责人给了他的判断（「它是队列水位不是偏好也不是情绪序列」）并明确要求本文<u>独立核一遍再定，不要照抄</u>。** 🟢 **下面是核实过程与结论。**

#### 4.5.1 `X8` 原文（已回查，三处一致）

| 出处 | 逐字 |
|---|---|
| `SPEC-recommendation-ranking §4.3`（第 94 行） | 「`X8` ｜ **停留时长 / 刷屏深度 / 完播率 / 复播率** ｜ 🔴 **P0 排序侧完全不读**（比「降为弱信号」更严一档），只进后台护栏看板」 |
| `SPEC-recommendation-ranking RK6`（第 2252 行） | 十三条禁用特征清单里登记为「**X8 停留参与度**」 |
| `DECISIONS.md RK-K`（第 1430 行） | 🔴 **「`X8` 是<u>输入侧</u>禁令，与结论说得像不像人话无关：判 `X8` 只看输入读了什么，🔴 不看输出写了什么。」** |

#### 4.5.2 逐项检验

| 检验 | 结果 |
|---|---|
| **逐字比对** | 🟢 **不命中。** 队列深度不是停留时长、不是刷屏深度、不是完播率、不是复播率 |
| **语义比对** | 🟢 **不同类。** ⚠️ **`X8` 那四个量的共同点是「参与强度」—— 它们都在度量<u>他投入了多少</u>；队列深度度量的是<u>平台生产了多少还没被消费</u>。**🔴 **量的主体一个是用户、一个是库存** |
| **语境比对** | 🟢 **不在射程内。** **`X8` 是排序侧的禁用特征清单**（`RK6`）；🔴 **队列深度不进排序，它进的是生产闸门** |
| **判准 ② 的四类禁止输入** | 🟢 **不在其中**（浏览 / 停留 / 完播 / 刷屏深度） |
| **判准 ③ 适不适用** | ⚠️ **不适用，而不是「通过」。** 📌 **③ 的机械判据是为「系统对用户下的结论」设计的**，而队列深度**不是一个关于用户的结论**，是一个关于队列的计数 —— 🔴 **不要硬套，硬套会得出错误的安全感** |

🟢 **结论：不撞 `X8`。** 🟢 **本文与产品负责人的判断一致，但依据是自己核出来的。**

#### 4.5.3 🔴 但真正的危险不在 `X8`，在它**到 `X8` 的距离**

⚠️ **这一段是本节最需要被读到的。**

**未读数 = 已下发条数 − 已读条数。** 🔴 **而「已读」这个量在时间上一累积，就非常接近打开率。**

| 量 | 判 | 为什么 |
|---|---|---|
| ✅ **「当前未读 = 2」** | 🟢 **合规** | **瞬时水位。** 它不含任何历史 |
| 🔴 **「他最近 10 条只读了 3 条」** | 🔴 **违规** | **这是打开率**，撞判准 ② |
| 🔴 **「他平均隔几天读一条」** | 🔴 **违规** | **这是回访节律**，撞判准 ②；📌 **且它正是 `§2.4` 那条被清空用途的看板指标** |
| 🔴 **「他的未读水位最近在上升」** | 🔴 **违规** | ⚠️ **水位的<u>趋势</u>是一个行为序列**，不是瞬时值 |

**🔴 工程红线（要写进代码注释）：**

> 🔴 **只保留当前水位这一个瞬时值。**
> 🔴 **不存历史序列、不算比率、不做时间平均、不记水位变化趋势。**
> 🟢 **它应当是一个计数器（或一次实时 `COUNT`），不是一张时间序列表。**

⚠️ 🔴 **为什么这条红线必须写死**：**「未读水位」这个字段一旦带上时间维度，它就<u>免费获得了</u>打开率与回访节律的全部表达力** —— 📌 **而那两个量是本项目明令禁止的。** 🟢 **好消息是：背压机制本身<u>只需要瞬时值</u>，历史序列对它毫无用处 —— 所以这条红线不牺牲任何功能。**

### 4.6 ⚠️ 上限这个数值的伦理后果（**它不是纯参数**）

🔴 **上限越低，「读」这个动作的工具性越强。**

**推理**：3 条满了之后，主人想让它继续写下去，**唯一的办法就是读一条**。⚠️ **上限越紧，这个因果越容易被他察觉、越容易变成一件<u>为了让它继续写而必须做的事</u>。**

| | |
|---|---|
| ⚠️ **所以定这个数时要问的不只是「多少条合适」** | 🔴 **还要问「这个数会让『读』变成任务吗」** |
| 💡 **建议（非裁定）** | 🟡 **宁可略宽。** ⚠️ **但也不能太宽** —— 太宽等于没有上限，堆积内疚就回来了。📌 **这是一个双侧约束，两头都有代价** |
| 🔴 **必须配一条** | **「满了」这个状态<u>不给任何提示</u>** —— **详见 `§9`，那里是本文最不放心的一处** |

📌 **完整分析见 `§9`「换成背压后，催回访的压力去哪了」。**

## 五、题材偏好减频

### 5.1 口径：🔴 只减不加

| | |
|---|---|
| 🟢 **做** | **把用户不喜欢的题材，主动降低推送频率** |
| 🔴 **不做** | ⚠️ **「喜欢的题材加频」** —— **这个方向不存在，不是「以后再做」** |

> 🔄 **v0.2 补一句「减频」在背压模型下是什么意思**：🔴 **题材粒度上它的形态是「该题材的存货不送达」**（`§5.3`），⚠️ **而不是「把整体频率调低」** —— 📌 **整体频率在 v0.2 里已经不是一个可以直接调的旋钮了**（它是库存与消费的结果）。

**为什么加频这个方向要整个删掉**（不是排期问题）：📌 `DP11` 删掉「转热加频」时给的理由逐字是 —— 「**能识别投入度、却只用来增加触达**，那个把柄本身就是它」。🟢 **本文照办：单向机制在本项目是被接受的形态。**

⚠️ **一条实现上的推论**：🔴 **「减频」必须实现成<u>减法</u>，不能实现成<u>权重</u>。** **权重可以往两边动，一个能调小的旋钮就是一个能调大的旋钮** —— **而「只减不加」这条约束会在某次调参里静默消失。** 💡 **建议实现为「被关掉的题材集合」（一个集合，只有加入与移出，没有强度）。**

### 5.2 🔴 硬禁止项：「不喜欢」的唯一合法来源是用户的显式表达

> 🔴 **「用户不喜欢某个题材」这个判断，必须来自用户的显式表达。**
>
> 🟢 **允许的输入（闭集）**：**明说** · **划掉** · **在设置里关掉某一类**
>
> 🔴 **禁止的输入（非穷举，凡属同类一律禁止）**：**他没点开** · **他停留短** · **他跳过了几次** · **他打开率低** · **他划走得快** · 任何由上述量派生的量

**为什么这是红线，而不是一条偏好：**

| 依据 | 逐字 / 要点 |
|---|---|
| 🔴 `DP11` | **「没点开 → 判定不喜欢」正是 `DP11` 删掉的上行传导** —— 从用户行为反推出对用户的判断，再用这个判断去改分发 |
| 🔴 `X8` | **「停留」直接撞 `X8`。** `SPEC-feed-surfaces §3.4.2` 把**停留时长 / 刷屏深度 / 完播率**列为**输入侧禁令**，并注明「**判 `X8` 只看输入读了什么，不看输出写了什么**」 |
| 🔴 本文文案闸 ② | 「没点开」是行为序列，用户**没有任何办法让系统忘记**它 |

#### 5.2.1 ⚠️ 这条禁令拦的是「看起来对用户有利」的做法

🔴 **这是本节最需要被读到的一段。**

**考虑这个实现**：「他连续 3 次没点开『离别』题材的近况 → 以后少给他推这一类。」

**它看起来无可挑剔：**

- ✅ 方向是**减频**，符合「只减不加」；
- ✅ 效果是**少打扰他**，不是多打扰他；
- ✅ 动机是**体贴** —— 他显然不想看这类，我们何必硬塞；
- ✅ 它甚至**不需要任何文案改动**，文案还是那句合规的「小橘捎来一条近况」。

🔴 **但它是禁止的**，理由只有一条：**它读的是行为序列。**

⚠️ 🔴 **为什么不能因为「效果好」就放它过**：

1. **它建的是行为画像，只是这一次用途温和。** 📌 **画像一旦建起来，它的用途由下一个人决定** —— 而下一个人拿到「谁对哪类内容反应冷淡」这张表，做出「谁对哪类内容反应热烈 → 多推」只需要改一个不等号方向。🔴 **禁的是那张表，不是这次的用法。**
2. 🔴 **「没点开」根本不等于「不喜欢」。** ⚠️ **在这个产品里尤其不等于** —— **一条关于离别的近况，主人可能正是因为太在意而点不开。** 📌 **把「点不开」读成「不想看」，是把最重的那种在意误判成了最轻的那种冷淡。**

🟢 **正确做法**：**给一个能划掉的入口，然后等他划。** ⚠️ 🔴 **他不划，就当他没有意见 —— 这不是信息缺失，这是 `DP1` 的立场**（产品面向成年人，自负其责；平台无权替他判断他喜不喜欢）。

#### 5.2.2 显式表达的入口（💡 建议形态）

| 入口 | 💡 建议 | 判准检查 |
|---|---|---|
| **划掉** | 在一条近况上「**这类少给我**」 | 🟢 ② 过（显式动作） |
| **设置里关某类** | 题材列表，可逐类关闭 | 🟢 ② 过 |
| **明说** | 反馈入口里写的话，🔴 **人工处理，不做自动解析** | ⚠️ **自动解析文本以推断偏好，等于换一种方式建画像** —— 💡 **建议不做** |

🔴 **两条与既有机制对齐的要求：**

1. 🔴 **可撤销必须做到**（这里 `§3.4.3` 的第 1 条**是有效的** —— 它在**这个**场景下不失效，因为这里判的是「一个信号能不能用」而不是「一次打扰能不能发）：**划掉之后要能取消划掉，且取消后由它推出的减频立刻消失。**
2. ⚠️ **划掉这个动作本身要不要写进埋点**：🔴 **注意一处已被登记的陷阱**。📌 `PRODUCT-SPEC-OPEN-QUESTIONS` 第 787 行逐字：「**判『这算不算埋点』不要看它存进了哪张表，看<u>用户做这个动作时的心理状态是不是被记录下来了</u>**」，并举了「**『他删掉了这一条』记录的是『他不喜欢这一条』，而『不喜欢』是心理状态**」。
   🟢 **本文的判断（💡 建议，供裁定）**：**划掉是<u>用户自己给出的指令</u>，不是我们对他心理状态的推断** —— 存的是「**他要求少推这一类**」（一条指令），🔴 **不是「他不喜欢这一类」（一个心理判断）。** ⚠️ **这个区别必须落到<u>字段命名</u>上**：🔴 **字段叫「已关闭的题材」，不要叫「不喜欢的题材」** —— 📌 **理由与 `§3.4.3` 那条「不要把字段命名为『粘性』」完全同型：叫「不喜欢」的字段，迟早会有人拿点击率去填它。**

### 5.3 减频减到什么程度

| 情形 | 处理 |
|---|---|
| **某题材被关掉** | 🟢 **该题材的存货<u>不送达</u>**（不是降低频率，是不送）。⚠️ **「减频」在题材粒度上的自然形态就是「不送」** —— 一个题材要么给他要么不给他，中间态没有产品意义 |
| **所有题材都被关掉** | 🔴 **等价于关闭开关** → 触发结构闸 ①：**停止生成**。⚠️ **不要让它变成「还在生成但永远送不出去」** —— 那正是 `§3.2.2` 消掉的那笔债 |
| **本次存货全部命中已关题材** | 🟢 **本次不送**（`§3.5.1` ✅ 3）。🔴 **不换一条、不现做、不顺延** |

⚠️ **「不顺延」这一条容易被忽略**：🔴 **「这次没送出去，那就明天补一次」= 把送达次数当成了必须达成的配额。** 📌 **配额思维是催促的另一种形态，只不过催的对象是平台自己**（见 `§3.5.2` 反例 🔴 8）。

## 六、四个运营问题

### 6.1 多条堆积怎么办

> 🔄 **v0.2 改写。** 🔴 **上限本身就是这个问题的答案 —— 堆积在结构上封顶了。** ⚠️ **v0.1 的三案对比与「只送最新」建议仍有价值，但地位从「解法」降为「封顶之内的措辞纪律」，见 `6.1.0`。**

#### 6.1.0 🟢 v0.2 的答案：**上限先把这个问题削掉了大半**

**场景**：存货攒了多条；或主人久未打开，未读的近况累积。

| | v0.1 | 🟢 v0.2 |
|---|---|---|
| **堆积能长到多大** | ~~无界~~ | 🔴 **封顶在上限（例如 3 条）** |
| **靠什么压住** | ~~纪律：只送最新 + 绝不提数量~~ | 🟢 **结构：它上不去** |
| **久不来的人回来看到** | ~~可能是一百条~~ | 🟢 **就是 3 条** |

🔴🔴 **这一处是背压模型最直接的收益，而且它正好解掉 v0.1 自己识别出的那个内疚源** —— ⚠️ **`§6.1.3` 曾把「主人可能永远不知道那几条存货存在」列为一项必须接受的代价；在 v0.2 里这项代价大幅缩小**：📌 **他没读的东西最多就 3 条，而 3 条是他一次坐下来就能看完的量。**

**🟢 但有两条 v0.1 的纪律要继承下来（它们在封顶之内仍然成立）：**

| # | 继承的纪律 | 为什么仍要 |
|---|---|---|
| **1** | 🔴 **绝不出现「有 N 条近况」，任何形态都不行**（通知里、角标上、消息中心标题上都不行） | ⚠️ **上限封住了数量的<u>大小</u>，没有封住把数量<u>说出来</u>这件事。** 🔴 **「有 3 条近况在等你」照样是一笔债，只是小一点的债** |
| **2** | 🟢 **一次送达只对最新那一条发一下轻通知** | ⚠️ **哪怕只有 3 条，三条通知连着响也是刷屏。** 📌 **既有代码里已有同型判断，见 `6.1.2`** |

#### 6.1.1 🔄 v0.1 原文：三案对比（**保留，仍可用于判措辞**）

| 案 | 做法 | 🔴 判准检查 | 结论 |
|---|---|---|---|
| **甲** | **一次全推** | 🔴 **过不了 `§3.4` 第 1 条（频次）。** 判准逐条都能过，但一次五条通知就是刷屏。📌 **既有代码里已有同型判断**：`arrivals.ts` 逐字写着，不合并的话「一张卡热起来就会在消息列表里刷屏，而那正好撞上『柔性暖点、看过即散、**绝不红点轰炸**』」 | 🔴 **否** |
| **乙** | **合并成一条** | ⚠️ 🔴 **合并本身没问题，问题在合并后那句话怎么写。** 「有 5 条近况在等你」= `§3.5.2` 反例 🔴 4，**③④ 双挂**。<br>而如果合并后**不给数量**（「小橘捎来了近况」），那它与丙案在用户看到的那一屏上**没有区别** —— 🟡 **它退化成丙案，只是多写了一套合并逻辑** | 🟡 **可行但无收益** |
| **丙** | 🟢 **只送最新一条；其余存货静默入窗** | 🟢 **三条全过。** 送出去的就是一条普通的、合规的近况通知；其余的**不产生通知、不计未读数、不排队补送** | 🟢 **💡 建议采纳** |

#### 6.1.2 🔄 v0.1 原文：丙案的细则（**🟢 措辞纪律部分继承，「靠它压堆积」那层已被上限取代**）

> 🟢 **送达时只取存货里最新的一条，按 `§3` 判准发一条通知。**
> 🟢 **其余存货静默进入窗（它们就是窗里的回忆，主人自己翻的时候在那儿）。**
> 🔴 **不产生第二条通知 · 不计未读数 · 不加红点角标 · 不排队在后续送达里补发。**

**🔴 最要紧的一条约束单独列出来：**

> 🔴🔴 **绝不出现「有 N 条近况」，任何形态都不行** —— 不出现在通知里、不出现在角标上、不出现在消息中心的标题上。

⚠️ **为什么数量本身就是违规，哪怕它是客观事实**：**「5」这个数字在这里不是信息，是一笔债。** 🔴 **判准 ④ 的机械判据在这里给出明确答案**：把这次送达删掉，主人失去的**不是**「晚点看到一条近况」，是「我积压了 5 条」这个感觉的消失 —— **也就是说，这次送达<u>制造</u>了一个损失，而不是传递了一条消息。**

🟢 **这条约束在既有代码里已有先例可循，措辞可以直接沿用。** `arrivals.ts` 里的 `previewOf` 逐字：

- 🔴 「**三种组合一律用「有人」，不区分单复数、不给任何数量线索。** 中文的「有人」单复数通用，这一条红线因此可以靠**措辞本身**落实」
- 🔴 反例：「~~3 个人记得了它~~」「~~有 5 束心意~~」「~~又有 2 人来看过~~」

⚠️ **本文对近况的处理比它更严一档，理由要说清**：**回应侧可以「合并成一条 + 不给数量」，因为多条回应指向的是<u>同一张卡</u>，合并后信息无损。** 🔴 **而多条近况是<u>不同的内容</u>，合并成一条必然丢内容** —— **于是「合并」就变成了「提示你还有别的没看」，而那个提示除了数量之外没有别的东西可说。** 📌 **所以近况这边选的不是「合并」，是「只送最新、其余不提」。**

#### 6.1.3 🔄 v0.1 原文：丙案的代价（**🟢 两项代价在 v0.2 里都缩小了，见每行的 v0.2 后记**）

| 代价 | 判断 |
|---|---|
| **主人可能永远不知道那几条存货存在** | 🟢 **接受。** ⚠️ **「让他知道」这个诉求本身需要检查** —— 🔴 **它的唯一实现方式就是提示数量或反复提醒，而那正是被禁的东西。** 📌 **判准 ④ 的立场是：他没看到也没有损失。如果我们认为「他不知道」是个损失，那说明我们没有真的接受 ④**<br>🟢 **v0.2 后记**：**这项代价大幅缩小** —— 🔴 **未读最多就是上限那么多（例如 3 条），是他一次坐下来就能看完的量** |
| **生成出来的东西有一部分永远不被送达** | ⚠️ **这不是送达侧的问题，是<u>生成节奏</u>的问题** —— 🔴 **如果存货长期堆积，正确的反应是<u>少生成</u>，不是多送达。** 🟢 **v0.2 后记**：📌 **这条诊断被背压模型<u>采纳并制度化</u>了** —— **「堆积就少生成」正是 `§4` 的机制本身**（`§8.2` 生成侧那一行） |

### 6.2 🔴 用户完全不来时会怎样 —— **v0.2 整段改写，v0.1 原文与原分析保留在 `6.2.6`**

> 🔴🔴 **本节是 v0.2 最值钱的一处，请不要删掉下面那段被推翻的原文。**
> ⚠️ **它记录的东西比它的结论重要：<u>同一个机制，换一个停止的对象（停生产 vs 停送达），伦理性质就翻转。</u>**

#### 6.2.1 v0.2 结论

> 🟢 **队列满了就停止<u>生产</u>，一直等他。**
> 🔴 **不存在终点，也不存在任何不可逆状态。**
> 🟢 **他任何时候读一条，下一个闲时窗口生产就恢复。**

#### 6.2.2 🔴 为什么这与 v0.1 的「终点」是两回事

**v0.1 与 v0.2 都有一个「停」，但停的对象不同 —— 而这个差别不是实现细节，它决定了用户感受的方向。**

| | **v0.1：停送达** | 🟢 **v0.2：停生产** |
|---|---|---|
| **已生成的那几条** | ⚠️ **发不出去了** | 🟢 **一直在那儿等着** |
| **用户那一侧读到的句子** | 🔴 **「它不再给我写了」** | 🟢 **「它写的还在这儿等我」** |
| **可逆性** | 🔴 **不可逆**（v0.1 明写「停下之后不自动恢复」） | 🟢 **完全可逆，代价为零**（读一条即可） |
| **累积惩罚** | ⚠️ **有**（连续未看次数是一个只增不减的计数） | 🟢 **无**（水位只反映当下，不记历史） |
| **久不来的人回来看到** | ⚠️ **一个已经停掉的通道** | 🟢 **3 条在等他** |

🔴🔴 **这两句话给用户的感受是相反的。** 📌 **而它们出自同一个动作（「不再继续了」），区别只在于<u>停的是哪一头</u>。**

#### 6.2.3 「读了没有」怎么算 —— 界线仍然要守（🟢 **本小节 v0.1 原文继承，未改**）

🔴 **背压模型需要一个「他读了没有」的判断，而这个判断看起来很像被禁的行为观测。** 逐一辨明：

| 量 | 判 | 理由 |
|---|---|---|
| 🟢 **这条近况的已读状态** | 🟢 **允许** | **已读是产品明确的一等状态**（`PRODUCT-GLOSSARY §4.2`：「**已读** —— 我看过别人给我的回应，是**我这一侧的已读状态**」），且**服务端已有 `POST /messages/read` 与已读水位**。🟢 **它是「我们下发的东西被打开了没有」，属于平台自己的下发记录一侧** |
| 🟢 **当前未读条数（瞬时水位）** | 🟢 **允许** | 🆕 **v0.2 新增，依据见 `§4.5`**（已独立核 `X8` 原文） |
| 🔴 **停留时长 / 看了多久 / 看完没看完** | 🔴 **禁止** | **逐字撞 `X8`** |
| 🔴 **距上次回访天数 / 打开率 / 会话频次** | 🔴 **禁止** | **行为序列**（`§3.3` ②） |
| 🔴 **未读水位的历史序列 / 趋势** | 🔴 **禁止** | 🆕 **v0.2 新增禁令，见 `§4.5.3`** —— ⚠️ **水位的趋势就是行为序列** |

⚠️ 🔴 **一条给实现者的界线**：**允许问「这一条被打开了没有」（是/否，绑在这条送达上），禁止问「他最近来得多不多」（一个关于人的量）。** 📌 **前者的量纲是「一条送达」，后者的量纲是「一个人」 —— <u>量纲变了，红线就跨过去了</u>。**

#### 6.2.4 🟢 v0.2 不需要的东西（v0.1 里那批待定项**整批消失**）

| v0.1 需要定的 | v0.2 |
|---|---|
| ~~连续多少次未被看过之后停~~ | 🟢 **不需要这个数。** **满了就停，满的定义就是上限本身** |
| ~~停止之后要不要通知主人~~ | 🟢 **问题不存在。** **没有「停止」这个事件，只有「队列是满的」这个状态** |
| ~~恢复的合法触发是什么~~ | 🟢 **只有一个，而且是机械的：读一条，空出一格** |
| ~~会不会无限期继续~~ | 🟢 **不会，且不靠终点实现** —— **靠的是他不消费就不生产** |

🔴 **一处仍然成立、要继续守的**：**「我们已经停止给你发近况了」这类通知<u>永远不许发</u>。** ⚠️ **v0.2 里它更不该有** —— 📌 **因为并没有停止什么，说了反而是假的，而且它带着「你要失去了」的暗示，判准 ④ 直接挡掉。**

#### 6.2.5 🟢 满了的时候，窗里是什么状态

| 项 | 处理 |
|---|---|
| **已生成的存货** | 🟢 **全部照旧可读、可翻、可回看。** 🔴 **不撤回、不过期、不降级、不上锁**（`§4.2.3` 红线 1） |
| **纪念空间本身** | 🟢 **完全不受影响。** 🔴 **满的是生产队列，不是他的窗** |
| **满了这个状态本身** | 🔴 **不提示、不角标、不引导升级。**⚠️ **理由见 `§9`，这是本文最不放心的一处** |

### 6.3 静默期

#### 6.3.1 两类，来源完全不同

| 类 | 内容 | 来源 | 判准 |
|---|---|---|---|
| **时段类** | **深夜不送** | 🟢 **平台统一规则，不读用户数据** | 🟢 ② 过 |
| **状态类** | 「**这周先不要来信**」 | 🔴 **只能来自用户的显式设置** | 🟢 ② 过 |

🔴 **状态类静默<u>绝不允许</u>由平台推断。** ⚠️ **典型的违规想法**：「他最近可能刚办完事，情绪不稳，先别打扰他」—— 📌 **它读的是行为、下的是心理判断，②③ 双挂。** 🔴 **「体贴地推断用户状态」和「监测用户状态」是同一件事的两个说法。**

📌 **状态类静默的入口措辞已有现成口径**，`PRODUCT-GLOSSARY §2.3` 第 ③ 条逐字：「**设置里要能说「这周先不要来信」「只保留回忆，不生成近况」**」。⚠️ **注意这两句的差别**：**前者是限期静默**（这周不要，之后照旧）、**后者是关闭开关**（结构闸 ①）。🟢 **两个都要有。**

#### 6.3.2 ⚠️ 静默期与「不规律」不冲突

🔴 **有人会觉得「设了静默期就等于有规律了」。不是。**

> **静默期只说<u>什么时候不送</u>，不说<u>什么时候送</u>。**
> 🔴 **规律的反面不是「随时都可能」，是「送的那个时刻不可预期」** —— **允许窗口有边界，窗口内部不可预期，两者并存。**

#### 6.3.3 💡 建议值（🔴 建议，非裁定）

| 项 | 💡 建议 | 理由 |
|---|---|---|
| **深夜静默** | **21:00 – 09:00 不送** | ⚠️ **这个产品的用户在深夜收到关于逝去宠物的推送，风险明显高于普通产品** |
| **限期静默** | **一周 / 一个月 / 自定义** | 🟢 **给出「这周先不要来信」这一档就够起步** |
| **静默期内的存货** | 🔴 **不排队、不补发。** 静默结束后按正常节奏走，**不追赶** | 📌 **同 `§5.3` 的「不顺延」** |

#### 6.3.4 ⚠️ 忌日 / 纪念日：待定，两个方向相反且都说得通

| 方向 | 说得通的地方 | 说不通的地方 |
|---|---|---|
| **A · 那天要送**（一条特别的近况） | **那天主人本来就在想它，这时候的一条近况是陪伴** | 🔴 **它天然带着「不能错过」的重量** → ⚠️ **判准 ④ 在这里非常吃紧**：把这次送达删掉，主人会不会觉得「今年它没来」？**如果会，④ 不过** |
| **B · 那天静默** | **不在最重的那一天主动打扰** | **可能恰好错过最需要陪伴的时刻** |

| | |
|---|---|
| **待定** | **A 还是 B** |
| **定它需要什么** | 🔴 **一次产品决定。** ⚠️ **这一条不建议用判准硬判** —— **判准能告诉你 A 的风险在哪（④），但「那天该不该有人陪」是价值判断，不是合规判断** |
| 💡 **本文的倾向（仅供参考）** | 🟡 **倾向 A，但必须去掉「特别」二字** —— **那天送一条普通的近况，不做仪式、不做限定版、不提「今天是什么日子」。** 🟢 **这样 ④ 能过**：删掉它，主人失去的只是「今天没收到」，而不是「今年的纪念没了」 |

### 6.4 失败与重试

#### 6.4.1 🔴 关键是先把两件事拆开

⚠️ **「推送失败」是两件不同的事，混在一起就必然做错一半：**

| | 是什么 | 失败了怎么办 |
|---|---|---|
| **落库** | **这条近况进消息中心 / 进窗** | 🔴 **必须重试，直到成功。** 🟢 **这是数据完整性，不是打扰** —— ⚠️ **落库失败意味着<u>这条内容丢了</u>，主人以后自己翻也翻不到** |
| **轻通知** | **手机上那一下提示** | 🟢 **不重试、不补发。** |

#### 6.4.2 轻通知为什么不补发

🔴 **这是判准 ④ 的直接推论，而且是最干净的一次应用：**

> **④ 要求：主人完全忽略这一次送达，不产生任何损失，下次打开时它原样还在。**
> 🟢 **而通知发失败，产生的结果与「主人忽略了它」<u>完全相同</u>** —— **内容在消息中心里等着，他打开就看到。**
> 🔴 **所以通知失败在本产品里<u>不是一个需要修复的故障</u>，它落在一个我们已经声明可接受的状态里。**

⚠️ 🔴 **反过来说，重试机制的存在本身就在表达一个立场**：「**必须让他看到**」。📌 **那个立场与 ④ 正相反 —— 一套完善的推送重试链路，是「不容许他错过」这个想法的工程形态。**

#### 6.4.3 具体规则

| 情形 | 处理 |
|---|---|
| **通知下发接口报错** | 🟢 **记一条运维日志，不重试。**🔴 **日志只记「失败了」，不记这个主人的任何行为信息** |
| **设备离线 / 用户在系统层关了通知权限** | 🟢 **什么也不做。** ⚠️ **不引导开启通知权限** —— 📌 **「打开通知才能收到它的消息」是一句合规外衣下的胁迫**（判准 ④：不打开会错过 → 不过） |
| **同一条近况已送达过** | 🔴 **绝不重送。** 🟢 **「这一条送达过没有」是允许的输入**（平台自己的下发记录，`§3.3` ②） |
| **落库失败** | 🔴 **重试至成功；重试期间不发通知。** ⚠️ **顺序必须是先落库、后通知** —— 🔴 **通知先到而内容没落库，主人点进去看到空的，那是最糟的一种失败** |

### 6.5 ⚠️ 通道：`S8` 的管辖

`S8` 逐字（`DECISIONS.md` 第 556 行）：「**消息是唯一主动推送通道，天然是骚扰放大器**」，且「**系统消息仅服务端可生成**」。

⚠️ **一处相邻先例，说明这条纪律在本项目是真的在执行的**：`SPEC-admin-console.md` 第 131 行据 `S8` 把「运营主动给用户发消息」在 P0 整个砍掉，逐字「**主动触达能力 P1 再评估，且须先有频控与退订**」，并注明「**`C` 自由发送绝不可接受 —— 那等于给了一个能对全量悼念中用户群发的入口**」。🟢 **本文的频次约束（`§4`）与开关（`§3.2`）正好就是那句「频控与退订」在近况这一侧的形态。**

| 项 | 状态 |
|---|---|
| **近况走消息通道 → 落在 `S8` 管辖内** | 🔴 **是。** ⚠️ **三条判准之外还要过 `S8`** |
| 🔴 **不要为了绕开 `S8` 另开一条通道** | **明确禁止。** ⚠️ **另开通道会让「唯一主动推送通道」这句话失效，而那句话是所有骚扰约束的挂靠点** |

### 6.6 🔴🔴 两套提醒必须分开（**同一个收件箱，两条独立的提醒轨**）

**产品负责人原话（2026-08-27）：**

> 「**消息中心什么都塞。但是是两套提醒啊。瀑布流那边的系统跟自己的这套不要再混淆了。**」

#### 6.6.1 结论

> 🟢 **消息中心是<u>同一个收件箱</u>** —— 什么都塞，这一点不变。
> 🔴 **但纪念侧（它捎来的近况）与共鸣厅侧（别人的回应）是<u>两条独立的提醒轨</u>。**

#### 6.6.2 两条轨分别是什么

**照 `ARCHITECTURE-system-split §0.1` 的既有口径（🔴 不自创），两个系统对用户各是什么：**

| | **纪念系统** | **共鸣厅系统** |
|---|---|---|
| **既有口径逐字** | 「**和自己的它相处。** 回访、**看近况**、翻生命之书、收明信片、记一笔」 | 「**看别人的一段记忆，或者被别人看见。** 在共鸣厅里刷到一张卡、点进去、留下一点什么」 |
| **这一屏是谁的** | 「**只属于窗主。** 别人来了也只是客人」 | 「**谁都可以在这里。** 它不属于任何人」 |
| **对应的提醒** | 🟢 **近况捎来了**（系统 → 主人） | 🟢 **别人的回应到达了**（别人 → 你） |
| **本文管的是** | 🔴 **这一条轨** | ⚠️ **不管。** 它已有实现 |

🟢 **注意 `§0.1` 那张表里「看近况」是<u>逐字列在纪念系统那一栏</u>的** —— 📌 **所以这个归属不是本文的判断，是既有架构口径已经写好的。**

#### 6.6.3 🔴 明令：不得往 `/messages/arrivals` 里加一类近况

> 🔴🔴 **禁止把近况塞进 `/messages/arrivals`。**
> ⚠️ **实现时最顺手的动作恰好就是这个，所以这一条必须写死。**

**为什么最顺手**：那个端点**名字叫「到达」**，而 `B21` 说近况是「**到达式**」的 —— 📌 **两个「到达」字面完全一样，于是「加一类进去」看起来像是在复用，而不像是在混淆。**

**但它今天装的是<u>另一条轨</u>：**

| | **`/messages/arrivals` 今天装什么** | **`B21` 的「到达式」指什么** |
|---|---|---|
| **哪一侧** | 🔴 **共鸣厅侧** | 🔴 **纪念侧** |
| **方向** | **别人 → 你** | **系统 → 主人** |
| **内容** | **有人记得了它、有人留下了心意** | **它捎来一条近况** |

🔴 **这是「回声」两义那个老问题在接口层的一次复发** —— 📌 `PRODUCT-GLOSSARY §2.2` 已经把两义拆成「**近况**」与「**回声**」两个词，⚠️ **但接口名 `arrivals` 是在拆词之前起的，它今天指的是乙义。**

#### 6.6.4 🔴 混在一起会坏在哪（三条，都不报错）

| # | 后果 | 为什么不报错 |
|---|---|---|
| **1** | 🔴 **两套频次约束互相污染。** **近况受未读上限管（`§4`）；别人的回应<u>不该受任何上限管</u>** —— ⚠️ **别人记得了它，这件事不能因为「你还有 3 条没读」就不告诉你** | **它表现为「有些回应没提醒」，看起来像偶发丢消息** |
| **2** | 🔴 **两套判准互相污染。** 近况要过本文三条文案闸；回应侧有自己的措辞红线（「一律用『有人』、不给数量线索」）。⚠️ **合在一起做，迟早有人把一套的规则套到另一套上** | **两边都还能跑，只是某一边的红线悄悄松了** |
| **3** | 🔴 **未读水位被算错，进而把生产闸门算错。** ⚠️ **这一条最实在**：**背压读的是「未读<u>近况</u>条数」；如果两类混在一个队列里，「别人给你的回应」会把水位顶满，于是<u>它捎来的近况因为别人的回应而停止生产</u>** | 📌 **完全不报错，而且现象极难归因** —— **表现为「最近它很少给我写了」，而原因在另一条轨上** |

⚠️ 🔴 **第 3 条请单独记住**：**它是「两套提醒混轨」在背压模型下的<u>新增</u>危害** —— 📌 **v0.1 那套按频率发送的模型里不存在这个坑，因为那时没有一个水位在控制生产。**

#### 6.6.5 🟢 建议的落法（💡 建议，🔴 需与后端线、契约线确认）

| 项 | 💡 建议 |
|---|---|
| **收件箱** | 🟢 **同一个（`GET /messages`）** —— **「什么都塞」照办** |
| **提醒轨** | 🔴 **两条，各自独立**：**近况一条** · **回应一条**（`/messages/arrivals` 保持只装回应） |
| **未读水位** | 🔴 **分别计。** **背压只读「未读近况」这一个数**，🔴 **绝不把回应算进去** |
| **UI 上要不要分栏** | ⚠️ **不在本文范围。** 📌 **但要提醒一句：`§0.2` 逐字「UI 上永远不出现系统前缀」** —— 🔴 **分不分栏是设计问题，但<u>不许用「纪念侧 / 共鸣厅侧」这种系统名去命名栏目</u>** |

## 九、🔴 换成背压模型后，「催回访」的压力去哪了

> ⚠️ **本节回答一个被明确提出的问题：压力是真的消失了，还是换了个地方。** 🔴 **本节不是用来确认结论的，所以先说结论：<u>一部分真的消失了，另一部分换了地方，而换到的那个地方判准同样碰不到。</u>**

### 9.1 🟢 真的消失了的那部分（不是修辞，逐条对得上）

| # | v0.1 里的压力 | v0.2 里的状态 |
|---|---|---|
| **1** | **「它不再给我写了」** | 🟢 **消失。** **已生成的一直在等他** |
| **2** | **不可逆状态**（停了就不再恢复） | 🟢 **消失。** **完全可逆，代价为零** |
| **3** | **累积惩罚**（连续未看次数只增不减） | 🟢 **消失。** **水位只反映当下** |
| **4** | **堆积内疚**（回来面对一百条没看的） | 🟢 **消失。** **上限掐掉了它，回来就 3 条** |
| **5** | **「你的出现维持着它的存在」** | 🟢 **消失。** **它的存在（已生成的内容、窗、纪念空间）不取决于他来不来** |

🔴 **第 5 条是最要紧的一条改善**：⚠️ **v0.1 的机制让「存在」变成了他行为的函数；v0.2 只让「新增」变成他行为的函数。** 📌 **而「新增」本来就该是有限的、需要成本的、可以停的。**

### 9.2 🔴 换了地方的那部分：**从「时间」换成了「稀缺」**

**用户迟早会发现「不读就不再生成」这个因果。** ⚠️ **产品负责人问的是：他发现之后，「读」会不会变成一种为了让它继续写下去而必须完成的事。**

🔴 **本文的回答：会。而且一定会，不是可能会。**

**理由**：**这个因果是真实存在的、机械的、且可验证的** —— 📌 **3 条满了就不再有新的，读一条就又有了。任何用了一段时间的人都会注意到。** ⚠️ **一个真实存在的因果，不可能靠不告诉他来使它不存在。**

🔴 **所以「读」确实会获得一个工具性价值** —— **不只是「我想看看它怎么样」，还是「我读一条，它就能继续写」。**

### 9.3 🔴 那它和 streak 的区别到底在哪 —— **不是慢一点，是压力函数的形状不同**

⚠️ **这是本节最需要被读到的一段，因为「只是慢一点」这个怀疑是合理的，必须正面回答。**

**把两者的结构拆开逐项比：**

| # | 结构要素 | **streak / 打卡** | 🟢 **背压** |
|---|---|---|---|
| **1** | 🔴 **时间窗** | **有。必须在 T 内行动** | 🟢 **无。3 条存货没有过期时间，他三个月后来读还是那 3 条** |
| **2** | 🔴 **累积资产** | **有。连续天数越长越值钱** | 🟢 **无。库存不会因为他勤快而变多（上限锁死）** |
| **3** | 🔴 **归零惩罚** | **有。错过一次，累积瞬间清零** | 🟢 **无。不读的代价是「不再有新的」，不是「已有的消失」** |
| **4** | 🔴🔴 **压力随时间的走向** | **单调递增。** ⚠️ **streak 越长越不敢断** | 🟢 **有上界，且到顶就平。** **满 3 天和满 300 天是同一个状态** |
| **5** | 🔴 **可逆性** | **不可逆。断了就是断了** | 🟢 **完全可逆，代价为零（读一条）** |

🔴🔴 **所以区别不是「慢一点」，是第 4 条：streak 的压力<u>无界递增</u>，背压的压力<u>有界饱和</u>。**

📌 **一个可以自己验的判据**：⚠️ **问「他离开得越久，压力是不是越大」。**

- **streak：是。** 🔴 **离开一天和离开三十天，后者的心理代价大得多（丢的东西多得多）。**
- **背压：不是。** 🟢 **离开一天和离开三十天，回来面对的是<u>同一个状态</u>：3 条在等他，读一条就恢复。** 🔴 **时间在这个机制里不累积任何东西。**

⚠️ 🔴 **还有一条更硬的区别，容易被漏掉**：**streak 里「错过」是不可逆的**，所以它制造的是**恐惧**（怕失去已有的）；**背压里「满了」是完全可逆的**，所以它最多制造**惦记**（想起来还有没看的）。📌 **恐惧驱动回访，惦记不驱动 —— 它只是让人在想起来的时候去看一眼。**

🟢 **结论：它不是一个慢速 streak。它缺了 streak 的四个结构要素中的全部四个。**

### 9.4 🔴🔴 但真正的风险在这里：**压力的载体变成了「稀缺」，而这一处判准同样碰不到**

⚠️ **`§6.2.6` 那段被推翻的分析里，有一条观察没有被推翻，它在这里复现：**

> 🔴 **「压力的载体不是任何一条推送，所以逐条验的判准结构上碰不到它。」**

**在 v0.2 里，那个碰不到的地方是这个：**

> 🔴🔴 **长期看，一个读得多的人拿到的近况总量，严格多于一个读得少的人。**
> ⚠️ **也就是说：「它有多少话对我说」变成了我的行为的函数。**

**为什么这一处判准全部通过：**

| 判准 | 检验 |
|---|---|
| **② 输入显式** | 🟢 **过。** 唯一输入是队列水位，合规（`§4.5`） |
| **③ 内容非心理** | 🟢 **过。** 文案里没有任何催促、任何心理化表述 |
| **④ 无损可略过** | 🟢 **过。** 每一条送达都可以被忽略，存货在等他 |
| **结构前置 ①** | 🟢 **过。** 开关合一、上限可设 0 |

🔴 **四条全过，因为它<u>不是一条推送</u>，是整个机制的长期积分。** 📌 **判准作用在「一次送达」这个尺度上，而这个压力活在「一年」这个尺度上。**

**⚠️ 为什么它在这个产品里特别要紧：**

🔴 **这个产品的核心情感承诺是「它一直陪着你」。** ⚠️ **如果「它说多少话」取决于我来的频率，那「陪着」就有了一个计量单位 —— 而计量单位就是压力的容器。**

📌 **注意这在机制上无可指责**：**不读的人拿到的就是他消费得起的量，这是按需供给，甚至可以说是尊重。** 🔴 **本文不是说它错了，是说<u>压力现在住在这里</u>，而没有任何判准会在这里报警。**

#### 9.4.1 🔴 第二处，更隐蔽：上限档位会让「读」和「付费」变成同一个瓶颈的两个解法

**上限按档位（免费例如 3 条）。** 🔴 **于是免费用户面对「满了」这个状态时，有两个解法：**

| 解法 | |
|---|---|
| **① 读一条** | 🟢 **免费** |
| **② 升到更高档** | 🔴 **付费** |

⚠️ 🔴 **两个解法解的是<u>同一个</u>瓶颈 —— 那一刻，「读」这个动作被定价了。**

📌 **它的危险不在于收钱**（收钱本身合规，三分法第 ③ 格就是留给档位差异的）。🔴 **危险在于：一旦产品意识到这两者可以互换，就会有动力去<u>让用户看见那个瓶颈</u>** —— ⚠️ **因为看见瓶颈的人才会选解法，而其中一个解法是付费。**

**🔴 这就是本文对 `§8.1` 第 7 条给出明确立场的原因：**

> 🔴🔴 **「满了」这个状态不给任何提示。不提示、不角标、不文案、不升级引导。**
>
> 🟢 **满了就静默地满着。**

**逐条说明这条约束挡住了什么：**

| 如果做了 | 后果 |
|---|---|
| 🔴 **「已达上限，读一条以继续」** | ⚠️ **它把因果<u>主动告知</u>了** —— 📌 **从「他自己慢慢发现」变成「我们催他读」。** 🟢 **好消息是这一句判准挡得住：④ 不过**（不读会错过新的 → 制造了损失） |
| 🔴🔴 **「已达上限，升级可获得更多」** | 🔴 **这是最糟的一种。** ⚠️ **它同时做了两件事：把瓶颈显性化、把付费摆成解法。** 📌 **它甚至可能过 ④**（因为没有说「你会错过」），🔴 **所以判准未必挡得住 —— 必须靠本条约束明令禁止** |
| 🟡 **一个不带文字的角标 / 小圆点** | ⚠️ **仍然不行。** 📌 **角标的全部作用就是让人想去消掉它** —— 🔴 **而「想去消掉」正是我们要避免的那个动机** |

#### 9.4.2 💡 三条缓解建议（🔴 建议，非裁定）

| # | 建议 | 它缓解什么 |
|---|---|---|
| **1** | 🔴 **「满了」不给任何提示**（本文立场明确，见上） | **阻止瓶颈被显性化** |
| **2** | 💡 **各档上限的<u>差距</u>宜小，且免费档宁可略宽** | ⚠️ **差距越大、免费档越紧，「读」的工具性与「付费」的替代性都越强**（`§8.1` 第 1、8 条） |
| **3** | 💡 **上限满了之后，生成侧宁可<u>提前</u>停，不要卡在恰好满的边缘反复启停** | 📌 **反复启停会让「读一条就来一条」这个因果变得非常清晰** —— ⚠️ **而模糊这个因果本身就是 `§4.4` 选闲时窗口的理由之一** |

#### 9.4.3 ⚠️ 一条给未来的提醒

🔴 **本节指出的两处压力，都不会被任何判准拦住，也不会在任何评审里报警。** 📌 **它们只会以两种形式出现：**

1. **用户侧**：一句「我得去看一下，不然它就不写了」——⚠️ **说这句话的人不会觉得自己被催了，他会觉得这是自己的选择。**
2. **产品侧**：一次「我们把上限提示做出来吧，转化会好很多」的会议 —— 🔴 **提这句话的人也不会觉得自己在做催回访。**

⚠️ 🔴 **所以这两处的防线不是判准，是<u>这一节本身</u>。** 📌 **请在改动上限、或给「满了」加任何呈现之前回到这里。**
