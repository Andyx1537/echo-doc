## 0. 三条读之前必须知道的更正

**本文的结论建立在这三条之上。如果这三条里有一条被推翻，对应的结论要跟着重算。**

### 0.1 🔴 北极星不叫「被记得率」

| 出处 | 原文 |
|---|---|
| `DECISIONS.md:225` `GTM4` | 运营北极星 = **「被接住的发布率」**（发布 7 天内获 ≥1 合规回声且未撤回），优先于 DAU/浏览量 |
| `SPEC-recommendation-ranking.md:1554` | 被接住的发布率 = 公开卡自过审时刻起 7 天内获 **≥1 条合规回声（`R1`–`R5`）**，且作者未撤回、未关互动的占比 |
| 同上 `:166` | `R1` = 记得。`R2` 留脚印 · `R3` 留一句话 · `R4` 我也想起一件事 · `R5` 共同留一束心意 |

**「记得」是北极星分子里的五分之一，不是北极星本身。**

🔴 **这个名字之差有具体后果，所以单独提出来**：按「被记得率」理解，自然的下一步是去优化记得数 —— 而 `SPEC-recommendation-ranking §4.3 X6` 明令**互动计数不得进排序**，`§11.5` 还专门留了一句「看到北极星走低时不要把复活池加回来」。**用错名字会把人推向一条已被明令禁止的优化路径。**

⚠️ **但代价核算的方向不变，而且更强**：`R1` 是五条回声里**门槛最低**的一条（一次点击，无输入、无审核、无需对方处理）。给「记得」增加一层点击成本，压低的是北极星分子中**最容易达成的那一路**，伤害比按「被记得率」估算的更大，不是更小。

### 0.2 🔴 「明信片墙对任何广场访客都渲染」在真后端上不成立

`GET /windows/:id` 的真实实现（`EchoApi.java:693-710`）：


`windowCard()`（`EchoApi.java:1329-1349`）下发的是 `id / petName / ownerId / ownerName / ownerAvatar / recent / signature / warmthLevel / cover / span`。

🔴 **既没有 `postcards`，也没有 `echoes`。** 明信片的唯一端点是 `GET /pet/me/postcards`（`EchoApi.java:209` 注册，`:732` 实现），走 `requireMyPet` —— **只有本人拿得到**。

`DetailScreen.tsx:333` 那段 `w.postcards && w.postcards.length > 0` 在演示里会渲染，是因为 `VITE_API_BASE` 为空时走本地 mock（`api/client.ts:14/17`），而 mock 的 `catalog` 给每一扇窗都硬编码了 `postcards`（`data/mock.ts:148 / 174 / 199 / 225 / 251 / 276 / 304 / 331 / 359 / 386 / 413 / 440`）。

**因此**：`SPEC-interaction-flow §10.6 #1` 登记的「照 `N3` 执行 = 收回一个已在线上的可见面，是行为变更不是漏实现」，**在真后端上不成立**。准确的表述是：**这是一个只存在于 mock 演示数据里的行为，真后端实现时不要把它实现出来。**

⚠️ **一处需要运营回一句**：对外发布过的演示站是 mock 模式还是接了真后端？若是 mock 模式且有真实用户看过，对那批用户来说仍是一次收回。**本文按「从未在真后端在线」写**，因为没有任何证据表明真后端下发过明信片，按另一种写法会把一个不存在的代价写进决策依据。

### 0.3 🔴 「五块窗口级内容」里至少两块不是窗级

| 块 | 前提说它是 | 实际 |
|---|---|---|
| `echoes` | 窗口级 | 🔴 **已经是卡级**。`LeaveWordsApi` 注册的是 `POST /cards/:cardId/messages` 与 `GET /cards/:cardId/messages/pending`（`LeaveWordsApi.java:92-93`），认的是 `t_memory_card.id`；类注释明写「`/cards/` 收 cardId，`/windows/` 收 petId，**没有例外**」。`DetailScreen.tsx:424/426` 也刻意传 `cardId` 而非 `petId` |

## 1. 每一块到底是关于谁的（🔴 本文的核心，不要跳过）

> 逐块回答四个问题：**主语是谁 · 粒度 · 内容还是回应 · 谁会来看它**。每条判断给出处。

### 1.1 `lifeBook` 生命之书

| 问题 | 答案 | 依据 |
|---|---|---|
| **主语** | 🟢 **那只它**。三条固定形状 `{title, year, desc}`：「第一次回家 2019 / 那天，它用小鼻子闻了闻新家的味道」「最爱的窗台 2021」「最后一个春天 2023」 | `data/mock.ts:138-142`；服务端 `lifeBookView()`（`EchoApi.java:1351-1362`）遍历 `pet.lifeBook`，字段即 `title/year/desc` |
| **粒度** | 🟡 **今天是窗级容器，目标态是卡的列表**。挂在 `PetProfile.lifeBook` 上；但按 `PRODUCT-MINDMAP §3.3.1` 裁定，生命之书的每一条都是**可发布成卡**的 | `EchoApi.java:1351` · `PRODUCT-MINDMAP §3.3.1/§4.17` |
| **内容 / 回应** | 🟢 **内容**。owner 自己写的，无第三方参与 | `POST /pet` 建档时随档案一起落 |
| **谁看、为什么** | 本人回看（这是他为它整理的一生）· 亲友（认识这只它的人）· 陌生人（**这是陌生人唯一能理解「这只它是谁」的东西**） | — |

🔴 **老板说的「生命之书层级最低」是对的，但理由值得说准**：它层级最低不是因为它不重要，而是因为**它是唯一一块「谁都可以看、看了也不会侵犯任何人」的内容** —— 主语是它，材料是 owner 主动写的，不含第三方信息，也不含 owner 的行为度量。它是这五块里**可见性讨论最简单的一块**。

### 1.2 `rememberWall` 暖光面孔墙

🔴 **这一块是整件事的关键，也是最容易判错的一块。** 先把它下发的东西摊开：

```616:633:Echo/echo-server/src/main/java/com/echo/http/EchoApi.java
    private Map<String, Object> rememberWallView(String petId, long viewer) {
        List<Long> faces = store.rememberFaces(petId);
        List<Object> faceViews = new ArrayList<>();
        int cap = Math.min(faces.size(), 60);
        for (int i = 0; i < cap; i++) {
            long fid = faces.get(i);
            AccountProfile fp = store.profile(fid);
            Map<String, Object> fv = Json.map();
            fv.put("accountId", String.valueOf(fid));
            fv.put("avatar", fp != null ? fp.avatar : "");
            faceViews.add(fv);
        }
        Map<String, Object> data = Json.map();
        data.put("warmthLevel", warmthLevel(faces.size()));
        data.put("faces", faceViews);
        data.put("meRemembered", store.isRemembered(petId, viewer));
        return data;
    }
```

**它其实是三样不同的东西挤在一个字段里**，三者的主语各不相同：

| 子块 | 主语 | 说明 |
|---|---|---|
| `warmthLevel`（暖光浓度） | 🟢 **那只它** | 「它被多少人记得」是它的一个属性 |
| `faces`（头像 + `accountId`） | 🔴 **访客群体** | 材料是**第三方的身份**，不是窗主的数据 |
| `meRemembered`（我记得没） | 🟢 **来访的这个人自己** | 是访客自己的状态，与这扇窗给谁看无关 |

#### 核实老板那句判断

> 「暖光面不是针对用户的侧写吗」

🟢 **这个判断成立，而且比字面更硬。** 交付要求里给的表述是「`rememberWall` 展示的是"记得过这只它的人的面孔"，主语其实是访客群体」—— 核实结果是：**语法主语是访客群体，谓语属于那只它**。也就是说它是「**关于它的一条属性，但用第三方的身份作材料**」。

**这个区分不是修辞，它决定了谁有权拍板这块的可见性**：

1. 🔴 **窗主无权替名单上的人决定要不要公开。** 一个人按下「我记得它」的时候，产品告诉他的是 **`D8`「一人一次的静默誓约」**、**`D4`「不显精确数、不排名」**、`CR6`「这片暖光代表**有人**也记得」（`COPY-GUIDE.md:152`，🔴 **明确要求不出现人数**）。**没有任何一处告诉他「你的头像会挂在这扇窗上给陌生人看」。** 这是同意范围问题，比可见性档位更硬。
2. 🔴 **`faces` 下发的是真实 `accountId`。** 前端只渲染头像色块（`DetailScreen.tsx:366-374`），但 `accountId` 在响应体里，拿去调 `GET /users/:id`（`EchoApi.java:851`）就能换回昵称、签名、粉丝数。**「静默誓约」在网络层不是匿名的。**
   ⚠️ **这不是实现疏忽，是契约字段**：前端类型 `Face { accountId: string; avatar: string }`（`types.ts:163-166`）与服务端 `rememberWallView` 两侧一致 —— 有人**特意**把它定进了契约。改动前先弄清它当初是给谁用的（前端今天唯一的用途是 `f.accountId === 'me'` 这个自我高亮判断，`DetailScreen.tsx:371`，而那件事用一个布尔就够了）。
3. 🔴 **献花有 `anonymous` 字段，记得没有。** `FlowerLog.anonymous`（`EchoApi.java:570`）允许匿名献花；`t_remember` 只有 `(petId, accountId)` 两列（`schema.sql:140`），**结构上就不支持匿名记得**。

| 问题 | 答案 | 依据 |
|---|---|---|
| **主语** | 🔴 **三个主语混在一个字段里**（见上表）。整体上是「**关于它的属性，用访客的身份作材料**」 | `EchoApi.java:616-633` |
| **粒度** | 🟢 **窗级**。`t_remember(accountId, petId)` 唯一索引 | `schema.sql:140` · `SPEC-trust-and-compliance.md:121` |
| **内容 / 回应** | 🟢 **回应**（`R1`） | `SPEC-recommendation-ranking.md:166` |
| **谁看、为什么** | owner 看精确数（`GET /pet/me/insights` 的 `rememberFacesCount`，`MeScreen`「被记得的回响」）· 访客看质性暖光 · 🔴 **名单上的人自己从来看不到自己在哪些墙上** | `EchoApi.java:720-728` · `MeScreen.tsx:98-108` |

#### 🔴 顺带核实出的一处：`warmthLevel` 会把精确数原样吐出来

```1824:1827:Echo/echo-server/src/main/java/com/echo/http/EchoApi.java
    private double warmthLevel(int faces) {
        // 记得人数 → 暖光浓度（0..1），饱和函数，绝不对外暴露精确数字
        return Math.min(1.0, faces / 20.0);
    }
```

`faces < 20` 时这是一个**可逆函数**：`faces = warmthLevel × 20`。而 `warmthLevel` 是**浮点数直接下发**，在 `GET /plaza` 的每一张卡上都有（`EchoApi.java:1342`），在 `GET /windows/:id` 与 `GET /windows/:id/remember` 上也有。

**注释写的「绝不对外暴露精确数字」，在种子期（每扇窗的记得人数几乎都 < 20）是不成立的。** 前端确实把它化成了质性描述（`PlazaScreen.tsx:30-34` 的 `warmthPhrase`）与 CSS 变量，但**下发的是数字**，读一次响应体就能还原。`faces` 数组的长度（`< 60` 时等于精确人数）是同一件事的第二个出口。

🟡 **这不是本文要解的题，但它与「面孔墙给谁看」是同一个决定的两面**，登记在 §4.5。

### 1.3 `echoes` 温柔的回声

| 问题 | 答案 | 依据 |
|---|---|---|
| **主语** | 🔴 **留言的人自己**，不是那只它，也不是主人。看内容就知道：「**我家也有**一只爱追蝴蝶的，看到这扇窗，突然就想它了」「**我也**有一间夏天的教室」「**我也**总站在旧站牌下，等一趟不会来的车」 | `data/mock.ts:144-146 / 300-302 / 356-357` |
| **粒度** | 🟢 **卡级，且已经落地**。`POST /cards/:cardId/messages`，键是 `t_memory_card.id` | `LeaveWordsApi.java:92-93 / 133 / 148` |
| **内容 / 回应** | 🟢 **回应**（`R3` 留一句话 / `R4` 我也想起一件事），且是**经作者显式处置后**才出现的 —— 作者三选一：收下公开 / 只自己看 / 不留 | `LeaveWordsApi.java:26` · `DetailScreen.tsx:414-427` |
| **谁看、为什么** | 作者（收信）· 其他访客（看到「原来还有人也这样」——这是共鸣厅的社会性证明）· 陌生人 | — |

🔴 **这一块的主语判断推翻了「回声是针对这个对象的」这个印象。** 老板原话说「回声和献花是针对这个对象的」—— 献花成立（见 §1.4 的辨析），**回声不成立**：回声在形式上挂在这扇窗下，在内容上讲的是**留言者自己的事**。这只窗是引子，不是主语。

**这个区分有一条实际后果**：如果回声的主语是留言者自己，那么它**天然属于「这一条卡」而不是「这只它」** —— 因为唤起他的是那一条具体的内容（一张落叶的照片），不是那只宠物的一生。这与 `LeaveWordsApi` 已经落在卡级完全自洽。

⚠️ **一处顺带查出的不一致（不影响归属结论，登记备查）**：前端 `http.ts:219-222` 调的是 `/windows/:id/messages`，后端注册的是 `/cards/:cardId/messages`。**路径对不上，真后端会 404。** 因为 `flags.leaveMessage` 默认关闭（`DECISIONS S13`），今天不触发。`LeaveWordsApi` 类注释说明了后端是**刻意搬的**（「趁 C1 还是 P0 默认关、没有线上消费者时搬，代价近乎为零」），前端没跟。

### 1.5 `postcards` 记忆明信片墙

| 问题 | 答案 | 依据 |
|---|---|---|

#### 🔴 已解锁位与未解锁位是两种不同的东西，敏感度差一整档

| | 内容 | 泄露什么 |
|---|---|---|

### 2.2 推荐与理由

🟢 **推荐方案甲，并吸收丙的一条：`lifeBook` 不作为「一块内容」搬到窗口页，而是直接对齐 `B18`。**

**理由三条：**

1. **它是唯一一个能一句话说清、且日后不需要重判的规则**。「主语是谁就归谁」这条规则对**下一块新内容**同样适用 —— 而方案乙、丙给的都是「这一批怎么办」，下一块来了还要再吵一次。`SPEC-interaction-flow §10.1` 立 fail-closed 的理由是「新增区块默认不可见」，那是安全兜底；**归属这边也需要一条能自动作用于新增内容的规则**，否则每加一块都要开一次会。
2. **它把「转化」这个代价从方案里彻底移除了**，而不是权衡掉。§2.0.2 已核实展示与动作可分且数据已就绪；`R1` 的触发场景规格本就写着「卡片」。所以甲方案下，「记得」不但没有多一层，**反而从今天的一处（详情页）变成规格要求的两处（卡片 + 窗口页）**。
3. **`echoes` 留在卡上是唯一与其主语一致、且与已落地实现一致的选择**。乙方案要把它反向聚合回窗页，那是**主动制造一次和 `LeaveWordsApi` 相反的改动**，而 `LeaveWordsApi` 刚为了这件事把 URL 前缀从 `/windows/` 搬到 `/cards/`。

⚠️ **推荐是有条件的**：**甲必须与 §3 的第③步裁定一起落**，否则会做出 §2.1 代价 3 那个界面。若第③步暂时定不了，可行的过渡是：**卡上的记得按钮先只在「这只它的第一张卡」上出现**，其余卡只出暖光不出按钮 —— 丑，但不会让用户看到自动变亮。

### 3.2 冲突本身

**一个人记得同一只它的 5 张卡，算几次？**

- **按 `D8`：1 次。** 誓约的对象是「它」，「不可叠加」是它与献花的分界线（`PRD-echo-social.md:41`）。
- **按第③步：5 行。** 唯一键变成 `(cardId, accountId)`。
- **按北极星：必须能归因到卡。** 否则「这张卡有没有被接住」算不出来。

🔴 **两边都不能简单放弃：**

- 放弃 `D8` → 「静默誓约」变成可叠加的点赞，`PRD-echo-social §0.6` 建立在「不可叠加」上的整套区分（记得 vs 献花 vs 看过）失效。
- 放弃卡级归因 → 北极星算不出来；**且 `S4 自然流掉` 永远开不了**。`InteractionScopeMigration` 的类注释把后果写得很具体：

> 在卡级互动者恒为 0 的前提下，这个条件对**每一张卡**都成立：上线满 14 天的那一刻，全库的卡会**同时**被判流掉，而报表上它看起来只是「内容陆续自然退场了」——退场率曲线平滑，没有异常，没有任何一条日志会说「因为互动还挂在窗上，所以我把所有卡都流掉了」。

### 4.2 🔴 我认为最容易出事的格子：**W3 `faces` 对陌生人**

**三条理由，第三条是关键：**

1. **它下发的不是窗主的数据，是第三方的名单。** 出事的时候，受害人不是窗主 —— 是那些以为自己按了个「静默」开关的人。他们既不会收到通知，也没有任何界面能看到自己被列在哪些窗上（`GET /accounts/blocked` 那类「我做过什么」的自查入口，`remember` 这边**没有**）。
2. **产品对他们的承诺是白纸黑字的**：`D8`「静默誓约」· `D4`「不显精确数、不排名」· `CR6`「这片暖光代表**有人**也记得」（`COPY-GUIDE.md:152` 明确要求**不出现人数**）。而 `faces` 数组的长度在 60 人以下时**就是精确人数**。
3. 🔴 **fail-closed 抓不到它。** `SPEC-interaction-flow §10.4` 已经把暖光面孔墙标成「未定 → 按不可见」，看起来这一格已经安全了。**但 `GET /windows/:id/remember` 是一个独立端点，任何人都能直接调，与页面渲染不渲染完全无关** —— 而且它**连 `canView` 都没有**（见 §4.6 第 3 条）。

> **fail-closed 保护的是「页面上渲染什么」，保护不了「端点下发什么」。** `§10.5` 第 1 条已经点出过这个区别（「不渲染的东西仍在响应体里，抓一次包就看得见」），🔴 **而 `faces` 这一格是它的最坏形态：不但字段在响应体里，端点本身也没有任何门。**

**次险的一格是 W12**（未解锁位对亲友）。它险在**判错了敏感度的方向**：整墙被当成「内容」判成「仅亲友」，而未解锁位其实是「关于主人的判语」，比已解锁的内容更该收。这类错误的特点是**看起来已经处理过了**，所以不会有人回头再看第二遍。

### 4.5 🟡 与矩阵绑在一起、必须一起定的一条：`warmthLevel` 的精度

W2 判「公开」的前提是它**只是一个质性信号**。而 §1.2 已核实：`warmthLevel = min(1, faces/20)` 在 20 人以下是**可逆函数**，`faces` 数组长度在 60 人以下**就是精确人数**。

**两条出口都通向 `D4`「不显精确数」被绕过，且都在响应体里、前端做什么都没用。**

| 可能的收口 | 代价 |
|---|---|
| 服务端**只下发档位**（如 `warmth: 'low'/'mid'/'high'`），不下发浮点 | 前端 CSS 的连续光晕要改成三档；广场卡的视觉层次变粗 |
| 下发浮点但**加噪/取整到档位边界** | 视觉不变；但「加了噪的数字」在合规叙述上不如「根本没下发数字」干净 |
| `faces` 一律只下发**固定条数**（如恒 8 个，不足则重复/留空） | 面孔墙的视觉不变；但如果 W3 判「陌生人不可见」，这一条就不需要了 |

🔴 **这一条与 W3 是同一个决定的两面**：如果 `faces` 对外一律不下发，剩下的只有 `warmthLevel` 一个出口，收口成本低得多。

### 5.1 路径一：`toggleRemember` 写后回读 —— 🟢 **属实**，且**影响范围比已报的更大**

**核实**


🔴 **影响范围的扩大（本文新增）**：**修掉这一处回读不够。**

`GET /windows/:id`（`EchoApi.java:708`）**同样内嵌 `rememberWallView`，同样返回真实的 `meRemembered`**。而 `DetailScreen` 的 `useEffect`（`:123-129`）在**每次进入这扇窗时**都会 `setWall(d.rememberWall)`。

**所以：只改 `toggleRemember` 不回读，泄露从「点完立刻翻回」变成「下次进来时翻回」。** 后者更隐蔽 —— 用户会以为是自己记错了，或是没保存上，然后再点一次，再翻回。**修法必须落在服务端**：`GET /windows/:id/remember` 与 `windowDetail` 内嵌的那份，在 `!canInteract(owner, viewer)` 时都应回显「被拉黑方以为的那个状态」，而不是真实状态。

⚠️ **但这带来一个服务端要一起想清楚的问题**：服务端不存被拉黑方「以为」的状态（写入被丢弃了）。所以要么在读侧对被拉黑方**恒回 `meRemembered: false` 且把写也恒回 `true`**（不自洽），要么**给被拉黑方的写操作留一条不进主表的影子记录**。这一条超出本文范围，登记给服务端。

### 🔴 关于「明信片墙私密」这条倾向本身，我的判断

**我不认为这条倾向是错的，但我认为它是用错误的理由得到的正确答案 —— 而错误的理由会在下一块内容上给出错误的答案。**

- **它对的地方**：未解锁位确实不该给非本人看，因为 `unlockHint` 说的是「你还差多久」，是**关于主人的判语**，而温度这个更弱的信号都已经被 `B5` 判为陌生人不出。
- **它错的地方**：这条理由**只覆盖未解锁位**。用它去论证整墙私密，是扩大解释。已解锁的明信片就是一张图 + 一句话 + 日期，与一张公开的回忆卡在敏感度上分不出来 —— **同样的内容作为卡发出来是公开的，作为明信片就是私密，这条界限说不通**。
- **它的代价被低估了**：`§10.3` 自己写了陌生人那一屏裁完只剩「封面 + 名字」，还需要一个温柔空态。明信片是那一屏上唯一一块能让人停下来的东西。**收掉它，就是把「陌生人进来看到什么」这个问题从「有点薄」推到「什么都没有」。**
- **我的建议**：按位分档（已解锁跟窗走 / 未解锁位对非本人一律不出）。若因实现成本选整墙私密，请让理由写成「**服务端整块不下发，实现上更难出错**」，而不是「明信片是隐私」。**理由写对了，下一块内容来的时候才不会判错。**
