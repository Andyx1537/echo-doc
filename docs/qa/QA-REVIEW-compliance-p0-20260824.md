## 0. 一句话结论

G0-1~G0-6 作为**裁定**是清楚的，与 CM-D1~D8 **逐条对得上、无相互矛盾**。问题全部出在「裁定 → 可执行规格」这一段：

1. **旧口径没回改干净**。SPEC 自己的 v0.1 残留（宽限期+硬删）已经改好了，但**外围三份文档还停在旧世界**，其中 `ACCEPTANCE.md TC-29` 白纸黑字写着「可删除并**级联清理**派生内容」——与 CM-D1「禁止级联清理」**方向相反**。而 TC-29 正是 QA 每轮 L0 必跑的那张表，不改，QA 会拿反向标准去判 Pass。
2. **规格内部有 5 处打架**，其中「向量检索归哪类授权」「授权期这个概念在字段里根本不存在」「本期到底做不做加密落盘」三处是开发一开工就会卡住的。
3. **点名的四条容易含糊的（G0-1 视图 / G0-3 不进训练 / G0-5 明示告知 / G0-2 本期验什么）目前全部不可验**，本报告 §3 逐条给了可执行判据。
4. **CR 红线目前是"靠人眼看"**，而 QA 实测代码里**已有 5 处物理删除**（含一处标准的四表级联清理），规格没给存量处置口径。§5 给了三层可自动化的检查办法 + 存量逐处清单。

### 1.3 不一致清单（**必须回改**）

#### ❌ 不一致-1（最严重）`ACCEPTANCE.md` TC-29 写的是反向标准
```
### TC-29 导出 / 带走 / 删除 — 状态：规划中(P0 缺口 CM-G1，判 ➖ 并催办)
- 【预期】可导出回忆集（图+文）；可删除并**级联清理派生内容**；均留痕。
```
- 与 CM-D1 / G0-1「**不做级联清理**」**方向相反**。
- 危害不是"文档不好看"：TC-29 在 QA 每轮 L0 必跑的总表里，`QA-CHARTER §2 L0` 要求逐条判。**开发按 SPEC 做了软删，QA 按 ACCEPTANCE 会判它"没做级联清理 = ❌ 不过"**，或者反过来开发照 TC-29 去做级联清理并通过验收——两种都是错的。
- **处置**：TC-29 预期整段重写为软删口径；建议直接拆成 TC-EXP-01~08（见 §4），TC-29 保留为指向新用例的索引条目。

#### ❌ 不一致-2 `AI-CAPABILITIES.md §7` 整节停留在旧世界（三处）
1. **训练样本直接引用原始素材**：§7 `t_train_sample` 字段写 `{ 输入素材ref, ... }`，「存什么」里明写「**原始素材**：肖像、补充照片、音视频 → 私有对象存储，**保留原件 + resourceId**」，并把它列为训练语料的组成。→ 与 G0-3 / CM-D4「训练语料库只入派生物、原图不进训练链路」**冲突**。这是研发最可能直接照抄的一节（它是"落地清单"）。
2. **「用完按策略清理」**（未同意素材）→「清理」= 物理删除语义，与 G0-1 冲突。
3. **「可撤回 + 可删除：用户随时撤回同意、删除素材；训练集同步剔除」** → 与 G0-4「撤回不清除既有产物」+ G0-1「软删」冲突；且「训练集同步剔除」把**语料库剔除**（该做）与**权重回滚**（D6 明确不做）混在一句里，容易被读成要回滚。
4. **术语打架**：§7 写「**去标识/匿名化**：训练样本剥离账号身份」，而 CM-D5 明确「派生物只要可关联账号即属**去标识化而非匿名化**，仍是个人信息」。§7 用「匿名化」这个法律术语会误导合规起草（匿名化在 PIPL 下是**排除适用**的强主张，主张错了是实质风险）。
- **处置**：§7 四处逐一回改，并在节首加一行「本节口径以 `SPEC-trust-and-compliance §CM-G0` 为准」。

#### ❌ 不一致-3 `SPEC-publish-and-ops.md §1.4`
```
└─ 删除(软删 + 关联互动一并清理)
```
- 「软删」对了，「一并**清理**」错了。意图大概率是"一并不可见"，但字面就是级联清理，与 CM-D1 冲突。同节 TC-CARD-03 的措辞（「即时同步消失/停更」）是对的，**同一份文档里两种说法**。
- **处置**：改为「删除（软删置位 + 关联互动一并**转为不可见/停更**，不做数据清理）」。

#### ❌ 不一致-4 `API-CONTRACT.md` 的删除端点与 SPEC 对不上
- API-CONTRACT：`DELETE /pet/me — 删除当前宠物，回到未建档态（**dev-only，非生产**）`
- SPEC CM-G1：`DELETE /pet/:id`（语义=软删置位）
- 路径不同（`/pet/me` vs `/pet/:id`）、语义不同（重置 vs 软删）、生产可用性不同（dev-only vs 正式能力）。且现网该端点的实现（`PgEchoStore.deletePet`）是**四表物理连删**。
- 规格**没有说这个已存在的 dev-only 端点怎么处置**（保留并改软删？下线？只留测试环境？）→ 开发必然自行发挥。
- **处置**：PM 在 SPEC CM-G1「字段/API」里明确：正式端点路径定死一个；`DELETE /pet/me` 是下线、还是改为软删、还是保留为测试专用（保留则必须进 CR 红线白名单并标注仅非生产 profile 装配）。

#### ❌ 不一致-5 G0-2 的本期范围自相矛盾（**开发一开工就会卡**）
同一节里两句话：
- 「素材落盘时按用户维度**独立密钥加密存储**」——这是实打实的改造：密钥表/KMS、加解密读写路径、与 CM-G4 缩略图派生和签名 URL 的交互全要动。
- 「本开关本期不实现 UI、不对用户暴露，**只做数据结构与密钥管理的预留**」——听起来只建表不落地。

CM-D3 原文是「不实现、不对 C 端暴露 + 数据结构预留」，也没有裁死加密落盘做不做。**「预留」和「加密落盘」是两个数量级的工作量**，本期是哪个必须写死。
- **连带**：与 CM-G4 未打通——原图加密落盘后，缩略图在哪层派生、缩略图/水印呈现图是否同样受该用户密钥保护，规格没写。若不写，未来销毁密钥时**缩略图和公开层呈现图仍可还原内容**，crypto-shredding 的承诺当场落空，而这一点**在验收时无法判定**（因为没有边界定义）。
- **处置**：见 §3 的 U-4，给出本期可验交付物二选一。

#### ❌ 不一致-6 「向量检索」的授权归属没有说法（G0-5 ↔ CM-G3）
- CM-G3 P0 范围：授权按能力分为 **`识别 / 定妆生成 / 近况生成 / 向量检索 / 训练`** —— **5 项**。
- G0-5 / CM-D7：使用类**三项**（识别/定妆/近况）打包；训练独立 opt-in。
- **向量检索既不在打包三项里，也不是训练**。它归哪类？打包进"服务所必需"？独立 opt-in？还是根本不需要单独授权？
- TC-CON-01 只写「使用类三项打包」，**验收时向量检索这一项无从判定**。
- 这不是文字游戏：向量检索会把素材内容做成 embedding 长期留在 pgvector 里，是**独立的处理活动**，归类错了直接影响协议怎么写（G0-6）。
- **处置**：PM 裁定归属并同步 G0-5、CM-G3、TC-CON-01、G0-6 协议条款。

#### ❌ 不一致-7 「授权期」这个概念在数据结构里不存在
- G0-4 / CM-D6 反复用「**授权期内**已产生的产物不清除」，CM-G3 目标也说「用到何时」。
- 但 `t_ai_consent { id, ownerId, materialRef, capability, granted, grantedAt, revokedAt, source, version }` —— **没有任何表示期限的字段**（无 `expiresAt`）。
- 于是「授权期内」实际等价于「撤回前」。两种可能：(a) 本来就没打算做期限，那全文措辞该统一为「撤回前」；(b) 打算做期限，那字段缺了。
- **验收影响**：TC-CON-03「已生成产物仍在」判起来没歧义，但一旦有人按字面理解"授权期"去实现一个过期机制，行为就完全不同。**术语与数据结构必须对齐。**
- **处置**：二选一写死。QA 建议选 (a)（本期无期限概念，全文改「撤回前」），理由是加期限会引出"到期后既有产物怎么办"的新裁定需求，超出本期范围。

#### ⚠️ 不一致-8 CR 红线的例外口径两边不一样
- SPEC G0-1：「出现 `DELETE FROM` / 级联 `ON DELETE CASCADE` 一律打回（**迁移脚本除外**）」
- DECISIONS CM-D1：「业务数据出现 `DELETE FROM` / `ON DELETE CASCADE` 一律打回」—— **没有"迁移脚本除外"**，但多了「**业务数据**」这个限定词。
- 两边都不完整：DECISIONS 没给例外、SPEC 没定义"业务数据"边界。→ 红线**当前不可执行**（详见 §5）。

## 3. 可验收性逐条判定（点名的四条 + 其余不可验条目）

### U-1 · G0-1「立刻从所有对外视图消失」——**不可验**（视图集合未定义）

**问题**：「所有对外视图」括号里只举了 5 个例子（共鸣厅、他人主页、精选、搜索、亲友动态），是**举例不是穷举**。QA 无法判"所有"，开发也不知道要改几处。项目现状是读路径分散在 `PgEchoStore` / `EchoApi` / 前端 `mock.ts` 三处，靠自觉必漏。

**建议判据（把"所有"落到端点清单 + 三身份遍历）**：

补一张清单，本期至少覆盖：

| # | 对外视图 | 端点 |
|---|---|---|
| 1 | 共鸣厅瀑布 | `GET /plaza` |
| 2 | 精选位 / 主题池 | `GET /plaza/curated` |
| 3 | 窗口详情（直链） | `GET /windows/:id` |
| 4 | 搜索三分区 | `GET /search?q=` |
| 5 | 记得·面孔墙 | `GET /windows/:id/remember` |
| 6 | 亲友列表与动态光环 | `GET /relations` |
| 7 | 消息流（他人侧） | `GET /messages` |
| 8 | 近况流（若删的是回声） | `GET /pet/me/echoes` |
| 9 | 明信片墙 | `GET /pet/me/postcards` |
| 10 | 记录流 | `GET /records` |
| 11 | 素材下发 | `GET /api/v1/files/{key}`（对应签名 URL 须失效） |
| 12 | 分享链接 / OG 预览卡 | 分享出去的链接与外部预览抓取 |

**判据写法**：软删一条内容后，用 **owner / 已授权亲友 / 未登录游客** 三种身份遍历上表，断言：
- 列表端点：目标 `id` 不出现在任何 `items[]`；
- 详情端点：返回统一约定的状态码（**须钉死是 404 还是 410**，两者对前端兜底文案影响不同）；
- 素材：原签名 URL 立即失效；
- **前端 mock 模式同样断言**（否则 mock 下的 Pass 是假 Pass，见 §6 R-4）。

**还需补两点**：
- **「立刻」的量化**：强一致，还是允许缓存 TTL？有 CDN/精选缓存就必须给上限（建议 ≤5s，且验收允许在上限内重试一次）。
- **owner 本人视图归不归"对外视图"**（= B-3 裁定项）。不裁定这条，TC-EXP-03 判不了。

**可维护性建议**：把上表做成**表驱动的参数化测试**（新增列表端点不登记就跑不过），比一次性写 12 个用例更抗腐蚀。

### U-2 · G0-3「原图不进训练链路」——**不可验**（否定命题 + 术语未定义）

**问题**：这是一个**否定命题**，无法靠"跑一遍看看"证明。而且规格主动放弃了一半可验性（「具体维度由算法侧定义，产品侧只要求原图不进训练链路」）——放弃拆解维度的可验性是**可以接受的**（那确实是算法侧的事），但那就必须把剩下这句话变得极其硬。目前它只是一句愿望。

另外**「训练链路」本身没定义**：把原图做成 embedding 存进 pgvector（CM-G3 里的"向量检索"能力）算不算进了训练链路？做 few-shot / RAG 时把原图喂给多模态模型算不算？**不定义就无法判定。**

**建议判据（四层，逐层都可自动化）**：

1. **接口类型层**：`ITrainingCorpus` 的写入方法**在类型上就不接受原图**——入参只收 `derivedRef`（派生物引用），不收 `resourceId`/字节流。让"原图进训练"成为编译不过的事，而不是靠 review 发现。
2. **数据层（最硬）**：一条 SQL 断言随测试跑——`t_train_sample` 的素材引用列 100% join 中派生物表、0% join 中原始素材表。这条断言可以常驻回归，防止未来回退。
3. **调用链层**：给原图读取路径（如 `IStorage` 的取原件方法）加**调用方审计**；断言训练/语料任务在整个测试过程中对原图读取次数 = **0**。
4. **依赖规则层**：训练/语料模块**不得 import** 原图存储类（ArchUnit 或等价依赖规则，违反即构建失败）。

5. **术语补充**：PM 明确「训练链路」是否包含 embedding 入库与 RAG 取用。QA 建议：**包含**（embedding 是原图内容的长期留存派生，且 CM-G3 已把向量检索单列为一项能力，理应同受 G0-3 约束）。

### U-3 · G0-5「打包明示告知」——**不可验**（"明示"是形容词，"到什么程度算合规"无判据）

**问题**：现状是 `OnboardingScreen.tsx` 里一个 `allowUse`（"允许使用场景"）+ 一个 `trainConsent` 勾选，**没有任何三项能力的告知文本**，「我」页也没有授权查看/撤回入口。规格说"明示告知"，但没说要告知什么、放在哪、什么形式，开发照现状交付也能自称做了。

**建议判据（9 条要件清单，每条二值、可截图判定，任一缺失 = Fail）**：

| # | 要件 |
|---|---|
| 1 | 三项能力**逐一列名**（认出它 / 做形象 / 写近况），不能只写"用于提供服务" |
| 2 | 每项说明**处理什么信息、做什么用** |
| 3 | 说明**存储方式与保存期限** |
| 4 | 明确「这是提供服务所必需，不同意则无法完成建档」 |
| 5 | 全文**可点开查看**（不是只有一句摘要，摘要须有"查看全文"入口） |
| 6 | 与训练授权在**视觉上分块**、**不是同一个勾选框** |
| 7 | 训练项**默认未勾**，且**不因勾选使用类而被带动** |
| 8 | 是**主动勾选**，不是默认已勾、不是"点击继续即视为同意" |
| 9 | 建档完成后，「我」页能查到**同一份告知全文**与各项已授权状态 |

第 6/7/8 条同时是 `AI-CAPABILITIES §7` PIPL 红线与 CM-D7 的落点，**任一 Fail = Blocker**。第 9 条依赖 C-5 补的授权查看端点。

### U-4 · G0-2「本期不实现 UI」——**这期到底验什么？**

**问题**：如果本期只是"预留"，这一条在验收上就是**空条款**（QA 无从判 Pass/Fail），研发也可以什么都不做。必须给出本期的可验交付物。

**建议判据**（先由 B-1 裁定"做不做加密落盘"，再取对应一组）：

**无论哪种，都必须验的（3 条）**：
1. 配置项存在且**默认 false**：环境变量未设置时读到 `false`（单元测试断言）；`DEPLOY.md` 环境变量表已登记。
2. 开关置 true **不改变任何 C 端行为**：断言无任何 C 端路由/前端代码读取该配置。
3. 结构预留状态**写死一个事实**：要么本期建 `t_user_key{ownerId, keyRef, algo, createdAt, destroyedAt}`（可验：表存在、建档时写入一行），要么明写"本期不建表"。二选一，不能留白。

**若裁定"本期做加密落盘"，加验 3 条**：
4. 素材落盘为**密文**：直接读存储层字节 ≠ 明文原图。
5. **跨用户密钥不可解**：用 A 用户密钥解 B 用户素材失败。
6. **crypto-shredding 语义可验**：走受保护的测试路径销毁密钥后，素材不可还原，而**数据行、外键、统计口径全部不变**（这正是 G0-2 承诺的效果，不验就是空承诺）。

**若裁定"本期不做加密落盘"，必须落一条风险记录**：明写"本期素材明文落盘，本期及此前的存量素材未来开启开关时无密钥可销毁、crypto-shredding 对存量永久失效"，并同步进 G0-6 协议措辞（不能承诺做不到的事）。

### CM-G1 导出 / 删除（TC-EXP）

#### TC-EXP-01 把自己的回忆集整包带走 — 状态：规划中(本期开发)
- 【测什么】用户能不能把属于自己的东西完整下载下来。
- 【怎么操作】进「我」页 → 点「导出我的回忆集」→ 等它准备好 → 点下载 → 解压打开看。
- 【预期】能发起，等待时有温柔的"正在为你准备"提示、不卡住页面；准备好后给一个下载链接；下载到一个压缩包；打开后**照片能正常打开、文字不是乱码**，记录/回声/生命之书的内容都在，还有一份说明索引；**整个过程不要求付费**。

#### TC-EXP-02 下载链接会过期，也不能转给别人用 — 状态：规划中(本期开发)
- 【测什么】导出的东西不会变成一条谁捡到都能打开的链接。
- 【怎么操作】拿到链接后放着超过约定时长再点；再把链接发给另一个账号打开；再试着改链接里的编号去拿别人的包。
- 【预期】过期后点开是温柔的"这个链接已经过期了，重新导出一次吧"，**不是一脸报错**；别人拿到链接打不开；改编号拿别人的包会被拒绝。

#### TC-EXP-03 移除之后，外面立刻就看不到了 — 状态：规划中(本期开发)
- 【测什么】点了"移除"，是不是真的马上从所有别人能看到的地方消失。
- 【怎么操作】挑一条已经公开的内容 → 移除 → 立刻换两个身份去找它：一个亲友、一个没登录的路人。要找的地方：共鸣厅、精选和主题、搜索、这条的直接链接、暖光面孔墙、亲友动态、消息里。
- 【预期】上面**每一处**都看不到了，直接点链接也打不开；别人页面上不会残留缩略图；不用刷新很多次、不用等很久。

#### TC-EXP-04 移除了，但东西其实还留着 — 状态：规划中(本期开发)
- 【测什么】"移除"是打标记，不是真删。
- 【怎么操作】移除之后，请后台同学确认这条数据还在不在。
- 【预期】数据还在，只是被打上了"已移除"的标记；**没有任何一行数据被真的删掉**，相关的互动、明信片、回声也都还在（只是一起看不见了）。

#### TC-EXP-05 App 里找不到"自己撤销移除"的入口 — 状态：规划中(本期开发)
- 【测什么】找回必须走人工，不给自助后悔药。
- 【怎么操作】移除后在 App 里到处找：回收站、撤销、找回、历史记录。
- 【预期】**找不到任何自助找回入口**；如果有相关说明文字，会温柔地告诉用户"想找回的话联系我们"；说明文字过词表，不冷冰冰。

#### TC-EXP-06 找客服能把东西原样恢复回来 — 状态：待裁定(B-6)，本期是否交付需 PM 确认
- 【测什么】承诺的"人工可找回"是真有这个能力，不是一句话。
- 【怎么操作】模拟一次客服申请：核实身份 → 后台执行恢复 → 用户端去看。
- 【预期】内容原样回来，**原来的公开状态、互动、明信片都还在**，不是回来一个空壳；这次恢复操作有留痕（谁恢复的、什么时候）。

#### TC-EXP-07 导出和移除都留了记录 — 状态：规划中(本期开发)
- 【测什么】这两个动作事后查得到。
- 【怎么操作】做一次导出、做一次移除 → 后台查操作记录。
- 【预期】能查到"**谁、什么时候、对哪些内容、做了什么**"四样，一样不缺；这些记录**C 端一律看不到**。

#### TC-EXP-08 代码里没有"真删" — 状态：规划中(本期开发，由 QA 执行扫描)
- 【测什么】这条红线是真守住了，不是嘴上说说。
- 【怎么操作】按约定规则扫一遍后端代码；再在测试库里故意执行一次删除。
- 【预期】扫描结果为 0（白名单以外一条都没有）；测试库里的删除**被数据库直接拒绝**。

### CM-G2 AI 标识 + 溯源（TC-AIP）

#### TC-AIP-01 公开出去的 AI 图，能被认出是 AI 做的 — 状态：规划中(本期开发)
- 【测什么】别人把图存下来，还能看出这是 AI 生成的。
- 【怎么操作】把一张 AI 生成的形象公开出去 → 从共鸣厅把图另存下来 → 用约定的工具看文件信息。
- 【预期】文件信息里读得到：**这是 AI 生成的、哪家服务、什么模型、什么时候生成、对应哪条内容**。

#### TC-AIP-02 C 端一眼能看出这是想象、不是事实 — 状态：已实现(文案基础)，本期复验
- 【测什么】用户看到 AI 近况时不会误以为它还在。
- 【怎么操作】看几条 AI 近况/回声。
- 【预期】页面上明说「基于你记忆的温柔想象」这类话；**不会出现"它还活着/在等你"这种说法**；措辞温柔、过词表。

#### TC-AIP-03 每条 AI 产物都说得清来历 — 状态：规划中(本期开发)
- 【测什么】随便挑一条 AI 做的东西，都能回答"它是怎么来的"。
- 【怎么操作】挑三条不同类型的 AI 产物（形象、近况、回声）→ 后台查它们的来历记录。
- 【预期】每条都能回答：**谁生成的、用什么模型、基于哪几份素材、用户授权了没**；三条都齐，不能有空白项。

#### TC-AIP-04 记录没写上，就不能公开 — 状态：规划中(本期开发)
- 【测什么】不能出现"外面看得到、后台查不到来历"的东西。
- 【怎么操作】模拟一次"生成成功但来历记录写失败"。
- 【预期】要么这条**不出现在公开层**，要么事后自动补上记录；**绝不允许公开层有内容而后台查不到来历**。

#### TC-AIP-05 缩到小图、打了水印，标识还在 — 状态：规划中(本期开发)
- 【测什么】用户实际看到的是小图和带水印的图，这些图也得能被认出是 AI 做的。
- 【怎么操作】看共鸣厅列表里的缩略图、看公开页上带水印的展示图 → 分别存下来查文件信息。
- 【预期】**两种图都还能读到 AI 标识**，不是只有原图有。

### CM-G3 授权账本（TC-CON）

#### TC-CON-01 训练授权和普通使用授权是分开的两件事 — 状态：规划中(本期开发)
- 【测什么】建档时不会把"训练"偷偷夹在"使用"里一起同意掉。
- 【怎么操作】走一遍建档，停在授权那一屏仔细看：有几个勾选框、默认勾了没、能不能只同意一部分。
- 【预期】使用类（认出它/做形象/写近况）是**一段说清楚的告知，点头一次**；训练是**另一个单独的勾选框、默认没勾**；**不勾训练照样能建档完成**；勾使用类**不会连带把训练也勾上**。

#### TC-CON-02 没同意训练，东西就不会进训练库 — 状态：规划中(本期开发)
- 【测什么】默认不勾训练是真的有效。
- 【怎么操作】不勾训练 → 完成建档 → 后台看训练语料库里有没有这个人的东西。
- 【预期】**一条都没有**——不只是原图没有，**拆解之后的那些派生数据也一样没有**。

#### TC-CON-03 「我」页能看到自己授权了什么、能收回 — 状态：规划中(本期开发)
- 【测什么】授权不是同意完就消失，随时能查、能改主意。
- 【怎么操作】进「我」页找到授权 → 看列表 → 关掉其中一项。
- 【预期】能看到每一项授权的**状态和时间**；能一键关掉；关掉时有温柔的确认，**说清楚"以后不再用了，但已经做出来的东西还留着"**。

#### TC-CON-04 收回之后就真的不用了，但已有的还在 — 状态：规划中(本期开发)
- 【测什么】收回授权的效果符合承诺，既不继续用、也不把回忆抹掉。
- 【怎么操作】收回"写近况"的授权 → 再触发一次近况 → 回头看以前生成的近况还在不在。
- 【预期】不再用这份素材去生成新的；**以前生成的近况还好好在那儿，没被清掉**；后台的来历记录上标了"这份素材的授权已经收回"。

#### TC-CON-05 后来补传的照片，授权怎么算 — 状态：待裁定(B-5)
- 【测什么】建档之后再补素材，不能出现"没说清楚就默认全授权"。
- 【怎么操作】建档完成后，在「补充素材」传一张新照片。
- 【预期】<按 PM 裁定填写>——要么沿用建档时的授权**并在补传处有一句明示**，要么单独再问一次。**不能没有说法、不能悄无声息。**

#### TC-CON-06 关掉某项授权后，去用那个功能会得到温柔提示 — 状态：规划中(本期开发)
- 【测什么】没授权时用户看到的是解释，不是白屏或报错。
- 【怎么操作】关掉某项授权 → 去用对应功能。
- 【预期】给一句温柔说明 + 一个"去打开"的入口；**不卡死、不报错、也不是点了没反应**；文案过词表。

## 5. CR 红线（禁止 `DELETE FROM` / `ON DELETE CASCADE`）怎么在验收中实际检查

> 结论：**当前这条红线不可执行**——因为例外边界没定义（不一致-8），且没有任何自动化手段，纯靠"人眼 CR"。QA 建议做成下面**三层防线 + 两张表**。

### 5.1 第一层：静态扫描做成 CI 门禁（不靠人眼）

- **扫描规则**（命中即构建失败）：
  - `DELETE\s+FROM`（含 SQL 字符串、注解、XML）
  - `ON\s+DELETE\s+CASCADE`
  - ORM 级联：`CascadeType.REMOVE`、`orphanRemoval\s*=\s*true`
  - 仓储层通用删除方法的调用点（如 `PgRepository.remove(`）
- **扫描范围**：`echo-server/src/main/**`；**排除** `resources/sql/migration/**` 与 `src/test/**`。
- **前置依赖**：必须先有 D-1 的白名单表，否则规则要么一片红、要么被迫放宽到形同虚设。

### 5.2 第二层：架构规则测试（防"绕过去"）

- 业务模块**禁止调用**仓储层的物理删除方法（ArchUnit 或等价依赖规则）。
- 训练/语料模块**禁止 import** 原图存储类（同时满足 U-2 的第 4 层判据）。
- 这层比正则强：它拦的是"换个写法删"。

### 5.3 第三层：数据库权限兜底（**最硬的一道，强烈建议**）

给业务表加 `BEFORE DELETE` 触发器直接抛异常，或**收回应用数据库账号在业务表上的 DELETE 权限**（只留 SELECT/INSERT/UPDATE），迁移/运维用独立高权账号。

这一层的价值：**即便有人写了删除，也执行不了**。验收方式非常简单——在测试库故意执行一次删除，断言被拒绝（即 TC-EXP-08 后半段）。相比之下前两层只能防"写进代码库"，防不了运行期。

### 5.4 存量违规（QA 已实测定位，本期必须逐处处置 → 对应 D-2）

| # | 位置 | 现状 | QA 判读 |
|---|---|---|---|
| 1 | `echo-server/.../store/PgEchoStore.java:318-323` `deletePet` | 连删 `t_pet_echo` / `t_postcard` / `t_remember` / `t_pet` **四张表** | **这就是 CM-D1 明令禁止的级联清理**，且它正是 `DELETE /pet/me` 的实现。必须改软删（并与 A-4 一起裁定端点去留） |
| 2 | `PgEchoStore.java:471-473` | 取消「记得」= `DELETE FROM t_remember` | **边界问题，需 PM 定性**：这是"开关取消"还是"删除语义"？见 §5.5 |
| 3 | `PgEchoStore.java:512` | 明信片重置 = `DELETE FROM t_postcard` | 同上，且"重置"语义本身需要确认是否还保留 |
| 4 | `infra/persistence/PgRepository.java:419` `remove()` | 通用物理删除方法 | 建议**直接下线该方法**或标 `@Deprecated` + 依赖规则禁止调用（留着就一定有人用） |
| 5 | `module/echo/EchoRepository.java:26` | 按 `expireAt` 清过期回声 | 属 TTL 清理，**建议进白名单**，但必须在 D-1 里显式登记（现在是"没人管"的状态） |

**另外一个好消息**：`schema.sql` 全文**没有 `ON DELETE CASCADE`**，红线的这一半目前是干净的，加扫描即可保持。

### 5.5 需要 PM 定性的边界：「开关型取消」算不算删除

G0-1 说适用范围含「**互动**」「所有用户可见的『删除』语义，无一例外」。但取消记得、取消置顶、取消勾选，语义是**状态回退**而不是删除内容。现在的实现是物理删行。

**QA 建议**（供裁定）：这类也**改成状态字段**（`active=false` + 时间戳），理由不是钻字眼，而是 CM-D1 的"数据留底、可追溯"同样适用——**"谁在什么时候取消了记得"本身就是审计信息**，而且这样红线扫描不需要为它开例外，口径统一、长期更省事。

## 6. 风险提示（质量视角）

> 按要求：**不再讨论 CM-D3 已被接受的法律暴露面本身**。以下全部是它或其他裁定**连带引发的可测性 / 数据一致性 / 工程时限**问题。

### R-1 · 软删撞唯一约束 —— 必现的线上 500（数据一致性，**最紧急**）
软删不删行，那些带唯一键的表会直接炸：
- `t_remember(petId, accountId)` —— 取消记得（软删）后**再点一次记得**，插入撞唯一键。
- `t_pet` 若有 owner 维度唯一约束 —— 软删回忆集后**重新建档**，撞唯一键。

这不是"可能有风险"，是**改成软删的那一刻就必现**。规格必须给统一约束（→ C-7）：**所有含唯一键的业务表，唯一索引改为部分索引 `WHERE "deletedAt" IS NULL`**。不写这一句，三个开发会有三种绕法（有的加随机后缀、有的把唯一键去掉），后果是数据长期不一致且极难回溯。

### R-2 · 统计口径漂移 —— 看板"对不对"变得无法判定（可测性）
软删数据留底后，北极星「被接住的发布率」、撤回率、举报率、CM-G5 的所有聚合，**分母含不含软删内容**没有定义。同一个指标，不同实现会给出不同的数，而 QA **无法判断哪个是对的**（因为没有基准）。
- **建议**：在 CM-G5 补一句总口径（QA 建议：**所有对外/运营指标默认排除软删内容**，需要含软删的场景单独标注），并给一条验收断言：软删一条已发布内容后，看板对应指标的分子分母各减 1。

### R-3 · "默认过滤软删"会漏 —— 靠自觉必出事（可测性 + 质量）
G0-1 说"所有读路径默认过滤软删数据"。但读路径散在 `PgEchoStore` / `EchoApi` / 前端 `mock.ts` 三处，靠每个人记得加过滤条件，**必漏**，而且漏的那一处很可能就是最要命的那一处（比如分享链接的 OG 预览）。
- **建议**：改为**仓储层强制**——基类统一拼过滤条件，只有显式调用 `includeDeleted()` 才能绕过（后台恢复流程用），并把 U-1 的端点清单做成**表驱动参数化测试**，新端点不登记就跑不过。这一条同时把"所有对外视图"从一句形容词变成一个可维护的机制。

### R-4 · mock 与真后端双实现漂移 —— 假 Pass（可测性）
前端有整套 `mock.ts`。软删语义如果只在真后端实现，前端在 mock 模式下开发和自测都是"删了还能看见"或"删了直接消失得干干净净"——**两种都可能与真后端不一致**，QA 在 mock 模式下判的 Pass 是假 Pass。搜索那一轮（TC-31）已经踩过这个坑。
- **建议**：验收明确要求**两种模式都跑**，且 U-1 的三身份遍历在两种模式下各跑一次。

### R-5 · crypto-shredding 有一个"只能现在做"的时限（工程时限，非法律讨论）
这不是劝改 CM-D3 的取向，而是提醒它有一个**不可回溯的窗口**：per-user 加密落盘如果本期不做，**今天之前上传的 + 本期新增的所有素材，未来即使打开开关也没有密钥可以销毁**——crypto-shredding 对存量数据永久失效，届时只能靠"真删素材文件"补救，而那又与 G0-1 冲突。
- 越晚做，"shred 不掉的存量"越大，且**无法追溯补救**。这正是 B-1 建议本期就做的原因。若裁定不做，请至少让 G0-6 的协议措辞与实际能力对齐（别写成"可彻底销毁"）。

### R-6 · "人工可找回"目前没有实现规格（承诺 vs 能力）
CM-D2 承诺人工恢复，G0-6 第 3 条要写进协议。但**恢复工具、操作权限、身份校验标准、SLA 全部没有规格**。若本期不交付后台恢复能力，实际效果就是"删了就真找不回"，而协议里却写着可以申请——这是**承诺与能力不符**，比单纯的功能缺失更麻烦。→ 见 B-6。

### R-7 · 溯源写入的原子性没定义（可测性）
G2 要求"产出时同步写 `t_ai_provenance`"。若生成成功、账本写失败，就出现**公开层有 AI 产物、后台查不到来历**——这是硬合规缺口。规格没定义失败策略（同事务？失败则不发布？补偿任务？），QA 遇到只能记成"偶发"，无法判定是否符合预期。→ 已落成用例 TC-AIP-04，但**规格侧要先给策略**。

### R-8 · 存量公开 AI 内容没有隐式标识
规格只写"发布到公开层前必做"，**没写上线前已经公开出去的那些 AI 产物怎么办**（回刷补标识？下架？仅标注？）。《标识办法》已施行，存量同样在射程内。
- **建议**：PM 补一条存量处置口径 + 一条验收（上线后抽查存量公开 AI 内容，标识覆盖率 100% 或已按裁定处置）。

### R-9 · 导出可能成为拖库通道（安全）
导出把一个账号的全部内容打成一个可下载的包，而**频率、并发、体积、越权校验**全无规格（U-5.3）。一旦签名 URL 实现有瑕疵（CM-G4 本身也在本期做），影响面从"一条内容"放大到"一个人的全部回忆"。→ 已落成用例 TC-EXP-02 后半段，规格侧需补上限。
