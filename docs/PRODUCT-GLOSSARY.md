## 0. 概述（🔴 读完这一节即拿到本文全部结论，不需要往下读）

### 0.1 🔴 一句话的总纲：Echo 有两侧，**每个概念必须先归侧**

**纪念侧**是一只宠物和它的主人之间的事：**窗**是它的纪念空间，**温度**是这段关系的状态，**回声（AI 生成的近况）**是它捎来的消息。**这一侧的东西不参与分发。**

**共鸣厅侧**是陌生人之间的事：**卡**是可被看见的一条回忆，**记得 / 看见 / 献花 / 回声（别人的回应）**是别人留下的痕迹。

🔴 **本项目绝大多数术语混乱，根子是一个词同时活在两侧，而两侧对它的期待相反。** 所以本表每一条都强制标注归哪一侧；**跨侧的词一律拆成两个词，不靠限定词区分**。

### 0.2 🔴 各组的结论（每条独立成立）

📌 **原为「六组」**（那六组是<u>改名</u>造成的混乱）；🆕 **第 7 组是 2026-08-27 新增，性质不同 —— 它不是改名，是<u>一个从来没被定义过的词</u>。**

| # | 组 | 🔴 结论 |
|---|---|---|
| **1** | **窗 与 卡** | 🔴 **窗是对象，卡是作品。** **窗 = 一只宠物的纪念空间**（一只宠物一扇窗，是被指向的那个「谁」）；**卡 = 一条可被分发的回忆**（是被看见的那个「什么」）。<br>🔴 **边界写死：分发单元只有卡，窗不再是分发单元。** 共鸣厅里流动的是卡，不是窗。<br>⚠️ 🔴 **但「窗不再是分发单元」不等于「窗上什么都不剩」** —— **记得与献花仍然挂在窗上**（`RK-H` 2026-08-26 裁定，终态）。**理由是产品性的：挂到卡上就是给作品点赞，而点赞正是立项时砍掉的东西。**<br>🔴 **窗今天有六个名字**（窗口 / 一扇窗 / 回忆集 / 数字纪念空间 / 宠物档案 / 往宠档案）。**建议对外只留两个**：品类词说「数字纪念空间」，功能名说「一扇窗」，其余停用。**这是建议，需产品负责人拍板。** |
| **2** | **回声** | 🟢 **乙义（别人对你的卡的回应）保留「回声」** —— 已裁定，北极星数的是这一义。<br>🟢 **甲义（AI 生成的它的近况）让出这个词，正式改叫「近况 / 它的近况」；它到达这个动作叫「捎来」**（2026-08-27 采纳）。<br>🔴🔴 **本表对交办那一问的判断：甲义<u>不是</u>独立品类，它是卡的一种来源。** 但**它需要名字的位置比「来源」多**，所以要的是**两个词**（「近况」+「捎来」），**而不是一个平行于「回声」的产品概念**。依据见 `§2.3`。<br>⚠️ **子品牌名「回声·往宠」怎么办 → 仍待定**，见 `§2.5`。 |
| **3** | **温度 与 暖意** | 🔴 **这里是三个量，不是两个**：**温度**（主人回访驱动，私域，纪念侧）· **暖光**（别人的记得聚成的浓度，窗级，共鸣厅侧看得见）· **热度**（分发侧的排序权重，纯内部）。<br>🔴 **「暖意」今天同时指两个方向相反的东西，且<u>两义各自都有正式裁定撑着</u>**（甲义 `C3`/`C4`/`E5`/`B20`：主人自己攒的活跃度；乙义 `RK-H` 与实现：别人的记得聚成的暖光）。<br>🟢 **已定（2026-08-27）：「暖意」这个词整个停用，不做二选一。** 别人给的那一份叫**暖光**，主人自己攒的那一份叫**陪伴值**。**理由：两义都写作「暖意」，加限定词无效；且这个词正压在「外部行为不改温度」这条红线上，一句话两种读法一个合规一个违规。** |

| **5** | **献花** | 🟢 **已拍板（2026-08-27 · `FL1`）：花是给「它」的，窗级。**🔴 **`D8`「献花 = 对主人本人的社交心意」推翻，原文保留并标注。**<br>🔴 **依据一句话**：**现实里扫墓献花也要花钱，钱付给花店，没人指望逝者家属收钱。**「花要花钱买」和「花是给逝者的」从来不矛盾。<br>🟢 **它解开了一个死结**：「不可提现、不给主人分成」在旧口径下很拧（说是给主人的心意、主人却什么也收不到），**新口径下从别扭变成自然——这笔钱本来就不该流向主人。**<br>⚠️ 🔴 **一条最容易被顺手改错的**：**献花归窗级 ≠ 献花算进暖光。暖光只数「记得」，一朵花都不数。** |
| 🆕 **7** | **陌生人 与 亲友** | 🔴 **「陌生人」是<u>关系</u>，不是权限档。** **权限档只有三个：公开 / 亲友 / 私密。**<br>**陌生人 = 不是主人、且不在这扇窗亲友名单里的访客，只看得到公开档。** 🔴 **亲友是<u>窗主</u>拉进来的，关注是<u>访客</u>自己按的 —— 访客不能给自己升权限。**<br>🔴🔴 **关注不改变权限：已关注者在权限上仍然是陌生人**，只在到达提示的措辞上被区分（2026-08-27 裁定）。⚠️ **不写死这一句，下一个人一定会把关注做成第四档。**<br>⚠️ **被拉黑的人不是陌生人，是不可达。**<br>**两处打架见 `§6A.4`**：① ~~`A5` 字面「单向关注 + 动态圈」与实现及新裁定不符~~ → 🟢 **2026-08-27 已处置，`A5` 直接改写**；② 🔴 **仍登记未调和：「亲友多看一档」只对<u>卡</u>成立，对<u>窗上的块</u>不成立**（`VIS2` 面孔墙：亲友与陌生人同档）。 |
| **6** | **共鸣 / 共鸣厅** | 🔴 **有，而且比「回声」更碎：「共鸣」今天有四义。** 但**四义里只有一组会真的伤到用户理解**：「共鸣厅」这个场所名，与「一次共鸣」这个动作名。<br>🔴 **另有一条本表新登记的**：**「共鸣厅」自己的范围也有两读** —— 有的地方它指整个公开层，有的地方它只指瀑布那一屏。见 `§6`。 |

## 1. 窗 与 卡

🔴 **这一组是全部混乱的总根，所以放在第一条，而且写得比别的组长。**

### 1.1 两个词各自指什么

| | **窗** | **卡** |
|---|---|---|
| **指什么** | 🔴 **一只宠物的纪念空间。** 一只宠物一扇窗，它是这只宠物在 Echo 里的**那个「谁」**：名字、样子、温度、别人留下的痕迹，都长在这里。 | 🔴 **一条可以被别人看见的回忆。** 一张照片、一段文字、一页生命之书、一张明信片——**它是被看见的那个「什么」**。 |
| **属于哪一侧** | 🔴 **两侧都在，但角色不同。** 在纪念侧它是主人和它相处的地方；在共鸣厅侧它是**别人到达的终点**（顺着一张卡走进来，看见的是这只宠物）。 | 🔴 **共鸣厅侧。** 卡是**唯一的分发单元** —— 广场上流动的、被推荐的、被计入曝光的，全部是卡。 |
| **用户看到的说法** | **「一扇窗」**（功能名）· **「数字纪念空间」**（对外品类词） | **「回忆」**（用户从不说「卡」，用户说「发一条回忆」「这条回忆」） |
| **内部说法** | **窗 / 窗口**（口语）· 数据上是**往宠档案**这一条主记录 | **回忆卡 / 卡** |

### 1.2 🔴 边界写死：三条

**① 分发单元只有卡。** 广场发的是卡不是窗；北极星「被接住的发布率」，**分母数的是卡**。

**② 窗是被指向的对象，不是被分发的内容。** 用户看到一张卡 → 被打动 → 走进这扇窗。🔴 **窗永远是「到了之后看见的东西」，不是「在流里滑过的东西」。**

**③ 🔴 挂在窗上的两样东西不搬到卡上：记得、献花。**（`RK-H` 2026-08-26 裁定，明确为**终态**，不是过渡态。）

⚠️ 🔴 **第三条最容易被当成历史遗留而「顺手修掉」，所以理由必须写在这里，让下一个人不必重新论证：**

> **把记得搬到卡级，字面读下来就是「给这张卡点赞」——而点赞正是立项时明确砍掉的东西。**
>
> **记得是对「它」这个生命的一次表态，不是对某一张照片拍得好不好的评价。** 一个人可以在同一扇窗里看到十张卡，但他记住的是**这只宠物**，不是第七张照片。所以这个动作**天然是窗级的、一人一次的**。
>
> 🔴 **卡级只保留一件事：「这个人是从哪张卡走进来的」。** 这一笔**只用于回答「哪张卡把人叫来了」，不展示、不计数、不排行、不比较**。⚠️ **一旦它出现在用户能看见的地方，当场退化成点赞。**

### 1.3 🔴 为什么会乱：窗曾经既是空间又是分发单元

**早期只有窗。** 那时候「一扇窗」同时是主人的私人空间**和**别人能进来留痕的地方——**这两个角色压在同一个词上**。

**后来卡出现，把分发这个角色接走了**（2026-08）。⚠️ 🔴 **但接走的是角色，没接走的是词** —— 「窗」这个词在很多地方仍然按老意思用着，而读的人分不出哪一处是老意思。

📌 **产品上要记住的只有一句**：**凡是看到「窗」出现在「被推荐 / 被曝光 / 被排序」这类句子里，那句话是过期的。**

### 1.4 🔴 窗的六个名字（一物多名）

| 名字 | 在哪儿用 | 🟢 **结论（2026-08-27）** |
|---|---|---|
| **数字纪念空间** | 对外品类词 | 🟢 **保留（正式）**，这是跟外部（媒体、应用商店、合规材料）说的话 |
| **一扇窗** | 产品功能名 | 🟢 **保留（正式）**，这是跟用户说的话 |
| **窗口** | 内部口语、页面名 | 🟡 **收敛为「窗」**，不要再写「窗口」——它还会被误读成「时间窗口」 |
| **回忆集** | 数据侧注释 | 🔴 **停用（已定 2026-08-27）**，它听起来像「一批卡」，实际指的是窗 |
| **宠物档案 / 往宠档案** | 内部 | 🟡 **内部可留**，⚠️ **但不要出现在用户可见文案里**——「档案」是管理口吻，与产品调性相反 |

⚠️ 🔴 **这六个名字没有任何一处文档说过它们是同一个东西。** 要找齐「所有关于窗的规定」，今天必须搜六个词——**这是产品负责人感觉到的「雷同近似的语义」最直接的一个样本。**

## 2. 回声

### 2.1 两义

| | **甲义（要让出这个词的）** | **乙义（保留这个词的）** |
|---|---|---|
| **指什么** | 🔴 **它捎来的一条近况。** 系统按节奏生成、主动送到主人面前的一条消息——「它今天怎么样」。**方向是：系统 → 主人。** | 🔴 **别人对你发出去的那条回忆的回应。** 有人记住了它、有人留下一句话、有人说「我也是」。**方向是：别人 → 你。** |
| **属于哪一侧** | **纪念侧。** 这是主人和它之间的事。 | **共鸣厅侧。** 这是陌生人给你的东西。 |
| **用户看到的说法** | 🟢 **「近况」/「它的近况」**（2026-08-27 定）。**它到达这个动作叫「捎来」。** | **「回声」** —— 🟢 **保留，已裁定。** |
| **内部说法** | 今天叫 `sourceType='echo'`（卡的一种来源） | 卡级的一次回应 |

### 2.2 🔴 已经拍死的一句：北极星数的是乙义

**北极星「被接住的发布率」里的「回声」= 乙义。**（2026-08-27 已就地写死。）

🔴 **必须写死的理由，是本组最值钱的一句话，产品负责人可以直接拿去讲：**

> **两义正好落在同一个比率的两边。**
>
> **甲义（AI 生成的近况）在<u>分母</u>** —— 它是一条被发布出去的回忆，所以它会让分母变大。
> **乙义（别人的回应）在<u>分子</u>** —— 只有别人的动作才算「被接住」。
>
> ⚠️ 🔴 **所以按甲义读，北极星会变成「我们自己发了多少条 AI 近况」——一个我们完全可控、发得越多越好看的产量数。**

🔴 **给了一条谁都能自查的判据**：**分子只能由<u>别人</u>的动作产生。凡是我们自己生成就能增加的东西，一律不是分子。**

### 2.3 🔴🔴 交办那一问的判断：**甲义不是独立品类，它是卡的一种来源**

**结论：成立。** 但**只说「它是一种来源」不够**，会漏掉一半。下面是完整回答。

**依据一（形态）：它和其他回忆平级，不是另一类东西。**
一条近况落到产品里就是**一张卡**，和主人手写的记录、生命之书的一页、一张明信片**四者平级**。它没有自己的容器、没有自己的列表、没有自己的可见性规则——**用户在窗里看到它的位置，和看到别的回忆是同一个位置。**

**依据二（反证）：如果它是独立品类，北极星那个 bug 就不会存在。**
🔴 **甲义之所以能进分母，恰恰是因为「它就是一张卡」。** 一个真正独立的品类不会被「发布数」数进去。⚠️ **换句话说，「它是不是独立品类」这个问题，产品早就用行动回答过了，只是没人把答案写下来。**

**依据三（用户视角）：用户不需要知道有这么一个品类。**
用户需要知道的是**「它来信了」这件事**，不是「这是一个叫 X 的内容品类」。**品类是给我们自己分类用的；对用户来说这就是它捎来的一句话。**

---

🔴 **但这里必须补一层，否则会照着「只是个来源」去做，然后发现名字不够用：**

> **它需要名字的位置比「来源」多。** 至少还有三处：
> ① **到达的时刻** —— 它是被**送到**主人面前的，有推送、有消息中心、有轻通知；
> ② **节奏** —— 它有自己的频率规则（多久来一次、只降不升、跟温度走）；
> ③ **开关** —— 设置里要能说「这周先不要来信」「只保留回忆，不生成近况」。
>
> ⚠️ **「来源」这个词描述的是它<u>落成了什么</u>，描述不了它<u>怎么产生、怎么送达</u>。**

🟢 **所以给了它<u>两个词</u>，不是一个（2026-08-27 定）：**

| 位置 | 🟢 **正式说法** | 为什么 |
|---|---|---|
| **这条东西本身** | **近况**（全称「它的近况」） | 它是一条回忆的一种来源，和手写、生命之书、明信片并列 |
| **它到达这个动作** | **捎来**（「它捎来一条近况」） | ⚠️ **动作需要一个名字，否则推送文案、设置项、频率规则会各写各的** |

🔴 **这两个词加起来，仍然<u>不构成一个平行于「回声」的产品概念</u>** —— 它们描述的是**卡的一种来源 + 一种到达方式**，而「回声」描述的是**别人给你的一次回应**。**两者不在同一个层级上，所以本来就不该共用一个词。**

### 2.4 🟢 为什么叫「近况」，以及它的代价

**取「近况 / 它的近况」的理由：**
- **它说的正是这件事本身** —— 用户打开看到的就是「它最近怎么样」；
- 🟢 **它不暗示有人在写。**⚠️ 🔴 **这一条是硬要求**：产品有一条明确的红线是「必须让用户知道这是 AI 生成的」，**任何暗示「有人在给你写信」的名字都会和这条红线正面打架。**

**它的代价，要一起说清：**
- 🔴 **「近况」本身不含任何「这是 AI」的信息**，所以**披露这件事完全靠界面上的显著提示扛**，名字帮不上忙；
- 🔴 **它是个通用名词，做品类名偏弱** —— 但这一点在本表的判断里**恰好是优点**：⚠️ **既然它本来就不是独立品类，就不该找一个像品类名的词。**

📌 **另有四个候选（含「来信」「只改文案层」「反过来给乙义改名」「都不改只加限定词」）与各自代价，见 `RESEARCH-echo-term-disambiguation §0.3`，本表不重复。**

### 2.5 🔴 待定：子品牌名「回声·往宠」

**产品的第一步子品牌叫「回声·往宠」，而这里的「回声」指的就是甲义。**

🔴 **所以如果甲义让出「回声」，这个子品牌名就不再指它所命名的东西。**

⚠️ **待定 + 定它需要什么**：**跟着甲义的命名结论一起拍，不要单独改。** 命名要一次看全盘才不会再撞一次——**单独改子品牌名，等于在还没定的结论上先付一次成本。**

## 3. 温度 与 暖意

### 3.1 🔴 先说清：这里是**三个**量，不是两个

⚠️ 🔴 **只把「温度」和「暖意」拿出来比，本身就已经漏了一个。** 产品里同时存在三个「温度感」的量，**它们的驱动方、可见范围、单位全都不同**：

| | **温度** | **暖光** | **热度** |
|---|---|---|---|
| **指什么** | 🔴 **这段关系今天的状态。** 主人常来看它、陪它，它就暖；久不来，会慢慢凉下去——**但永远不会低到失去它。** | 🔴 **有多少人记得它。** 别人的「记得」聚成的一层光，挂在这扇窗上。 | **一条内容在广场上被推荐的力度。** |
| **谁驱动它** | 🔴 **只有主人。** 外人做什么都不改温度。 | 🔴 **只有外人。** 主人自己动不了它。 | 系统按规则算，谁也不直接驱动。 |
| **属于哪一侧** | **纪念侧**，私域 | **窗上，共鸣厅侧的人看得见** | **共鸣厅侧**，纯内部 |
| **用户看到的说法** | **「温度」** —— 🟢 用户看得见，但默认不裸露数字，呈现为随温度变化的光 | **「暖光」** —— 🟢 用户看得见的是光的浓淡，不是数字 | 🔴 **用户永远看不见这个词。** |
| **内部说法** | 温度 | 暖光 | 热度 / 排序权重 |

🔴 **三条产品红线，写在这里免得每次重新翻：**
1. **外部行为完全不改温度。**（别人献花、别人记得，一度都不加。）
2. **温度有一条绝对下界，永不失去它。**
3. **暖光不做数字、不做排行、不做余额观感。**

### 3.2 🔴 问题在哪：「暖意」一个词，两个方向相反的意思

| | **甲义** | **乙义** |
|---|---|---|
| **意思** | 🔴 **主人<u>自己</u>攒的活跃度。** 常来看它、每天到访、纪念日到场，就攒得多。 | 🔴 **<u>别人</u>的「记得」聚成的那层光。** |
| **方向** | **我 → 它** | **别人 → 我** |
| **哪来的** | 2026-07-27 的正式裁定，说得很明白：**「暖意不是虚拟货币，是类似『热度』的活跃指标」**，还给它配了爱心的呈现、配了「每宠独立的消耗速率」 | 后来做窗上那层光时**顺着英文字段名带进来的**——⚠️ 🔴 **中文侧从来没有人宣布过「暖意从此指别人给的」** |

### 3.3 🔴 为什么这一组必须动手：它压在一条红线上

**红线是：外部行为完全不改温度。**

- **按甲义读「暖意上去了，温度也跟着上去」** → 🟢 **合法**，因为那是主人自己的活跃。
- 🔴 **按乙义读同一句话** → **直接违规**，因为那变成了「别人的行为改我的温度」。

⚠️ 🔴 **同一句话，两种读法一个合规一个违规，而句子本身不带任何限定词。**

📌 **这就是为什么这一组不能靠「引用时加个限定词」解决。** 别处有过一个成功的先例（「两层/三层/四层」各带限定词，不去统一它），🔴 **但那个办法之所以有效，是因为那三个数字<u>彼此看得出不同</u>，人读到会停下来问。** ⚠️ **「暖意」的两义都写作「暖意」，看不出来，人不会停。**

### 3.4 🟢 已定（2026-08-27）：废掉「暖意」这个词，不做二选一

| 是哪一份 | 🟢 **正式说法** | 说明 |
|---|---|---|
| **别人给的那一份** | 🟢 **暖光** | **这个词已经在用了**，用户看到的也确实是一层光。**直接扶正，成本最低。** |
| **主人自己攒的那一份** | 🟢 **陪伴值** | 它把「谁在做这件事」写进了词里——**陪伴只能是主人自己的行为**，⚠️ **换成任何别人的动作，这个词自己就说不通了。** |

🔴 **为什么废掉而不是二选一：**「暖意」这两个字**读起来就是「暖的感觉」，本身不指方向**。⚠️ **无论判给哪一边，另一边的人都会觉得自己那个用法也讲得通，然后继续用。** **词本身不带方向，就压不住误用。**

⚠️ 🔴 **另外提醒一句取名上的坑**：「暖意」和「暖光」**都是暖字打头**，两个词摆在一起时人眼会先看到相同的那个字。🔴 **所以新名<u>刻意不用「暖」字开头</u>** —— 这是选「陪伴值」而不是「暖度」「暖心值」的主要理由。

### 3.5 🔴 待定：甲义今天还在不在产品范围内

📌 **本表核实到的事实（落盘前回代码查过，不是照抄文档）：**

- 🟢 **甲义在裁定层<u>没有被推翻</u>** —— 四条裁定都还在，其中一条还专门给它配了「每宠独立的消耗速率」，说明当时是打算真做的。
- 🔴 **但服务端今天<u>只存在乙义</u>** —— 代码里所有写着「暖意」的地方，指的都是别人的记得聚成的那份光。**甲义那套活跃度累积，一行都没有。**

⚠️ 🔴 **所以甲义现在的状态是「有裁定、没实现」。**

**待定 + 定它需要什么**：**产品负责人确认甲义要做还是要撤。**
- **要做** → 🔴 **必须先改名再动手**，否则第一行代码写下去就会撞上乙义；
- **要撤** → **那四条裁定要标注推翻时间与原因**，⚠️ **不要直接删** —— 否则下一个人会重新提出同一个方案。

## 4. 记得 与 看见

🔴 **一句话记住这一组：记得挂<u>对象</u>，看见挂<u>内容</u>。**

### 4.1 记得

| 栏位 | 内容 |
|---|---|
| **指什么** | 🔴 **对「它」的一次静默誓约。** 一个人看到这只宠物，说「我记住它了」。<br>🔴 **一人一次，不可叠加，不显示数字。** 记过就是记过，第二次点没有意义，也没有「记得数」这个东西给人刷。 |
| **属于哪一侧** | 🔴 **共鸣厅侧的动作，落在纪念侧的对象上。** 做这个动作的是外人，而它挂在**这只宠物**身上。 |
| **用户看到的说法** | **「记得」** —— 🟢 用户看到的是这两个字本身，以及它汇成的一层暖光和一面面孔墙。⚠️ **用户看不到任何数字。** |
| **内部说法** | **记得**（同名）。📌 **一处消歧**：内部这条记录是**窗级**的，键是「谁 + 哪只宠物」，**不带卡**。 |

🔴 **为什么它必须挂对象、不能挂卡（`D8` 原意，`RK-H` 确认为终态）：**

> **记得的是这只宠物，不是这张照片。** 一个人在同一扇窗里翻了十张卡，他记住的是**它**。
>
> ⚠️ 🔴 **挂到卡上会发生两件事，都是产品不要的**：① **同一个人可以在十张卡上各点一次，「记得」当场变成可以刷的数字**；② **它会开始评价作品好坏——那就是点赞，而点赞是立项时砍掉的。**

📌 **卡级唯一保留的一笔是「这个人是从哪张卡走进来的」**，🔴 **只用于回答「哪张卡把人叫来了」，不展示、不计数、不排行。**⚠️ **它一旦被下发到用户能看见的地方，当场退化成点赞。**

### 4.2 看见

⚠️ 🔴 **「看见」今天在三个地方各指一件事，而且三处都写作「看」。这是开发反复搞混的直接原因。**

| | 甲 | 乙 | 丙 |
|---|---|---|---|
| **指什么** | **有人看过我的窗。** 陌生人来过，留了个脚印。 | 🔴 **我看过别人给我的回应。** 是**我这一侧的已读状态**。 | **亲友那边有没有我还没看过的新内容。** |
| **方向** | **别人 → 我** | 🔴 **我 → 别人给我的东西**（方向正好反过来） | **别人 → 我，但问的是「有没有新的」** |
| **属于哪一侧** | 共鸣厅侧 | **纪念侧**（我在自己的消息里读东西） | 纪念侧 |
| **改之前的说法** | 「看过」 | 「看过 / 已看」 | 「有没有看过」 |
| 🟢 **正式说法（2026-08-27）** | 🟢 **看过** | 🟢 **已读** | 🟢 **有更新** |

🔴 **为什么分成三个词，而不是加限定词：**

> **甲和乙的箭头方向是相反的。** 甲是「别人看了我」，乙是「我看了别人给我的」。⚠️ 🔴 **两件事在产品上没有任何共同点，共用一个词纯粹是巧合——中文的「看」既能主动也能被动。**
>
> 🔴 **今天没出错，是运气**：这两件事各自的记录里都带了「是谁」，所以主人的已读和访客的脚印天然分得开。⚠️ **但它们描述同一扇窗、动词又同名，下一个人要在两者之间挑一个时没有任何提示可依。**

### 4.3 🔴 记得 / 看过 / 献花 三者的产品差别（现行明文口径）

⚠️ 🔴 **这三个词经常被一起说成「互动」，但它们指向的东西完全不同**，写在一起对照最清楚：

| | **记得** | **看过** | **献花** |
|---|---|---|---|
| **是对谁的** | 🔴 **对「它」**（这只宠物） | **对这扇窗**（只是路过） | 🟢 **对「它」**（`FL1` 2026-08-27 定；原 `D8`「对主人本人」已推翻） |
| **是不是表态** | 🟢 **是**，一次郑重的表态 | 🔴 **不是**，是被动痕迹 | 🟢 **是**，一份社交心意 |
| **能不能叠加** | 🔴 **不能**，一人一次 | 累加计数 | 🟢 **能**，可叠可买 |
| **谁看得见** | 汇成暖光和面孔墙 | 🔴 **只有主人自己看得见** | 主人看得见 |

📌 **献花归属已于 2026-08-27 拍板为「给它」（`FL1`），见 `§5`。**⚠️ 🔴 **但要注意：三者里只有「记得」喂暖光，献花不喂，看过更不喂** —— 见 `§5.6` 第 3 条。

## 5. 献花

🟢 **已拍板（2026-08-27 · `FL1`）：花是给「它」的，窗级。** 🔴 **`D8`「献花 = 对主人本人的社交心意」已被推翻。**

📌 **本节的 `§5.5` 保留了推翻前的三种读法与各自后果**——**推翻的东西不删，留着是为了让下一个人不必重新论证一遍。**

### 5.1 词条

| **用户看到的说法** | **「献花」**、**「留一束心意」** —— 🔴 **措辞去游戏化**：说「心意 / 增值」，**不说「金币 / 充值 / 商城」**。 |

### 5.2 🔴 裁定：花是给「它」的（`FL1` · 2026-08-27）

| | |
|---|---|
| **归属** | 🔴 **献花的对象是这只宠物。** 不是主人，也不是某一张卡。 |
| **层级** | **窗级。** |
| **主人这一侧收到什么** | 🔴 **一个信号：「有人来看过它」。不是钱。** |

🔴 **依据（产品负责人可以直接拿去讲的那一句）：**

> **现实里扫墓献花也要花钱，钱付给花店，没人指望逝者家属收钱。**
>
> 🔴 **所以「花要花钱买」和「花是给逝者的」从来就不矛盾。**⚠️ **此前之所以觉得矛盾，是把「谁付钱」和「花给谁」当成了同一个问题。**

🟢 **它顺带解开了一个一直别扭的死结：**「不可提现、不给主人分成」这两条，在「花是给主人的心意」这个前提下读起来很拧——**说是给主人的心意，主人却什么也收不到。**🔴 **改成「给它」之后，这两条从别扭变成自然：这笔钱本来就不该流向主人，正如买花的钱不流向家属。**

📌 **注意：这两条规则一个字都没改，改的只是它们的理由。**

### 5.3 🔴 献花与记得，现在是同构的

**`FL1` 之后，共鸣厅侧留给「它」的痕迹只有两种，而它们的对象终于一致了：**

| | **记得** | **献花** |
|---|---|---|
| **给谁** | 🟢 **给「它」** | 🟢 **给「它」**（`FL1` 之后） |
| **能不能叠加** | 🔴 **不能**，一人一次 | 🟢 **能**，可叠可买 |
| **要不要花钱** | **不要** | **额度用完可以买** |
| **喂不喂暖光** | 🟢 **喂** | 🔴 **不喂**，见 `§5.6` 第 3 条 |

🔴 **两者的差别现在只剩「能不能叠加」这一条，而这一条是有理由的：** **记得是一次表态，表过就是表过；献花是一次到访，来一次就是来一次，来十次不冲突。**

### 5.5 📌 推翻前的三种读法与后果（保留，不删）

🔴 **保留理由**：这三条各自都有出处、都自洽，**不留着，下一个人会重新提出同一个方案并重新论证一遍。**

**当时的三种读法**：**甲 · 卡级**（花是给这条回忆的，出处是内容互动字典把它登记为卡级）· **乙 · 窗级**（花是献给这只宠物的，出处是现行实现）· **丙 · 人级**（花是给主人本人的，出处是 `D8`）。🟢 **最终取乙，并把「给谁」写死为「它」。**

**当时列出的后果如下：**

#### 甲 · 卡级：花是给这条回忆的

- 🟢 **好在哪**：**北极星那个比率会变得干净** —— 分母是卡，分子也是卡，问的是同一个问题「我发出去的这条，有没有人接住」。
- 🔴 **代价一（最重）**：⚠️ 🔴 **它会把献花变成一个作品评价。** 十张卡各能收花，花多的那张就是「好卡」——**这在形态上就是打赏式点赞**，与「记得为什么不能挂卡」是同一个理由。**献花可叠、可买，所以它比记得更容易滑过去。**
- 🔴 **代价二**：**同一扇窗里的十张卡开始互相比较**，而这个产品从头到尾在避免让纪念内容进入比较关系。
- 🟡 **代价三**：**用户的动机对不上。** 用户在窗里献花时想的是「给它献一束花」，**没有人会想「我要给这张照片献花」。**

#### 乙 · 窗级：花是献给这只宠物的

- 🟢 **好在哪**：**和用户的直觉一致**，也和现行实现一致，**改动最小**。
- 🟢 **好在哪（第二条）**：**它天然避开了作品评价** —— 花是给它的，不是给某张照片的。
- 🔴 **代价**：⚠️ **北极星那个比率会变成「分母是卡、分子是窗」** —— **一扇窗发了十张卡，有人来献花，从窗级看不出是哪张卡把人叫来的。** 🔴 **这个比率会失真。**
  - 📌 **这个代价<u>已经有解</u>，不必当成阻断项**：现行做法是「互动本身留在窗级，另记一笔『从哪张卡进来的』**只做归因、不做计数**」。**同一套办法可以照搬到献花上。**

#### 丙 · 人级：花是给主人本人的

- 🟢 **好在哪**：**它是唯一能解释「为什么献花可以花钱买」的读法。** ⚠️ 🔴 **给逝去的宠物买花说不通，给一个陪伴过它的人表达心意说得通** —— **付费这件事需要一个人在另一头接住。**
- 🔴 **代价一**：⚠️ **它和「不给主人分成、不可提现」放在一起有点拧** —— **说是给主人的心意，主人却什么也收不到。**🔴 **这条不是反对意见，是产品要准备好的回答**（心意本身就是心意，不是钱）。
- 🔴 **代价二**：**它让献花和记得的对象分了家** —— **记得是给「它」的，献花是给「主人」的。**⚠️ **这两件事在界面上挨着，用户不会意识到它们指向不同的人。**

🔴 **当时那句提醒，`FL1` 之后仍然成立、而且更重要了**：**「不加温度、不排名」是防住「献花变成打赏排行」的东西。**⚠️ **花现在明确是给它的，一旦排起名来，比的就是「谁家的它更被爱」——那是这个产品最不该出现的画面。**

🔴🔴 **反向说明（这一段是本节最要紧的一段，请勿删）：**

> **「献花归窗级」不等于「献花喂暖光」。**
>
> ⚠️ 🔴 **下一个人极容易这样推理**：「记得是窗级的，它喂暖光；现在献花也确认是窗级的了，那就一起算进暖光吧。」——**这个推理看起来非常顺，但它是错的。**
>
> 🔴 **暖光量的是「有多少人记得它」，不是「它收到了多少东西」。**
> - **记得一人一次、不可叠加**，所以人数和次数是同一个数，**它可以安全地变成一层光**；
> - 🔴 **献花可叠、可买。** ⚠️ **一旦花进了暖光，暖光就变成了一个<u>能用钱买浓</u>的东西** —— **那一刻它同时踩碎三条红线**：「不加温度」的精神、「不排名」、以及「暖光不做钱包余额观感」。
>
> 🔴 **判据一句话：暖光的输入必须是<u>不可叠加、不可购买</u>的动作。献花两条都不满足，所以它永远不进暖光。**

### 5.7 🔴 `FL1` 之后，一处设计的存在理由没了（📋 需产品负责人再拍一次）

⚠️ 🔴 **这一条不会报错，它会继续正常运行——只是理由没了。**

**是什么**：**主人可见的「私密羁绊名单」** —— **主人能看到「某个人给它献过多少朵花」，精确到朵数。**（实测：服务端有这个查询，两处内部注释逐字称它为「**owner 视角的私密羁绊名单**」「**仅供 owner 内部**」；献花成功后还会回一句 **「你为它献过 N 朵」**。）

🔴 **它的存在理由建立在「花是给主人的」之上**：既然是别人给**你**的心意，你当然有权知道是谁给的、给了多少。⚠️ 🔴 **`FL1` 之后这个前提没了——花是给它的，主人凭什么拿到一份具名、具数的清单？**

🔴 **它和同一侧的「记得」摆在一起，反差已经很刺眼：**

| | **记得** | **私密羁绊名单** |
|---|---|---|
| **主人能知道是谁吗** | 只汇成一层光和一面面孔墙 | 🔴 **能，具名到人** |
| **主人能知道有多少吗** | 🔴 **不能** —— 到达提示一律说「**有人**」，**刻意不区分单复数、不给任何数量线索** | 🔴 **能，精确到朵数** |

⚠️ 🔴 **同样是别人留给它的痕迹，一种匿名且无数量，另一种具名且有精确数字。** **这个差别此前由「花是给主人的、记得是给它的」来解释；现在两者的对象一样了，差别就失去了依据。**

📋 **待拍 + 定它需要什么**：**产品负责人在两条里选一条** ——
- **留**：那要给一个新理由（例如「这是主人自己的记忆，不是给别人看的排行」），🔴 **并明确它永远不外露、不进任何比较**；
- **撤**：那要说清撤到什么程度（只去掉朵数？还是连人也不显示？）。

⚠️ 🔴 **另有一个连带的错，顺便登记**：那句「**你为它献过 N 朵**」里的「它」**实际数的是「你给这个<u>主人</u>献过多少朵」** —— 实测这个统计按**主人账号**聚合，**不带宠物**。**所以一个主人有两只宠物时，你给 A 献了 5 朵，走到 B 的窗上也会看到「你为它献过 5 朵」，而你从没给 B 献过花。**🔴 **这个错今天不报错、也不是 `FL1` 造成的，但它正是「花是给主人的」那个旧口径留下的痕迹** —— 📋 **归工程线，本表只登记。**

## 6. 共鸣 / 共鸣厅

🔴 **交办要问的是「这个词有没有和『回声』一样的双义问题」。回答：有，而且比「回声」更碎——今天是四义。但四义里只有两条会真的伤到产品理解，另外两条是内部检索问题。**

### 6.1 「共鸣」的四义

| | 指什么 | 属于哪一侧 | 🔴 要不要处理 |
|---|---|---|---|
| **甲** | **两个用户的相似度达到某个门槛的关系。** | 🔴 **不属于任何一侧——它是上一代产品的词。** | 🔴 **要处理，但归工程侧。** 上一代产品（做「意识空间 + 向量匹配」的那个）留下的一整套东西**至今一行未删**。⚠️ **产品侧今天不用这个意思，但它还在库里占着这个词。** |
| **乙** | **别人对一张卡的一次回应。** 记住了它、留一句话、说「我也是」。 | 共鸣厅侧 | 🟢 **这是今天的正统义**，保留。 |
| **丙** | **共鸣厅** —— 大家能看到彼此回忆的那个地方。 | 共鸣厅侧 | 🟡 **保留，但范围要收口**，见 `§6.2`。 |
| **丁** | **深共鸣率** —— 一个只数「留一句话」和「我也是」这两种深回应的指标。 | 共鸣厅侧，纯内部 | 🟢 **保留。** 🔴 **它是内部指标名，用户永远看不到。** |

🔴 **与「回声」那一组的区别，一句话说清（这一句决定了处理办法不同）：**

> **「回声」的两义是<u>同一层级上的两个东西</u>**（都是内容、都在卡上），🔴 **所以必须二选一，一个让出这个词。**
>
> **「共鸣」的四义是<u>不同层级</u>**：**乙是动作、丙是场所、丁是指标**。⚠️ **这三个层级并存在产品语言里是正常的**——就像「消费」既能指行为也能指场所。🔴 **所以它不需要像「回声」那样让词，只需要各自把话说完整。**
>
> 🔴 **真正需要处理的只有甲义**：它和乙丙丁**没有任何关系**，是上一代产品原样留下的。**它不是双义，是撞名。**

### 6.2 🔴 本表新登记的一条：「共鸣厅」自己的范围有两读

⚠️ 🔴 **这一条此前没有被登记过。**

| 读法 | 「共鸣厅」指什么 | 出处 |
|---|---|---|
| **宽读** | 🔴 **整个公开层** —— 瀑布那一屏、点开的全屏单卡、作者主页、宠物窗口页，全都算共鸣厅。 | **`D24` 逐字：「共鸣厅 = 瀑布发现层 + 全屏单卡层 + 主页」** |
| **窄读** | 🔴 **只指瀑布那一屏。** | **`SPEC-interaction-flow.md:217` 逐字把「广场、发现页、共鸣厅」列为<u>瀑布发现层的同义词</u>** |

⚠️ 🔴 **什么时候会出事**：**任何一句「共鸣厅里 X 要怎样」的规定。**
> 举例：**「共鸣厅里不展示温度」**——
> **按宽读**：走进宠物窗口页也不展示温度。
> **按窄读**：只有瀑布那一屏不展示，点进窗口页照常展示。
>
> 🔴 **这两种做法在屏幕上差别巨大，而句子本身看不出作者是哪一读。**⚠️ **可见性规定按错的那一读做，方向是内容多露了。**

### 6.3 🟢 已定（2026-08-27）：分词，不加限定词

| 位置 | 🟢 **正式说法** |
|---|---|
| **整个公开层**（宽读） | 🟢 **公开层** —— **内部用语，用户看不到。** |
| **瀑布那一屏**（窄读） | 🟢 **共鸣厅** —— **用户看到的说法，就指他滑瀑布的那一屏。** |
| **原来的两个别名** | 🔴 **「广场」「发现页」停用。** 它们和「共鸣厅」指同一件事，但都不带 Echo 的调性——**「广场」尤其别扭，这个产品的公开层不是广场那种气氛。** |

🔴 **为什么把「共鸣厅」判给窄读而不是宽读：** **它是用户能看见的词**，而**用户看得见的词应该指用户看得见的那一屏**。⚠️ **「整个公开层」是我们自己的分类概念，用户从来不需要知道它有几层。**

## 6A. 陌生人 与 亲友（🆕 2026-08-27 新增）

> 🔴 **为什么补这一条**：产品负责人问「**陌生人如何定义**」，
> 🔴 **全库没有一处讲清楚** —— 这个词在规格里到处用，却从来没被定义过。

### 6A.1 🔴 结论（读这一段就够）

> 🔴 **「陌生人」是<u>关系</u>，不是<u>权限档</u>。**
>
> **权限档只有三个：公开 / 亲友 / 私密。**
> **陌生人 = 不是主人、且不在这扇窗的亲友名单里的访客。**

**三种身份,一句话各一个**：

| 身份 | 是谁 | 看得到 |
|---|---|---|
| **主人** | 这扇窗的所有者 | **全部** |
| **亲友** | 🔴 **被<u>窗主</u>列进名单的人** | 公开档 **+ 亲友档** |
| **陌生人** | **其余所有访客**（含游客） | **只有公开档** |

⚠️ **私密档谁都看不到**，主人自己除外。

### 6A.2 🔴 关注**不**改变权限（本节最要紧的一句）

> 🔴 **已关注者在权限上仍然是陌生人。** ⚠️ **关注只在<u>到达提示的措辞</u>上被区分**（2026-08-27 裁定，验收用例 `ACCEPTANCE.md TC-ARR-01`）。

🔴 **必须写死这一句的理由**：⚠️ **不写，下一个人一定会把「关注」做成第四档权限。**
**那看起来是件很自然的事**（「他都关注我了，多给他看一点」），🔴 **但它会当场把可见性从三档变成四档，
而三档这个数写在校验里、写在文案里（「可见性就三档：私密 / 挚友可见 / 公开」）、写在契约里。**

📌 **两个词的方向本来就不同**，记住这个就不会搞混：

- **亲友是<u>窗主</u>拉进来的** —— **他决定谁能多看一档**
- **关注是<u>访客</u>自己按的** —— 🔴 **访客不能给自己升权限**

### 6A.3 ⚠️ 被拉黑的人**不是**陌生人

🔴 **被拉黑方是「不可达」，不是「按陌生人裁剪」。** 📌 **这一条在代码里有逐字注释**：

> 「**把拉黑揉进身份判定会让『不可达』退化成『按陌生人裁剪』，那等于给被拉黑方留了一条看公开内容的路。**」

⚠️ **所以身份判定那一层只有三个值**（主人 / 亲友 / 陌生人）；**拉黑在更前面一层就把人挡掉了。**

### 6A.4 🔴 两处与既有裁定对不上的地方（**只登记，不调和**）

⚠️ **落笔前已 grep 核对，发现两处打架。** 🔴 **按纪律如实报出，本表不自行调和。**

## 7. 本表怎么维护

- 🔴 **本表只管「词指什么」。** 规则与口径以 `DECISIONS.md` 为准；**两处冲突时以 `DECISIONS.md` 为准并修正本表。**
- 🔴 **新增或改动一个概念时，四样必须齐**：指什么 · 属于哪一侧 · 用户看到的说法 · 内部说法。⚠️ **缺「属于哪一侧」的条目不算写完** —— 本项目的术语混乱几乎全部出在这一栏上。
- 🔴 **被推翻的结论保留原文并标注推翻时间与原因，不要直接删。**
- 🔴 **本表定的是「叫什么」，不负责把它改到别处去。** 传播清单见 `§8`，📋 **归后续的命名专项**。
- 🟡 **本表尚未覆盖的词**（下一轮）：**发布**（作者点发布的那一刻 ⟷ 内容真正能被看见的那一刻）· **曝光**（被列出 ⟷ 被真的看到）· **可见性**（作者选的档位 ⟷ 实际生效的档位）· **回响**（产品代号 ⟷ 消息中心的频道名 ⟷ 社交层正式名）。📌 **这四组的共同点是「说了」和「做到了」之间有差**，与本轮六组的成因不同，**建议单独一轮处理。**
