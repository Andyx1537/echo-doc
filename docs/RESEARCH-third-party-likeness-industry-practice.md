## 摘要：五个结论

### 结论 1：制作人的直觉**基本成立**，但成立的原因和他想的不完全一样

同业主流**确实**是"授权承诺 + 留痕 + 事后处置"，而**不是**"检测到疑似他人肖像就不让用"。这一点有一手证据（见 §1.1 妙鸭记者实测、§1.4 三家协议原文、§1.6 新华社制服照实测）。

但真正决定核验强度的分界线**不是"素材敏不敏感"，而是"这是自助 UGC 产品还是人工定制/企业服务"**：

| 形态 | 授权核验 | 一手证据 |
| --- | --- | --- |
| **自助 C 端 UGC**（妙鸭、可灵、即梦、剪映、AI 换装小程序） | **无核验**。协议一句"你保证已获授权"，事后靠举报下架 | §1.1 §1.4 §1.6 |
| **企业级 / 人工定制**（腾讯云数智人、阿里云灵境、超级头脑 AI 复活） | **有核验**。授权书（书面+口述视频）、人工审核 3 工作日、关系证明+死亡证明 | §1.2 §1.3 §1.5 |

**这条分界线对 Echo 的意义**：Echo 是自助 C 端 UGC 形态，同业对标应看第一行；但 Echo 卖的是「AI 复活」这个品类，而这个品类在国内**唯一有核验的先例（超级头脑）恰恰是人工定制形态**。Echo 处在两者之间，同业无直接可抄的先例——这本身是需要制作人知道的事实。

### 结论 2：四类里，只有**一类**同业是硬拦的，而且它不是人格权类

| 类别 | 同业实际做法 | 硬拦？ | 证据强度 |
| --- | --- | --- | --- |
| **① 公众人物 / 政治人物** | **矛盾登记**：涉政侧有明确拦截能力（内容安全服务商的"禁忌人物库"）；肖像侧未找到一手证据证明某平台会拒绝明星脸上传 | **部分**（涉政拦，肖像未证实） | 🟢+🔴 混合，见 §1.7 |
| **② 未成年人为素材主体** | **不拦**。可灵/即梦/剪映三家协议措辞近乎一致：一经上传"**即视为您已获得权利人同意**" | **否** | 🟢 一手协议原文，§1.4 |
| **③ 证件照 / 制服照** | **不拦**。新华社记者实测：AI 军装换装小程序不要求身份证明、连风险提示都没有 | **否** | 🟢 一手官媒实测，§1.6 |
| **④ 第三方 IP 角色** | **硬拦，且是被法院判着拦的**。广州互联网法院要求达到"用户正常使用相关提示词不能生成实质性相似图片" | **是** | 🟢 一手判决，§1.8 |

🔴 **这个分布恰好推翻了规格原稿的论证结构**。规格原稿把四类打包，理由是"这四类涉及的权利不在上传者手上"。但事实是：**唯一被硬拦的第④类，恰恰是规格自己标注为"著作权不是人格权、与本规格主线无关"的那一类**。而规格用人格权论证得最重的第①②类，同业都没拦。

也就是说：规格把"权利不在上传者手上"当成了拦截理由，但同业的实际拦截理由是"**有没有一个会来起诉你的、有组织的权利人**"。IP 权利人（圆谷、迪士尼）有法务部、会批量取证起诉；被 AI 换脸的普通小孩没有。这是个不好听但真实的机制。

### 结论 3：《深度合成规定》第 14 条的义务是「平台去提示」，不是「平台去取得同意」

🟢 **一手原文**（第十四条第二款）：

> 深度合成服务提供者和技术支持者提供人脸、人声等生物识别信息编辑功能的，**应当提示深度合成服务使用者依法告知被编辑的个人，并取得其单独同意**。

句子的主干是「提供者……应当**提示**使用者」。「依法告知被编辑的个人，并取得其单独同意」是**使用者**要做的动作，不是提供者要做的动作。

**平台的法定义务止于"提示"**。取得同意的义务主体是使用者。详见 §2.3 的句法拆解与同业落地写法。

⚠️ **但有两处不能顺着这个结论一路滑到底**，见 §2.3.3 和 §2.6，都是对 Echo 不利的方向。

### 结论 4：1:N 悖论有解，同业走的是三条路，Echo 能用其中两条

🟢 **关键法条定义**（《人脸识别技术应用安全管理办法》第十九条）：

> （三）人脸识别技术，是指**以人脸信息作为识别个体身份**的个体生物特征识别技术。

🟡 环球律师事务所解读得很直接：**"如处理活动不以识别为目的，则不属于《管理办法》所规定的'人脸识别技术'。"**

**所以"只做检测不做识别"这条路是通的，规格 §7.3 的技术选型判断正确。** 三条路径与 Echo 的适用性见 §3。

### 结论 5：监管实际的执法抓手不是"你没核验肖像授权"

🟢 **国家网信办执法典型案例**（经新华社 2025-10 报道）：浙江某公司运营的换脸类 App 被**责令下架**。违规事由是：

- 未按规定落实**安全评估**要求
- 深度合成内容未作**显著标识**

**不是**"未核验被换脸人的授权"。

同期"清朗"专项行动第一阶段（2025）处置 AI 产品 3500 余款、（2026）处置 1.4 万余款，公布的整治重点全部集中在**备案、安全评估、标识、训练语料、数据投毒**，没有一项是"上传端肖像授权核验不到位"。

🔴 **这对 Echo 的资源分配是个强信号**：把工程量投在"上传端拦人脸"上，对降低**被监管处罚**的概率贡献很小；投在"备案 + 安全评估 + 标识"上才是。上传端拦截主要防的是**民事被诉**，两者是不同的风险池，不该混在一个预算里算。

## 第一章 同业实际做法

### 1.1 妙鸭相机（阿里，AI 写真）

**为什么值得单看**：这是国内唯一一个因肖像授权条款上过全国热搜、并被上海消保委点名的 AI 影像产品，公开信息最完整。

#### 🟢 产品里实际发生的（一手：中国青年网 / 中国经济网记者实测，2023-07）

记者随机下载了一张网络上他人的正面照片测试：

> 「短短几十秒内便通过了'正面照片'的审核，**且审核期间没有盗用他人照片的风险提示**。」
>
> 「对于是否为本人照片，小程序目前的机制**尚未严格界定**，存在可以冒用他人照片使用的可能性。」

记者随后联系官方客服，客服回应：

> 「隐私协议第 11 条有规定，使用他人照片需得到他人授权」「平台不鼓励这种行为」

记者追问实际发生后如何处理，客服答：

> 「需要承担相应法律责任」

🔴 **这段对话就是制作人直觉的教科书式印证**：核验为零、提示为零、全部靠协议条款把责任推给用户、出事之后靠"你自己承担法律责任"。

#### 🟢 协议里写的（一手：妙鸭用户协议，经多家媒体引述）

> 「您保证对于您的上传内容拥有相应的合法权利或已取得他人合法授权并有权用于本服务；否则，造成的一切后果及损失由您自行承担」

#### 🟡 那场舆情争的其实不是这件事

需要给制作人纠正一个可能的误解：妙鸭 2023-07 那场热搜，**争的是"平台能不能拿用户的脸去干别的"，不是"用户能不能上传别人的脸"**。

被骂的原始条款是：

> 「您特此授予我方在全世界（包括元宇宙等虚拟空间）范围内享有**永久的、不可撤销的、可转让的、可转授权的**、免费的和非独家的许可……」

妙鸭 2023-07-20 道歉并删除该条款，改为承诺「上传的照片只会用于数字分身制作，不会提取也不会用于识别和其他用途，且分身制作完成后自动删除」。

🟡 律师意见（新京报引述彭根）：原条款与 PIPL 直接抵触，因为 PIPL 明确同意可撤回，而条款写"不可撤销"；且属于典型的一揽子授权。

🔴 **对 Echo 的直接教训（这条比同业做法更要紧）**：Echo 是"逝者数字资产"产品，用户上传的是**不可再生**的遗物素材。妙鸭的教训是——**用户对"平台拿我的素材去训练/商用"的敏感度，远高于对"我传了别人的脸"的敏感度**。Echo 的协议若出现任何"永久/不可撤销/可转授权/用于模型训练"的表述，触发的舆情量级会显著大于四类敏感素材加起来。这一条建议同步给文档线。

#### ⬜ 未检索到

- 妙鸭是否对明星/公众人物人脸做专项拦截。**记者实测只测了"陌生人的照片"，没测明星。** 无任何一手或二手证据。
- 妙鸭对未成年人素材的处理。
- 妙鸭 2023 年之后是否加装了核验（产品已大幅降温，近期评测稀少）。

### 1.2 腾讯云智能数智人 / 腾讯智影（企业级数字人克隆）

🟢 **一手：腾讯云官方文档**（`cloud.tencent.com/document/product/1240/96268` 及 2D 小样本形象定制指引 PDF）

这是**有真核验**的一侧，而且腾讯把法条直接写进了文档：

> 「为保障客户及定制人的合法权益，**根据《互联网信息服务深度合成管理规定》规定**，需要采取相应措施确保已取得用户合法授权同意。客户取得用户授权后，方可通过线上接口或线下方式向腾讯云提供授权材料。**每个形象都需要配套提交本人的授权材料**，可支持提交视频口述授权、书面材料授权两种授权模式（**优选同时提供两种授权模式**）。」

授权形式（腾讯提供模板下载）：

| 形式 | 说明 | API 参数 |
| --- | --- | --- |
| **口述形象授权书** | 本人出镜录视频口述授权 | `IdentityCosUrl`（mp4，≤5GB） |
| **书面形象授权书** | PDF 扫描件 | `IdentityWrittenCosUrl`（pdf，≤10MB） |

审核：🟡 提交后需人工审核，一般 **3 个工作日**；未通过可查看原因并重新提交。

#### 🔴 但有一个必须报出来的例外，它推翻了"腾讯是严格派"的简单印象

🟢 **一手：定制接口文档参数说明原文**：

> 「**除 `IMAGE_PHOTO`、`ZERO_SHOT_VOICE` 定制类型无需填写外**，其他定制类型与 `IdentityWrittenCosUrl` 二选一或二者都填」

翻译成人话：

| 定制类型 | 要授权书？ |
| --- | --- |
| 视频形象定制（专属口型 / 通用口型 / 高精版） | **要** |
| 完整声音复刻（100 句音频） | **要** |
| `IMAGE_PHOTO`（**一张照片**生成形象） | **不要** |
| `ZERO_SHOT_VOICE`（**极速**声音复刻） | **不要** |

🔴 **这是本次调研最有决策价值的单条发现。** 同一家公司、同一套产品、同一部《深度合成规定》之下，**核验强度不是按"素材敏感度"分档的，而是按"定制深度/成本"分档的**：

- 你要传 2–10 分钟 4K 视频做高精形象 → 要授权书 + 3 天人工审核
- 你只传**一张照片**做形象 → 一张照片就能开工，**不要授权书**

而"一张照片"恰恰是**最容易拿到别人的**那种素材。从"防止盗用他人肖像"的角度看，这个梯度是**反的**。

🟡 **对这个反常现象的两种解释，并列登记，不择一**：

| 解释 A | 解释 B |
| --- | --- |
| 腾讯认为 `IMAGE_PHOTO`/`ZERO_SHOT_VOICE` 生成的相似度不足以构成《深度合成规定》第 14 条意义上的"生物识别信息编辑"，故不触发提示义务 | 授权书是**摩擦成本**，会杀死轻量级 API 的调用量。腾讯在轻量档做了商业取舍，用协议条款兜责任 |
| 若成立，则 Echo 可论证"低相似度输出可免核验" | 若成立，则该做法不构成合规依据，只是商业惯例，Echo 不能引用它当护身符 |

⬜ **未检索到**：腾讯是否对提交的授权书做真实性核验（比对授权书上的人脸与素材人脸是否一致），还是仅检查文件存在且清晰。**这个缺口很关键**——如果只检查"有没有这个文件"，那所谓核验实质上仍是留痕，不是核验。

### 1.3 阿里系（钉钉数字员工 / 阿里云灵境 / 阿里云声音复刻）

#### 🟢 钉钉"真人互动数字人"：最明确的「本人念指定文案」一手证据

🟢 **一手：钉钉开放平台官方文档**，形象定制拍摄指南要求：

| 项 | 要求 |
| --- | --- |
| 拍摄时长 | 15 秒左右 |
| 要求 | 1. **确保由本人录制授权视频**。2. 确保面部清晰，不遮挡面部，与镜头距离适中。3. **完整阅读指定文案内容**。 |
| **阅读文案（原文）** | 「**我是在数字员工企业版形象定制中上传视频的模特本人，我承诺已经按照平台规则进行了合法授权，特此承诺。**」 |
| 错误示范 | 1. 面部露出不全。2. **非数字人本人形象**。 |

🔴 **请注意这段文案的法律构造，它比看起来精巧**：录像里的人说的是"**我承诺已经按照平台规则进行了合法授权**"——即**被克隆者本人在镜头前做出的、可回放的、带面部的授权表示**。

这个设计同时解决了三个问题，而且**一次 1:N 比对都不需要**：

1. **在场性**：这个人此刻在镜头前，配合，知道自己在被克隆
2. **一致性**：说话的这张脸就是要被克隆的那张脸（1:1 自比，不查库）
3. **可追溯性**：出事时有一段"本人亲口承诺"的视频，举证强度远高于一个勾选框

🟢 **这是回答制作人问题的最佳同业范式**：它既是"留痕追溯"（符合制作人直觉），又比"勾选框"强得多，**且完全不触碰身份识别**。详见 §3.2。

#### 🟢 阿里云灵境数字人（形象定制）

🟢 **一手：阿里云帮助中心**。重人工流程：

- 正式拍摄前，需将**定妆照（含妆造/服装）、试录视频发给客户经理审核**
- 录制 5 分钟自然播报视频，**一镜到底，不允许后期拼接剪辑**，不允许画外音提醒、模特出错、**第三人出镜**
- 交付经阿里云盘或钉钉直接传输
- 形象与音色定制完成后，**在钉群与客户确认验收**

⬜ **未检索到**：阿里云灵境形象定制的授权书具体形式与模板（文档为邀请制/工单制，公开页未展示授权材料要求）。

#### 🟢 阿里云智能媒体服务声音复刻

🟢 **一手**：控制台录制或上传音频后，「系统会自动进行审核，审核通过后即可使用」。审核状态含"审核中/审核通过/审核失败"。审核失败的排查项列的是：**音频内容是否符合服务协议（不含违法违规内容）、格式技术要求、音质噪音**。

🔴 **注意这份排查清单里没有"是否为本人"**。这说明该审核是**内容安全审核**，不是**授权核验**。这是一个容易被误读为"阿里做了核验"的地方，必须标清。

### 1.4 字节系（即梦 AI / 剪映）与快手（可灵）——自助 UGC 的行业模板

这一节是**未成年人素材**问题的直接答案，也是"协议 vs 实际"分野最清晰的一节。

#### 🟢 协议里写的（三家一手原文，措辞高度雷同）

**可灵 AI 用户协议 14.5**（`ppg.viviv.com/doodle/oarzodFE.html`）：

> 「为更好地保护未成年人隐私权益，我们提醒您，严格遵守相关法律法规，**慎重发布包含未成年人素材的内容，一经发布，即视为您已获得权利人同意**在"可灵AI"中展示未成年人的肖像、声音等信息，且允许我们依据本协议使用、处理该等与未成年人相关的内容。」

**即梦 AI 付费服务协议 12.2**：

> 「我们特别提醒您在填写未成年人个人信息时应加强保护意识并谨慎发布包含未成年人素材的内容。**您应当取得权利人同意展示未成年人的肖像、声音等信息**，且允许我们依据本协议使用、处理该等与未成年人相关的内容。」

**剪映 AI 功能使用规范 §五（未成年人保护）**：

> 「特别提醒您在填写未成年人个人信息时应加强保护意识并谨慎使用和发布包含未成年人素材的内容。**您应当取得使用和展示未成年人的肖像、声音等信息的全部合法授权及同意**……」

**可灵付费服务协议 §3**（一般肖像条款）：

> 「您需保证，在使用"可灵AI"各项功能及服务时，对于您所上传、输入、提交、输出、发布的视频、图片、照片及其他素材……**不侵犯任何第三方的合法权益（包括但不限于肖像权、人格权……）**，如您违反该要求，相关纠纷需由您自行解决，相关法律责任需由您自行承担……**公司向您提供相关服务，不视为认可您上传和发布的"信息内容"合法、合规以及不侵权**」

🔴 **三点必须点出来**：

1. **三家措辞近乎逐字雷同**（"谨慎发布包含未成年人素材的内容"+"取得权利人同意展示未成年人的肖像、声音"），说明这是**行业通用模板**，不是某一家的独立判断。作为"同业普遍做法"的证据强度很高。
2. **可灵那句"一经发布，即视为您已获得权利人同意"是推定条款**，其法律效力存疑（后文 §2.5 展开），但它清楚地说明了产品设计意图：**不核验、不拦截、把授权状态推定为"已具备"**。
3. 「不视为认可……合法、合规以及不侵权」是**避风港式免责**的标准写法——平台明确声明自己不做实质审核。

#### 🟢 百度曦灵大陆用户平台协议——第 14 条落地的最干净样本

🟢 **一手原文**（`xiling.cloud.baidu.com/doc/AI_DH_CLOUD/s/9m64xy7u7`）：

> 「对于您使用我们提供的克隆功能，**所编辑的非您本人的人脸、人声等生物识别信息，您应依法告知被编辑的个人，并取得其单独同意，否则您承担所有不利后果。**」

🟢 **百度智能云声音复刻协议 4.1**：

> 「您为使用本服务而收集、获取以及提供给百度智能云用于训练定制音色的全部数据所包含的全部个人信息……**您确认已通过隐私政策或者其他授权形式取得了信息主体合法、充分且明确的同意（涉及敏感个人信息的，还需另行获得信息主体的单独同意）**……**百度智能云无需再另行获得任何主体的授权或许可。**」

🔴 **这两段是本次调研中「第 14 条义务主体」问题的最强实证**。百度把《深度合成规定》第 14 条第 2 款的句子几乎原样抄进协议，把「告知 + 取得单独同意」的动作**明确指派给使用者**，并且在声音复刻协议里直接写明「百度**无需再另行获得**任何主体的授权」。

这就是一个头部云厂商的法务部门对第 14 条的解读：**平台的义务是把这句话告诉你（提示），取得同意是你的事。** 见 §2.3。

#### 🟢 产品里实际发生的：即梦"出镜"分身的录制流程

🟡 **二手（教程站，2026-07 版本）**，但描述与 🟢 一手的 36 氪报道相互印证：

即梦创建数字分身的流程：正面打光、摘掉眼镜帽子口罩、**按语音提示读"123 456 789"**、缓慢左右转头约 30 度、点头两次，**录满 12 秒以上**（少于 10 秒判定无效）。

🟢 **一手（36 氪，2025）** 对同一流程的描述：

> 「对着镜头念出'1、2、3'，朝左看，朝右看……短短 30 秒，你就能创建好自己的数字分身。只是这一套流程**怎么看都跟银行、支付平台的真人认证如出一辙**。这怎么不算一种反向的图灵测试呢。」

🔴 **这是一个必须精确读的证据，很容易读错**：

这套流程是**活体检测 / 在场性验证**（proof of presence），**不是身份核验**。它证明的是"镜头前有一个真人在配合做动作"，**不证明"这个人是谁"**，更不查任何人脸库。

**它的合规作用是什么**：它把"上传一张从网上下载的别人的照片"这条最省力的滥用路径**在工程上堵掉了**——你没法让一张静态照片左右转头点头。这不是身份识别，但它把"随手盗用他人肖像"的成本从"零"提到了"要把本人拉到镜头前"。

🟢 **这条路径 Echo 用不了，必须说清楚，不能给制作人错误的希望**：Echo 的素材主体是**已故的宠物 / 逝者**，定义上无法出镜配合活体检测。P0 的宠物场景更是完全不适用。**这是 Echo 与全部数字人同业的结构性差异**：数字人产品可以要求被克隆者本人出镜，Echo 的被克隆对象已经死了。

🔴 **由此得出一个对裁定有直接影响的推论**：同业"最强的非识别式核验手段"（本人出镜/活体/念指定文案）对 Echo **整类不可用**。所以 Echo 只剩两条：往下退到"承诺 + 留痕"，或往上走到"提交关系证明等材料"（即 §1.5 超级头脑那条路）。**中间那档不存在。** 这一点应当进入 `Q-6` 的选项表。

#### 🟡–🔴 公众人物拦截：证据在此处最弱

🟡 **二手（第三方教程站 `aigwx.org`，2026）**，可灵"人物面部参考"功能：

> 「注意：不要上传明星、公众人物的脸，**会被合规系统拦截**。」

🟡 **二手（`aistacknav.com`）**，审核不通过的原因列举中含：

> 「提示词包含敏感、暴力、露骨、**未成年人**、政治争议、侵权商标/人物等风险元素。」
> 「上传图片本身存在版权、人像、敏感画面或不适合生成的内容。」
> 建议：「不要上传带有明显版权水印、影视截图、**名人照片**、商标包装的素材。」

🔴 **弱证据，登记但不采信**：`17golang.com` 一篇文章称可灵"通过**图像哈希比对与声纹特征库进行双重校验**"。该站内容特征符合 AI 批量生成的 SEO 农场（同页另有教用户用不可见 Unicode 字符规避审核的"教程"），**"图像哈希比对+声纹特征库双重校验"这个技术描述极可能是编造的**。仅作为"网络上存在这种说法"记录，**不得引用为技术事实**。

⬜ **未检索到（这是本次调研最重要的缺口）**：

- **可灵/即梦官方**关于"明星人脸会被拦截"的任何公开说明或帮助文档条目。所有说法都来自第三方教程站。
- 任何**一手实测**（用户投诉截图、媒体评测、拒绝提示原文）证明上传明星照片会被拒。
- **拦截的实现层**：是在**上传端**拦人脸，还是在**提示词**里拦人名，还是在**输出端**审核成图？这三者对 Echo 的技术选型影响完全不同（Echo 无提示词环节，用户只上传照片），但公开信息完全无法区分。

### 1.5 「AI 复活逝者」类：超级头脑、硅基智能

🔴 **这一节对 Echo 的相关性最高——它是同品类，不是类比。**

#### 🟢 超级头脑（南京/上海，张泽伟团队）：有真核验，且核验的是"关系"不是"身份"

🟢 **一手引述**（新华日报《新知》2024-03；央视/中国青年报专家解读节目 2024-04；腾讯新闻 2024-01）：

> 「就'AI 复活'服务而言，超级头脑会要求客户在申请技术服务项目时**提供与逝者的关系证明及其死亡证明**，并在需求讨论过后**签署相关合同协议**。」

> 「超级头脑团队在进行相关业务时，如果要'复活'逝者，**必须由直系亲属提供能证明关系的材料**；而如果要'克隆'没有去世的人的数字人形象，**必须由本人现场进行声明**。」

创始人张泽伟原话（央视采访）：

> 「会从他的一个授权，对授权和关系证明上去做证明跟约束，比如说你要给自己做，你必须自己授权给我们。你要给别人做，你需要得到别人的授权。**如果是别人已经去世了，你必须要得到逝者的直系亲属的授权来做。**」

🔴 **这里有一个对 Echo 极其重要的机制差异，请单独读**：

超级头脑核验的**不是"这张脸是谁"，而是"你和这张脸是什么关系"**。

- 身份核验（1:N 人脸比对）→ 踩 PIPL 28 条，见 §3
- **关系核验**（关系证明 + 死亡证明）→ **完全不需要人脸识别**

这是一条绕开 1:N 悖论的**独立路径**，而且它是**逝者复活品类的原生做法**，不是从数字人品类借来的。

🟡 **但要如实说明它的形态限制**：超级头脑是**人工定制服务**（媒体报道客单价数千元、截至 2024-01 服务约 600 个家庭），有客户经理、有需求讨论、有线下签合同。**关系证明是人工审的。** Echo 是自助 App，要把这套搬进 P0 的自助流程，需要解决：

- 什么材料算"关系证明"（户口本？出生证明？两人合影？）——**宠物场景下这一整套都无对应物**
- 谁来审（人工审不了量，机器审不了真伪）
- 审材料本身就是在收集**更敏感**的个人信息（户口本含全家身份证号），这会显著扩大 PIPL 处理面与泄露面，可能得不偿失

🔴 **P0 只做宠物，这条路在 P0 基本不可用**：宠物没有死亡证明，没有户口本，"关系证明"无法定义。**这一条应当明确写进裁定依据**——不是"Echo 选择不做关系核验"，而是"P0 的素材类型使关系核验无对象可核"。

#### 🟢 硅基智能

🟢 **一手引述**（21 世纪经济报道 2024-03，硅基智能团队回应记者）：

> 「合规性是从业者和企业必须严格遵守的原则。在该公司提供相关服务时，**会先确保已经获得本人或家属的授权**，保障用户的肖像权、隐私权等。公司对生成内容会进行严格的审核，确保不会产生误导公众或侵犯他人权益的情况。」

🔴 **这段话强度低于超级头脑**：只说"会先确保已经获得授权"，**未披露核验形式**。可能是审材料，也可能只是让客户签承诺。**不能作为"硅基智能做了实质核验"的证据。**

#### 🟢 一个必须知道的行业事实：授权书是这个品类的通行证

🟢 **一手（新华日报 2024-03）**：2024-03-28 李玟母亲发布律师声明，要求停止未经近亲属同意的"AI 复活李玟"短视频。而同一篇报道指出：

> 「在南京，一家名为'超级头脑'的信息技术有限公司**早在舆论风波之前便拿到了由李玟生前经纪公司及近亲属的授权书**，被授权'使用已故国际巨星李玟的形象和相关资料制作 AI 数字分身'。」

🔴 **这个对照极有说服力，建议直接给制作人看**：同一个逝者（李玟）、同一类技术、同一个时间窗口——

- **没有授权书**的网络用户 → 收到律师函，被要求立即停止
- **有授权书**的超级头脑 → 同一件事，合法经营

**区别只在有没有那张纸。** 这正是制作人说的"出事追溯有依据"。授权链条的**存在与可举证性**，而不是"平台有没有在上传时拦住你"，是这个品类的实际风险分界线。

#### 🟢 另一个必须知道的事实：地方在建数字人备案系统

🟢 **一手引述**（腾讯新闻 2024-01，北京理工大学翁冬冬）：

> 「北京朝阳区已经出台了**数字人备案系统**，目前正在试运行阶段，相关企业可以将自己生成的数字人拿去系统备案，**虽然不具备法律效应，但如果产生版权纠纷时，备案声明能够作为一个证据**。上海、广州等地区也在推动类似系统落地。」

🟡 **这是"留痕追溯"路线的官方背书信号**：地方政府建的机制，其功能定位就是**存证**——"不具备法律效应，但能作为证据"。这与制作人的直觉高度一致。

⬜ **未检索到**：这些备案系统 2024 年之后的进展、是否已正式运行、C 端产品能否接入。**建议单独立项跟进**——如果朝阳/上海的数字人备案系统已可接入，Echo 的"留痕"就能从"自家数据库里的一条记录"升级为"有第三方时间戳的存证"，举证强度差一个量级。

### 1.6 AI 换装 / 制服照类（证件照、军警制服）

🔴 **这一节是「③ 证件照/制服照」的直接答案，且证据强度最高（官媒实测）。**

#### 🟢 产品里实际发生的（一手：新华社"新华视点"记者实测，2025-10）

> 「记者在某社交平台上浏览到一些网友发布 AI 变装视频，通过视频下方小程序链接进入后，按要求上传三张本人面部清晰的照片；系统经过十几分钟的 AI 合成，便生成了军装变装视频。这期间，**平台和小程序并未要求上传身份证明信息，也没有给出不得将合成视频用于违法违规领域的提示**。」

> 「9 月 1 日起施行的《人工智能生成合成内容标识办法》要求 AI 合成内容必须明确标注，但记者在使用**多款** AI 换装应用后发现，**用户合成发布的视频并未标注**。」

🔴 **结论明确**：军警制服这一类，同业**既不拦、也不核验、连风险提示都没有，甚至连法定的标识义务都没落实**。这是"③ 证件照/制服照"最强的一手反证——规格原稿主张这一类锁死，同业实际做法与之相距最远。

#### 🟢 但这一类的滥用后果最重，且平台真的被罚了

🟢 **一手（新华社同篇，引国家网信办执法典型案例）**：

> 「国家网信办不久前发布了一起执法典型案例：浙江某公司运营的 App 提供视频换脸、图片换脸、照片舞动配音等图片处理功能，用户可对上传图片、视频中的人物进行换脸，但**未按规定落实安全评估要求**，相关深度合成内容也**未作显著标识**，存在较大安全风险，违反《互联网信息服务深度合成管理规定》《生成式人工智能服务管理暂行办法》等规定。**网信部门责令平台对该 App 予以下架处置。**」

🔴 **请精确读这个案例的违规事由**——这是本次调研对 Echo 资源分配最有价值的单条证据：

| 平台被罚的原因 | 是否与"上传端肖像核验"有关 |
| --- | --- |
| 未落实**安全评估** | ❌ 无关 |
| 深度合成内容**未作显著标识** | ❌ 无关 |

**罚的不是"你没核验被换脸人的授权"。** 一个提供任意换脸功能的 App 被下架，理由是**程序性合规缺失**（评估 + 标识），不是**实体性授权缺失**。

**使用者侧的处罚（🟢 一手，同篇 + 人民日报）**：

| 案例 | 行为 | 处理 |
| --- | --- | --- |
| 安徽黄山江某（2025-03） | AI 合成军装照 + 发布"经军委同意，任命我为黄山军分区司令员"虚假信息 | 公安机关**治安处罚** |
| 网友吴某 | 身着仿制警服、AI 合成元素制作"执法场景"视频并发布 | 公安机关**行政警告** |
| 江苏江阴路某（2025-04 判决） | 盗用网络军人训练照 → AI 合成自己头像到军装照 → 花钱伪造军官证 → 骗取 6 名女性信任，诈骗 3 万余元 | **冒充军人招摇撞骗罪，有期徒刑 2 年** |

🔴 **这三个案例的责任全部落在使用者身上，没有一个平台被连带追责。** 这一点与制作人的直觉一致，但见 §2.6 的反向警示——不能推广到所有情形。

#### 🟢 法律禁止得非常清楚，禁的是"用"，不是"生成工具"

🟢 **一手法条**：

- **《人民警察法》**：警用标志、制式服装、警械、证件为人民警察**专用**，其他个人和组织**不得持有和使用**。
- **《军服管理条例》**：现役军人及依法可穿着军服的人员应按规定着装；影视演艺人员因扮演军人穿军服的，**非拍摄演出时不得穿着**，且不得损害军队和军人形象。
- **《互联网军事信息传播管理办法》第十七条**（十部门联合印发，2025-03-01 施行）：

  > 「互联网军事信息服务提供者和用户使用语音社交、**深度合成**、区块链、**生成式人工智能**、加密及匿名通信工具、算法推荐、信息众筹平台等新技术新应用，或者利用卫星互联网制作、复制、发布、传播军事信息的，**不得损害人民军队形象**，不得制作、复制、发布、传播本办法第十三条至第十五条所列禁止性内容的信息。」

🔴 **注意第十七条的义务主体是「服务提供者**和**用户」——双方都受约束。** 这与《深度合成规定》第 14 条（平台只负责提示）不同：**涉军内容安全的义务是平台自己的，不能通过协议推给用户。**

🔴 **由此得出对第③类的分类结论——它必须被拆成两个不同的东西**：

| 子类 | 性质 | 义务主体 | 能否靠"用户承诺 + 留痕"过 |
| --- | --- | --- | --- |
| **军警制服 / 涉军内容** | **内容安全红线**（不是人格权） | 平台**和**用户，平台不能推卸 | 🔴 **不能**。《互联网军事信息传播管理办法》第 17 条直接约束提供者 |
| **证件照 / 证件版式**（身份证、警官证等版式） | 伪造证件、冒用身份 | 主要在使用者（伪造证件是使用者行为） | 🟡 部分可以，但生成"证件版式"本身风险高 |

🔴 **这是本次调研对规格原稿的一处实质修正意见**：第③类"证件照/制服照"在规格里被当成一个类别处理，但**军警制服和证件版式的义务主体不同**。军警制服是平台自己的红线（不可推给用户），证件版式更接近使用者责任。**建议在 `SPEC-subject-recognition-and-degradation.md` §5 的 `SR-4` 表中拆行。**

🟢 **一个技术上的好消息**（与规格 §5 表格第 128 行的判断一致）：制服与证件版式是**图像特征**，检测它们**不需要人脸识别**，不触发 §3 的 1:N 悖论。这一类是四类中**技术上最容易拦、法律上最必须拦**的一类。

### 1.7 公众人物 / 政治人物：矛盾结论并列登记

🔴 **按项目纪律，此处两个方向的结论并列，不择一。**

#### 结论 A：涉政侧**确实有硬拦**，通过第三方内容安全服务商实现

🟢 **一手：网易易盾 AI 内容审核产品页**（`dun.163.com/product/ai-content-censor`）：

> 「**政治敏感与暴恐扫描**：基于易盾 20 余年的安全数据积累，建立动态更新的权威敏感库。针对涉政错误表述、**禁忌人物**、非法旗帜、暴恐画面等提供'**零容忍**'级别的精准拦截。」

> 「**深度伪造（Deepfake）检测**：针对 AIGC 产生的数字人、仿真照片进行真伪鉴别。能够识别肉眼难辨的 AI 换脸、人声克隆（Voice Cloning）等风险。」

> 「内容纠错与严谨性辅助：提供错别字检测、语法错误纠正、**领袖人物头衔校对**等高阶功能。」

🟡 数美科技产品页列有场景标签：「AIGC 业务风控」「未成年人保护」「社交优质人像」。

🔴 **这是"涉政人物识别"在中国互联网的真实实现方式**：**不是每家平台自建人脸库，而是采购第三方内容安全服务商的"禁忌人物库"。** 这一点直接影响 §3 的 1:N 悖论解法。

#### 结论 B：**肖像**侧未找到任何一手证据证明有平台拦明星脸

如 §1.4 所述，"不要上传明星脸会被拦截"这个说法**只在第三方教程站出现**，没有任何官方说明、用户投诉截图、媒体实测支撑。同时 §1.1 妙鸭记者实测证明了陌生人照片可以顺利通过。

🔴 **两个结论并不真的矛盾，它们讲的是两件事**——建议制作人按这个框架理解：

| 维度 | 涉政人物 | 明星 / 一般公众人物 |
| --- | --- | --- |
| 风险性质 | **内容安全**（政治） | **民事侵权**（肖像权） |
| 后果 | App 下架、约谈、刑责 | 律师函、民事赔偿 |
| 拦截能力 | 🟢 **有**，第三方敏感库，"零容忍" | 🟡 存疑，无一手证据 |
| 谁在管 | 平台**必须**管（自己的红线） | 靠权利人举报 + 事后下架 |

**即：涉政被拦，是因为它是内容安全问题，不是因为它是肖像权问题。**

🔴 **对规格的修正意见**：`SR-4` 把"公众人物 / 政治人物"合成一行，但这两者的**风险性质、义务来源、可行技术手段、处置强度全部不同**。规格 §5 表格第 125 行已经注意到"可能涉政（性质从民事纠纷升为内容安全事件）"，本调研的证据支持**把这一行拆开**：

- **政治人物 / 涉政** → 内容安全红线，采购第三方敏感库（见 §3.3），**平台必须拦，不能靠用户承诺**
- **明星 / 一般公众人物** → 肖像权，同业无一手证据表明有事前拦，**可靠承诺 + 留痕 + 举报响应**

#### ⬜ 未检索到

- 第三方内容安全服务商的"禁忌人物库"是否覆盖**娱乐明星**，还是仅覆盖政治人物。**这个缺口直接决定拆行之后明星那一档有没有现成工具。**
- 服务商敏感库的**技术实现**（是 1:N 人脸比对，还是人脸特征哈希黑名单匹配）。这个区分对 §3 的责任外置论证是否成立至关重要。
- 采购该类服务时，**处理责任如何在委托方与受托方之间分配**（PIPL 第 21 条委托处理），是否真能实现"责任外置"。

### 1.8 第三方 IP 角色（著作权）——四类中唯一被法院判着拦的

🔴 **这一类是著作权/商标，不是人格权，性质与前三类不同，单独论证。**

#### 🟢 一手：广州互联网法院"奥特曼案"（2024-02 判决，全球首例 AIGC 平台侵权判决）

**案情**：被告运营 AI 绘画网站，用户输入"生成一个奥特曼"即生成与奥特曼形象相似的图片；输入"奥特曼融合美少女战士"生成拼接形象。该功能为**付费功能**（需购买会员或充值"算力"）。原告为圆谷株式会社在中国大陆的著作权独占被授权人。

**判决要点**：

1. **侵权成立**：生成图片"部分或完全复制了奥特曼作品这一美术形象的独创性表达，并在多个关键特征与作品具有极高的相似度，构成实质性相似"；生成含局部特征或特殊风格（如插画风）的图片构成违法"改编"。侵害**复制权和改编权**。

2. 🔴 **关键：被告已经做了关键词屏蔽，法院认为不够**：

   > 「AI 公司表示在应诉后已经采取关键词屏蔽措施，阻断网站生成奥特曼相关形象，当输入包含'奥特曼'的提示词，网站会弹出'您发送的信息包含不合规的内容'，无法生成图片。**然而，庭审中，在网站输入其他相关的关键词如'迪迦'，仍可生成与迪迦奥特曼复合型原图高度相似的图片。**」

3. 🔴 **法院给出的义务标准（本节最重要的一句）**：

   > 「防范程度应达到：**用户正常使用与奥特曼相关的提示词，不能生成与案涉奥特曼作品实质性相似的图片。**」

4. **平台其他注意义务**：建立投诉举报机制、**在用户服务协议中着重提示用户不得侵害他人著作权**（法院认定被告"欠缺此项提示"）、生成内容显著标识。

5. **训练数据删除请求被驳回**：因被告是 AIGC 服务提供者而非大模型开发者，未实际进行模型训练。

🟢 **相关案例（杭州，首例涉生成式 AI 平台侵害信息网络传播权案）**：原告诉请包括"停止提供奥特曼有关模型的训练和发布服务，并删除已有奥特曼训练模型、图片等全部物料和相关数据，对奥特曼及相关关键词**在全平台的未授权使用行为进行屏蔽**"。该平台支持用户**上传图片素材自训练模型并分享**。

🔴 **IP 类的结论，与前三类形成鲜明对比**：

| 问题 | 答案 |
| --- | --- |
| 同业是否硬拦 IP 角色 | 🟢 **是**，而且是被法院判决要求的 |
| "用户协议提示 + 事后删除"够不够 | 🟢 **不够**。奥特曼案被告有协议、应诉后加了关键词屏蔽，仍被判侵权 + 要求进一步技术措施 |
| 义务标准 | 🟢 **结果导向**：正常使用相关提示词**不能**生成实质性相似图片。这是**事前拦截**义务 |
| 为什么这一类不同 | 权利人是有组织的商业主体（圆谷/迪士尼），有法务、有独占被授权人、会批量取证起诉；被侵权即被诉 |

#### 🔴 一个必须给制作人指出的差异，否则会误判

奥特曼案的拦截点是**提示词 / 输出端**，不是**上传素材端**。而 Echo 的用户**不输入提示词，只上传照片**。

这意味着：

- 奥特曼案的判决**不能直接套用**到"上传端检测第三方 IP 角色"上——法院要求的是"输入提示词不能生成侵权图"，而 Echo 没有提示词这个环节
- 但**杭州案**涉及"用户**上传图片素材**自训练模型"，法院要求屏蔽，这一点**与 Echo 的形态更接近**
- Echo 真实的风险敞口是：用户上传一张手办 / 玩偶 / 动漫周边的照片，Echo 把它当"宠物"生成了衍生内容

🟡 **对 P0 的风险量级判断（这是推论，非检索结果，标明如此）**：Echo P0 只做宠物，用户上传第三方 IP 角色照片的**动机很弱**（他们上传的是自己死去的宠物的真实照片）。这一类在 P0 更可能是**误传 / 少量猎奇**，而非批量滥用。相对第①③类，这一类**在 P0 的优先级可能最低**——但它是四类中唯一有明确司法义务标准的，一旦发生，法律上的抗辩空间也最小。

⬜ **未检索到**：奥特曼案之后，即梦/可灵/通义万相等主流平台**在上传端**（而非提示词端）对第三方 IP 图像的检测做法。无任何公开技术披露。

## 第二章 法规：授权承诺 + 留痕能否替代事前拦截

🔴 **本章只谈法定义务，不谈同业做法。同业做法在第一章。**

### 2.1 《民法典》肖像权与声音权

🟢 **第一千零一十八条**：

> 自然人享有肖像权，有权依法制作、使用、公开或者许可他人使用自己的肖像。
> 肖像是通过影像、雕塑、绘画等方式在一定载体上所反映的**特定自然人可以被识别的外部形象**。

🟢 **第一千零一十九条**：

> 任何组织或者个人不得以丑化、污损，或者**利用信息技术手段伪造**等方式侵害他人的肖像权。**未经肖像权人同意，不得制作、使用、公开肖像权人的肖像**，但是法律另有规定的除外。

🔴 **两个必须注意的点**：

1. **「利用信息技术手段伪造」是 2020 年民法典新增的表述，直指深度合成。**
2. 🔴 **禁止的动作里包含「制作」**，不只是"使用"和"公开"。**这意味着"只生成不发布"也可能构成侵权。**

   这一点对 Echo 已裁定的形态有直接影响：规格已裁定"生成时偏向用户主动填写的意愿"。若用户把他人肖像标为"我有权使用"，Echo 据此生成——**即使内容从不发布，只在用户私域**，第 1019 条意义上的"制作"已经完成。留痕能证明"是用户主动声明的"，但不能让"制作"这个动作消失。

   🟡 **这不推翻已有裁定**（因为责任主体仍主要是使用者，见 §2.3），但它说明**"不发布就没事"是错的**，如果规格或文案里有这个假设，需要修正。

🟢 **第一千零二十条**（肖像权合理使用，五种情形）：个人学习/艺术欣赏/课堂教学/科学研究在必要范围内使用**已公开**的肖像；新闻报道不可避免；国家机关依法履职；展示特定公共环境不可避免；为维护公共利益或肖像权人合法权益。

🔴 **注意：这五项里没有一项能覆盖 Echo 的场景。** "情感慰藉"不属于任何一项合理使用。**Echo 不能主张肖像权合理使用抗辩。**

🟢 **第一千零二十三条**：

> 对姓名等的许可使用，参照适用肖像许可使用的有关规定。
> **对自然人声音的保护，参照适用肖像权保护的有关规定。**

🟡 **最高法法答网（第十九批，人格权专题）** 明确：第 1018 条（权能）、1019 条（禁止行为）、1020 条（合理使用）、1021–1022 条（商业利用）**均可参照适用于声音权益**。

🟡 但"参照"不是"直接适用"，有一处重要差异：**单纯模仿他人声音（如电视台"模仿秀"）不宜认定为侵权**；但以侮辱性或违背公序良俗的方式模仿或伪造，则可适用肖像权规则禁止。

🟢 **第九百九十四条（逝者，Echo 的核心条款）**：

> 死者的姓名、肖像、名誉、荣誉、隐私、遗体等受到侵害的，其配偶、子女、父母有权依法请求行为人承担民事责任；死者没有配偶、子女且父母已经死亡的，其他近亲属有权依法请求行为人承担民事责任。

🔴 **这条对 Echo 的意义（虽不在本次四类问题内，但必须记录）**：逝者的肖像权益由**近亲属**行使。Echo 的用户如果**不是**逝者的近亲属（如朋友、远亲、前伴侣），即使他"主动声明我有权使用"，也**不构成有效授权**——授权权限本身不在他手上。

🟡 专家意见（北航赵精武，央视）：「如果没有经过死者近亲属同意的话，那么擅自利用 AI 技术复活死者的行为就属于非常典型的侵权行为。」

🔴 **建议**：这构成一个**第五类敏感情形**（"上传者与逝者的关系"），规格的四类里没有它，但它对 Echo 的相关性高于"第三方 IP 角色"。**建议提请 `Q-6` 一并考虑。** P0 只做宠物可暂时回避（宠物是财产，不是人格权主体），但 P1 开放人像时这一条会立刻成为主要风险。

### 2.2 《个人信息保护法》第 28、29、31 条

🟢 **第二十八条**：

> 敏感个人信息是一旦泄露或者非法使用，容易导致自然人的人格尊严受到侵害或者人身、财产安全受到危害的个人信息，包括**生物识别**、宗教信仰、特定身份、医疗健康、金融账户、行踪轨迹等信息，以及**不满十四周岁未成年人的个人信息**。
>
> 只有在具有**特定的目的和充分的必要性**，并采取**严格保护措施**的情形下，个人信息处理者方可处理敏感个人信息。

🟢 **第二十九条**：

> 处理敏感个人信息应当取得个人的**单独同意**；法律、行政法规规定处理敏感个人信息应当取得书面同意的，从其规定。

🟢 **第三十一条**：

> 个人信息处理者处理**不满十四周岁**未成年人个人信息的，应当取得未成年人的**父母或者其他监护人的同意**。
> 个人信息处理者处理不满十四周岁未成年人个人信息的，应当**制定专门的个人信息处理规则**。

🔴 **对第②类（未成年人为素材主体）的法律结论**：

1. 不满十四周岁未成年人的个人信息，**无论内容为何**，一律属敏感个人信息（🟡 学界通说，见宁园《敏感个人信息的法律基准与范畴界定》：「不论个人信息内容为何，只要信息主体为未成年人，即为敏感个人信息」）。
2. 处理需**监护人同意**（第 31 条），且需**制定专门处理规则**（第 31 条第 2 款）。
3. 🔴 **第 31 条的义务主体是「个人信息处理者」，即 Echo 自己**，不是"提示使用者去取得"。这与《深度合成规定》第 14 条的结构**不同**。

🔴 **所以第②类在法律上的位置比第①类更硬**：

| 类别 | 义务条款 | 义务主体 |
| --- | --- | --- |
| 一般他人肖像 | 深度合成规定 §14 II | **提示**使用者去取得（平台义务止于提示） |
| **不满 14 周岁未成年人** | **PIPL §31** | **平台自己**取得监护人同意 + 制定专门规则 |

🔴 **但这里有一个规格必须面对的、无解的技术困境**——它和 §3 的 1:N 悖论是同构的：

PIPL 第 31 条的门槛是"**不满十四周岁**"，这是一个**精确年龄**。而机器视觉能做的是"疑似未成年人"这种**模糊判断**，且：

- 判 14 岁这个界线，机器错误率极高（13 岁与 15 岁在图像上几乎不可分）
- 🔴 **要精确判断年龄，需要处理面部特征做年龄估计——这本身就是对"生物识别信息"的处理，同样落 PIPL 第 28 条**
- 🔴 更糟的是：**Echo 判定"这是个小孩"这个动作本身，就是在生成一条关于该儿童的敏感个人信息标签**，而 Echo 恰恰**没有**该儿童监护人的同意

**即：为了履行第 31 条而做的年龄检测，其本身可能违反第 28/29 条。** 这与 §3 的公众人物悖论是同一个结构，规格 §9 `Q-5` 只登记了公众人物那一个，**建议把未成年人这一个也登记进去**——它的严重性不低，而且第 31 条的义务主体是平台自己，跑不掉。

⬜ **未检索到**：任何中国大陆产品对"素材主体是未成年人"做事前检测的一手证据。§1.4 三家协议的做法（推定已获授权）是目前找到的**唯一**同业处理方式。

### 2.3 🔴 《互联网信息服务深度合成管理规定》第 14 条——义务主体的确定回答

#### 2.3.1 原文（🟢 一手，中国政府网 / 国务院公报 / 工信部三处互校，文字一致）

**第十四条**：

> 深度合成服务提供者和技术支持者应当加强训练数据管理，采取必要措施保障训练数据安全；训练数据包含个人信息的，应当遵守个人信息保护的有关规定。
>
> 深度合成服务提供者和技术支持者提供人脸、人声等生物识别信息编辑功能的，**应当提示深度合成服务使用者依法告知被编辑的个人，并取得其单独同意。**

#### 2.3.2 句法拆解：义务主体是谁

| 成分 | 内容 |
| --- | --- |
| **主语** | 深度合成服务提供者和技术支持者 |
| **谓语** | 应当**提示** |
| **提示的对象** | 深度合成服务使用者 |
| **提示的内容** | 「依法告知被编辑的个人，并取得其单独同意」 |

🔴 **结论明确**：

- **平台的法定义务 = 提示。** 完成一次有效提示，第 14 条第 2 款的义务即已履行。
- **「取得单独同意」的义务主体 = 使用者。** 平台不承担代为取得同意的义务，**也不承担核验使用者是否真的取得了同意的义务**。
- 条文中**没有任何**关于"核验""审查""拦截"的表述。

#### 2.3.3 🔴 两个不能顺着这个结论滑到底的地方

**（一）第 10 条另有独立的审核义务**

🟢 **第十条**：

> 深度合成服务提供者应当加强深度合成内容管理，**采取技术或者人工方式对深度合成服务使用者的输入数据和合成结果进行审核**。

🔴 **注意：第 10 条的义务主体是平台自己，且明确要求审核「输入数据」。** 所以准确的表述是：

- 第 14 条不要求平台核验**授权**
- 第 10 条要求平台审核**输入数据**（内容安全审核）

这两者不是一回事，但**边界模糊**。规格 §5.5 已警告"超出第 10 条审核义务的必需范围"会失去庇护，这个判断方向正确：**第 10 条是"内容安全审核"的授权依据，不是"身份识别"的授权依据。** 用第 10 条为 1:N 人脸识别背书，是把"审核"扩张解释为"识别"，站不住。

**（二）平台还有第 6、7、12、16、17 条的一整套独立义务**

🟢 相关条文：

- **第六条**：任何组织和个人不得利用深度合成服务制作、复制、发布、传播法律、行政法规禁止的信息，不得……侵犯他人合法权益等法律、行政法规禁止的活动。
- **第七条**：深度合成服务提供者应当落实信息安全主体责任，建立健全用户注册、算法机制机理审核、科技伦理审查、信息发布审核、数据安全、个人信息保护、反电信网络诈骗、应急处置等管理制度。
- **第十二条**：应当设置便捷的用户申诉和公众投诉、举报入口，公布处理流程和反馈时限。
- **第十六条**：应当对生成或编辑的信息内容添加**不影响用户使用的标识**，并**依照规定保存日志信息**。
- **第十七条**：可能导致公众混淆或误认的，应当在**合理位置、区域进行显著标识**，向公众提示深度合成情况。第一款第（三）项明确包括「人脸生成、人脸替换、人脸操控、姿态操控等人物图像、视频生成或者显著改变个人身份特征的编辑服务」。

🔴 **第 16 条的「保存日志信息」是"留痕"路线的法定依据。** 制作人的"留痕追溯"直觉在这里有明确的法条支撑——法规**要求**平台留日志，这正是"出事追溯有依据"的机制。

#### 2.3.4 同业怎么落地这条"提示"义务（🟢 一手，回到第一章的证据）

**百度曦灵**（几乎是把法条抄进协议）：

> 「对于您使用我们提供的克隆功能，**所编辑的非您本人的人脸、人声等生物识别信息，您应依法告知被编辑的个人，并取得其单独同意**，否则您承担所有不利后果。」

**百度智能云声音复刻协议 4.1**（把结论说到底）：

> 「……您确认已……取得了信息主体合法、充分且明确的同意（涉及敏感个人信息的，还需另行获得信息主体的单独同意）……**百度智能云无需再另行获得任何主体的授权或许可。**」

**腾讯云**（同一条法条，走的是另一条路）：

> 「**根据《互联网信息服务深度合成管理规定》规定**，需要采取相应措施确保已取得用户合法授权同意。客户取得用户授权后，方可……提供授权材料。」

🔴 **同一部法规、同一条款，两个头部厂商的落地强度差一个量级**：

| 厂商 | 落地方式 | 摩擦成本 |
| --- | --- | --- |
| 百度（曦灵/声音复刻） | 协议里写一句话，明确说"我方无需另行获得授权" | 零 |
| 腾讯（数智人，重档） | 要求提交授权书 + 3 工作日人工审核 | 高 |
| 腾讯（数智人，轻档 `IMAGE_PHOTO`/`ZERO_SHOT_VOICE`） | 不要授权书 | 零 |

**这个差异本身就是答案**：法条只要求"提示"，所以"写一句话"是**合规下限**；腾讯的授权书是**自愿加码**（商业客户、企业场景、可追偿对象明确，加码的边际成本可承受）。

🔴 **对 Echo 的推论**：Echo 做"提示 + 留痕"就已经满足第 14 条第 2 款。做授权书核验是**超出法定要求的自愿加码**，其成本收益应按商业逻辑而非合规逻辑来算。**这一条支持制作人的方向。**

### 2.4 《生成式人工智能服务管理暂行办法》

🟢 **第四条第（四）项**：

> 尊重他人合法权益，不得危害他人身心健康，**不得侵害他人肖像权、名誉权、荣誉权、隐私权和个人信息权益**；

🔴 **注意第四条的开头是「提供**和**使用生成式人工智能服务，应当……」——义务主体是提供者和使用者双方。** 这与第 14 条（平台只提示）不同，此处平台不能完全推卸。但第四条是**原则性条款**，没有规定具体的核验手段。

🟢 **第九条**：

> 提供者应当依法承担**网络信息内容生产者责任**，履行网络信息安全义务。涉及个人信息的，依法承担**个人信息处理者责任**，履行个人信息保护义务。
> 提供者应当与注册其服务的生成式人工智能服务使用者签订**服务协议**，明确双方权利义务。

🔴 **第九条第 2 款是"用协议分配责任"的法定依据。** 法规明确要求平台与使用者签协议"明确双方权利义务"——这正是同业把授权责任写进协议的合法性基础。**这一条也支持制作人的方向。**

🟢 **第十四条**：

> 提供者发现违法内容的，应当及时采取**停止生成、停止传输、消除**等处置措施，采取模型优化训练等措施进行整改，并向有关主管部门报告。
> 提供者发现使用者利用生成式人工智能服务从事违法活动的，应当依法依约采取**警示、限制功能、暂停或者终止**向其提供服务等处置措施，**保存有关记录**，并向有关主管部门报告。

🔴 **这一条是"事后处置 + 留痕"路线最直接的法条支撑，而且它规定的动作序列恰好就是制作人描述的那套机制**：

发现 → 停止生成/传输/消除 → 对使用者警示/限制功能/暂停/终止 → **保存记录** → 报告主管部门

**法规的默认假设就是"事后发现、事后处置、保存记录"**，而不是"事前逐条核验、拦住不让用"。这是第二章里对制作人直觉最有力的单条支撑。

🟢 **第十条**（与 Echo 相关）：

> 提供者应当明确并公开其服务的适用人群、场合、用途，指导使用者科学理性认识和依法使用生成式人工智能技术，采取有效措施**防范未成年人用户过度依赖或者沉迷**生成式人工智能服务。

🔴 注意这里的"未成年人"是指**使用者是未成年人**，与第②类（素材主体是未成年人）**不是一回事**。规格已正确区分，此处再次确认。

### 2.5 《人工智能生成合成内容标识办法》（2025-09-01 施行）

🟢 **第五条**：

> 服务提供者应当按照《互联网信息服务深度合成管理规定》第十六条的规定，在生成合成内容的**文件元数据中添加隐式标识**，隐式标识包含生成合成内容属性信息、服务提供者名称或者编码、内容编号等制作要素信息。

🟢 服务提供者提供生成合成内容下载、复制、导出等功能时，应当确保文件中含有满足要求的**显式标识**。

🟢 **任何组织和个人不得恶意删除、篡改、伪造、隐匿本办法规定的生成合成内容标识**，不得为他人实施上述恶意行为提供工具或者服务。

🔴 **这是"留痕"的另一层，而且是强制的**：隐式标识里的"内容编号"本身就是一个**可追溯锚点**。法规不仅允许留痕，而且**强制要求把追溯信息嵌进文件本身**。

🔴 **这也是 §1.6 那个 App 被下架的两条事由之一。这是 Echo 必须做对的事，优先级高于四类拦截。**

#### 关于可灵那条"视为已获得权利人同意"的推定条款

🔴 **按纪律并列登记两种判断，不择一**：

| 判断 A：条款可能无效 | 判断 B：条款有实际作用 |
| --- | --- |
| 这是**格式条款**。上海星瀚吴晴霞（南都，评妙鸭）：「原协议中的强制许可条款，排除了用户的选择权，涉嫌利用其信息、市场地位等优势，迫使用户接受未实际磋商的合同条件而构成霸王条款。」 | 该条款不是"用户授权平台"，而是"用户向平台声明其已获第三方授权"，**性质是陈述与保证（representation & warranty）**，不是许可授予 |
| 🔴 更关键：**未成年人的肖像权属于该未成年人本人（及其监护人），上传者根本无权处分。** 用户"视为已获同意"不能替代真实的监护人同意——**无权处分的人做的声明，不产生权利** | 它的作用不在于"取得授权"，而在于**分配违约责任 + 建立追偿依据**。即使不能对抗真正的权利人，也能在平台与用户之间成立 |
| 由此：该条款**不能对抗真正的权利人**（被侵权的未成年人及其监护人），平台仍可能被诉 | 由此：它确实实现了制作人说的"出事追溯有依据" |

🔴 **两个判断可以同时成立，这才是完整图景**：该条款**对外**（对被侵权人）几乎无效，**对内**（对上传用户）有效。它把平台的责任从"侵权赔偿"转化为"侵权赔偿 + 向用户追偿"，**降低净损失，但不消除被诉风险**。

**这正是"留痕"路线的真实功效边界，建议原样告知制作人**：留痕不能让 Echo 不被起诉，只能让 Echo 被起诉后有东西可以举证、有人可以追偿。

### 2.6 🔴 一个必须给制作人的反向警示：Echo 在责任链上的位置很差

#### 🟢 一手：殷某桢诉北京某智能科技公司等人格权纠纷案（全国首例 AI 声音侵权案）

北京互联网法院 2024-04-23 一审判决，案号 (2023)京0491民初12142号，**已入库参考案例**（入库编号 2025-07-2-474-001）。

**案情链条**：

1. 配音师殷某接受**被告二**某文化传媒公司委托录制录音制品，被告二为录音制品**著作权人**
2. 被告二与**被告三**某软件公司签《数据授权使用协议》，提供录音数据，并提供了一份**非殷某本人签字的《数据授权书》**
3. 被告三仅以殷某一人的录音作素材，**做 AI 化处理**，生成文本转语音产品
4. 该产品在**被告四**运营的云服务平台对外出售
5. **被告一**（运营 App 的智能科技公司）经**被告五**（采购中介）向被告三下单采购，以 **API 形式直接调取**在其平台使用

**判决的责任分配**（🔴 这张表是本节的核心）：

| 被告 | 角色 | 责任 |
| --- | --- | --- |
| 被告二 | 录音著作权人，**提供了无效授权** | **赔礼道歉 + 赔偿 25 万元** |
| 被告三 | **做 AI 化处理的技术方** | **赔礼道歉 + 赔偿 25 万元**（与被告二共同侵权） |
| 被告一 | 产品实际使用者 / API 调用方 | 赔礼道歉，**不担赔偿**（合法采购抗辩不成立但无主观过错） |
| 被告四 | 云服务平台 | **无主观过错，不担责** |
| 被告五 | 采购中介 | **无主观过错，不担责** |

**法院对授权的认定**：

> 「被告二某文化公司对录音制品享有著作权等权利，但**不包括授权他人对殷某桢声音进行 AI 化使用的权利**。根据已查明事实，《数据授权书》**并非殷某桢本人签署**，因此……授权被告三某软件公司 AI 化使用原告声音的行为**无合法权利来源**。」

🔴 **这个案子对 Echo 有三条直接教训，每一条都在收窄"承诺 + 留痕"的安全边界**：

**教训一：Echo 在责任链上占的是要赔钱的位置。**

判决中免责的是"云服务商"和"采购中介"——纯通道角色。**赔钱的是"做 AI 化处理的技术方"（被告三）。** Echo 自己做生成，**结构上就是被告三的位置**，不是被告四的位置。

🔴 所以**不能**从"平台一般不担责"推出"Echo 不担责"。前一章 §1.6 那三个军警案例里平台没被追责，是因为那些平台的角色更接近"提供工具"；而 Echo 是**自己执行生成动作**的那一方。

**教训二：拿到一张"授权书"不等于免责，法院会审授权链条是否真实。**

被告三拿到了一份**书面授权书**，但因为不是权利人本人签的，法院直接认定"无合法权利来源"。

🔴 **推论**：如果 Echo 走"要求用户提交授权材料"的路，**收到材料本身不产生免责效果**。法院会问的是"这个授权链条真实吗"。一份用户随手填的、无从核验的授权声明，在诉讼中的作用接近于零——**它的价值在追偿（对内），不在抗辩（对外）**。这与 §2.5 的结论一致。

**教训三：上游的合法授权，不覆盖"AI 化使用"这个新用途。**

被告二**确实**是录音制品的著作权人，**确实**有权授权他人使用该录音。但法院认定这个授权**不包括** AI 化使用。

🔴 **对 Echo 的推论**：这对 Echo 的**逝者场景**是直接的警示。假设用户是逝者的合法继承人，继承了照片视频的**所有权/著作权**——按本案逻辑，**这不等于有权授权把逝者的肖像/声音做 AI 化处理**。人格权益（肖像权、声音权益）与财产权益（照片的所有权、著作权）是**两条线**，前者由近亲属依第 994 条行使，不随物的所有权转移。

🔴 **这条推论应当提请规格线注意**：它意味着 Echo 的授权设计不能建立在"用户拥有这些素材"之上，必须建立在"用户是有权行使该逝者人格权益的近亲属"之上。P0 只做宠物可回避（宠物无人格权），**但这是 P1 的一道硬门槛**。

### 2.7 涉政 / 军警 / 证件的内容安全强制拦截要求

见 §1.6 的法条部分。归纳：

| 类别 | 法条 | 义务主体 | 能否推给用户 |
| --- | --- | --- | --- |
| 涉军 / 军队形象 | 《互联网军事信息传播管理办法》**第 17 条**（2025-03-01 施行） | 提供者**和**用户 | 🔴 **不能** |
| 警用标志 / 制服 / 证件 | 《人民警察法》 | 任何个人和组织不得持有和使用 | — |
| 军服 | 《军服管理条例》 | 着装人 | — |
| 一般违法内容 | 《生成式人工智能服务管理暂行办法》第 4 条第（一）项、第 14 条 | 提供和使用双方 | 🔴 **不能** |
| 深度合成输入数据审核 | 《深度合成规定》**第 10 条** | 提供者 | 🔴 **不能** |

🔴 **结论：涉政、涉军这一类的义务在法条上明确落在平台自己身上，与《深度合成规定》第 14 条（平台只需提示）的结构不同。这一类不能靠"用户承诺 + 留痕"过。**

🟢 **同时**，这一类**在技术上不需要人脸识别**：制服、证件版式是图像特征。所以它是四类中**唯一"法律上必须拦、技术上也拦得起"**的一类。

### 2.8 🔴 一部本次调研意外发现的、对 Echo 直接适用的新规

## 第三章 🔴 1:N 悖论：同业怎么解的

### 3.1 悖论的准确表述

规格 §7.3 / §9 `Q-5` 的表述是准确的，此处用法条把它钉死：

> 为了保护公众人物肖像权而做的**检测**，其本身可能是**更重的个人信息处理行为**。

**法条依据**（🟢《人脸识别技术应用安全管理办法》第十九条，2025-06-01 施行）：

> （三）**人脸识别技术**，是指**以人脸信息作为识别个体身份**的个体生物特征识别技术。
> （五）**验证个人身份**，是指通过收集获得的人脸信息与信息系统存储的**特定**人脸信息进行"**一对一**"比对，确认和核对两者是否为同一人。
> （六）**辨识特定个人**，是指通过收集获得的人脸信息与信息系统存储的**特定范围内**人脸信息进行"**一对多**"比对，识别具有特定身份的个人。

🔴 **"判断这张脸是不是某个公众人物"精确落在第（六）项「辨识特定个人」上**：与"特定范围内人脸信息"（公众人物库）做"一对多"比对，识别"具有特定身份的个人"。

**这意味着做公众人物识别会触发**：

| 义务 | 条款 |
| --- | --- |
| 特定目的 + 充分必要性 + 严格保护措施 | PIPL §28 II |
| **单独同意** | PIPL §29 |
| 告知处理必要性及对个人权益的影响 | PIPL §30；人脸办法 §5 |
| **事前个人信息保护影响评估**（PIA）+ 记录处理情况 | 人脸办法 §9 |
| 人脸信息**存储于人脸识别设备内，不得通过互联网对外传输**（除法律另有规定或取得单独同意） | 人脸办法 §8 |
| 存储量达 **10 万人**时向省级以上网信部门**备案** | 人脸办法 §15 |
| 鼓励优先使用**国家人口基础信息库、国家网络身份认证公共服务** | 人脸办法（答记者问） |

🔴 **注意第 8 条对 Echo 是致命的**：人脸信息应存储于人脸识别设备内、不得通过互联网对外传输。Echo 是云端服务，素材必然上传。要合规就得取得**每一个被检测者的单独同意**——而被检测的公众人物**当然不会**给 Echo 单独同意。

**逻辑闭环**：为了保护公众人物的肖像权而检测他，需要先取得他的单独同意；取不到，检测本身就违法。**这个悖论在"自建人脸库做 1:N"这条路上是无解的。规格 §9 `Q-5` 选项 B 的判断正确。**

### 3.2 解法一：只做检测不做识别（🟢 有法条与律所支撑，Echo 可用）

🟢 **法条依据**：《人脸识别办法》第十九条第（三）项的定义中，"人脸识别技术"的构成要件包含 **"以人脸信息作为识别个体身份"** 这一目的要素。

🟡 **律所解读**（环球律师事务所，2025-03-25，`glo.com.cn/Content/2025/03-25/1349350055.html`）：

> 「'人脸识别技术'：是以人脸信息识别个体身份的个体生物特征识别技术。**如处理活动如不以识别为目的，则不属于《管理办法》所规定的'人脸识别技术'。**」

同文另指出，正式稿相较征求意见稿**删除了**"提供人脸识别技术产品或者服务"的情形，「即排除了未应用该技术处理人脸信息活动的适用……使监管能够聚焦于'应用该技术处理人脸信息'的情形」。

🔴 **结论：规格 §7.3 的技术选型（"必须只做检测、不做识别"）在法律上是站得住的，而且有律所文章可引。**

**能力边界必须诚实说明**：

| 能做（不落《人脸办法》） | 不能做（落《人脸办法》） |
| --- | --- |
| 画面里有没有人脸 | 这张脸是谁 |
| 主体是动物还是人 | 这张脸是不是公众人物 |
| 有没有制服 / 证件版式（图像特征，非人脸） | 这张脸多少岁（🔴 见 §2.2，年龄估计仍是对生物特征的处理） |

🔴 **由此产生的能力上限，必须写进裁定**：

- 第①类（公众人物）**在不做 1:N 的前提下判不出来**。规格 §9 `Q-5` 已认识到这点，正确。
- 第②类（未成年人）**同样判不出来**，而且理由更硬（14 岁精确门槛 + 年龄估计本身是生物特征处理）。🔴 **规格 §9 只登记了 `Q-5`（公众人物），建议把未成年人这一项也登记为独立开放问题。**
- 第③类（制服/证件）**判得出来**，因为不依赖人脸。
- 第④类（IP 角色）**判得出来**（图像相似度/特征匹配，不是人脸），但需另一套能力。

🔴 **注意这个分布的含义**：四类里，**技术上判得出来的正好是不涉及人格权的两类（③④），判不出来的正好是涉及人格权的两类（①②）。** 规格原稿把四类打包"锁死不许用户改"，但其中两类**根本无法可靠触发**——锁死一个判不出来的类别，等于写了一条纸面规则。这与规格 §9 `Q-5` 选项 A 的顾虑一致。

### 3.3 解法二：责任外置给第三方内容安全服务商（🟡 同业主流，Echo 部分可用）

🟢 **一手证据**：网易易盾提供"政治敏感与暴恐扫描……**禁忌人物**……零容忍级别的精准拦截"（见 §1.7）。数美科技提供 AIGC 业务风控、未成年人保护等场景标签。

🔴 **这是中国互联网"涉政人物识别"的实际实现方式**：绝大多数平台**不自建**人脸库，而是采购第三方内容安全服务商的敏感库。

**这条路的合规意义**：

| 自建 1:N 人脸库 | 采购第三方内容安全服务 |
| --- | --- |
| Echo 是人脸信息处理者，全套 PIPL 28/29/30 + 人脸办法义务 | Echo 是**委托方**，服务商是受托处理方（PIPL §21） |
| 需自己做 PIA、备案（10 万人门槛）、承担泄露风险 | 服务商已有资质（数美通过中国信通院内容安全解决方案标准认证、泰尔实验室检测） |
| 处理面、泄露面全在 Echo | Echo 不落地人脸库 |

🔴 **但必须并列登记这条路的三个未解问题**：

1. ⬜ **PIPL 第 21 条的委托处理并不免除委托方责任。** 委托方仍须对处理目的、方式负责，并监督受托方。"责任外置"是**风险分担**，不是**责任消灭**。⬜ 未检索到司法案例明确采购内容安全服务后委托方的责任边界。
2. ⬜ **服务商的技术实现未知**。如果服务商内部做的就是 1:N 人脸比对，那么"处理行为"客观上仍然发生了，只是执行主体变了。这是否改变**法律定性**，未检索到明确依据。
3. ⬜ **敏感库的覆盖范围未知**。易盾文案说的是"**禁忌人物**"和"**领袖人物**头衔校对"——语义指向**政治人物**。是否覆盖娱乐明星，未检索到。

🔴 **对 Echo 的可用性判断**：

- **涉政人物** → 🟢 这条路可用，而且是同业主流。且因为涉政是内容安全红线（§2.7，平台不能推给用户），**Echo 大概率必须走这条路**。
- **娱乐明星 / 一般公众人物** → 🟡 这条路能否覆盖未知（缺口 3）。若覆盖，则搭车解决；若不覆盖，则回到"无技术手段"，只能靠承诺 + 留痕 + 举报响应。

### 3.4 解法三：验"在场"不验"身份"（🟢 同业最优范式，🔴 但 Echo 用不了）

见 §1.3（钉钉本人念指定文案）与 §1.4（即梦念数字转头点头）。

**这条路的精妙之处**：

| 它验证了什么 | 它没做什么 |
| --- | --- |
| 镜头前有一个活人在配合（活体） | ❌ 不查任何人脸库 |
| 说话的这张脸就是要被克隆的脸（1:1 自比，不查库） | ❌ 不做"这张脸是谁"的判断 |
| 本人亲口做出授权表示，可回放、带面部（强举证） | ❌ 不触发《人脸办法》第（六）项"辨识特定个人" |

🟢 **它同时满足了制作人的直觉（留痕追溯）和规格的顾虑（不做身份识别）。这是本次调研找到的最优同业范式。**

🔴 **但 Echo 结构性地用不了这条路**，理由必须说清楚，不能给制作人错误的希望：

- Echo 的素材主体是**已故的宠物 / 逝者**，**定义上无法出镜配合活体检测**
- P0 只做宠物，宠物即使活着也无法"念指定文案"
- 这是 Echo 与**全部**数字人同业的结构性差异：数字人产品的被克隆者是活人且在场，Echo 的被克隆对象已经死了

🔴 **这个差异的后果，应当进入 `Q-6` 的选项表**：

同业的核验强度谱系是：

```
零核验（协议承诺）  →  活体/在场性验证  →  授权书+人工审核  →  关系证明+死亡证明
     ↑                      ↑                                        ↑
  Echo 可用          🔴 Echo 不可用                          🔴 P0 无对象可核
                    （主体已故，无法出镜）                （宠物无死亡证明/户口本）
```

**中间那两档对 Echo 都不可用。** 所以 Echo 的实际选择空间比同业窄得多——**不是"Echo 选择了最弱的方案"，而是"更强的方案在 Echo 的场景里没有实施对象"。** 这一点在裁定文档里应当明确写出，否则会被误读为 Echo 在合规上偷懒。

### 3.5 综合：Echo 的可行组合

| 类别 | 技术上能否判（不踩 PIPL 28） | 法律是否强制平台拦 | 建议路径 |
| --- | --- | --- | --- |
| 政治人物 / 涉政 | 🟡 自己判不了；采购第三方敏感库可判 | 🟢 **是**（内容安全，平台义务，见 §2.7） | 采购第三方内容安全服务（§3.3） |
| 明星 / 一般公众人物 | 🔴 **判不了**（1:N 悖论，§3.1） | ❌ 无强制事前拦要求 | 承诺 + 留痕 + 举报响应 |
| 未成年人为素材主体 | 🔴 **判不了**（年龄估计本身是生物特征处理，§2.2） | 🟡 PIPL §31 要求平台取得监护人同意，但**技术上无法识别谁是未成年人** | 🔴 **无解，需专门裁定**（见下） |
| 证件照 / 制服照 | 🟢 **能判**（图像特征，非人脸） | 🟢 **是**（军警：军事信息办法 §17，平台义务） | 事前检测 + 拦截 |
| 第三方 IP 角色 | 🟢 **能判**（图像相似度，非人脸） | 🟢 **是**（奥特曼案司法标准，§1.8） | 事前检测 + 拦截，但注意 Echo 无提示词环节 |

🔴 **第②类（未成年人）是本次调研发现的真正死结，必须单独提请裁定**：

- 法律要求最硬（PIPL §31，义务主体是平台自己，不是"提示使用者"）
- 技术上判不出来（14 岁精确门槛；且年龄估计本身触发 PIPL §28）
- 同业唯一做法是协议推定（可灵/即梦/剪映措辞雷同），而该推定对真正的权利人**无效**（§2.5）
- 🔴 **即：这一类既不能拦（判不出来），又不能靠承诺过（推定条款对外无效，且义务主体是平台自己）**

🟡 **P0 的缓解因素**：P0 只做宠物。素材主体是未成年人的情形应当**罕见**（用户上传的是死去的宠物的照片）。但"合影里有小孩"是**高频**情形——用户的宠物照片里出现自家孩子是极自然的事。

🔴 **建议给 `Q-6` 的具体提问**：Echo 对"素材主体是未成年人"这一类，是否接受"技术上无法识别、法律上义务在平台、同业做法对外无效"这个三重困境，并明确选择一个**已知有缺口**的方案？这个选择应当被显式记录为**已知风险敞口**，而不是被"锁死不许用户改"这条纸面规则掩盖过去。

### 4.3 本文方法论上的限制（🔴 请连同结论一起读）

1. **未做任何产品实测。** 无账号、未跑浏览器自动化（按委托要求）。所有"产品里实际发生的"证据均来自**他人**的实测报道（记者、律所、评测），最新的一手实测是新华社 2025-10 的制服照那篇。**产品行为可能已变化。**
2. **同业协议为检索时点版本。** 妙鸭 2023 年 3 天内改过两版协议——**这类协议变动频繁**，引用前应重新核对。
3. **"未找到证据"≠"证据不存在"。** 尤其第 20、21 条：本文对"法规未强制事前拦"的判断建立在**未找到相反规定**之上。这是检索的局限，不是确证。
4. **弱证据已隔离但未剔除。** §1.4 的 🔴 标注内容（可灵"图像哈希+声纹库双重校验"）**极可能是 AI 生成的编造**，登记它只是为了说明"网络上流传这种说法"，**不得引用**。
5. **第三章的部分推论是本文的分析，不是检索结果**：§3.4 "Echo 用不了活体验证"、§3.5 的组合表、§2.6 教训三对逝者场景的推广——这些是从一手材料推出的**论证**，标注为推论。一手材料本身在各节已标 🟢。
