## 0. 概述（读完这一节等于拿到全部结论）

### 0.1 方案核实：**方向成立，但前提有一处是反的，且落地必须改两行代码**

被核实的方案：低置信度时预填「说不清」，用户不改就自然落 `L1`；`SR-D1` 的触发条件改为「素材置信度低 **且** 用户未改动预填值」。

| # | 结论 |
|---|---|
| **1** | 🔴 **「现在已经是预填形态」这个前提，在低置信度那条路径上恰恰不成立。** 高置信度（`subjects.length === 1`）确实是预填已选中；但 `subjects.length === 0`（一个主体都没认出——最典型的低置信度形态）时 `machineSubjectType` 恒为 `null`，四个选项**一个都不选中**，那一步就是**一道空白必答题**。所以方案落地不是「改一下触发条件」，而是**先把低置信度那条路径上缺失的预填值补上**。方向对，工作量比设想的大。 |

## 1. 核实点 1 · 这一步到底是不是预填形态

代码在 `OnboardingScreen.tsx`：

```
const subjectSelected: SubjectType | null =
  userSubjectPick === 'defer' ? null : (userSubjectPick ?? machineSubjectType)
```

预填靠的是末尾那个 `?? machineSubjectType`。而 `machineSubjectType` **只在 `applySubject()` 里被写入**，`applySubject` 只有两个调用点：

- `subjects.length === 1` → 自动调用（**高置信度路径，预填成立**）
- 多主体时用户点选某一个 → 调用

🔴 **`subjects.length === 0` 时它一次都不被调用**，于是 `machineSubjectType` 停在 `null`，`subjectSelected` 也是 `null`——**四个选项全部未选中**。而那条路径同时把 `correcting` 置为 `true`，种类滚轮直接展开、`species` 是空串（滚轮上也没有任何一项高亮）。

**所以低置信度那一屏现在的真实观感是：一张读不出东西的照片 + 一道没有预设答案的题 + 一个什么都没选中的滚轮。** 方案要预填的那个值，在这条路径上还不存在。

## 2. 核实点 2 · 置信度信号在前端拿不拿得到

**拿得到。** `api/backend.ts`：

```
export interface DetectSubject {
  subjectType: 'animal' | 'person' | 'other'
  species: string
  confidence: number
  box?: { x: number; y: number; w: number; h: number }
}
```

mock 也照形状给了值（0.5 / 0.62 / 0.55）。⚠️ **但 `OnboardingScreen` 全文没有任何一处读 `confidence`**——字段有，没用。

🔴 **两个限制必须如实登记：**

1. **`subjects: []` 时没有 `confidence` 可读。** 「一个主体都没认出」这种最典型的低置信度形态，前端只有「空数组」这一个信号，阈值比较在这里用不上。前端判据得是两支并存：`subjects.length === 0` **或** `max(confidence) < 阈值`。
2. 🔴 **更要紧的一条：`/detect` 的 `confidence` 与规格 `SR-8` 要比的 `assetSubjectConfidence` 不是同一个量。** 前者是**肖像种类识别**的置信度，后者是**素材侧主体判定**的置信度（服务端，规格 `§7.1`）。前端可以拿 `/detect` 的数决定**这一屏长什么样**，🔴 **但绝不能拿它决定 `L1` 落不落**——门控判据在服务端，前端在这件事上没有裁量权。

🟢 **好消息，也是方案能落地的关键**：新触发条件的后半句「用户未改动预填值」**在契约里已经有载体**。`buildSubjectDeclaration` 产出的 `subjectSource` 已经随 `/start` 上报：

- 用户点过任一选项 → `'user'`
- 用户没碰过 → `'machine'`（有机器判定）或 `'default'`（没有）

于是「未改动」== `subjectSource !== 'user'`。**后端已经能同时看到「素材置信度」（自己算的）与「用户有没有主动填」（前端上报的），新触发条件不需要新增任何字段。**

## 3. 核实点 3 · 「说不清」用到主体类型上语义成不成立

**成立，而且论证已经做过。** `SPEC-topic-taxonomy-and-heat.md` §4.3 为兜底叶选词时比过一轮，结论原文：

> 「说不清」✅ **建议** | 🟢 **已在既有词表里，语气过过一遍。** 关键在它描述的是**信息状态**（我说不清）而不是**分类结果**（你没归好）

既有用例在 `SPEC-recommendation-ranking.md` 的 `era` 维度（`80s / 90s / 00s / 10s / 20s / 说不清`）。

**「其他」与「说不清」不是同一个东西**，差别是**断言 vs 未断言**：

| | 语义 | 用户的心理状态 |
|---|---|---|
| `other`，label「一个地方，或一件东西」 | **确定的断言** —— 主体既不是动物也不是人 | 我知道它是什么 |
| 「我也说不清」 | **未断言** —— 我没有对分类作出判断 | 我不知道 / 我不想判 |

🔴 **但两个硬约束把它压回 label 层，不许做成第四个值：**

1. 取值域 `animal|person|other` 是线上契约字段，`subjectDeclaration.ts` 文件头明写「🔴 不改名、不扩值，它是线上字段」。加第四个 value = 扩值。
2. `SR-D9` 明文「**不想说就选「其他」**」——裁定层已经**故意**把「不想说」映射到 `other`。在数据层重新劈开就是推翻 `SR-D9`。

**落法（图上就是这么做的）：四个界面项 → 三个契约值**，「一个地方，或一件东西」与「我也说不清」都提交 `other`。

⚠️ **代价如实登记**：同一个 value 有两个 label，留库时分不出用户点了哪一个。**这在门控上无所谓**（都是 `other`）；要区分只能另走埋点，不进契约。另外高置信度屏**不出**「说不清」（机器认准了，没有信息状态可言），于是同一个 value 在两条路径上 label 数量不同——这是 `SR-D9` 分路径做法的延续，但要在 `COPY-GUIDE §2.7` 登记，否则后人会当成漏改。

## 4. 核实点 4 · 与 `SR-D9`「不提供以后再说」抵不抵

**不抵触。产品负责人的判断成立，而且可以给出比「给答案 vs 不给答案」更硬的依据。**

`SR-D9` 自己写下的理由（`DECISIONS.md §G⁗⁗⁗⁗‴ §七`）：

> 🔴 **模型认不准时** → 那条路径上它本来就是一道题。⚠️ **「以后再说」并不能让这道题消失，只能让它延后**，而延后之后系统仍然不知道对象是什么，🔴 **后面每一个依赖它的门控都要再问一次或者带着未知值往下跑**。

🔴 **这条理由的落点是「系统知不知道」，不是「用户有没有主动」。** 预填「说不清」→ `other` 时，系统**知道**一个值，而且是最保守的那个值：门控不必再问，也不带未知值往下跑。**按 `SR-D9` 自己给的判准，本方案通过。**

🟢 **更进一步：方案把 `SR-D1` 与 `SR-D4` 接上了。** `SR-D4 ①` 原文「用户**主动填过**这个事实**本身就是偏向他的理由**」——

- 主动点了任一选项 → `subjectSource = 'user'` → 拿到那份偏向
- 预填不动 → `'machine'` / `'default'` → **拿不到偏向 → 落 `L1`**

**这正是 `DECISIONS.md §G⁗⁗⁗⁗‴ §十二` 第 4 条与 `PRODUCT-MINDMAP §4.18` 登记的那个敞口的解**：`SR-D1` 的兜底分支重新有了触发条件，不再是「一个永远进不去的分支」。

🔴 **一条必须报给制作人、设计线不替它定**：`SR-D9` 的「真实代价」原文是「模型认不准时建档**多出一个必答项、不选走不下去**」。本方案**取消了这个代价**（预填之后可以直走）。结论方向一致，但它**推翻了 `SR-D9` 明写的代价段**——是「代价段作废」还是「本条另立编号」，需要一次裁定。

### 5.1 为什么推荐 V2 + V5 的视觉

- **V1 太轻。** 对着 `subject-highconf.png` 看 `subject-lowconf-v1.png`：除了少一个大字species和确认按钮，那一屏与高置信度屏**几乎没有差别**。用户没有任何理由去动那颗预填的「我也说不清」——而按方案，不动就落 `L1`，生成能力静默变窄。**这等于系统替他做了决定，`SR-D1`「把选择权交回用户」名存实亡。**
- **V3 太重。** 「说实话，这一张我们没认准」在一个丧亲者给逝去伴侣建档的时刻，把系统的失败摊到台面上；而且图上那一行是**整屏唯一的暖色文字**，视觉权重压过了那一问本身。
- **V2 的关键手法是换主语。** 主语是「这一张（照片）」——不是「我们（系统没本事）」，也不是「你（没拍好）」。逆光是照片的客观属性，说出来不指责任何人，也**没有暴露任何判定结果**（守住 `SR-6-COPY` 那三条禁令）。分寸落在「说了，但没把谁架上台」。
- **V5 的虚线建议与 V2 合并采用。** 图上那一颗明显读作「还没定，你看一眼」，正是我们要的语义；且它**不是 disabled、不是灰置**（`app.css` 那段注释写死了「灰置等于变相报错」）。**文案负责「为什么」，视觉负责「这个还没定」，两者分工不重叠。**

### 5.2 🔴 「要不要提示这个选择影响生成能力」：不提示

1. 🔴 **这不是偏好，是既有明文禁令。** `subjectDeclaration.ts` 文件头：「🔴 也**不得有任何选项暗示「选了某个答案会被限制」**」。规格 `§10` 第 11 项还要给 `COPY-GUIDE` 新增「**不得在任何面向用户的文案中暴露主体识别的判定结果**」。V4 那一行是这条禁令的正面违反。
2. **谎报风险是实的，而且不对称。** 这一屏正是 `SR-7` 亲口承认的那个漏洞所在（用户可以把人指认成宠物）。加一句「说得越准能做的越多」，等于**在漏洞旁边贴上收益说明**；而收益方向是单一的——「一只小动物」是能力最宽的那个选项，提示只会把人往那一个推。
3. 🔄 🔴 **本条的前提已被推翻（2026-08-26 制作人）。原文保留，不删：**

   > 3. **「用户不理解为什么功能变少」是真问题，但这一屏不是解决它的地方。** 收缩的表现形式已裁定为「这里没有这个入口」（`A7 ①`），发生在 `MineScreen`，与这一屏隔着整个建档流程；在指认时说后果，用户在那个时点也无从验证。🔴 **对症的做法是在能力真的收缩时给出解释与改判路径**——这是本节推导出的**新待办**，交产品线，不靠这一屏的一行字。

   **推翻原因（制作人原话）**：「你用户不主动传或者没有资料。你怪我生成不了。就很搞笑吧。这个场景。他理解个什么呢。他都没提供合适的素材」。
   🔴 **错在把两种「功能变少」混成了一件事**：**素材不足 / 认不出来 → 落 `L1`** 不是能力收缩，是**输入不够**，系统认不出来是如实反馈，🔴 **不需要解释路径**；只有**识别出敏感主体 → 按政策降档**（用户给了好素材却被限制）才是真正的能力收缩，才需要解释与改判。
   ✅ **待办已按新口径收窄后重立**，只覆盖后者 —— 见 `SPEC-subject-recognition-and-degradation.md §10` 第 22 项。
   ⚠️ **不影响本节结论**：「这一屏不提示能力影响」照旧成立，第 1、2、4 条依据未被触动。
4. **图上还看得见一个代价**：V4 加上那一行后，那一屏出现**两处暖色文字**（预填项 + 提示行），视觉重心从「那一问」挪到了「后果」。
