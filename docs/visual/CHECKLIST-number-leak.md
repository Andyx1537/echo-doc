# 自查 · 这一处在给人发一个可反解的量吗

> 2026-08-27 · 前端视觉线立，同日据一次全仓只读排查扩写。
> **做任何涉及「别人给的量」的界面或出参之前，先过这一页。**
>
> 起因：同一类缺陷在三个不同的地方各躲过了两轮检查（`MeScreen` 那格精确数、`DetailScreen` 面孔墙、
> `warmthLevel` 出参）。**一处一处地找会漏**，所以把判准写下来，不再依赖「这次要仔细一点」。

---

## 概述

**判准两问，缺一不可。**

> ① **把这一屏截图给一个不认识这个产品的人，问他能不能从图上还原出一个数。能，就漏了。**
>
> ② 🔴 **然后必须再问一遍：不看屏幕、只看网络响应，能不能还原出来。**

🔴 **第二问从来没人问过**，`C-10`（`warmthLevel` 是连续 double、`min(1, faces/20)` 一步反解）就是这么漏掉的。**渲染层不给 ≠ 数据没发**，抓一次包看的是后者。

**三个手法，按发现难度从易到难：** ① 可数的重复对象（头像、心、格子）；② 有序列表里的位置；③ **连续值直接下发**——这一条在屏幕上完全看不出来，只能查出参。

**🔴 最重要的结论：这不是普遍现象，是集中在一条产品线上。** 全仓排查显示，其他域（审核 `appealAt`、软删、打卡 `streak`、分享边界）的红线条文大多**直接写后果**，或形态与后果本来等价。**同类缺陷全部集中在 `D4` / `D5`「互动计数与排名」这一条线上，至少 7 处**——而这 7 处**不是七道防线，是同一个判断被抄了七遍**。详见 §二。

**🔴 所以「多处一致」在这条线上不构成证据。** 七处都说没问题，看起来像交叉验证，实际上它们**一起错，而且错得一模一样**。

**正面模板（可抄）。** 三个已找到的做对了的例子——`appealUsed` 用 `appealAt IS NOT NULL` 而不是计数列；卡的生效可见性取 `min(卡, 窗)`；`faces[]` 对非本人**裁成空数组而不是删键**（裁剪结果与「还没人记得」不可区分）。**共同点：它们都不是「禁止暴露 X」，而是「让 X 根本不在数据里」。** 详见 §三。

**🔴 而且只有这一类办法管用。** §二 里那条照抄的注释**是本线自己写的，写的时候正在做这条红线的排查**——所以这不是「有人不知道红线」，**是这种写法本来就是默认写法**。指望提醒、加注释、让人更小心，等于在同一个机制里加剂量。📌 **判一个补救办法值不值得做，问一句：它需不需要下一个人配合？需要，就是第八次抄写。**

**🔴 假绿第五例，已核实成立，且比报上来的更坏。** `EchoApiTest.rememberWallHasNoExactCount` 只断言响应不含 `count` / `total` / `rememberCount` / `rank` 这几个**键名**，`warmthLevel` 在场即通过；⚠️ **而它上面一行还 `containsKeys("warmthLevel", "faces")`** —— 这条名为「无精确计数」的红线测试，**同时是保证泄漏面必须存在的测试**，解冻后动 `C-8` / `C-10` 会先被它挡住。详见 §四。

**两条半机械规则已登记、🔴 不实现**（归工程线，且要等冻结解除）。详见 §八。

⚠️ **不要信注释和红线条文的自我声明。** 上面每一处都写着类似「不显数字 / 不排名 / 不返回精确总数」的话，**每一句都是真话，但每一句描述的都是实现、不是后果**。通则见 `docs/COPY-GUARD-CROSSWALK.md` §3。

## 一、两问怎么用

**第一问（屏幕）。** 找一个不知道背景的人，或者自己隔一天再看。问的**不是**「这里有没有数字」——那个问题太窄，实例里只有一处是明写的数字。问的是**「你能不能还原出一个数」**：

- 数得清的重复对象 → 数一遍就是那个数；
- 有长度、有宽度的条 → 量一下就是那个数；
- 有序列表里的位置 → 位置本身就是名次。

**第二问（网线）。** 打开控制台，看这一屏对应的响应体。问：

- 有没有字段虽然前端不渲染、但仍在下发？（`C-8`：面孔墙超阈值后前端不画了，`faces` 还传不传？）
- 有没有字段虽然是浮点/枚举，但**能反解回原始计数**？（`C-10`）
- 反解公式是不是就写在这个仓库里？（是的话，反解成本 ≈ 0）
- 有没有**列表型端点一次返回多个**这样的量？一次返回多个 = 就地可排名。

## 二、🔴 同一个判断被抄了七遍

2026-08-27 的全仓只读排查给出的核心结论，原文照录：

> 这 7 处不是七道防线，**是同一个判断被抄了七遍**。它们的表述全是「没有 X 字段 / 不展示数字」，
> 而真正的泄漏面是 `warmthLevel` 公式 + owner 侧 `faces[]` + `insights` 三个精确整数。
> **看起来像交叉验证——七处都说没问题，谁还会怀疑——实际上它们一起错，而且错得一模一样。**

### 七处在哪

| 处 | 位置 | 说的是什么形态 |
| --- | --- | --- |
| 1 | `API-CONTRACT.md` §5 `GET /windows/:id/remember` | 「不返回精确总数字段、不排名」 |
| 2 | `API-CONTRACT.md` §6.0.2（卡的不下发字段表） | 「任何互动计数……暖意走窗级 `warmthLevel`」 |
| 3 | `API-CONTRACT.md` §12 | 同类表述 |
| 4 | `DECISIONS.md` `D4` 与 `RK-F` | 「不显精确数字、不排名」 |

| 6 | 前端 `DetailScreen.tsx:98`、`types.ts:92`、`api/mock.ts:266` | 「不显数字、不排名」「不返回精确总数」 |
| 7 | 契约测试 `EchoApiTest:288`（断言在 `:289`） | 「红线：不返回精确总数/排名字段」 |

⚠️ 行号会漂移，**以内容为准**。

### 真正的泄漏面（三项，与上表零交集）

1. **`warmthLevel` 公式** —— `min(1, faces / 20)`，`faces = round(warmthLevel × 20)` 一步反解，算式在仓库里。
2. **owner 侧 `faces[]`** —— 整批下发，前端超阈值后不画，`faces.length` 照样在响应体里。
3. **`insights` 三个精确整数** —— 前端已全部不显示数值，服务端照旧下发。

**七处条文，一条都没有落在这三项上。**

### 🔴 本线核实的两处（用户点名要核，结论如下）

**`echo-h5-proto/src/api/mock.ts:266` —— 成立，但措辞要改。**

```266:277:echo-client/echo-h5-proto/src/api/mock.ts
/** 暖光浓度 → 面孔墙（有上限，不返回精确总数；§0.7 #4 红线） */
function facesFor(windowId: string, warmth: number, meRemembered: boolean, myAvatar: string): Face[] {
  const count = Math.min(11, Math.max(2, Math.round(warmth * 11)))
  // ...按 count 造出等长的 faces[] 返回
}
```

排查线说它「注释与它自己的行为相反」。**核下来是成立的，但不是「相反」，是「同型」** —— 注释字面为真（返回值里确实没有一个叫「总数」的字段），而返回的**数组长度就是那个总数**。这个区别不是咬文嚼字：**登记成「注释写错了」，修法是改注释；登记成「条文约束形态、不约束后果」，修法是改数据形状。** 后者才是真的。

⚠️ 附带一条：mock 的分母是 `11`，服务端是 `20`。**两边都可反解，但反解系数不同** —— 照着 mock 推线上人数会推错，属于 `S-14`「照 mock 判契约会判错」的又一例。

**`echo-h5-proto/src/styles/app.css:112` —— 成立，但要说清它是哪一类。**

那条注释说「契约 §6 用 `warmthLevel` 换掉精确 `rememberCount`」。**换字段名并没有消除可反解性，这一点排查线说得对。** 但要如实说明两件事：

- 它**不是一处守卫条文**，它的主旨是记录一次死样式清理（`.w-remember` / `.blossom` 已删）；「换掉 `rememberCount`」只是背景陈述。
- 🔴 **它的危害在于把「换掉」写成了一个已完成的动作** —— 读的人会以为那件事办完了。**这正是第七次抄写的形态：不是有人在撒谎，是每个人都在转述上一个人的话。**
- 🔴 **这条注释是本线自己写的**（`S-7`）。登记在这里不是甩锅，是因为**它证明知道这条红线的人也会照抄** —— 我写它的时候刚查完那一处死样式，仍然照抄了「换掉了」这个说法。

### 提炼

🔴 **这一条线上没有一处是独立判断出来的。** 所以在 `D4` / `D5` 这条线上：

> **「多处一致」不是证据，是同一份稿子的复印件数量。**

判一处红线守没守住，要看**它约束的是形态还是后果**，不看有多少处附议。

## 三、正面模板：让 X 根本不在数据里

今天找到两个做对了的例子，**可以直接抄**：

| 模板 | 在哪 | 怎么做的 |
| --- | --- | --- |
| `appealUsed` | `API-CONTRACT.md` §17.2 | **不由计数列推导，用 `appealAt IS NOT NULL`。** 🔴 **形态选择本身直接锁住了后果——没有可绕的量存在。** 「一张卡一生只有一次申诉」这条规则，靠的不是「不许暴露申诉次数」，而是**次数这个量压根没被存下来** |
| 卡的生效可见性 | 切分线报的 `min(卡, 窗)` | 生效档位是交集，不是两个独立字段让消费方自己判。**消费方没有判错的机会，因为没有第二个值可判** |
| `faces[]` 的裁剪 | `WindowVisibilityTrimTest` 约 `:298`：非本人**裁成空数组，而不是删键** | 🟢 **空数组与「还没人记得」不可区分** —— 观察者分不出「被裁了」和「没有人」。删键就会重新可区分。**同一个形态：让那个量不在数据里，而不是禁止读它** |

### 🔴 共同点（这一句是这两个模板的全部价值）

> **它们都不是「禁止暴露 X」，而是「让 X 根本不在数据里」。**

再往前推一步，就是判断一条红线强不强的标准：

> 🔴 **红线的强度不取决于写得多严，取决于违反它需不需要人配合。**
>
> 「禁止暴露 X」要靠**每一个后来的人都记得遵守**——七处抄写就是这么来的，每一处都是一个人记得了、并且转述给了下一个人，而没有一个人回去验过后果。
> 「X 不在数据里」**不需要任何人记得**。

对照 `D4` / `D5` 这条线：`warmthLevel` 之所以守不住，正因为它是前一种——**那个量被完整地存下来、算出来、发出去了，只是没有给它起名叫 `rememberCount`。**

### 🔴 为什么「提醒、加注释、让人更小心」这一类办法一定不管用

§二 里 `app.css:112` 那条注释是**本线自己写的**——写它的人当时**正在做这条红线的排查**。这一处不是「有人不知道红线」：

> 🔴 **这种写法本来就是默认写法。知道红线、正在做红线的人，照样写出同一种句子。**

所以指望「下次注意一点」「把红线写得更醒目」「在评审时提醒一句」是**在同一个机制里加剂量** —— 那七处抄写每一处都是这么来的，每一处都是有人认真记得了、并且认真转述给了下一个人。

**能用的只有上表那一类：把量从数据里拿掉。** 它不要求任何人记得，因此也不受「写的人是不是刚好在状态上」影响。

> 📌 **判一个补救办法值不值得做，问一句：它需不需要下一个人配合？需要，就是第八次抄写。**

## 四、🔴 假绿第五例：测试名说后果，断言只查形态

**核实结论：成立。而且比报上来的更坏一层。**

```272:290:echo/echo-server/src/test/java/com/echo/http/EchoApiTest.java
    void rememberWallHasNoExactCount() throws Exception {
        // ...
        Map<String, Object> wall = invoke("GET", "/windows/" + windowId + "/remember", visitor, null);
        assertThat(wall).containsKeys("warmthLevel", "faces", "meRemembered");
        assertThat(wall.get("meRemembered")).isEqualTo(true);
```

**报上来的那一半（成立）**：最后一行只检查四个**键名**在不在。`warmthLevel` 和 `faces` 都在场，测试照样绿。测试名写着 `NoExactCount`，它测的却是「没有叫这几个名字的字段」——**这就是「条文约束形态」的测试版**。

**🔴 核实时发现的另一半（更坏）**：倒数第三行 `containsKeys("warmthLevel", "faces", "meRemembered")` —— **它把泄漏面断言成了必须存在的契约。**

后果是具体的：解冻后要动 `C-10`（把 `warmthLevel` 改成档位枚举）或 `C-8`（对某些视角不发 `faces`），**这条名叫「无精确计数」的红线测试会第一个变红**，把修复挡在门外。

> 🔴 **它不只是没在守这条红线，它在守这条红线的反面。**

⚠️ 这一层不改变「不修任何东西」的结论——**冻结期间照样不动它**。登记在这里是为了让解冻的人知道：**动出参之前先看这条测试，别把它的变红当成自己改坏了。**

**登记点**：本例已作为**第五处假绿**写进 `echo-server/docs/BUILD-VERIFICATION.md` §七之二（前四处在 §一 / §五 / §六 / §七）。

## 六、`HeartRow`：为什么说这是房屋风格

`MineScreen` 的羁绊温度渲染成**六颗心**：`filled = round(temperature / 100 * 6)`。

这是**和面孔墙一模一样的手法**——把一个连续量渲染成一排可数的重复对象。它危害小，因为分母是自己的温度（自我记录，不是别人给的），而且旁边就印着精确度数，心并没有多泄露什么。

🔴 **但它证明这个手法不是一次意外，是这个工程默认的表达方式。** 所以：

- 第四处不会是最后一处；
- 要防的**不是某一处，是这个手法本身**；
- 下一个人的任务是**系统性地过一遍所有「量 → 视觉」的映射**，而不是再抓一只。

⚠️ 与 §二 合看，结论更收紧一点：**手法遍布全仓，但缺陷集中在 `D4` / `D5` 这一条线上。** 手法本身不是缺陷——`HeartRow` 用同一个手法却没事，因为它的量分母是自己。**决定它是不是缺陷的，是那个量的分母是谁。**

## 八、两条半机械规则（🔴 只登记，不实现）

排查线的判断是「这类缺陷没有通用的机械办法」，本节同意。**但下面两条成本极低，是例外，值得单独留着。**

| # | 规则 | 为什么便宜 |
| --- | --- | --- |
| 1 | 若契约或注释里出现「精确总数」这类措辞，**而同一个出参里含 `warmthLevel`**，就告警 | 🔴 **反解公式在仓库里是明文**，不需要任何推理，纯文本共现即可判 |
| 2 | 凡测试名含 `NoExactCount` / `红线` 之类**承诺后果**的词，而断言只是 `doesNotContainKeys(...)` 之类**只查形态**的调用，标记为**形态测试、非后果测试** | 名字与断言的落差是可静态识别的，不需要理解被测语义 |

🔴 **本轮只登记，不实现。** 实现归工程线，**且要等 `C-8` / `C-10` 解冻**——在冻结期间加告警，只会得到一批当天就被当成噪音的红灯。

⚠️ 规则 2 有一条已知的实施陷阱：它会把**合理的形态测试**也标出来（有些字段本来就该用键名判）。所以它的产物是**「需要人看一眼」的清单，不是失败**——做成阻断会立刻被关掉。
