# 作品域规格（SPEC-works）

> 状态：v0.2 · 2026-09-01 · 作品公开闭环目标态已收口
> 关联：`DECISIONS G-27`、`PRODUCT-DECISION-WORK-PUBLICATION.md`、`PRODUCT-IMPLEMENTATION-AUDIT §0/§0b`
> 实现：`echo` 仓 `t_work` / `WorksApi` / `WorkStore`；`echo-client` 仓 `PublishScreen` / `WorksFeedScreen`

> 🔴 **目标态与现状必须分开理解**：本文的数据结构、端点和前端章节记录当前已有实现；
> `§0`、`§5`—`§7` 是本轮拍板后的目标产品契约，尚未核实完成的能力不得视作已经上线。

## 0. 目标产品基线（2026-09-01）

1. **回忆卡是私域内容源，作品是唯一公开对象。** 回忆卡继续承载 AI 定期生成、用户独享、
   前中后引导与下一轮生成反馈；任何内容进入广场前，都必须先形成独立 `Work`。
2. **作品有两个来源**：用户自行上传；用户将一张回忆卡发布为作品。后一种只以
   `sourceCardId` 记录来源，不把回忆卡本身改成公开对象。
3. **`plaza` 是公共瀑布流广场，`works` 是用户自己的作品墙场景。** 广场的内容元素仍然是作品，
   但两个名称表达的是不同用户视角，不是两个公开流。原“广场展示窗、卡还是作品”的待定项
   已由 `DECISIONS G-27/WP1` 关闭。
4. **审核按内容版本复用，不按对象名称豁免。** 来源回忆卡若已有面向公开分发的有效审核凭证、
   发布内容未修改且发布轻闸通过，可直接公开；否则进入作品审核队列。
5. **公开互动只归属作品。** 点赞、共鸣、留言、举报、曝光、通知和来源追踪统一以 `workId`
   记事实；“广场视角、作者视角、消息视角”只是同一事实的不同投影。
6. **私域反馈与公开互动隔离。** 回忆卡上的观看、回答和引导反馈继续服务下一次生成，
   不因生成作品而搬迁；陌生人不能触达私域卡。

## 概述

**本次落地补上了主线第 10 步。** 此前服务端没有任何创建可发布内容的入口，
审核、分发、曝光整条下游只能处理测试代码手塞的数据。现在有了。

已拍板并已实现的结论：

1. **作品与回忆卡分开建模，各有各的发布页。** 回忆卡是私域产物（用户什么都不做也会长出来，
   默认私密）；作品是公开物（每一条对应一次明确的作者意图）。两者由 `t_work.sourceCardId`
   外键连接——作者把一张回忆卡「发出去」，就长出一个作品，外键记住来路。
2. **发布口从第一天同时收图片与视频。** AI 生成管线接进来时不需要再改契约。
3. **当前实现中发布 ≠ 公开。** `POST /works` 一律落 `status='pending'`，回执文案是「已提交」。
   目标态将增加“有效审核凭证 + 内容未变 + 发布轻闸”直发分支，详见 §5；这不是合并生成、
   发布、过审三个业务时刻，而是复用同一内容版本的审核结论。
4. **AI 生成标识 `aiGenerated` 独立成列，不从外键 join 推导。** 来路卡被删不该让作品
   变成「非 AI 生成」——那是对监管说的假话。列表面每一条都下发这个键（S-8 显式标识）。
5. **服务端存原始宽高，不存 `tall`/`short` 档位。** 瀑布错落是渲染决定，档位会把布局焊进数据。
6. **软删（G0-1）。** `WorkStore` 不提供物理删除方法；所有读路径带 `deletedAt IS NULL`。
7. **一张回忆卡只能发出一个未删除的作品**（局部唯一索引，S-7）。删掉之后可以重发。

🔴 **仍然待核实 / 待实现的**：

- **广场目标已定为作品，但迁移方式未实现** —— 现在服务端 `/plaza` 仍发回忆卡，`GET /works`
  仍承担全站作品列表。目标应调整为：`/plaza` 承担公共发现流；作品墙只读取指定用户（默认本人）
  的作品。需要迁移的是查询语义，不是二选一删除某个产品场景。
- **AI 生成的视频从哪来** —— `GeneratedMediaPublisher` 的类注释写明「Echo 当前不生成
  任何图片/音频/视频，AI 只产出文本」。发布口已经能收视频，但**生成侧不存在**。
  定它需要先做 AI 中台那条线（`PLAN-worklines-20260830` L2）。
- **`originType` 对 AI 作品怎么记** —— 该列只有 `user | official`，是运营口径不是 AI 口径。
  AI 生成、用户发布的作品算 `user` 就会进北极星分母，而北极星要看的是「真人发的卡有没有人理」。
- **视频首帧谁来抽** —— 库约束（`t_work_ck_video_poster`）已经强制视频必须有 `posterKey`，
  但客户端目前没有抽帧实现，前端暂时拿素材本身顶替。定它需要选客户端抽帧还是服务端转码。
- **媒体下发的鉴权与吊销** —— `GET /api/v1/files/{key}` 无鉴权无吊销，作品下架后 URL 仍可开，
  与 `CM-G4` 冲突。归属安全线（L1 `E1`/`E5`）。⚠️ 同线的 `E4`（素材归属）已于 2026-08-30
  修完（`echo@c97da41`，见 `SPEC-security §4.14 E4`），顺带补出 `t_resource`——
  它是吊销的前置：`IStorage` 没有 delete 方法，要清字节得先知道有哪些 key。
- 🔴 **`t_work.status` 没有「生成中」这一态** —— 现有六态（`draft`/`pending`/`public`/
  `rejected`/`takendown`/`appealing`）默认媒体在发布那一刻已经存在。而 AI 生成是异步的
  （`ILlmClient.complete` 是 20 秒同步调用，连异步任务模型都还没有），生成期间这条作品
  处在哪一态、`mediaKey` 填什么，现在无解。**定它必须和异步任务模型一起定**，
  单独给枚举加一个值只会造出一批 `mediaKey` 为空却又不是草稿的行。
  来源：`TECH-AI-PLATFORM` 视频作品九项缺口盘点。

## 1. 数据模型

`t_work`，建表语句在 `echo/echo-server/src/main/resources/sql/schema.sql` 末尾。

| 列 | 说明 |
|---|---|
| `sourceCardId` | 来路回忆卡。自制上传为 `NULL`——🔴 是合法值，不要用 0 代替 |
| `sourceType` | **目标新增**：`user_upload \| memory_card`；不得仅靠 `sourceCardId IS NULL` 猜来源 |
| `sourceContentHash` | **目标新增**：发布时冻结的内容版本摘要，用于判定能否复用审核 |
| `reviewEvidenceId` | **目标新增**：所复用或新生成的公开审核凭证；必须能追溯策略版本与审核时间 |
| `mediaType` | `image \| video` |
| `mediaKey` / `posterKey` | `POST /upload` 返回的 resourceId。视频必须另有首帧 |
| `durationMs` / `width` / `height` | 客户端读出后带上 |
| `visibility` | `private \| friends \| public` |
| `status` | `draft \| pending \| public \| rejected \| takendown \| appealing \| deleted` |
| `originType` | `user \| official`，无默认值（G-1 前置闸门，漏写则报错） |
| `aiGenerated` | 独立列，见概述第 4 条 |
| `deletedAt/By/Reason` | 软删三列（G0-1） |

**状态比回忆卡少两态**，是刻意的：`active` 在卡那边表示「已存在但未公开」，
而作品没有这种中间态（没发布就是 `draft`）；`blocked` 是机审直拦，
作品走的是先 `pending` 后人工，没有机审直拦这条路。

## 2. 端点

| 方法 | 路径 | 鉴权 | 说明 |
|---|---|---|---|
| POST | `/works` | 登录 + **绑定**（S1′） | 发布。落 `pending` |
| GET | `/works` | 登录 | **当前实现**：全站作品瀑布；目标态不再承担公共广场语义 |
| GET | `/works/:workId` | 登录 | 详情，含正文全文 |
| GET | `/users/:userId/works` | 登录 | 个人作品页。本人可见未公开的 |
| DELETE | `/works/:workId` | 登录 | 作者软删自己的作品 |

**下发面拆成两个方法**（`WorkView.listItem` / `detail`），不是一个带 flag 的：
合并之后漏传一个 `false` 就是正文全文泄漏，而这个漏传在页面上看不出来。

**不可见一律回 404**，不区分「不存在」与「你看不了」——区分开来等于泄漏「它存在」。

## 5. 审核复用与发布状态（目标态）

| 来源 | 内容处理 | 发布结果 |
|---|---|---|
| 用户自行上传 | 新建作品内容版本 | `pending`，走完整作品审核 |
| 回忆卡发布且未修改 | 校验卡的公开审核凭证与发布轻闸 | 有效则 `public`；无效则 `pending` |
| 回忆卡发布但修改了标题、正文、媒体或封面 | 形成新的作品内容版本 | `pending`，不得复用旧结论 |

审核凭证至少包含：`contentHash`、`result`、`policyVersion`、`reviewedAt`、AIGC 标识准备状态、
授权快照和风险标记。只证明“适合私下给本人看”的生成检查，**不等于**公开分发审核凭证。

发布轻闸负责审核之后仍会变化的条件：用户发布意愿、可见范围、授权/同意快照、账号状态、
素材可用性与吊销状态、AIGC 标识完整性。任何一项失败都不得直接公开。

目标状态迁移为 `draft → pending → public → takendown → appealing → public|takendown`；
`pending → rejected`；作者可从允许的非终态软删为 `deleted`。从回忆卡直发只是跳过重复内容审核，
仍必须创建 `Work`、冻结版本、写发布记录并通过发布轻闸；不得把卡状态当作作品状态。

## 6. 互动、归因与消息（目标态）

- 所有公开行为先写一条以 `workId` 为主归属的事实，再投影到广场反馈、作者消息、运营统计。
- 事实至少记录 `interactionId/workId/actorId/type/sourceSurface/occurredAt`；需要通知或活动归因时，
  再带 `recipientId/campaignId/referrerId`。
- 发起视角只影响 `sourceSurface`，不改变归属对象；不得向卡互动与作品互动重复写同一次行为。
- 作品被下架或删除后停止新增公开互动；历史通知和审计保留，跳转按当前可见性兜底。
- 删除来源卡不自动删除作品，作品保存冻结快照；撤销必要授权时，作品下架并进入审计流程。

## 7. 前后端查漏补缺入口

本规格只确定产品目标，不宣称以下能力已经存在。联合核查以
`PRODUCT-DECISION-WORK-PUBLICATION.md` 的 W-01—W-14 为验收矩阵，重点确认：

1. 两种来源能否原子创建作品，并写入来源、内容快照、审核凭证和状态迁移记录；
2. 是否存在唯一的作品审核队列、处置接口、申诉链路和双流水审计；
3. `/plaza` 是否已改为公共作品瀑布，作品墙是否只按当前/指定用户查询，二者详情 ID 是否全用 `workId`；
4. 互动、通知、举报、统计是否从同一个 `workId` 事实派生，且不会穿透私域回忆卡；
5. 来源卡删除、作品下架、授权撤销、媒体吊销和旧客户端兼容是否有明确降级行为。
