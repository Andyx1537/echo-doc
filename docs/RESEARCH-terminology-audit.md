## 1. 歧义形态分类（🔴 先分清种类，再往里填词）

### 1.1 为什么必须先分形态

⚠️ **同一个处置办法只对一种形态有效。** `XC4`「层」用的是「加限定词」，那个办法之所以成立，是因为**两层/三层/四个面这三个数字彼此看得出不同**，人读到会停下来问。🔴 **把同一个办法套到「暖意」上必然失效** —— 两义**都写作「暖意」**，看不出。**分形态不是为了整齐，是为了让「该用哪一招」有依据。**

### 1.2 五种形态

#### Ⅰ · 实体层级混用（9 条）

**判据**：两义指**同一条从属链上不同层级的实体**。本项目那条链是 **账号 → 窗（宠物 / `t_pet`）→ 卡（`t_memory_card`）→ 一次互动（`t_resonance`）**，另有一条旁支 **主题（`t_topic`）**。

🔴 **典型失效方式**：**id 传得过去、调得通、只是指错了东西** —— 因为两层的 id 都是雪花 bigint，**类型系统看不出区别**。前端已用「两个互不兼容的品牌类型」把它变成编译期问题（`lib/ids.ts`，提交 `ec59e9e`），🔴 **服务端没有对应机制**（Java 侧两边都是 `String`/`long`）。

#### Ⅱ · 流向相反（4 条）

**判据**：两义的**箭头方向相反**。三种方向在本项目里都出现过：**系统 → 用户**（AI 近况）· **其他用户 → 作者**（回应）· **我 → 我自己**（活跃累积）。

🔴 **典型失效方式**：**一句话两种读法都通顺，而其中一种读法会让它变成一个我们自己可控的产量数。** `GTM4` 已因此止血一次（提交 `4b9cfc6`）。⚠️ **这一形态是本文认为最危险的**，因为**没有任何机械手段能发现它** —— 它不体现为类型、不体现为量纲、不体现为报错。

#### Ⅲ · 纯命名撞车（7 条）

**判据**：两义**毫无关系**，只是名字撞了。本项目的撞车有两个来源：**跨领域的普通词**（`temperature`、`scope`）和 🔴 **前后两代产品**（`t_echo` ⟷ `t_pet_echo`）。

🟢 **这一形态<u>最容易处置</u>**：加前缀、改名、删旧表，都不牵动产品语义。🔴 **但它的<u>发现</u>成本最高** —— 因为两义之间没有任何逻辑联系，**没人会主动去想它们可能撞**。

#### Ⅳ · 量纲不同（3 条）

**判据**：两义**都是数**，但单位或取值域不同，放在一起比较**无意义**（不是不够准，是算出来的数不指向任何东西）。

🔴 **典型失效方式**：**比率的分子分母来自两个不同的量。** `DECISIONS RK-H` 逐字记过一次：「**分母是卡、分子是窗，比率没有意义**」。

#### Ⅴ · 🆕 声明态 vs 生效态（3 条）——**本次新发现**

**判据**：两义**同实体、同流向、同量纲**。一个是**用户/作者声明的意图**，另一个是**系统实际执行的结果**。🔴 **两者可以长期不相等，而且系统是<u>刻意</u>让它们不相等的**（例：窗收窄时卡行故意不跟着改，好让窗改回来时能原样恢复）。

🔴 **为什么它必须单列，而不是并进前四种**：

| | 前四种 | 🔴 第五种 |
|---|---|---|
| 两义摆在一起 | **看得出不一样**（层级 / 方向 / 事物 / 单位） | 🔴 **看起来就是同一个东西**，差别只在「说了」还是「做到了」 |
| 能不能靠 review 发现 | 能 —— 读到「窗」和「卡」并列会起疑 | 🔴 **不能。** 读到两处都写 `visibility`，**没有任何东西提示你该起疑** |
| 失效的表现 | 多半是报错、404、数字对不上 | ⚠️ 🔴 **不报错。** 表现是**多发了一条内容**、**多算了一个分母**、**开关没生效** |

🔴 **本项目已经为它付过一次代价，并且付完之后才把它变成可检索的**：`CardVisibility.java:62`–`:64` 逐字记着 —— 「此前 `card.visibility` 与 `pet.visibility`（窗级，直接读是**对的**）在 **grep 里长得一模一样**，所以『扫出所有卡级裸读』这件事**做不到**」。**处置办法是改名 `visibility` → `visibilityIntent`（提交 `eac9df7`）+ 探针扫全仓** —— ⚠️ 🔴 **注意这两道都不是「更小心地读」，因为更小心地读对这一形态无效。**

🔴 **第五种的通用处置**：**让名字自己说出它是哪一态**（`…Intent` / `…Effective` / `…At`），并把「必须过某个函数」变成编译期或测试期的强制，而不是一句注释。

## 4. 根因：产品负责人的假设，验证结果

### 4.2 🟡 假设的**前半句**：成立，但它自己也是继承来的

**「窗最早既是私人空间又是分发单元」—— 🟢 成立。** 但 🔴 **它不是往宠时期发明的，是 6 月那套产品的原始设计。**

> **回声 (Echo)** ｜ 共鸣者留在**你世界里**的异步痕迹 / 录像式幽灵。
> **共鸣 (Resonance)** ｜ 两个用户向量相似度达到阈值的关系。

🔴 **读法**：第一条说它是**个人的**，第二条说**别人能进来留痕**。⚠️ 🔴 **「私人空间 = 别人能到达的地方」这个合体，从 2026-06-26 第一版术语表起就写在那里了。**

### 4.4 🔴 修订后的根因：**两层，缺一层都会低估收口成本**

| 层 | 内容 | 状态 |
|---|---|---|
| **外层（更早、更贵）** | 🔴 **2026-07-08 的战略转向<u>没有做词汇清算</u>** —— 6/26 为「意识空间 + 向量匹配」铸的词（回声 / 共鸣 / 空间）被「回声·往宠」**原样接手并重新指向**，而 🔴 **旧所指的表与服务一行未删**（`t_mind_space` · `t_resonance_record` · `t_echo` · `t_friendship` · `t_stall`，`schema.sql:72`–`:127`，今天仍在）。 | 🔴 **本文新提出**，产品负责人的假设未覆盖 |

### 4.5 🔴 一条**被推翻**的顺带发现（留痕）

⚠️ 🔴 **本文一度打算把「窗的六个名字」（词条 `9`）也归到外层根因，理由是「数字纪念空间」听起来像旧代词。核实后推翻：**
