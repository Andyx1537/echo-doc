# 需求：持久化统一到引擎（`M-6` 执行规格）

> 2026-08-31 起草 · 状态：**已确认，执行中** · 对应裁定 `DECISIONS QA6` / `AD6` · 跟踪编号 `M-6`
> 现状盘点见 `TECH-DB-INVENTORY`（尤其 §6 能力缺口量化）

## 0. 已拍板（2026-08-31 制作人）

§4 五条全部拍定：

| 条目 | 结论 |
|---|---|
| 查询意图形态 | **注解式命名查询**：Repository 接口上写 `@Query`，引擎解析成 SQL |
| 方言 | **引入方言层**，保留 MySQL 与 PG 两套；PG 独有特性在 MySQL 方言下抛不支持 |
| DDL 事实源 | **注解生成，`schema.sql` 降为生成产物并提交入仓**（供 review 与冷启动），配 CI 查一致 |
| 迁移节奏 | **先把引擎扩完，再一次性迁完** |
| 联表范围 | **只做按外键取关联实体（fetch 语义）**，不支持任意 join |

⚠️ 迁移节奏一条，起草时倾向逐域灰度，理由是「引擎 API 设计得对不对只有真正迁一个域才知道」。
制作人选一次性。**这条风险不消失，只是被接受了**：扩引擎期间没有真实用例校验设计，
返工若发生会发生在引擎扩完之后。缓解办法是扩每一项时**同步拿现有 SQL 做对照验证**
（该 SQL 能不能用新 API 等价表达），不要等到迁移阶段才发现表达不了。

## 概述

**目标：应用层不再出现任何 SQL 字符串，SQL 全部由引擎生成。**

这不是「把手写 SQL 删掉、退回引擎现有的等值查询」——那样会丢掉 21 处排序、
16 处分页、22 处软删谓词。而是**把生成 SQL 的职责收进引擎**：应用声明意图，
引擎产出语句。二并一发生在「谁写 SQL」这一层，不在「用不用 SQL」。

🔴 **本文档只整理需求，不含实现。确认后才动手。**

需求分三块：

1. **关系查询内化**（`R1`–`R6`）—— 引擎要能表达应用真正在用的查询：
   排序、分页、`IS NULL`、范围、`IN`、upsert、联表投影。
2. **DDL 表达完备**（`D1`–`D5`）—— 注解要能表达 `schema.sql` 里的约束：
   局部索引、列级 `DESC`、`CHECK`、真外键、原生类型（jsonb / vector）。
3. **向量一等公民**（`V1`–`V5`）—— pgvector 是本项目核心能力，不作例外处理：
   向量列由注解声明、维度写死在注解里、相似检索带过滤下推、索引类型与距离度量可声明、
   优化点沉在引擎。

已确认的前提（无需再查）：

- **`Aengine` 唯一的活跃消费方是 `echo-server`。** `Echo-legacy` 已归档，
  `game-engine` 是 Aengine 的前身而非消费方。**改引擎没有外部兼容负担。**
- **`ResonanceService` 是现成样板** —— 目前唯一被 WS 与 HTTP 两侧共用的领域服务，
  迁移照它的形状做（`TECH-DESIGN-feed-recall-and-exposure §2.5.1`）。
- **分裂发生在表内部，不只在表之间。** `t_self_vector` 同一张表同一行，
  关系元数据列归注解世界的 `SelfVectorRepository`，`embedding` 列归手写 SQL 的
  `PgVectorStore`。这是「两套写法」最具体的形态。

🔴 **仍然待定的**（五条，每条附「定它需要什么」，见 §4）：
查询意图的表达形态 · 是否保留 MySQL 方言 · DDL 事实源 · 迁移节奏 · 联表范围。

## 1. 关系查询内化

| 编号 | 需求 | 现状 | 用量依据 |
|---|---|---|---|
| `R1` | 排序（多列、升降序） | `PgRepository` 零处 `ORDER BY` | 现有 SQL 21 处 |
| `R2` | 分页（limit / offset 或 cursor） | 零处 `LIMIT` | 16 处 |
| `R3` | `IS NULL` / `IS NOT NULL` 谓词 | `buildWhereSQL` 只拼 `col = ?` | 22 处，**几乎全是软删守卫** |
| `R4` | 范围（`>=` / `<=`）、`IN`、**不等于 `<>`** | 无 | 分页游标与批量取都要；`<>` 是 §6.2 改写的前置 |
| `R5` | upsert（`ON CONFLICT`） | 无（现有 `save` 是先查后写） | 14 处，**幂等写靠它** |
| `R6` | 联表与投影到非实体形状 | 无 | 现有仅 2 处，但范围待定（§4.5） |

🔴 **`R3` 是优先级最高的一条，因为它关系到正确性而不只是能力。**
22 处 `IS NULL` 里绝大多数是 `WHERE deletedAt IS NULL`。表达不出来的后果不是查不了，
而是**查得出来但多出已删除的行**——不报错，只是删掉的东西重新出现。

### 1.1 一条硬约束

**迁移完成后，应用层不得出现 SQL 字符串。** 建议加一条 CI 检查：
`echo-server` 的 `src/main/java` 下命中 `SELECT `/`INSERT INTO `/`UPDATE `/`DELETE FROM `
即失败。⚠️ 没有这条检查，第一个赶工期的人会把 SQL 写回来，而且没人看得见。

## 2. DDL 表达完备

| 编号 | 需求 | 注解现状 | 缺口量 |
|---|---|---|---|
| `D1` | 局部索引（`WHERE ...`）与列级 `DESC` | `@Index` 只有 `name`/`columns`/`type` | 23 个局部索引 + 9 处 `DESC`（共 76 个索引） |
| `D2` | `CHECK` 约束 | 无 | 30 条 |
| `D3` | 真外键 | ⚠️ `@Fk` **只是一个索引类型标记，不生成外键** | 19 个 |
| `D4` | 原生类型直通（jsonb / vector） | `@Column` 只有 `length`/`charset` | 12 个 jsonb 列 + 1 个 vector 列 |
| `D5` | DDL 单一事实源 | 🔴 **两个**：注解运行时自动建表加列 + `schema.sql` 人工执行 | —— |

🔴 **`D1` 与软删是一件事。** 那 23 个局部索引里包含
「一张回忆卡只能发出一个未删除的作品」这类唯一约束（`t_work_uk_source_card`）。
表达不出来就得把约束搬到应用层，而**应用层的唯一性检查在并发下会漏**——
两个请求同时查到「没发过」，然后都插入。

🔴 **`D5` 是目前唯一正在造成损害的一条。** 注解那侧改字段线上库跟着变，
`schema.sql` 是死文件不会动，没有任何检查会发现分叉，表现为「本地复现不了线上的问题」。

## 3. 向量一等公民

不作例外处理。pgvector 是本项目核心能力，抽象与优化都归引擎，外部只见接口。

| 编号 | 需求 | 说明 |
|---|---|---|
| `V1` | 向量列由注解声明，**维度写在注解里** | 🔴 现在维度来自环境变量 `ECHO_EMBED_DIM`，可配任意正整数，而 SQL 列宽写死 768 且不校验。配错时启动正常、日志安静，**第一次写库才炸，错误指向 SQL 层，排查方向会跑偏**。维度声明在注解上，装配期就能断言 |
| `V2` | 相似检索接口：topN + 距离阈值 + **过滤下推** | 过滤必须下推到 SQL。在应用层过滤等于先取全量再筛，把索引的意义抵消掉 |
| `V3` | 索引类型与参数可声明（ivfflat / hnsw + `lists` / `m` / `ef_construction`） | 现在索引建在 `schema.sql` 里，与实体定义分离 |
| `V4` | 距离度量可选（cosine `<=>` / L2 `<->` / 内积 `<#>`） | 现硬编码 cosine |
| `V5` | 优化点沉在引擎 | 预过滤 vs 后过滤的选择、`ivfflat.probes` 调参、召回补偿。**这些是引擎该操心的事，应用不该知道** |

### 3.1 现有资产

`echo-server/src/main/java/com/echo/infra/vector/` 下已有 `IVectorStore`（接口）、
`PgVectorStore`（pgvector 实现）、`InMemoryVectorStore`（兜底）、`ScoredId`。
接口形状 `upsert(accountId, vector)` / `get(accountId)` / `topN(query, k, threshold)`。

⚠️ **它已经是个抽象，但绑死在 `accountId` 和 `t_self_vector` 上**，不通用。
内化到引擎时要泛化成「任意实体的任意向量列」。

⚠️ `IVectorStore.encode()` 有一个按字符求和的假 embedding 兜底实现。
迁移时要判断它是保留（无 embedding 服务时不至于崩）还是删除（假向量的检索结果是噪声，
留着可能比崩更坏）。**这一条需要单独决定，不要顺手处理掉。**

## 4. 🔴 待确认（五条）

### 4.1 查询意图用什么形态表达

- **A. 类型安全 Builder** —— `repo.query().eq("authorId", id).isNull("deletedAt").orderByDesc("publishedAt").limit(20).list()`。最灵活，学习成本低，但拼错列名要到运行时才发现。
- **B. 注解式命名查询** —— 在 Repository 接口上写 `@Query`，引擎解析成 SQL。最声明式，但要实现一套解析器。
- **C. 两者都要** —— 常用走注解，复杂走 Builder。

**定它需要**：判断团队更在意「写起来快」还是「改起来安全」。

### 4.2 `Aengine` 要不要保留 MySQL 能力

⚠️ 引擎原本是 MySQL 的（`@Column.charset()` 默认 `utf8mb4`，`JDBCRepository` 是 MySQL 实现），
PG 那份是 echo 侧的适配。jsonb、局部索引、pgvector **都是 PG 独有**。

- **A. 就此定为 PG 专用** —— 实现最简单，删掉 MySQL 分支。
- **B. 引入方言层** —— 保留两套，PG 独有特性在 MySQL 方言下抛不支持。

**定它需要**：确认 `Aengine` 以后会不会用在别的（MySQL 的）项目上。
本轮已核实**当前只有 `echo-server` 一个消费方**。

### 4.3 DDL 的事实源放哪

- **A. 注解生成，`schema.sql` 废除** —— 彻底单源，但失去「一眼看全库结构」的文件。
- **B. 注解生成，`schema.sql` 降级为生成产物**（提交进仓库，供 review 与冷启动）。
- **C. `schema.sql` 保留为权威，注解关掉 `autoCreate`** —— 改动最小，但注解就只是映射不是定义。

**定它需要**：判断是否需要保留一个人可读的全库结构快照。⚠️ 选 B 要配一条
CI 检查「生成结果与提交的文件一致」，否则又是两个源。

### 4.4 迁移节奏

- **A. 先把引擎扩完，再一次性迁完** —— 中间态短，但引擎扩完之前无法验证设计对不对。
- **B. 逐域灰度** —— 先扩查询端三样（`R1`/`R2`/`R3`），拿一个域（建议**作品域**，
  它最新、只有 5 条 SQL、有测试）跑通，再推广。

⚠️ 倾向 B，理由是 A 有一个具体风险：**引擎 API 设计得对不对，只有真正迁一个域才知道**，
而那时引擎已经扩完了，返工成本最高。

### 4.5 联表做到什么程度

- **A. 只做按外键取关联实体** —— 引擎解析 `@Fk`，提供 `fetch` 语义，不支持任意 join。
- **B. 支持投影到 Record/DTO** —— 能表达现有那 2 处 join。
- **C. 支持任意 join 返回 Map** —— 最灵活，但等于把 SQL 换了个写法，容易退化。

⚠️ 现有代码只有 **2 处 JOIN**，用量证据不支持一上来做 C。

## 5. 不在本次范围内

- **WS 那 8 条协议入口的存废** —— 属推翻 `QA6` 的「并存」，需单独拍板（`TECH-DB-INVENTORY §11`）。
- **`t_topic` 从零实现** —— 话题树是产品功能，不是持久化重构。
- **软删补列本身** —— `t_memory_card` 补 `deletedAt` 是数据模型变更，
  应在引擎具备 `D1`（局部索引）与 `R3`（`IS NULL` 谓词）之后做，否则补了也守不住。

## 6. 迁移期已知的改写项

「只做 fetch、不支持任意 join」这条定下后，现有 2 处 `JOIN` 都要改写。**两处都能等价表达，
不构成阻塞**，但形态不同，逐条记下免得迁移时重新分析：

### 6.1 `PgModerationStore.readResult`（`PgModerationStore.java:386`）

```sql
FROM "t_memory_card" c JOIN "t_moderation" m ON m."id" = ?
WHERE c."id" = ?
```

⚠️ **它根本不是 join。** `ON` 子句是个常量过滤而不是关联条件，实际语义是
「一次往返把两张表各一行读回来」的笛卡尔积。改写：**同一事务内两次 `get(id)`**。
语义不变，多一次往返。

### 6.2 `PgEchoStore.reactionsReceived`（`PgEchoStore.java:563`，功能「被接住」`B20`）

真 join，但形态是**顺着外键过滤**：取「某人名下所有宠物」收到的「记得」，
再与献花流水 `UNION ALL` 成一条按时间倒序的归一列表。

改写成三步：

1. `petIds = petRepo` 按 `ownerAccountId` 取（外键侧）
2. 献花：`toOwnerAccountId = X AND fromAccountId <> X`，倒序取 `limit` 条
3. 记得：`petId IN petIds AND accountId <> X`，倒序取 `limit` 条
4. 应用层归并两个有序列表，截断到 `limit`

🔴 **两侧各取 `limit` 条再归并截断，结果与原 SQL 一致**（归并排序的性质），
不要为了省事只取一侧。代价是多两次往返、最多多取 `limit` 行。

⚠️ 这条依赖 `R4` 的 `IN` 与**不等于（`<>`）**。起草时 `R4` 只写了「范围与 `IN`」，
**`<>` 要一并纳入**，否则这个查询表达不出来。
