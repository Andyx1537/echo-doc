# 产品定案后的级联交付协议

本协议把一项已确认的产品决定转换为前端、后端、QA 可共同完成的功能切片。目标不是让三个专业分别“做完自己的部分”，而是让同一个用户结果经过评估、契约冻结、实现、真联调和验收后闭环。

## 1. 单一协调对象

每项已确认变更创建一个 `deliveryId` 和一份 `docs/delivery/<deliveryId>/MANIFEST.md`。该文件是该功能切片唯一任务账本，所有专业读取同一个基线版本，只回填本专业结论，不复制成互不关联的任务说明。

命名采用业务语义，例如 `PD-20260903-work-interaction`；不得包含编辑工具、人员或 agent 来源。

协调负责人只负责状态推进、差额分发、依赖和证据归档，不代替产品、前端、后端或 QA 作专业判断。

## 2. 级联状态机

```text
DRAFT
  → PRODUCT_CONFIRMED
  → DISTRIBUTED
  → TECH_ASSESSING
  → CONTRACT_REVIEW
  → READY_FOR_DEVELOPMENT
  → IMPLEMENTING
  → INTEGRATING
  → QA_VERIFYING
  → PRODUCT_ACCEPTING
  → ARCHIVED
```

允许的回退状态：

- `STOP_PRODUCT_REVIEW`：主干、大方向或产品语义需要重新定调；
- `BLOCKED_DEPENDENCY`：环境、外部依赖、数据或权限无法满足；
- `REWORK`：联调或 QA 失败，退回对应责任方；
- `SUPERSEDED`：新决策替代本任务，原账本只读保留。

任何契约变化都必须从当前状态回到 `TECH_ASSESSING` 或 `CONTRACT_REVIEW`，更新版本后重新获得三方确认。不得口头修改后沿旧任务继续编码。

## 3. 自动派发触发器

产品定案只有同时完成以下动作才视为 `PRODUCT_CONFIRMED`：

1. 决策登记和简述基线已经更新；
2. 旧方案、当前实现、新方案和精确差额已经列明；
3. 主线步骤、对象、状态、权限、用户旅程和非目标已经明确；
4. 受影响规格、接口和可执行验收已更新或明确列为待技术评估；
5. 文档提交已推送远端并记录提交号。

达到后，协调负责人立即创建交付账本，并同时派发三个只读评估任务：

- 前端评估：页面、状态、导航、接口消费、缓存恢复、设计资产与工作量；
- 后端评估：数据、API、状态机、权限、事务、迁移、运行风险与工作量；
- QA 评估：规格可测性、红线、测试数据、联调场景、回归范围与工作量。

三方评估可以并行；在三方回执齐全前，不得把实现任务分给开发 agent。

## 4. 统一派发包

每次派发只发送当前版本相对上一版本的新差额，同时保留以下完整定位信息：

- `deliveryId`、`decisionId`、基线提交号和任务版本；
- 产品主线步骤、受影响系统和用户结果；
- 旧定案、当前实现、新定案、精确差额和被替代条目；
- 用户角色与完整状态矩阵；
- 对象、主键、生命周期、权限、可见性和事实来源；
- API、DTO、空值、ID 语义、状态机、错误、时序、幂等和分页；
- 非目标、保留不变量、迁移和兼容边界；
- 依赖关系、文件所有权、目标仓库、基线提交和分支；
- 验收用例、测试数据、运行开关、回滚和观测要求；
- 需要专业方确认的问题和回执期限。

禁止只转发一句需求、一个设计稿或一个文档链接。链接不能替代差额摘要。

## 5. 三方评估回执

三方统一先返回：

```text
ACK: accepted | accepted-with-risks | blocked | needs-product-decision
Owner:
Expected window: 区间 + 依赖条件 + 置信度
Reuse / add / migrate / replace / deprecate / unchanged:
Affected files, modules, contracts and systems:
Dependencies and ordering:
Risks and failure behavior:
Open questions:
Evidence and acceptance plan:
```

### 5.1 前端必须补充

- 页面、路由、组件、视图模型和接口映射影响；
- 匿名/绑定、本人/他人、私域/公开的完整 UI 状态；
- 默认、加载、空、失败、禁止、冲突、离线、成功和返回路径；
- 缺失后端契约，按 `data/state/action/error/timing/authority` 报告；
- Mock 与真接口一致策略、截图/交互证据和真后端 E2E 计划。

前端不得通过隐藏按钮、本地状态、Mock 字段或客户端计算创造服务端业务规则。

### 5.2 后端必须补充

- 表、索引、DTO、API、协议、状态机、缓存、任务和外部依赖影响；
- 权限、可见性、审核、幂等、事务、并发和一致性；
- schema 版本、迁移/回填、兼容窗、双读写退出条件和回滚；
- 超时、重试、降级、容量、成本、安全、监控和告警；
- 提供给前端与 QA 的固定契约、样例、夹具和可信验证路径。

后端不得只交付字段或路由而遗漏状态迁移、失败语义和用户可见结果。

### 5.3 QA 必须补充

- 规格歧义、冲突和不可执行验收项；
- 受影响用例集、核心烟测、产品红线和发布前全量回归范围；
- 真联调环境、数据、开关、设备和可观测性需求；
- 前后端消费者/提供者契约检查及负路径；
- `PASS / REWORK` 可测性意见。

QA 不得以 Mock 成功或单端测试通过证明整条用户链路完成。

## 6. 联合契约冻结门

只有同时满足以下条件，状态才可进入 `READY_FOR_DEVELOPMENT`：

1. 前端、后端、QA 回执齐全；
2. 前后端共同确认 API、DTO、ID、状态、权限、错误、时序和幂等；
3. QA 确认可执行验收、联调环境和测试数据；
4. 依赖图、文件归属、分支、合并顺序与回滚路径已明确；
5. 所有 `needs-product-decision` 已由产品与技术共同定调并回写基线；
6. 契约版本或提交号写入交付账本。

三个结论分别记录为 `FE_ACK`、`BE_ACK`、`QA_ACK`。任一不是 `accepted` 或已签收的 `accepted-with-risks`，不得开始实现。

## 7. 开发 agent 协调

契约冻结后，协调负责人按依赖图拆分 agent：

- 每个 agent 只持有一个可独立验收的任务、明确文件所有权和禁止修改区；
- 共享契约文件指定唯一 owner，其他 agent 只提差异反馈；
- 前后端可并行实现，但消费者与提供者测试使用同一冻结契约版本；
- 依赖任务未完成时可完成本地实现和测试，不得以 Mock 宣称整链完成；
- 每个提交都带 `deliveryId`，回填提交号、测试证据、实际差异和剩余依赖；
- 新发现若改变契约或产品语义，立即触发停止闸，不得由 agent 自行选择替代方案。

## 8. 强制停止与重新定调

出现以下任一情况，状态立即转为 `STOP_PRODUCT_REVIEW`，暂停相关编码、合入和发布：

- 改变产品主线、系统边界、核心对象身份/主键/生命周期或事实来源；
- 改变私域/公开边界、用户权限、隐私、授权、审核、删除或安全政策；
- 改变主要用户流程、可见结果、关键文案或成功/失败语义；
- 需要破坏性 API、协议、schema 或旧客户端不兼容迁移；
- 前后端对字段、ID、状态、权限、错误、时序或幂等理解不一致；
- 需要前端临时承担后端权威，或只能用静默降级、假实现完成；
- 实现事实推翻产品前提，或成本、工期、容量、安全、合规显著超出定案前提；
- 验收标准不可执行、真源冲突或回滚不可行。

恢复步骤固定为：技术提交影响与备选 → 产品与技术联合定调 → QA 更新验收影响集 → 基线和契约升版 → 重新派发差额 → 三方重新 ACK。旧任务版本标记 `SUPERSEDED`，不可恢复使用。

## 9. 联调、缺陷与验收闭环

### 9.1 真联调门

进入 `INTEGRATING` 时必须固定：前端提交、后端提交、构建产物、环境、schema/迁移版本、开关和测试数据。逐端点保存真实请求/响应与错误态证据。Mock 只用于组件状态，不是联调证据。

### 9.2 缺陷状态

缺陷统一使用：

```text
OPEN → ACCEPTED → FIXING → READY_FOR_RETEST → VERIFIED → CLOSED
                                      ↘ REJECTED / REOPENED
```

每条缺陷包含责任方、严重度、对应定案/契约、复现、期望、实际、修复提交和复验报告。修复不能改变定案；需要改变时转产品停止闸。

### 9.3 QA 分层验证

- 每次提交：专项测试与受影响用例；
- 每个功能切片联调：前后端契约、核心烟测、负路径和受影响回归；
- 候选版本：全量产品红线与发布门禁。

QA 报告必须绑定被测提交、构建、环境、数据和契约版本。`Blocker > 0` 或 `Major > 0` 不得 PASS；任何例外需要产品、技术、QA共同风险签收、责任人和到期日。

### 9.4 收尾

只有以下证据齐全才可 `ARCHIVED`：

- 产品确认用户结果与定案一致；
- 前后端真环境整链路通过；
- QA 明确 PASS，并记录报告和被测版本；
- 迁移、回滚、监控、告警和操作说明就绪；
- 文档已更新为实际实现状态，未完成项有 owner 和期限；
- 各仓分支/提交/合并关系已记录并推送远端。

局部前端 PASS、局部后端 PASS 或单元测试全绿，均不能替代整条功能切片的联合完成证明。

## 10. 反馈时效

- 接单后第一回执必须先确认“已收到、读取的基线提交、是否具备评估条件”；
- 发现停止条件时立即反馈，不等待阶段结束；
- 无实质变化时报告阻塞原因和下一解除条件，不制造虚假进度；
- 具体小时数由每个交付账本按优先级填写，公共协议不写死统一时限。
