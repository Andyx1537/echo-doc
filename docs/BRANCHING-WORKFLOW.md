# 回声三仓统一分支、版本标记与状态对齐

> 状态：已确认 · 2026-09-03
> 适用仓库：产品文档、服务端、客户端。
> 唯一目标：三仓始终能回答“当前定案是什么、前后端分别实现到哪里、哪组提交共同构成一个可验收候选”。

## 1. 三条长期分支

| 分支 | 统一职责 | 允许内容 |
|---|---|---|
| `develop` | 唯一持续开发与产品定案线 | 已确认产品文档、日常代码、测试、联调修复、实现状态回填 |
| `release` | 唯一候选发布线 | 只接收三方验收通过的候选版本，不做日常修改 |
| `master` | 冻结历史基线 | 不再跟进维护，不接收定案、开发、修复或发布提交 |

文档仓的产品定案只有进入远端 `develop` 才算当前定案。业务分支可以用于隔离并行修改，但未合入 `develop` 的内容只能称为候选或草案。

前端和后端开发使用业务中立功能分支，完成专项验证后合入各自 `develop`。不得让多个并行任务直接覆盖同一未提交工作区；不得从 `master` 开新功能。

## 2. 每项定案的三仓对齐

产品定案进入文档仓 `develop` 后，级联交付账本必须记录：

```text
productCommit: 文档 develop 提交
frontendBase: 客户端 develop 基线提交
backendBase: 服务端 develop 基线提交
contractVersion: API/协议/状态机版本
frontendImplementation: 实现提交或 pending
backendImplementation: 实现提交或 pending
qaEvidence: 被测构建与报告或 pending
```

前后端无需拥有相同提交哈希，但必须引用同一 `deliveryId`、产品提交和契约版本。任一端改变共享契约，任务返回联合契约评审并更新三仓映射。

## 3. Tag 与 release 的区别

- `release` 是会继续前进的候选分支；Tag 是不可移动的版本坐标。
- `baseline-YYYY.MM.DD` 只记录某次三仓状态盘点的已提交基线，不表示可发布。
- `vX.Y.Z` 才表示正式候选通过并进入发布归档；三仓必须使用同一个版本号。
- 同名 Tag 在三个仓指向各自对应提交，映射写入对齐报告和交付账本。
- 工作区未提交修改不属于 Tag。Tag 打错不得移动或覆盖，只能增加修订 Tag。

## 4. 正式版本流程

1. 产品定案与契约已进入文档 `develop`；
2. 前后端各自功能提交进入 `develop`；
3. 固定文档、前端、后端提交和构建进行真联调；
4. QA 对固定候选给出 PASS，Blocker 与 Major 均为 0；
5. 三仓分别把同一候选送入 `release`；
6. 三仓在各自 `release` 对应提交创建相同 `vX.Y.Z`；
7. 推送分支和 Tag，并在交付账本记录远端提交；
8. 下一周期继续从已发布基线推进 `develop`。

任何一仓未验收，三仓都不得创建正式版本 Tag。

## 5. Master 冻结规则

- 不删除 `master`，保留历史追溯和仓库兼容；
- 远端默认分支改为 `develop`；
- 不再向 `master` 合并 `develop/release`；
- 文档、流水线和人员入口统一指向 `develop`；
- 紧急修复也从 `develop` 开始，验收后进入 `release`，不直接改 `master`。

## 6. 未提交修改保护

建立分支不会自动把未提交文件变成基线提交。发现既有修改时必须：

1. 保持文件原样；
2. 登记所在仓库、分支和文件范围；
3. 确认归属后再决定提交、拆分或继续开发；
4. 未确认前不得把它们纳入基线 Tag，也不得用清理命令丢弃。

## 7. 验收

- 三仓远端均存在 `develop` 与 `release`；
- 三仓工作入口均为 `develop`，`master` 不再前进；
- 对齐报告记录三个 `develop` 提交与未提交差异；
- 同名基线 Tag 在三仓远端可见，且映射到报告中的提交；
- 正式版本只有在交付账本、真联调和 QA 证据齐全后产生。
