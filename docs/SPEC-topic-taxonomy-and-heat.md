### 0.2 含义：这不是「部分失效」

> 🔴 **已拍板的这些东西，全部是对一个不存在的系统写的规格：**
> 权重衰减 `W = W0·γⁿ·T_eff·brakeFactor` · 负反馈制动的二维档位表 · `SURGE` 热点召回 · 八路召回通道与优先级 · 两层成分配比（45/30/25 与 25/40/35）· `HOT` 份额与差额转移 · `F1`–`F6` 加权打分公式 · 本文档设计的这整套话题树与层级衰减。

**「四张表缺失导致 30% 权重恒为 0」这个说法把问题说小了。** 不是 30%，是 100%——`score` 公式一行都没写。四张表是引擎的**输入**，引擎本身还是空的。

⚠️ **它为什么难被发现**：这套东西**不报错**。三个纯函数模型的单测全绿，日志里一句异常也没有，报表上看起来就是「这批内容的权重都很稳」。仓库里唯一喊出这件事的是启动告警 `RankingReadiness`，而它喊的是下游（`n` 恒为 0），不是「引擎不存在」本身。

### 1.4 🔄 「五维正交与三级树不相容」——**本条 v0.1 的结论整条作废，原因是我读窄了树的模型**

> 🔴 **按本项目纪律，被推翻的结论保留原文并注明推翻时间与原因，不直接删。**

| 项 | 内容 |
|---|---|
| **推翻时间** | 2026-08-26（v0.1 交付后当轮） |
| **v0.1 的原结论（❌ 已作废）** | ~~「正交维度装不进一棵树。一张卡同时是『猫』『90 年代』『江苏』『雨天』——做成树就要 `猫 > 90年代 > 江苏 > 雨天` 这类笛卡尔积分支，节点数是各维度基数的乘积，换个层级顺序就是完全不同的一棵树。」~~ 并据此给出「A：树只管题材 / B：树替换五维」二选一 |
| 🔴 **错在哪** | **原结论隐含了一个没写出来的前提：整个体系只有一棵树、只有一个根。** 产品负责人的原意不是这个 |
| **裁定原话** | 「题材年代地域场景不是三级树里面的对应的一些树的主干吗？用三级树概括成对应分类不就是 5 个维度了吗」 |

**✅ 正确的模型：每个维度各自是一棵树（各自是一根主干），树形结构长在维度内部，维度之间仍然正交。**

```
题材 theme     宠物 ──┬── 猫 ──┬── 英短            深度 3
                      │        └── 布偶
                      └── 犬 ──┴── 金毛
地域 region    中国 ──┬── 江苏 ─── 南京            深度 3（国→省→市）
年代 era       ──┬── 90s                          深度 1
场景 scene     ──┬── 雨天                          深度 1（或按需 2）
热词 hotword   ──┬── 铁皮文具盒                    深度 1
```

🔴 **「最多 3 级」是上限，不是要求。不同维度深度不一，完全正常。**

**由此，v0.1 里下列结论一并失效（逐条列出）：**

| # | v0.1 的说法 | 现状 |
|---|---|---|
| 1 | 「五维正交与三级树不相容」 | ❌ **作废。** 相容，且本来就该这么设计 |
| 2 | 「读法 B：树替换整个标签体系」这个选项 | ❌ **作废。** 它是误读的产物；正确模型下不存在「替换」这回事 |
| 3 | 「`era`/`region` 要从 P0 撤回，推翻 `t3` 裁定」的担忧 | ❌ **作废。🟢 `t3`（地域年代提到 P0）不撤回** |
| 4 | 「`F3` 分维权重 0.50/0.20/0.20/0.10 整套作废」的担忧 | ❌ **作废。🟢 分维权重保留**（但见 §5.5 一处新发现的失真） |
| 5 | 「树只是题材维度的内部结构，需要一句确认」 | 🔄 **方向对，范围放宽**：**任何维度都可以有内部层级，只是深度不同**。不再是待确认项 |
| 6 | 拍板清单第 1 条（A/B 二选一） | ❌ **撤销。** 已裁定 |
| 7 | `β = β^(3−level)` 粗标惩罚的公式形态 | ❌ **作废**，且有两个独立原因（§5.3）：硬编码的 `3` 假设了所有维度都三级；卡强制挂叶之后它也没有目标了 |
| 8 | §11 建议改动第 5 条（`t_tag` 结构） | 🔄 **改写**：`level` 是**维度内层级**不是全局 1/2/3；`parentId` 是**各维度树内父指针**，不只服务题材 |

**两条连带的机制约束（正确模型下才成立的）：**

1. 🔴 **层级匹配与衰减一律在维度内部进行。** `sim(p, c)` 只在 `p.dimension == c.dimension` 时有定义；**跨维度不算距离**（两棵树之间没有边）。
2. 🔴 **跨维度的组合仍走既有的分维权重**（题材 0.50 / 年代 0.20 / 地域 0.20 / 热词 0.10，`SPEC-recommendation-ranking.md:930`）。**层级机制不改顶层结构，只改每一维内部怎么算那个 [0,1] 的重叠度。**

**🆕 补一条职责划分（裁定原话，v0.3 追加）：**

> 「5 维设计是开始的时候定档基调，需要保存或者达成通识共鸣的基调，我们用三级只是推荐层面」

即 **两者各管一头，都保留，不是一个取代另一个**：

| | 五维 | 三级树 |
|---|---|---|
| 管什么 | **定基调**——这张卡是关于什么的，用来保存与达成共鸣 | **推荐层的检索与衰减**——从哪一层取、差几级打几折 |
| 面向谁 | 用户（建档时选、聚合页看） | 排序引擎（内部） |
| 变更成本 | 高，动了就是产品语义变了 | 低，是策略参数 |

🔴 **实现上的含义：维度的增删是产品决策，层级的深浅是运营/策略决策。** 前者要走裁定，后者运营台改词表即可。**不要把它们做进同一个配置面板**，否则运营调一次词表深度，会被误当成动了产品语义。

## 3. 🔴 通则：归类维度 vs 亲和信号

> **本节从「情感类话题」这一个案例升为通则。将来还会有别的维度需要「能归类但不参与分发」，不能每次重新论证一遍。**

### 3.1 通则本身

**树上的每个节点承担两个互不相干的职能，二者可以独立开关：**

| 职能 | 问的是 | 开关 | 关掉之后 |
|---|---|---|---|
| **内容归类** | 这张卡是关于什么的？ | 节点存在与否 | 卡无处可挂 |
| **亲和信号** | 这个 viewer 偏好什么？ | `excludedFromAffinity` 布尔（§4.6） | 卡照常归类、照常参与打散与供给反算，但**永不进任何人的偏好向量，也永不作为匹配目标** |

🔴 **禁入是双向的**：既不进 viewer 的偏好向量（不管他发过多少张、献过多少花），也不作为 `sim()` 的匹配目标。**单向禁会漏** —— 只禁前者的话，一个偏好「猫」的用户照样会因为某张情感类卡"离猫很近"而被推。

### 3.2 🟢 这条通则不是新发明的，仓库里已有三处同构先例

| 出处 | 原文要点 | 同构在哪 |
|---|---|---|
| **`PRD-RESONANCE-PUBLISHING.md:228`** | 推荐候选维度「主题」的**禁止误用**栏：🔴「**不把『告别/痛苦』作为流量标签**」 | 🔴 **这是本通则最直接的先例。** 同一份 PRD 的 `:66` 把「告别」「陪伴」列为**正常的主题选项** —— **可以归类，不可以当流量标签**，一字不差就是本通则 |
| `SPEC-recommendation-ranking.md:500`（`X1`） | 禁用「情绪强度 / 悲伤浓度 / 催泪度（任何名字、任何形态）」。理由：「刚失去的、情绪更浓烈的内容互动率天然更高，一旦让排序学到，产品会自动演化成悲情内容流」 | `X1` 禁的是「**进排序**」，不是「不许存在」 |
| `SPEC-recommendation-ranking.md:505`（`X6`）+ `:2096`（`RK4`） | 互动计数完全不进 `score`；`F7` 整条删除 | 同一形态：**数据可以存在、可以统计、可以进后台，就是不进打分** |

> ✅ **所以本通则是把一条已经存在于三处的做法显式化，不是新增约束。** 这一点在评审时很重要：它不需要论证正当性，只需要论证覆盖面。

### 3.3 应用：情感大类（已裁定）

**裁定三条：① 建「情感」大类；② 只归类、永不参与亲和匹配；③ chip 不对外展示。**

**① 建大类** —— 核实：既有词表里确实没有「情感」。

| 出处 | 现有取值 |
|---|---|
| `SPEC-recommendation-ranking.md:716` | 宠物 / 校园 / 家庭 / 地点 / 关系 / 日常 |
| 前端 `echo-h5-proto/src/types.ts:107` | `pet / youth / family / place / relationship / daily` |

**两边一致，都是六值。** 所以这是一次新增。🟢 **建它的主要收益不是归类整齐，而是 §4.6 的禁入布尔只有在情绪类聚成一棵子树时才可继承** —— 散在六个大类下面就只能逐词标，退回「记得去加」的黑名单模式。

**③ chip 不对外，依据要写清** —— 🔴 **「降低负面情绪导向」的落点在分发层，不在命名层。**

| 层 | 做法 | 为什么不够 / 为什么是它 |
|---|---|---|
| 命名层 | 不叫「痛失爱宠」叫「思念」 | 🔴 **改个名字不影响它被推给谁。** 两个词在匹配上都是 0（都禁入），改名只改变用户读到什么 |
| **分发层** ✅ | 禁入亲和（§3.1）+ **chip 不对外** | 🟢 禁入堵死「推更催泪的给你」；chip 不外露堵死剩下那条路——**用户点开一个叫「痛失爱宠」的聚合页，看到一整屏最痛的内容**。那不是排序问题，是聚合页问题 |
| 展示层的另一种做法 | 有归类但整体隐藏 | 🔴 **不做。** 制造一个用户无法理解也无法撤销的隐藏状态，与 `SPEC-feed-surfaces.md:305-306` 的可解释性、可撤销性两条判准正面相反 |

⚠️ **「chip 不对外」的两条实现含义**（不写清会被实现成不同的东西）：

1. **不出现在题材 chip 列表、不生成聚合页、不进搜索的主题分区**（`types.ts:396` 的 `SearchTopic`）。
2. 🟢 **但在「作者自己那张卡上」仍可显示** —— 作者知道自己选了什么，这是可解释性要求的。**隐藏的是「入口」，不是「这张卡挂了什么」。**
3. 🔴 **连带：情感类节点不得作为 `R6` 关注对象。** 没有 chip 就没有关注入口，这一条是自然结果，但要写下来防止后台另开一个入口。

### 3.4 兜底路径的后果（比预想的复杂，必须一起看）

**问题**：一个只发过情感类内容的用户，亲和向量是空的，会掉进什么路径？等于「新用户」吗？

**核实结论：不完全等于，但相关性是坏的。** `AFFINITY` 由四路召回承担（`SPEC-feed-surfaces.md:193-196`），禁入**只打空其中一路**：

| 通道 | 上限 | 受不受影响 |
|---|---|---|
| `REL` 亲友 / 共同守护 | ≤4/20 | 🟢 不受影响 |
| `FOL` 关注的发布者 | ≤4/20 | 🟢 不受影响（`REL`+`FOL` 合计受 `C5+C5b` 约束 ≤6/20） |
| `TAG` 多维标签 | ≤8/20 | 🔴 **空转** |
| `VEC` 共鸣相似 | ≤8/20 | ➖ P0 默认关闭（门控未就绪） |

- 🟢 **只要他有亲友或关注过任何人，就不等于新用户** —— `AFFINITY` 上限降到 6/20 = 30%（瀑布目标 45%）。
- 🔴 **但只发情感类内容的用户，恰好最可能是既没亲友也没关注的那种**（一个人来的、不社交的）。**两件事正相关，不是独立的。** 在这个交集上，他确实等于新用户。

**⚠️ 顺带查出一处规格空白：**

> `SPEC-feed-surfaces.md:218-244`（§3.2.3）只写了 **`HOT` 差额**的处置。
> 🔴 **`AFFINITY` 兑现不足时差额往哪儿去，规格里是空的。** 上面那种用户会直接踩到它，而缺省实现多半是「补到最方便的那个成分上」——`§3.2.2` 的取整规则里警告过同型问题。

**这个后果可以接受，三条理由**（供推翻）：

1. **代价比听起来小。** 被打掉的只是**这个用户自己**的个性化。他发的情感类内容照样能被别人的 `FRESH`/`HOT`/`REL` 通道看到——**归类职能保留意味着他的内容不会消失**。
2. **新用户路径不是惩罚路径。** `FRESH` 保底 ≥3/20 是下限不是上限，差额又都朝 `FRESH` 偏。
3. 🔴 **反过来的代价更大。** 允许情感类进亲和，一个只发悲伤内容的用户会被精确地喂更多悲伤内容——**这正是 `X1` 一字不差描述的场景**，而且发生在最脆弱的那批用户身上。

## 4. 树的结构与词表

### 4.1 每维一棵树（已裁定，见 §1.4）

**`t_tag` 的层级字段是维度内的**：`level` 从 1 开始数到该维度树的最深层；`parentId` 指向同维度内的父节点。🔴 **不同维度的 `level=2` 不是同一件事，任何跨维度比较 `level` 的代码都是错的。**

### 4.2 「挂到叶子」的精确定义（`force_leaf`）

**裁定：卡不允许挂非叶子节点。**

🔴 **精确定义：挂到「该维度这条路径上的最深可用层」，不是一律第 3 级。**

| 维度 | 最深层 | 叶子在哪 |
|---|---|---|
| 题材 | 3 | 第 3 级 |
| 地域 | 3（国→省→市） | 第 3 级；⚠️ 但直辖市只有两级，那么第 2 级就是叶 |
| 年代 / 场景 / 热词 | 1 | **第 1 级就是叶** |

**判据写成一句可机械执行的**：**`t_tag` 里没有任何 `parentId = 本节点` 的 `status='on'` 行 → 本节点是叶。**
🔴 **叶不叶是查出来的，不是按 `level` 判的。** 按 `level = 3` 判，直辖市和所有单层维度全都挂不上去。

⚠️ **一条随之而来的动态风险**：给一个叶子加子节点，会让它**当场变成非叶**，而已经挂在它上面的存量卡就全部违反 `force_leaf` 了。**建议**：`t_tag` 加子节点时，若父节点已有卡挂载，**必须同时为这些卡指定迁移目标**（通常是新建的兜底叶，§4.3）——写成建表约束或运营台的强制步骤，不要靠人记得。

#### 4.2.1 🆕 `force_leaf` 只约束**存储**，不约束**检索**（这一条不写死一定会被实现窄）

裁定原话：

> 卡必须挂到叶子意味着，该张卡有明确的叶子定位，但是仍旧在主干、分支上面可以有挂信息，就是说三个层级上面均可以 search 到该张卡。只是优先级的差异。

**我核实了 v0.2 的表述，结论分两半：**

| 处 | v0.2 写的 | 是否已是这个意思 |
|---|---|---|
| §5.1 召回阶梯 | 「放宽到父节点，**召回整棵子树**」 | ✅ **已经是**。放宽到 `猫` 时召回 `猫` 整棵子树，挂在 `英短` 的卡自然命中 |
| §5.2 打分 | `sim = δ^dist`，含「卡在偏好的父节点 = 0.600」 | ✅ **已经是**。距离是树上边数，从任何一层量都有定义，不是只在叶层比对 |
| §4.2 | 「卡不允许挂非叶子节点」 | 🔴 **窄了**。这句话孤立读会被理解成「卡只属于那一个叶子」，而正确的意思是「卡只**存**在那一个叶子上」 |

**所以要补的是一句语义定义，不是改机制**：

> 🔴 **标签只存储在叶子上；由树的父子关系，一张卡自动隶属于它所挂叶子的全部祖先节点。三层都能检索到同一张卡，差别只在检索的起点与优先级。**
>
> 「祖先隶属」是**推导出来的，不落库**。🔴 不要为了查询方便去给每张卡额外写祖先行——那等于把 `force_leaf` 的唯一性又打破了，而且树一改就全部失效。

**这一条有两个具体落点，都不在 §5 的召回阶梯里，容易被漏掉：**

1. **题材聚合页 / 搜索**：用户点 `猫`，必须看到挂在 `英短`/`橘猫`/`其他猫` 的全部卡。这不走 TAG 通道，是另一条查询路径，🔴 **它同样要做子树展开**。
2. **禁入名单的继承**（§4.6 已按继承设计）与这里是同一套父子关系，两处必须用同一个实现，不要各写一遍。

**实现选型（真正的开放项，代价不同）：**

| 做法 | 代价 | 适用 |
|---|---|---|
| **递归 CTE**（`WITH RECURSIVE` 展开子树） | 每次查询都要递归；树只有 3 级、节点数百量级时开销可忽略 | 🟢 **建议先用这个**。树浅、量小，不值得提前优化 |
| **物化路径**（`t_tag.path = '/1/17/243/'`，前缀 `LIKE` 匹配） | 树结构变更要批量重写 `path`；但查询变成一次索引扫描 | 节点数上万或聚合页成为热点后再换 |
| **闭包表** | 最灵活，但多一张表要维护一致性 | 🔴 **本项目不需要**，3 级树用不上 |

⚠️ **不是开放项、不要犹豫的**：「祖先隶属」是逻辑推导，**任何一种做法都不改变语义**，只改变查询开销。选错了可以换，不会污染数据。

### 4.3 🆕 兜底叶：从「垃圾桶」变成必需设施

> **v0.1 里我把「其他猫」当作 `force_leaf` 的**代价**来论证。裁定 `force_leaf` 之后它变成**设施**，要正经设计。**

#### 4.3.1 存在规则

🔴 **每个非叶节点必须配且只配一个兜底子叶，递归适用。**

```
宠物 (L1, 非叶)
├── 猫 (L2, 非叶)
│   ├── 英短 (L3, 叶)
│   ├── 布偶 (L3, 叶)
│   └── 〔兜底〕(L3, 叶)      ← 猫的兜底
├── 犬 (L2, 非叶)
│   ├── 金毛 (L3, 叶)
│   └── 〔兜底〕(L3, 叶)      ← 犬的兜底
└── 〔兜底〕(L2, 叶)          ← 宠物的兜底：连"是猫是狗"都不适用时的落脚点
```

**这条规则直接解掉裁定里点名的死角**：用户在**任何一层**都有落脚点，不会撞上「我的东西不属于这里任何一项」——而那条路径上他没有退路（已裁定不提供「以后再说」）。

**三条实现约束：**

| # | 约束 | 为什么 |
|---|---|---|
| 1 | **兜底叶由建表时自动生成，不靠运营手动加** | 手动加就会漏，而漏掉的那个节点直到有用户卡在那里才被发现 |
| 2 | 🔴 **`name` 可重复，`slug` 必须唯一** | 树上会有多个都叫「说不清」的节点。`t_topic` 已有唯一索引 `t_topic_uk_slug`（`schema.sql:396`），`t_tag` 沿用。建议 slug 形如 `pet-cat-unspecified` |
| 3 | 🔴 **兜底叶不得作为 `R6` 关注对象** | 「关注：说不清」没有产品含义，且会在偏好向量里造出一个巨大的模糊节点 |

#### 4.3.2 命名：不能读起来像「你没归好类」

🟢 **仓库里已有一个通过了产品调性的先例，直接沿用而不是另造**：`SPEC-recommendation-ranking.md:717` 的 `era` 维度取值是「80s / 90s / 00s / 10s / 20s / **说不清**」。

| 候选 | 判断 |
|---|---|
| **「说不清」** ✅ **建议** | 🟢 **已在既有词表里，语气过过一遍。** 关键在它描述的是**信息状态**（我说不清）而不是**分类结果**（你没归好） |
| 「其他」/「未分类」/「其它 XX」 | 🔴 **禁用。** 「其他」是相对于一个已知全集说的，它在告诉用户「你不在正常选项里」 |
| 上位词单数化（「一只猫」「一条狗」） | 🟡 可用，语气更暖，但**每个节点要单独想一个词**，规模化之后必然有想不好的 |
| 「还没想好怎么归」 | 🔴 **不用。** 把责任推给用户，且暗示他以后该回来改 |

🔴 **无法出图，如实说明**：按 `visual-decisions` 纪律，措辞类选择本该给渲染对比。**但发布界面在前端不存在**（`echo-h5-proto/src/components` 下没有任何发布组件），没有可以把这几个词放进去的屏。**发布 UI 落地后应当补一次真实对比再定案**，现在这三个候选只是文字论证。

#### 4.3.3 🔴 匹配上怎么处理：按普通叶子，不加惩罚

**建议：兜底叶就是普通叶子，`sim()` 不给它任何特殊待遇。**

**这个建议的关键依据是 `force_leaf` 本身**：

> 🔴 **选「猫 > 说不清」和选「猫 > 英短」的点击次数完全一样（都是 3 次）。**
> **兜底叶不比真实答案便宜，所以不存在「偷懒即得利」的激励**——而那正是 v0.1 里 `β` 要防的东西。
> **`force_leaf` 从结构上消掉了这个问题，不需要再用打分去补。**

**反过来看另一个选项，说明为什么不选它：**

| 选项 | 做法 | 判断 |
|---|---|---|
| **(i) 按普通叶** ✅ | 「猫>说不清」与「英短」是兄弟叶，`sim = δ² = 0.36` | ✅ **建议** |
| (ii) 按父节点定位 | 「说不清」语义上就是「猫」，按 `δ¹ = 0.60` 算 | 🟡 **信息论上更对**（一张「说不清品种的猫」有一定概率真的是英短，而布偶的概率是 0）；🔴 **但它让兜底叶压过所有真实兄弟叶**，而兜底叶每一层都有 |

> 🔴 **这是「信息正确」与「激励正确」的冲突，两者不能都要。**
> **建议选激励正确的那个（i）**，理由是：**激励错误会自我放大**（越多人选兜底 → 兜底叶越大 → 匹配越糊 → 更多人只能选兜底），**而信息不精确不会自我放大**。在没有任何数据的情况下，应当避开会自我放大的那一类错误。

**⚠️ 剩下的唯一口子（如实登记）**：浅层兜底叶确实省点击 —— 选「宠物 > 说不清」是 2 次，选「宠物 > 猫 > 说不清」是 3 次。
**建议用两条非打分手段管它，不要用打分惩罚**（打分惩罚会连带惩罚诚实的「我真不知道」）：

1. **UI：兜底叶在子列表里排最后，不加任何视觉强调。**
2. 🔴 **看板：按父节点统计兜底叶占比。** 某节点兜底占比过高（建议观察线 40%，🔴 **这个数是拍的**），说明**它的子叶词表设计得不对**（词不够 / 词看不懂），不是用户偷懒——因为选它并不省事。**这是词表完备性唯一可观测的指标，`force_leaf` 之后它是必须有的。**

### 4.4 🆕 `force_leaf` 对发布流程的体验代价（如实写）

#### 4.4.1 先澄清一件最容易被实现错的事

🔴 **`force_leaf` ≠ 强制填满五个维度。** 它说的是「**你在哪个维度打标，就要在那个维度走到底**」，不是「五维都要打」。

依据（两条都在既有文档里）：
- `PRD-RESONANCE-PUBLISHING.md:68`：**「最低可发布内容：一句话 + 一个主题即可。不要用『请补全更多资料才能发布』卡住用户。」**
- `SPEC-recommendation-ranking.md:734`：地域「用户**显式选择、默认留空**、可随时清空」。

**不写死这一句，实现方会把它读成「发一张卡要选五次到底」。**

#### 4.4.2 真实代价：最低发布门槛从 1 次选择变成 3 次

### 4.7 判准：两道测试

**第一道 · 这个词命名的是「发生了什么 / 是什么」，还是「感觉如何」？**
事件、对象、场所、关系、时期 → **事实类，可入**；感受、心境、情绪强度 → **情绪类，禁入**。

**第二道（兜底）· 把词填进这句话，读起来像不像在说「我们判断你喜欢这种情绪」：**

> 「因为你喜欢 ____ ，所以给你推了更多。」

这一句来自 `SPEC-feed-surfaces.md:305` 的可解释性判准。**说不出口的，就是禁入的。**

| 词 | 判定 | 理由 |
|---|---|---|
| **陪伴** | ✅ **事实类，可入** | 命名的是一段时间里发生的事，有可指认的对象与时段。🟢 **`PRD-RESONANCE-PUBLISHING.md:66` 已把它列为正常主题选项** |

## 5. 匹配：召回阶梯与维度内衰减

### 5.1 两件事要分开：召回阶梯 ≠ 打分衰减

裁定原话「其他的按照第三叶点先获取。不够再去二级大点范围内找，最后再去顶部找」描述的是**召回**，不是**打分**。

**召回阶梯（照裁定落，🔴 在单个维度内进行）：**

```
第 1 轮：取 viewer 在该维度的偏好节点，召回挂在这些节点上的卡
   ↓ 不足 TAG 通道配额（25 条池 / ≤8 条输出）
第 2 轮：放宽到这些节点的父节点，召回整棵子树
   ↓ 仍不足
第 3 轮：放宽到祖父（该维度根），召回整棵子树
   ↓ 仍不足
交给既有降级链（SPEC §12.7），🔴 不要在这里自己发明兜底
```

⚠️ **两条必须写死的实现约束：**

1. 🔴 **阶梯放宽只扩大候选集，不决定顺序。** 扩大后**全部重新按 §5.2 打分排序**。
   **不要实现成「第 2 轮的卡一律排在第 1 轮之后」** —— 那会让一张挂在近处但弱匹配的卡永远压过一张强匹配的卡。**而当拼接顺序与分数打架时，代码里赢的总是拼接顺序，分数会静默失效且不报错。**
2. 🔴 **`SPEC-recommendation-ranking.md:923` 的 20% 探索配额必须保留，不能用阶梯顶替。** 阶梯只在**同一棵树里**放宽，永远出不了用户已有的根；探索配额是**跨根、跨维度**的。两者不重复，都要。少了它，「标签召回会在两周内把用户锁进一个越来越小的题材茧房」（原文）。

### 5.2 打分：维度内一个参数

```
sim(p, c) = δ ^ dist(p, c)          δ = 0.60（🔴 点位待定，见 §8）
```

`p` = viewer 偏好节点，`c` = 卡挂载的节点，`dist` = **同一维度树上两点间的边数**。
🔴 **`p.dimension ≠ c.dimension` 时 `sim` 无定义**（两棵树之间没有边）；同维度但不同根时 `sim = 0`。

| 关系 | 边数 | `sim`（δ=0.6） |
|---|---|---|
| 完全相同 | 0 | **1.000** |
| 卡在偏好的父节点 | 1 | **0.600** |
| 兄弟叶 / 祖父节点 | 2 | **0.360** |
| 叔伯节点 | 3 | **0.216** |
| 堂表叶 | 4 | **0.130** |
| 不同根 | — | **0** |

**该维度的卡得分：**

```
dimScore(u, card, d) = max          Σ  ŵ_p · sim(p, t)
                     t ∈ card.tags[d]  p ∈ prefs(u)[d]
```

🔴 **对卡的多个标签取 `max` 而不是 `sum`，这是刻意的**：题材可挂 3 个，若求和，**挂满 3 个的卡会机械压过只挂 1 个的卡** —— 那是标签堆砌的反向激励。`SPEC-recommendation-ranking.md:823` 已就同型问题登记过担忧。**取 `max` 让堆标签没有收益。**

**跨维度合成不变**，仍走既有分维权重（`:930`）：`tagMatch = 0.50·dimScore(theme) + 0.20·dimScore(era) + 0.20·dimScore(region) + 0.10·dimScore(hotword)`。⚠️ **但见 §5.5 —— 这组权重在引入层级后不再表示实际影响力占比。**

### 5.3 🔴 `β` 粗标惩罚：取消

**v0.1 提的是 `tagAffinity × β^(3−level)`，用来矫正「粗标签占便宜」。核实结论：取消，两个独立原因，任一成立都足够。**

| # | 原因 |
|---|---|
| 1 | 🔴 **它的目标不存在了。** `β` 惩罚的是**挂得粗的卡**。`force_leaf` 之后**没有任何卡挂在非叶节点上**，惩罚项永远作用在一批空集上 |
| 2 | 🔴 **它的公式在正确的树模型下本来就是错的。** `β^(3−level)` 把 `3` 硬编码成"最深层"。修正后每维深度不同——**年代 / 场景 / 热词的叶子都在 `level=1`，会被 `β²=0.49` 整维打折**，而它们已经站在自己维度的最深层了。**这是一个会静默压低三个维度的 bug** |

**核实过它还有没有别的用途 —— 逐个查完，没有：**

| 候选用途 | 结论 |
|---|---|
| 惩罚兜底叶（防偷懒） | ❌ **不需要。** `force_leaf` 下选兜底叶和选真实叶点击次数相同，没有偷懒激励（§4.3.3 完整论证）。且打分惩罚会连带惩罚诚实的「我真不知道」 |
| 处理 `R6` 带来的非叶**偏好**节点（用户关注「猫」而非「英短」） | ❌ **不该惩罚。** 显式关注是最强信号，既有规格还给它 ×2。惩罚它方向相反 |
| 跨维度深度不均的归一 | ❌ **`β` 做不到**（它是逐节点的，不是逐维度的），而且这个问题 `β` 原来也没解决。**它是一个新问题，见 §5.5** |

> ✅ **`β` 取消。** 🔴 **但不要把「取消」读成「那个担忧消失了」** —— 它原来兼着的两件事，一件转移到 §4.3.3 的兜底叶规则上（用 UI 顺序 + 看板占比管，不用打分管），另一件是 §5.5 的新问题。

### 5.4 算例（`force_leaf` 模型下重做）

| 用户偏好分散程度 | 一个精确命中叶得分 | 浅层兜底叶得分 |
|---|---|---|
| 3 个偏好（本算例） | 0.634 | 0.216 |
| 5 个偏好，各 0.2 | ≈ 0.304 | 0.216 |
| **10 个偏好，各 0.1** | ≈ **0.217** | **0.216** |

> 🔴 **偏好越分散，浅层兜底叶越接近精确命中，在 10 个左右打平。**
> 这不是错误，是距离衰减的固有性质。**但它是 §4.3.3 里「兜底叶占比要进看板」这条监控的真正理由** —— 兜底叶占比高的时候，这个效应会同时从两头放大（更多卡挂兜底 + 用户偏好被摊薄）。

### 5.5 🆕 维度深度不均，会让既有分维权重不再表示实际影响力

**这是修正树模型之后才出现的问题，v0.1 的模型下不存在（那时只有题材是树）。**

`SPEC-recommendation-ranking.md:930` 定的分维权重是 **题材 0.50 / 年代 0.20 / 地域 0.20 / 热词 0.10**。这组数是在**每维只有"命中 / 不命中"**的前提下定的。**引入层级后，深树和浅树的 `dimScore` 期望值不一样：**

| 维度 | 深度 | 不精确命中时 `dimScore` |
|---|---|---|
| 题材 | 3 | 兄弟叶 0.36、堂表叶 0.13 —— **大量部分得分** |
| 年代 / 场景 / 热词 | 1 | **只有 0 或 1，没有中间值** |

> 🔴 **后果：题材维度的实际影响力高于它名义上的 0.50**，因为它在"不精确命中"时也持续贡献分数，而浅维度在同样情况下贡献 0。**深度越深，这个溢出越大。**
>
> **这不会报错，只会表现为「地域和年代好像没什么用」** —— 而那正是 `t3` 裁定（地域年代提到 P0）想避免的结果。

**两种修法，都需要真实数据才能定（列入 §8）：**

| 修法 | 做法 | 代价 |
|---|---|---|
| **归一化** | 每维的 `dimScore` 除以该维在随机配对下的期望值，再乘分维权重 | 分维权重恢复"就是影响力占比"的语义；代价是多一个需要用真实分布估计的量 |
| **重定分维权重** | 承认 0.50/0.20/0.20/0.10 是名义值，按实测影响力反算一组新的 | 简单；代价是每次改树深度都要重算一次权重 |

**本文档不选，因为两者都需要真实的标签分布，而现在库里是 0 张。** 🔴 **但必须现在登记** —— 否则实现方会照抄 0.50/0.20/0.20/0.10 并以为它表示影响力占比。

## 7. 网格板结的库存保底（已拍待细化）

### 7.1 现有形态：这条保底能自然嵌进去

现有权重是纯乘性的（`TECH-DESIGN-feed-recall-and-exposure.md:2285`）：`W = W0 × γⁿ × T_eff(a,n) × brakeFactor`。
`TECH:2316` 写明第一条理由：「🔴 **『只减不增』成为结构性保证**……这是**代数上的**保证，不需要任何运行时检查。加法做不到。」
`SPEC-feed-surfaces.md:636` 的方案 B 也已是这个形态：`G8 gridRecentlyListed`，跨会话近 7 天在网格列出过 → ×0.5。

> 🟢 **所以库存保底只要写成值域在 (0,1] 的乘性因子，就是自然嵌入，不是打补丁。**

### 7.2 落成可实现的形式

```
                 ┌ 1                                该卡近 7 天未在网格对该 viewer 列出过
G8(card, viewer) ┤
                 └ 1 − (1 − g_full) · s(V)          列出过

s(V) = clamp( V / V_full , s_min , 1 )
```

| 参数 | 值 | 来历 |
|---|---|---|
| `g_full` | **0.50** | 满库存时的抑制强度。🟢 **不是新数**，就是方案 B 的 ×0.5 |
| `V` | — | 当前可主动分发的公开卡总量（口径见 §7.4） |
| `V_full` | **5000** | 🔴 **今天新给的数，全仓查无出处**（§8）。它是**满强度点，不是阈值** |
| `s_min` | **0.30** | 🔴 **就是「保底」本身。** 库存再少，缩放也不降到 0 |

| 库存 `V` | `s(V)` | `G8` | 说明 |
|---|---|---|---|
| ≥ 5000 | 1.00 | **0.50** | 满强度，等同方案 B 原设计 |
| 3000 | 0.60 | **0.70** | 抑制减弱 |
| 1500 | 0.30 | **0.85** | 已触到 `s_min` 地板 |
| 200（种子期） | 0.30 | **0.85** | 🔴 **保底生效：仍有 15% 降权，不归零** |

### 7.3 三条必须写死的实现约束

**① 🔴 5000 是分母，不是阈值。** 写成 `V < 5000 ? 弱 : 强` 会在 4999 与 5001 之间跳变——用户能感觉到瀑布「突然变了」，且**库存在 5000 附近抖动时会反复发生**。连续缩放没有这个问题。

**② 🔴 `G8` 与 `T_eff` 相乘，不互相修改。** 两者正交：`T_eff` 管**这张卡老了没有**（`TECH:2460`：`T_eff(a,n) = max(T(a), n < D_min ? T_FLOOR : 0)`，`T_FLOOR=0.15`），`G8` 管**这个人最近见过它没有**。
**代数核对**：`G8 ∈ [0.50, 1.0] ⊂ (0,1]` → `W ≤ W0` 的代数保证不被破坏 ✅

**③ 🟢 `G8` 与 `FRESH` 保底位不冲突（我核过了，原以为会冲）。** 担心的是 `T_eff` 有一道欠投地板托着新卡，而 `G8` 会把新卡压下去。
**核实后不成立**：`SPEC-feed-surfaces.md:199` 与 `:348` 写明保底位是**条数下限**（≥3/20，「配比不得把保底位挤掉」），不是排序豁免。**`G8` 改变的是「哪张新卡占这 3 个位」，不改变「有 3 个位」。** 且它只在「这个 viewer 已经见过这张卡」时触发 —— **保底位管第一次被看见，`G8` 管第二次起**，两者恰好接力。

### 7.4 一处需要定义的口径

`V` 数什么？**建议：`status='public'` 且未流掉（非 `DRAINED`）且 `originType='user'` 的卡数。**

🔴 **排除官方号是刻意的**：种子期官方号内容占比高，算进库存会让系统以为「供给充足」从而全强度抑制真人内容——**而这条裁定要防的恰恰是种子期把瀑布抽空。** 依据同 `schema.sql:468-471`（官方号不进北极星分母的同一条理由）。

## 9. 🔴 `R6` 改判：它不是开关，是一条计算管线

### 9.1 改判原文与性质变化

> 关注题材从用户关注的用户那里根据他点关注的卡信息综合提炼他可能关注的题材。在未来推荐的时候强化这个列表。最终稳定描述这个用户的侧写。

| | 旧理解（v0.1/v0.2 据以估算） | 🔄 改判后 |
|---|---|---|
| `R6` 是什么 | 用户**按下的一个按钮**（关注某个题材 chip） | **算出来的一张表** |
| 缺什么 | 缺**一个入口**（UI + 端点 + `t_topic_follow`） | 缺**一条计算管线** |
| 用户参与 | 显式点击 | 🔴 **零参与，用户不知道这张表存在** |
| 在信号分类里 | 显式行为 | 🔴 **推断产物**（这一点是后面 §10.1 全部麻烦的来源） |

### 9.2 🔴 「保留 `R6` 等于新开一摊」这个判断：不成立了，但方向和我原先想的相反

**原判断**：保留 `R6` → 要做题材关注入口（chip 关注态 + 端点 + `t_topic_follow` 表 + 取关链路）→ 是一摊与主线无关的新活。

**改判后重新论证，结论分三段：**

| # | 结论 | 说明 |
|---|---|---|
| 1 | ✅ **省掉的那一半是真的省了** | 用户入口整摊消失：无 chip 关注态、无关注/取关端点、无 `t_topic_follow`、无「我关注的题材」管理页。🟢 **这部分工作量归零。** |
| 2 | 🔴 **换来的一半比省掉的大** | 一条离线管线 + 第二块侧写表 + 版本化重算 + 清空/抑制链路（§10.1 会说明为什么清空链路是**必须**的，不是可选） |
| 3 | 🟢 **但它不是「新开一摊」，是「在已经要建的东西上加一层」** | 它复用的三样东西**本来就在计划内**：①`t_tag` 树（本文档 §4，必建）②第一块侧写的事件表（`S4`/`S5` 献花与记得本来就要落卡级）③卡级迁移（§2，热度也在等它）。**真正的增量只有「第二块」的离线作业与清空链路。** |

**所以原判断作废**，替换为：

> 🔴 **`R6` 的增量成本不高，但它的<u>位置</u>变了：它从「可以随时插进去的一个小功能」变成「树、卡级迁移、第一块侧写三者都就位之后才能开工的下游」。**

### 9.5 第一块 · 显式内容偏好（事实记录）

**性质：追加型事实流。每一行都对应用户做过的一个具体动作，都能指着说「因为你在 X 时候对 Y 做了 Z」。**

```sql
t_user_topic_signal
  id           bigserial
  accountId    bigint      -- 谁
  tagId        bigint      -- 哪个叶子（🔴 只存叶子，祖先由树推导，见 §4.2.1）
  dimension    varchar     -- 冗余存一份，避免每次 join t_tag
  sourceType   varchar     -- publish | flower | remember     🔴 白名单枚举，不留 other
  sourceCardId bigint      -- 🔴 哪一张卡。可解释性与可撤销性全靠这一列
  createdAt    timestamptz
  revokedAt    timestamptz -- 软删：取消献花/取消记得时写入
```

| 项 | 设计 | 🔴 为什么 |
|---|---|---|
| **不存权重** | 只存事件，权重读时算 | 权重是时间的函数（§10.3 衰减）。**存下来就要定时刷新，而刷新作业挂了不会报错，只会让所有人的偏好静默冻结在某一天。** |
| **软删不硬删** | 取消动作写 `revokedAt`，行保留 | 硬删了就无法回答「为什么这个人的偏好突然变了」，排查会瞎 |
| **撤销即时生效** | 读取时过滤 `revokedAt IS NULL` | 满足 `SPEC-feed-surfaces §3.4.3` 的**可撤销性**要求（「用户取消关注，信号立刻消失」） |
| 🔴 **`sourceType` 不含 `view`/`dwell`** | 白名单三项封死 | **这是 `X8` 的落点**（§10.1）。加一个「浏览」就当场撞红线 |

- **更新时机**：动作发生时**同步写**，与 `t_resonance` 同一事务。
- **谁用**：🔴 **精排用它**（`F3 tagMatch` 的偏好侧主输入）+ **可解释性用它**（"因为你给这张卡献过花"）。

### 9.6 第二块 · 维度推断（推导产物）

**性质：可整体重算、可整体清空的物化结果。它不是事实，是一个当前版本算法在当前数据上的一次输出。**

```sql
t_user_dimension_profile
  accountId      bigint
  dimension      varchar
  tagId          bigint       -- 🔴 可以是非叶节点（推断的落点常在中层：「他喜欢猫」而不是「他喜欢英短」）
  score          numeric
  evidenceCount  int          -- 🔴 支撑它的第一块行数。低于门槛不下发（§10.2 方案丙）
  algoVersion    varchar      -- 🔴 算法版本
  computedAt     timestamptz
  suppressedUntil timestamptz -- 🔴 用户清空后的静默期（§10.1）
  PRIMARY KEY (accountId, dimension, tagId)
```

**三处与第一块的关键区别，每一处都有理由：**

| 区别 | 第一块 | 第二块 | 为什么不同 |
|---|---|---|---|
| `algoVersion` | 不需要 | 🔴 **必需** | 事实不因算法改变而失效；**推断会**。算法一改，整表作废重算，没有版本列就不知道该重算谁 |
| 挂载层级 | 🔴 只在叶 | **可在任意层** | 推断的自然产物就是中层结论。强行落到叶反而是**捏造精度** |
| 可清空 | 撤销单条 | 🔴 **可整体清空** | 见 §10.1：这是重划红线能否成立的**前置条件**，不是加分项 |

- **更新时机**：🔴 **离线作业，日级，不实时。** 三条理由：① 它是统计量，实时刷新在数学上没有意义；② 实时刷新会让用户感到侧写随每次点击抖动，**那比不给看更糟**；③ 日级批作业可以整表重算、可以回滚、可以对着上一版做 diff —— 实时增量更新三样都做不到。
- **谁用**：

| 环节 | 用哪块 | 理由 |
|---|---|---|
| **召回**（`TAG` 通道加权采样、§5.1 阶梯起点） | 🟢 **第二块为主** | 召回需要「面」。第一块太稀疏——Echo 的互动本来就少（北极星是「被接住率」，说明稀缺是常态），只用第一块会导致大部分用户召不出东西 |
| **精排**（`F3 tagMatch`） | 🟢 **第一块为主，第二块为辅** | 🔴 **第二块的贡献必须可分离**（配置项单独关掉），否则「推断到底帮了还是害了」永远测不出来 |
| **可解释性 / 对用户展示** | 🔴 **只能用第一块** | 第二块说不出「因为你做过什么」 |
| 🔴 **兜底**（`FALLBACK` 随机层、`FRESH` 保底位） | 🔴 **两块都不用** | **兜底的全部正当性就在于它与偏好无关。** 让侧写渗进兜底，兜底就不再是兜底了 |
| 🔴 **干涉档位**（`DP7`/`IL`） | 🔴 **两块都不许用，反向亦禁** | `IL-8`「两条链路不共用信号」；`SPEC-feed-surfaces.md:330` 已成条款 |

**一句话分工**：

> **第一块回答「他做过什么」**——事实，可追溯、可撤销、实时、给精排与解释用。
> **第二块回答「他可能也喜欢什么」**——推断，可重算、可清空、日级、给召回用。

##### 🟢 为什么「可撤销」是那条真分界（旧判准漏在哪）

同一张表里本来就写着答案（改写前 `:306`）：取消关注、收回献花、取消「记得」——**信号当场消失**；而「点开过、看完过、进过谁的主页」，🔴 **用户没有任何办法让系统忘记**。

**旧判准挑了「是不是按钮」这一行，而那一行区分不开这两类**（点开也是按钮）。**挑「可撤销」这一行，两类当场分开，而且五个允许信号全部落在可撤销这一侧——清单不用动。**

🔴 **对推断产物的延伸也顺理成章**：旧判准之所以一刀切禁掉推断，是因为它假定**推断天然撤不掉**。这个假定对第二块不成立——**给它一条清空链路，它就撤得掉。** 所以第 1 条对推断产物写成「产物可整体清空」，不是放宽，是**同一条标准的忠实适用**。

### 10.2 隐患二：作者层马太回路——**成立，但位置和你我说的都不太一样**

#### 10.2.1 核实：先看有没有现成机制已经切断它

| 既有护栏 | 出处 | 作用层 | 能不能拦住这条回路 |
|---|---|---|---|
| `X12` 禁读粉丝数 | `SPEC-recommendation-ranking.md:511` | 排序特征 | ⚠️ **拦不住。** 管线从头到尾**不读 `followerCount`**，逐字合规 |
| `X9` 禁作者攀比量 | `:508` | 排序特征 | ⚠️ **拦不住**，同上 |
| `X2` 禁类目级互动率反馈 | `SPEC-feed-surfaces.md:282` | 全局类目权重 | ⚠️ **拦不住。** 🔴 **关键区别：第二块是<u>逐 viewer</u> 的，不产生任何全局类目权重。**`X2` 禁的是「已远行类互动率高 → 全局加权」，而这里每个人的表只反映自己的关注 |
| `D14` 不做全站作者榜 | `RK14` | 展示 | 拦不住，与分发无关 |
| 权重衰减 `γⁿ` / 保底位 / 曝光基尼 | `TECH §8` · `§3.1` | 🔴 **内容层** | 🔴 **拦不住——它们全部作用在单卡上，对「一个题材出现在多少人的偏好表里」完全无感** |

🔴 **结论：现有护栏一条都没覆盖这里，因为它们全部在内容层与特征层，而这条回路在<u>偏好覆盖面</u>这一层，那一层今天没有任何护栏，也没有任何仪表。**

#### 10.2.2 🔴 但回路的形状要说准，不然会开错药

**它不是「作者 A 火 → A 更火」的自反馈。** 追一遍：A 的题材进我的偏好表，前提是**我关注了 A**；进表之后被强化的是**题材**，而该题材的卡不一定是 A 的。所以 A → A 这一支很弱。

**真正成立的是题材层的一条回路：**

```
高关注度作者的题材  →  出现在更多人的偏好表里  →  该题材在更多人的 TAG 通道有资格
       ↑                                                      ↓
   该题材作者更易被发现、更易涨粉  ←──────────────  该题材整体曝光上升
```

**三点判断，逐条给依据：**

1. 🟢 **它不违反 `X12` 的字面**——从不读粉丝数。但 🔴 **它的效果与「读粉丝数」同向**：粉丝多的作者，其题材的偏好覆盖面天然更宽。**`X12` 防的是算法自我强化，这里是<u>人的关注决策被算法逐个搬运并求和</u>。**
2. ⚠️ **每一次搬运本身都是正当的**——我关注了 A，我确实可能喜欢 A 的题材。**所以这不是一个应当被消除的回路，是一个应当被<u>限幅</u>的回路。**
3. 🔴 **它的记分牌是公开且精确的**（粉丝数已裁定公开展示精确数字，`RK14`）。**这带来的不是算法风险，是<u>策略行为</u>风险**：作者和运营都能看见这块表，能据此行动。**算法护栏防不了人。**

#### 10.2.3 三个抑制方案（🔴 均不采用「降低关注信号权重」）

> 用户已明确排除「降低关注信号权重」。**我同意排除**，理由要写清：关注是全系统**唯一**一个用户主动声明「我要看这个人」的信号，削它等于用一个真实且正当的信号去赔一个结构问题。

**方案甲 · 题材只从「我互动过的卡」提炼，不从「我关注的作者的全部发布」提炼。**

- 做法：关注作者只贡献 `F1b`（布尔）与 `FOL` 通道；题材偏好只来自我实际献花/记得/发布过的卡。
- 🟢 **收益：回路从根上断开**——作者层不再向题材层传导任何东西。
- 🔴 **代价：这等于把改判撤回一半。** 改判原话明写「从用户关注的用户那里…提炼」，甲方案否掉的正是这一句。且偏好表会显著变稀疏（关注远比互动频繁）。
- **适用**：如果产品认为「关注 → 题材」这条传导本身就不该存在。**这是价值判断，我不替拍。**

**方案乙 · 单作者贡献上限（去重 + 封顶）。**

- 做法：一个作者对我的偏好表最多贡献 **1 个单位**权重，不论他发了 1 张还是 100 张卡；同一题材需**来自不同作者**才累加。
- 🟢 收益：切断「高产作者主导我的偏好表」这一支。
- 🔴 **代价：切不断另一支**——「很多人关注他」那一支照旧。**乙方案只治单人，不治众人。** 且对「我只关注一个人、就是很爱他这个题材」的真实场景会压权重。

**方案丙 🟢（建议为主）· 题材入表需「跨作者确认」。**

- 做法：一个题材要进我的第二块侧写，需 **≥2 个不同来源**（不同作者的卡，或"作者 + 我自己的第一块互动"）。单一来源不入表。
- 🟢 🔴 **最强的理由是它<u>不是新发明</u>：`SPEC §5.2` 热词晋升门槛就是「7 天内被 ≥5 位不同作者使用」，按<u>不同作者数</u>而非次数计，明写理由是「单作者刷 100 次也晋升不了」。** 丙方案是同一范式在偏好侧的复用——论证、验收口径、防刷理由全部可以直接引用，不用重打一遍。
- 🔴 代价：偏好表更稀疏，冷启动更慢；「我只关注一个人就爱这个题材」会被挡在门外（与乙同向但更硬）。
- ⚠️ 门槛取 2 还是 3 是策略数字，**待真实关注分布**（登记在 §8.7 第 9 项）。🟢 **但范式现在就能定，门槛后调不返工。**

**方案丁（🔴 不是替代，是任选甲乙丙都必须配的）· 加一个仪表。**

> 🔴 **今天唯一的集中度仪表是曝光基尼，它在<u>内容层</u>。题材层的覆盖面集中度没有任何观测。**

### 10.3 隐患三：「最终稳定描述这个用户」——**担忧成立，且 Echo 有一条别处没有的加重理由**

#### 10.3.1 先核实：仓库里已经担心过这件事，而且给过机制

| 既有机制 | 出处 | 与「侧写松开」的关系 |
|---|---|---|
| 🟢 **20% 探索配额** | `SPEC-recommendation-ranking.md:923` | 🔴 **原文已明写理由**：「没有这个探索位，标签召回会**在两周内把用户锁进一个越来越小的题材茧房**」。**茧房担忧不是新提出的，仓库里已经在了** |
| 🟢 **热词晋升重新激活** | `SPEC §5.2` / `RK18` 三条出口之一 | 「一条当年没人理的『铁皮文具盒』，等这个词热起来了，它能重新被看见」——**内容侧的自松开先例** |
| 🟢 **`TM1` 温度回落** | `DECISIONS` 温度域 | 「温度缓慢回落至地板，🔴 **地板不为零**」——🔴 **本项目「自己往下走但不归零」的既有范式**，与 §7 网格库存保底的 `s_min` 同形 |
| 🟢 **`DP11` 只降不升** | `DECISIONS.md:907` | 「温度可以回落…温度可以回升，而回升同样不改变回声频率」——**单向机制在本项目是被接受的形态** |

#### 10.3.2 🔴 Echo 特有的加重理由：红线亲手封死了「知道何时该松」这条路

| 红线 | 原文 | 后果 |
|---|---|---|
| `X3` | 🔴 「**逝别时间距离** / 「刚失去」标记…用"刚失去多久"做分发依据，就是在脆弱事件上做定向分发」 | 禁止 |
| `X4` | 🔴 「**用户脆弱期标记**（vulnerability / **grief_stage** / 情绪低谷 或任何等价物）」 | 禁止 |
| `CS1` | 🔴 「哀伤支持资源…**不另立机制** —— **另立一套就会长出「判定用户处于哀伤哪一阶段」的需求，那正是本条不做的事**」 | 禁止 |

> 🔴 **这三条合起来说的是同一件事：我们<u>永远不会知道</u>一个用户是不是已经走出来了。**
>
> **所以「等他变了我们就跟着变」这条路是被裁定封死的。** 一个只在有新证据时才更新的侧写，加上一条禁止我们识别「他已经不同了」的红线，**结果就是永久锁定**——不是因为算法坏，是因为它没有任何机制知道该松手。
>
> 🔴 **结论：正因为 `X3`/`X4`/`CS1` 禁止阶段识别，侧写就<u>必须</u>有一个与用户状态无关的、机械的松开机制。这两件事不是矛盾，是一个逼出另一个。**

#### 10.3.3 🔴 反方也要说：这个担忧的受影响面比听起来窄

**可能的反驳**：侧写窄化需要足够的数据才会发生。Echo 的互动本来就稀缺（北极星选「被接住的发布率」，本身说明「有人回应」是稀缺事件），多数用户的第一块可能长期只有个位数行，**根本谈不上收敛**。

**我的判断：这个反驳<u>部分成立</u>，但它加强而不是削弱了结论。**

- ✅ **成立的部分**：种子期与低互动用户身上「锁死」不会发生，因为没数据可锁。**所以这不是一个上线第一天就会爆的问题。**
- 🔴 **但它恰好在最不该出问题的那批人身上成立**：会被锁死的，定义上就是**互动最多、投入最深**的那批用户——**也正是最可能长期停在一个题材上、最需要被松开的那批。**
- ⚠️ **所以真实结论是**：这是一个**低发生率、高严重度、且随产品成功而加重**的问题。**它不该抢在引擎前面做，但设计时必须留出位置**，不要等到用户量起来再回头改数据模型。

#### 10.3.4 三条机制建议（🔴 形态全部复用既有范式，不新发明）

| # | 机制 | 复用的既有形态 | 代价 |
|---|---|---|---|
| **甲** | 🟢 **时间衰减**：第一块的每一行按半衰期贡献递减，第二块每日重算时自然反映 | 与 `W = W₀ × γⁿ × T_eff` 的乘性衰减、`TM1` 温度回落同形。**读时算，不刷表**（§9.5） | 半衰期是策略数字，**待真实数据**（§8.7 第 8 项） |
| **乙** | 🟢 **地板不为零**：衰减到一个下界即止 | 🔴 **逐字复用 `TM1`「地板不为零」与 §7 网格保底的 `s_min`** | —— |
| | **为什么要地板**：一个人十年前的猫，仍然是他的猫。**把它衰减到零是另一种冒犯**，而且是产品最不该犯的那种 | | |
| **丙** | 🔴 **探索配额恒定，禁止自适应** | 现有 20% 探索配额（`:923`）**保留且写死为常数** | 牺牲一点「精准度」 |
| | 🔴 **这一条是本节最容易被实现错的地方**：自适应探索的自然写法是「侧写越确定 → 探索越少」。**那恰好在最需要松开的时候把松开机制关掉了。** 必须在规格里写死「探索配额不是置信度的函数」 | | |
| **丁** | 🔴 **不做**「阶段识别驱动的侧写重置」 | —— | 🔴 那需要 `grief_stage`，`X4` 逐字禁止。**松开必须是机械的、无状态的、对所有人一视同仁的** |

**与 `DP7` / 「不做依赖」的关系（核实后如实说）：**

🟢 **同向，且是同向里更强的一种。** `DP1` 的立场是「平台无权评价用户用得对不对」；`DP11` 把「转热加频」删掉的理由是「**能识别投入度、却只用来增加触达**，那个把柄本身」。**一个越准越窄、且永不松开的侧写，正是「能识别投入度、只用来强化既有投入」的同型物。**🔴 **按 `DP11` 的逻辑，自松开机制不是加分项，是与既有裁定保持一致的必要条件。**
