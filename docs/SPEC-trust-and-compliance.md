## CM-G0 · 制作人裁定（v0.2 新增，优先级高于下文原有描述）

### G0-1 · 删除一律软删（工程铁律）

**裁定**：凡涉及数据删除的操作，**一律用标识位实现，不做物理行删除、不做级联清理**。

- 用户点「移除」→ 置软删标识位，**立刻从所有对外视图消失**（共鸣厅、他人主页、精选、搜索、亲友动态）。
- 找回**不做自助入口**：需走人工客服申请 + 身份校验通过后由后台恢复。
- 数据留底，保留可追溯性。
- **适用范围**：回忆集、单条记录、回声、明信片、公开卡、互动——所有用户可见的「删除」语义，无一例外。
- **含「开关型取消」**（取消记得、取消置顶、取消勾选等状态回退）：同样**不得物理删行**，改为状态字段 `active=false` + 时间戳。理由不是钻字眼——「谁在什么时候取消了记得」本身就是 CM-D1 要求留底的审计信息，且口径统一后红线扫描无需为它开例外。逐处存量处置见 §CM-G0S S-10。

**实现要求**：
- 统一约定字段（如 `deletedAt` / `deletedBy` / `deleteReason`），**不允许各表各写一套**。
- 所有读路径默认过滤软删数据；**只有后台恢复流程可读取软删数据**（仓储层强制，见 G0-9）。
- Code Review 红线：出现 `DELETE FROM` / 级联 `ON DELETE CASCADE` 一律打回。

> **⚠️ v0.3 勘误（2026-08-24）**：取代 v0.2 原文「（迁移脚本除外）」。「迁移脚本除外」不是完整的例外定义，且与 `DECISIONS CM-D1`「业务数据」的限定词两边对不齐（QA 不一致-8）——红线因此**不可执行**。现统一为：例外**只认 §CM-G0S S-9 的白名单表**，白名单以外一律禁止，新增白名单项需 PM 批准。「业务数据」的边界即由该表定义，两份文档不再各自解释。

### G0-2 · 「彻底删除」做成默认关闭的配置开关

**背景**：PIPL 第 47 条赋予个人删除权。当前裁定为只软删、不清除，**存在法律暴露面，制作人已知悉并接受**。

**风险控制安排**：把彻底删除实现成**能力预留 + 配置开关（默认关闭、不对 C 端开放）**，使未来合规要求到来时是「改配置」而非「改架构」。

> **⚠️ v0.2 勘误（2026-08-24）**：本节初稿同时写了「加密存储」与「只做预留」，二者工作量差两个数量级，属产品侧表述失误。经制作人裁定（B-1）明确如下，**以此为准**。

**本期必须真做（不是预留）**：
- 素材落盘时按用户维度**独立密钥加密存储**。**这是一个只能现在做的窗口**——不做的话，本期及此前的存量素材未来即使开启开关也无密钥可销毁，加密销毁对存量永久失效且不可追溯补救。
- 密钥管理：主密钥走 env（不入库、不打印），用户密钥加密后落库。
- **与 CM-G4 的边界必须打通**：缩略图、水印呈现图等一切派生图**同样受该用户密钥保护**。否则销毁密钥后派生图仍可还原内容，crypto-shredding 当场落空。

**本期只做预留（不实现 UI、不对用户暴露）**：
- 配置开关 `ECHO_COMPLIANCE_HARD_DELETE_ENABLED`（默认 `false`）。
- 开启后的行为：**仍不删数据行**，仅销毁该用户密钥 + 个人信息字段不可逆处理（crypto-shredding）——数据行、外键、统计口径全部不受影响，内容永久不可还原。

**本期可验交付物**：逐条判据见 §CM-G0S **S-4**（6 条，全部为二值断言，任一 Fail 即本条不通过）。本节不再另列，避免两处描述漂移。

### G0-3 · 素材派生：提交即拆解，训练只消费派生物

**裁定**：不把用户原始文件直接投入训练。素材提交时即做结构化拆解，训练链路**只消费派生物**。

- 拆解维度：主体 / 背景 / 特征等多元拆分（具体维度由算法侧定义，产品侧只要求「原图不进训练链路」）。
- 原图：最小留存 + 加密存储 + 仅本人（及授权守护者）可取，走 CM-G4 签名 URL。
- 训练语料库只入派生物，不入原图。

**⚠️ 护栏（必须写进代码注释与 CR 清单）**：
> **拆解 ≠ 免授权。** 拆解后的派生物只要仍可关联到账号，在 PIPL 下即属**去标识化**而非**匿名化**，**仍是个人信息**。拆解降低的是泄露风险，**不减免任何授权义务**。未拿到训练授权的素材，其派生物**同样不得进入训练语料库**。

### G0-4 · 撤回授权的法理与处置

**法理依据**：《个人信息保护法》第 15 条——基于个人同意处理个人信息的，个人有权撤回同意；**撤回同意不影响撤回前基于个人同意已进行的个人信息处理活动的效力**。

**裁定处置**：
- 自撤回之时起：**不再采用该素材，也不再用其辅助生成**（校验入口见 G0-10 统一门控）。
- **撤回前**已产生的产物不做清除（已生成的回声、定妆形象等属于用户的回忆，清除比保留更伤人）。
- **已训练进模型权重的部分不需要回滚**——法条明确撤回前处理有效。这是可合法沉淀的资产。
- 用户如想删掉某条已生成产物，走 G0-1 的软删路径自行处理。

**前提（合规部门必须落实）**：以上处置必须在**用户协议 / 隐私政策中事先明写**。法条给了效力，但未事先告知的，事后争议仍由平台承担。

### G0-5 · 授权呈现方式

**裁定**：使用类授权（识别 / 定妆 / 近况生成）作为**「提供服务所必需」打包明示告知，一次同意**；**训练授权单独 opt-in、默认关闭**。

- 建档流程中明示告知，不做三项逐项勾选（避免流程碎裂到不可用）。
- 训练授权是**独立的第二个勾选项，默认不勾**，且不得与使用类授权捆绑（AI-CAPABILITIES §7 PIPL 红线）。
- **向量检索单列一行**（G0-7 B-2）：随使用类一并明示告知，但**在「我」页可单独关闭**；它是第四行，**不计入**打包三项、也不归训练。
- 「我」页提供授权查看与撤回入口（契约见 `API-CONTRACT §15.3`）。

> **「明示告知」到什么程度算合规**：见 §CM-G0S **S-3** 的 **9 条要件清单**（每条二值、可截图判定，任一缺失 = Fail；其中第 6/7/8 条 Fail = Blocker）。不给这张清单，开发照现状（一个 `allowUse` + 一个 `trainConsent` 勾选、零告知文本）交付也能自称"做了明示告知"。

### G0-8 · 术语统一

**「授权期内」全文改为「撤回前」**（解 QA 不一致-7）。`t_ai_consent` 本期**不设期限字段**，不引入过期机制——加期限会引出「到期后既有产物怎么办」的新裁定需求，超出本期范围。

> **回改留痕（v0.3）**：本文件 G0-4、G0-6 第 2 条、CM-G3 P0 范围三处的「授权期内」已按本条改写，取代 v0.2 原文。`DECISIONS CM-D6` 同步回改。**「授权期」这个词此后不得再出现在任何规格中**——它在数据结构里不存在对应字段，写了就会被实现成一个过期机制。

### G0-9 · 实现约束：软删与唯一约束

> 解 QA R-1（**改成软删的那一刻必现的线上 500**）。

**所有含唯一键的业务表，唯一索引一律改为部分索引 `WHERE "deletedAt" IS NULL`。**

典型必现场景：`t_remember(petId, accountId)` 取消记得后再点一次即撞唯一键；`t_pet` 软删回忆集后重新建档同样撞键。不写死这一条，多个开发会有多种绕法（加随机后缀、去掉唯一键），后果是数据长期不一致且极难回溯。

**配套**：读路径的软删过滤**在仓储层强制**（基类统一拼过滤条件），只有显式 `includeDeleted()` 才能绕过（仅后台恢复流程可用）。靠每个人记得加过滤条件必漏，而漏掉的很可能正是最要命的那处（如分享链接的预览）。

### G0-10 · 授权状态外键强关联 + 使用前统一门控（制作人追加裁定，2026-08-24）

> **来源**：制作人追加要求——「删除或授权撤回时，相关**语料和图片资源信息也要做外键关联约束**；训练或拿来参考的时候，同步看这部分的状态」，以避免法律纠纷。
> **范围说明**：本条与 QA `U-5.9` 是同一个问题，但**制作人要求的范围更大**——不只训练语料，**一切引用/参考素材或其派生物的场景**都必须校验。本条为**硬约束**，等级同 G0-1。

#### ① 数据结构：派生物必须能指回源素材与授权记录

凡由用户素材派生出来的东西，其表**必须带两列外键**：

| 列 | 指向 | 含义 |
|---|---|---|
| `materialRef` | 素材表主键 | 这份派生物来自哪份原始素材 |
| `consentRef` | `t_ai_consent.id` | 产生/使用它时依据的是哪条授权记录 |

**本期必须补齐这两列的表**（清单，逐表可查）：

| # | 派生物 | 表 / 载体 | 备注 |
|---|---|---|---|
| 1 | 拆解产物（主体 / 背景 / 特征） | 拆解产物表 | G0-3 的「派生物」本体 |
| 2 | embedding | 向量库行（pgvector） | 每一行向量都要能回溯 |
| 3 | 训练样本 | `t_train_sample` | 见 `AI-CAPABILITIES §7` 回改 |
| 4 | AI 产物溯源 | `t_ai_provenance` | 已有 `consentRef`，需补 `materialRef` 口径（`sourceMaterialRefs` 为多值，须可 join） |

> **CR 红线**：**没有这两列的派生物表一律不合格，评审直接打回。**新增任何派生物表，不带这两列不得合入。
> 素材表名以后端既有实现为准（本规格统一以 `t_material` 指代），但**列名口径 `materialRef` / `consentRef` 不得各表各写一套**。

#### ② 运行时校验（关键，不是建表就完事）

在**训练、向量检索、RAG 引用、以及任何把素材或其派生物拿来参考**之前，必须 join 校验，**四个条件同时成立**才允许使用：

| # | 条件 | 判定 |
|---|---|---|
| 1 | 对应 `capability` 的授权已给出 | `t_ai_consent.granted = true` |
| 2 | 未撤回 | `t_ai_consent."revokedAt" IS NULL` |
| 3 | 源素材未被软删 | `t_material."deletedAt" IS NULL` |
| 4 | 授权记录本身有效 | 记录存在、`capability` 与本次用途匹配、未被软删 |

**任一不成立 → 该素材及其全部派生物不得参与本次训练 / 检索 / 引用。**不是"跳过这一条继续"，是**这份素材连同它派生出的一切**都退出本次调用。

#### ③ 统一门控入口（散着写必漏一处，漏的那处就是法律风险点）

CM-G3 只说「每次 AI 使用素材前校验账本」，但校验点有**五处**：识别 / 定妆生成 / 近况生成 / 向量检索 / 训练。

**要求**：做成**统一门控入口**，五处调用同一个校验方法，例如：

```
IConsentGate.assertUsable(materialRef, capability)   // 不通过即抛出，调用方不得自行绕过
```

- 五处调用点**必须全部经由该入口**；任何一处自己写 join、自己判 `granted`，**CR 直接打回**。
- 依赖规则（ArchUnit 或等价）：AI 能力模块**不得直接查询 `t_ai_consent`**，只能经 `IConsentGate`。这条把"漏一处"从"靠人眼发现"变成"构建失败"。

#### ④ 可验证判据：全量核查 SQL 断言（定期跑，不是上线跑一次）

**断言**：训练语料库与向量库中所有样本，回溯到的 consent 记录必须 **100%** 满足 ②的四条件。**期望结果：0 行。**任一行即为合规缺口 → 阻断发布 + 立即清出该样本。

```sql
-- 合规核查：派生物 → 源素材 → 授权 的可追溯链必须全部有效
-- 期望：返回 0 行。返回任意行 = 存在"授权已撤回/素材已移除，但派生物还在被用"的样本
SELECT 'train_sample' AS src, s.id, s."materialRef", s."consentRef"
FROM t_train_sample s
LEFT JOIN t_ai_consent c ON c.id = s."consentRef"
LEFT JOIN t_material   m ON m.id = s."materialRef"
WHERE c.id IS NULL                 -- 授权记录不存在
   OR c.capability <> '训练'        -- 授权能力与用途不匹配
   OR c.granted IS NOT TRUE        -- 未授权
   OR c."revokedAt" IS NOT NULL    -- 已撤回
   OR m.id IS NULL                 -- 源素材不存在
   OR m."deletedAt" IS NOT NULL    -- 源素材已软删
UNION ALL
SELECT 'vector' AS src, v.id, v."materialRef", v."consentRef"
FROM t_vector_item v
LEFT JOIN t_ai_consent c ON c.id = v."consentRef"
LEFT JOIN t_material   m ON m.id = v."materialRef"
WHERE c.id IS NULL
   OR c.capability <> '向量检索'
   OR c.granted IS NOT TRUE
   OR c."revokedAt" IS NOT NULL
   OR m.id IS NULL
   OR m."deletedAt" IS NOT NULL;
```

**跑的频率**（这条是"定期"不是"一次性"）：
- 随每次回归测试跑（常驻断言，防未来回退）；
- 上线前跑一次全量；
- **上线后按日定时跑**，非 0 行即告警到合规责任人。

### G0-6 · 用户协议 / 隐私政策必须包含的条款（交合规起草）

1. 上传素材将经**结构化拆解处理后**用于平台模型训练与效果提升；**训练用途须用户单独授权**，默认不启用。
2. 撤回授权的效力范围：自撤回起停止使用，**撤回前已产生的产物及已完成的处理不受影响**（对应 PIPL 15）。（v0.3 按 G0-8 回改，取代 v0.2 原文「授权期内」。）
3. 删除的实际含义：**移除后内容立即不可见并停止使用**；找回需人工客服申请并通过身份校验，**平台具备该恢复能力**（对应 G0-7 B-6，本期交付最小后台恢复能力——协议里承诺得到的，能力上必须做得到）。
4. 原始素材的存储、加密与访问范围（仅本人及经授权的共同守护者）；**素材按用户维度独立密钥加密存储**（对应 G0-2 B-1 本期真做）。
5. AI 生成内容的标识与溯源说明（对应 CM-G2）。
6. **向量检索**：为提供共鸣推荐等服务，素材内容会被处理为向量特征并**长期留存**；该项**单独可关**（对应 G0-7 B-2）。
7. **补传素材的授权承继**：建档后补传的素材，使用类授权按账号承继（补传处保留明示），训练授权承继建档时的开关状态且可在补传处单独关闭（对应 G0-7 B-5）。

### S-2 · 「训练链路」的定义 + 原图不进训练的四层判据（解 C-2 / U-2）🔒

#### ① 术语定义（此前完全没定义，不定义就无法判定）

**「训练链路」= 以下四类处理活动的合集**：

| # | 活动 | 算不算训练链路 |
|---|---|---|
| 1 | 写入训练语料库 `t_train_sample` | **算** |
| 2 | 模型训练 / 微调（LoRA、DPO、继续预训练） | **算** |
| 3 | **把素材内容做成 embedding 存入向量库（pgvector）** | **算** —— embedding 是原图内容的**长期留存派生**，且 CM-G3 已把「向量检索」单列为一项能力，理应同受 G0-3 约束 |
| 4 | **RAG / few-shot 取用**（把素材或其派生物喂给模型做参考） | **算** |

> **裁定依据**：采纳 QA U-2 第 5 点建议。与 G0-7 **B-2**（向量检索单列一项授权）口径一致——既然它是独立的处理活动、要单独授权，就同样受「原图不进」约束。
> **连带**：③④ 两类同样必须过 G0-10 的 `IConsentGate` 统一门控。

#### ② 四层判据（否定命题不能靠"跑一遍看看"证明，逐层都可自动化）

| 层 | 判据 | 拦的是什么 |
|---|---|---|
| **1 接口类型层** | `ITrainingCorpus` 的写入方法**在类型上就不接受原图**——入参只收 `derivedRef`，**不收 `resourceId` / 不收字节流** | 让"原图进训练"成为**编译不过**的事，而不是靠 review 发现 |
| **2 数据层（最硬）** | 一条 SQL 随测试跑：`t_train_sample` 的素材引用列 **100% join 中派生物表、0% join 中原始素材表** | **常驻回归断言**，防未来回退 |
| **3 调用链层** | 给原图读取路径（`IStorage` 取原件方法）加**调用方审计**；断言训练 / 语料任务在整个测试过程中对原图读取次数 = **0** | 运行期真实行为 |
| **4 依赖规则层** | 训练 / 语料模块**不得 import 原图存储类**（ArchUnit 或等价，违反即**构建失败**） | 拦"换个写法绕过去" |

> **明确放弃的可验性**：拆解维度（主体 / 背景 / 特征怎么分）由算法侧定义，产品侧**不验**——这确实是算法侧的事。但正因为放弃了一半，剩下这句「原图不进训练链路」必须硬到上面四层，否则它只是一句愿望。

### S-4 · G0-2 本期可验交付物（解 C-4 / U-4）🔒

> **口径前提**：G0-7 **B-1** 已裁定**本期真做 per-user 加密落盘**（不是只预留）。故下面 6 条**全部适用**，不存在"二选一"。

| # | 判据 | 断言方式 |
|---|---|---|
| 1 | 配置项存在且**默认 false** | 环境变量 `ECHO_COMPLIANCE_HARD_DELETE_ENABLED` 未设置时读到 `false`（单元测试断言）；`DEPLOY.md` 环境变量表已登记 |
| 2 | 开关置 true **不改变任何 C 端行为** | 断言无任何 C 端路由 / 前端代码读取该配置 |
| 3 | 结构预留**写死一个事实** | **本期建表** `t_user_key { ownerId, keyRef, algo, createdAt, destroyedAt }`；可验：表存在、**建档时写入一行** |
| 4 | 素材落盘为**密文** | 直接读存储层字节 **≠** 明文原图 |
| 5 | **跨用户密钥不可解** | 用 A 用户密钥解 B 用户素材**失败** |
| 6 | **crypto-shredding 语义可验** | 走受保护的测试路径销毁密钥后：素材**不可还原**，而**数据行、外键、统计口径全部不变**（这正是 G0-2 承诺的效果，不验就是空承诺） |

**派生图边界（必验，否则承诺当场落空）**：缩略图、水印呈现图等**一切派生图同样受该用户密钥保护**（`DECISIONS CM-D9`）。判据：销毁密钥后，**缩略图与公开层呈现图同样不可还原**。若只加密原图不加密派生图，销毁密钥后派生图仍能还原内容——crypto-shredding 就是假的，而这一点**没有边界定义时在验收阶段根本无法判定**。

> **为什么本期必须做（工程时限，非法律讨论）**：per-user 加密落盘不做，**今天之前上传的 + 本期新增的所有素材，未来即使打开开关也没有密钥可以销毁**。越晚做，"shred 不掉的存量"越大，且**无法追溯补救**。这是一个**只能现在做的窗口**。

#### U-5.6 / U-5.10 的连带明确（一并在此定死，避免开发自行发挥）

**🔴 `Label` 的取值域（原规格完全没写，这一处最容易实现错）：**

### S-11 · 站外分享的 AI 标识缺口：分享落地页 + 分享预览图（v0.4 新增）🔒

**问题**：站内标识已达标——前端 `<span class="ai-gen-badge">` 覆盖瀑布流卡片、搜索缩略图、详情页头图三处，左下角，**DOM 渲染、不烧进图片**（`SPEC-recommendation-ranking §5.3.2` 定案，本期保留不改）。**但内容一旦分享到站外，标识覆盖率是 0。** 前端已核实三层事实：

| # | 事实 | 后果 |
|---|---|---|
| 1 | `echo-h5-proto/index.html` 里**连 `og:` / `twitter:` meta 标签都没有** | 分享到任何平台都没有标题、描述、缩略图 |
| 2 | 纯静态 SPA（`DEPLOY §1`）**无法按窗下发不同的 `og:image`**——社交平台爬虫**不执行 JS**，抓到的永远是同一份 `index.html` | 即使补上 meta 标签，也只能是全站一份写死的值 |
| 3 | 因此「标识用 DOM 角标承担」这个设计，在**站外分享场景下等于完全不存在** | `CM-G2` 显式标识在这条路径上**未覆盖** |

> **本节纠正一处此前的低估**：原判断是「服务端出图时把 AI 标识叠上去就行」。这只解决了一半——**叠好标识的图，爬虫也得能拿到才算数**。缺 meta 渲染，那张图根本不会被任何平台引用。所以本缺口需要**两个交付物**，不是一个。

#### ① 两个交付物，缺一不可

| 代号 | 交付物 | 缺了它会怎样 |
|---|---|---|
| **D1** | **分享落地页按窗渲染 meta**：让爬虫能抓到每扇窗**各自的** `og:title` / `og:image` / `og:description` | 只有 D2：标识图存在，但没有任何 `og:image` 指向它，站外仍是零标识 |
| **D2** | **服务端合成分享预览图，并把 AI 标识叠进图里** | 只有 D1：爬虫拿到了按窗的预览图，但图上**没有标识**——合规缺口原样保留 |

🔴 **两者必须同批交付。任一单独上线都不构成合规达标，不得按"先做一个、另一个后补"排期。**

#### ② D1 · 分享落地页按窗渲染 meta —— 方案选项与倾向

| 方案 | 做法 | 结论 |
|---|---|---|
| **A · 全站 SSR** | 前端改为 Node SSR（Next/Nuxt 之类），整站服务端渲染 | 🔴 **不采纳**。要在生产引入 Node 运行时、推翻 `DEPLOY §1` 的纯静态 CDN 托管拓扑、前端框架层级重构。MVP 的登录后主流程**不需要** SSR，为一条分享路径付整站代价 |
| **B · 构建期预渲染（SSG）** | 构建时为每扇窗生成一个静态 HTML | 🔴 **不采纳，且在本产品上根本不成立**。窗是 UGC、持续新增，构建期无法穷举；每次发布都要重构建全站。只对**固定的种子内容**可行，覆盖不了用户内容 |
| **C1 · 后端直出分享落地页（最小 HTML 骨架）** | echo-server 新增一条动态路由，服务端渲染一份**极简 HTML**：`<head>` 里注入该窗的 og/twitter meta，`<body>` 给一个可见首屏（封面 + 标题 + **DOM 角标**），随后挂载 SPA 接管 | 🟢 **倾向本方案**。理由见下 |
| **C2 · CDN 边缘函数注入 meta** | 静态站不动，在 CDN 边缘脚本里回源取窗数据、改写 `<head>` | 🟡 **备选**。效果等价，但把合规关键路径绑到 CDN 厂商的边缘计算能力与配额上；调试、灰度、回滚都不在我方掌控。**仅当 C1 因架构原因走不通时启用** |

**C1 被选中的五条理由**：

| # | 理由 |
|---|---|
| 1 | **保住既有拓扑**：主站仍是 `DEPLOY §1` 的纯静态 CDN，只多一条动态路由；不引入 Node 运行时，前端零框架改造 |
| 2 | **落在已有能力上**：echo-server 已经是 HTTP/JSON 网关（`DEPLOY §0`），出一份模板 HTML 不是新增基础设施 |
| 3 | **对爬虫与真人返回同一份 HTML，不做 UA 分流**——见下方微信约束第 5 条 |
| 4 | **标识双保险**：`<head>` 的 `og:image` 指向叠好标识的合成图（给爬虫），`<body>` 首屏仍是 DOM 角标（给真人点进来看），两条路径都覆盖，且**首屏不需要烧图** |
| 5 | **软删与可见性能在服务端一次过滤**——这条路由是 `S-1 ①` 第 12 项"分享链接 / OG 预览卡"迄今**缺失的端点落点**，补上它同时闭合了那一项 |

**微信生态的六条约束（MVP=H5、中国大陆优先、主要分享目标是微信，必须逐条满足）**：

| # | 约束 | 对实现的要求 |
|---|---|---|
| 1 | **微信爬虫不执行 JS** | meta 必须**服务端已经在 HTML 里**，这是 D1 存在的全部理由 |
| 2 | **域名须 ICP 备案** | 未备案域名在微信内会被拦截，链接连打开都做不到（备案见 `RELEASE.md`） |
| 3 | **`og:image` 须是可公网访问的 HTTPS 绝对 URL** | 🔴 **不得使用 `CM-G4` 的限时签名 URL**——签名过期后微信侧缩略图直接失效。分享预览图走**长期有效的公开 URL**；这不违反 `CM-G4`，因为它是我方合成的派生物料、不是用户素材（判定见 `TECH-DESIGN §3.12` C1–C3） |
| 4 | **微信会缓存缩略图，且缓存不可回收** | 与 `TECH-DESIGN §3.12.4`「第三方缓存残留」同一风险，处置口径沿用那一条：站内标识与元数据即时生效，预览图尽最大努力 |
| 5 | 🔴 **不做 UA 分流（不按 `MicroMessenger` 判爬虫）** | 微信 UA 会漂移、多平台各有自己的抓取 UA，靠 UA 白名单必漏一个；且给爬虫和真人返回不同内容属 cloaking。**统一返回同一份 HTML** |
| 6 | **微信内的「自定义转发」是另一条链路，与 meta 互补、不可互相替代** | meta 管「链接**首次被抓取**时的卡片长相」（微信爬虫、以及微博/QQ 等其它平台）；微信 JS-SDK `updateAppMessageShareData` 管「已在微信内打开的页面**再次转发**时的标题与缩略图」。两条都要，**且两条都必须引用同一张叠好标识的预览图**。⚠️ JS-SDK 依赖**公众号 + 微信认证 + JS 接口安全域名 + 签名下发端点**，这是**运营前置条件、不是工程问题**，已登记为下方 **P-6** |

> **其它平台**：同一份 `<head>` 里一并输出 `twitter:card` 系列。微信不读它，但对外分享不止微信一处，成本为零。

#### ③ D2 · 服务端合成分享预览图并叠 AI 标识

**裁定早已存在，本节只做归位、不重开讨论**：`TECH-DESIGN-feed-recall-and-exposure.md §7 Q15` 已裁定 **A**（在 `og:image` 上叠一行 AI 标识小字），实现约束见该文档 **§3.12.4**。本节补两条它未覆盖的：

| 项 | 约定 |
|---|---|
| **入参来源** | 服务端**不自行推断**内容含不含 AI 成分，由调用方把 `cover.aiGenerated` 一并传入出图接口。契约见 **`API-CONTRACT §16`** |
| **`aiGenerated` 缺省语义** | 🔴 **字段缺省 / null 一律按 `true` 处理并叠标识**。理由：漏叠是合规事故，多叠只是多一行小字。**不得把缺省当 `false`** |

#### ④ 🔴 边界（已有裁定，此处写死防扩大解释）

> **只有分享预览图叠标识。站内原图与用户素材一律不动。**（`TECH-DESIGN §3.12` 裁定原文）

- 可叠的物料**有且仅有** `og:image` 这一项，判定走 `TECH-DESIGN §3.12.1` 的 **C1–C3 三条 AND 条件**；防扩大解释红线 **L1（不得类推到其它物料）/ L2（导出下载永远不叠）/ L3（只叠 AI 标识、不夹带 logo 水印二维码追踪码）** 全部在本节继续生效，不复述细节。
- 🔴 **本节新增红线 L4**：**分享落地页首屏用的封面图，不得叠标识。** 它是用户素材的呈现（C1 不满足），标识由该页的 **DOM 角标**承担。这是 D1 带来的一条**新的扩大解释路径**——"落地页也是给站外看的，那它的封面图是不是也该烧字"——答案是**不**，必须提前堵掉。
- 🔴 **不得以"补齐站外标识"为由，修改用户原始素材的任何字节**（原图 / 压缩图 / 缩略图 / 裁剪图）。这是 `G0-3` 与 `§3.12` 共同守的线。

#### ⑤ 判定口径核对（哪些内容算「含 AI 成分」）

**唯一口径是 `SPEC-recommendation-ranking §5.3.2` 的判定原则，本节不另立标准**：

> 只要**用户可见的内容成分**中有任何一部分由 AI **生成、或被 AI 改变了表意内容**，就必须带标识；AI 仅参与**分发 / 检索 / 审核 / 打标 / 排版**等不改变表意的处理，不需要标识。

**与本规格既有口径的核对结论**：

| 口径 | 出处 | 是否一致 |
|---|---|---|
| AI 生成**特指有真实素材来源的派生物**（唤醒视频、回声、AI 生成图像），**平台不做凭空自创的内容** | `G0-3` 素材派生 · `SPEC-recommendation-ranking §17.4d`（`seed_ai` 类别已作废） | ✅ 一致。分享路径**沿用**该口径，不新增内容类型 |
| `aiGenerated` 与 `originType` **正交**——普通用户的唤醒视频 / 回声分享出去**同样要带标识** | `SPEC-recommendation-ranking §5.3.2` RK28b | ✅ 一致。🔴 **不是官方号专用**，这是最容易漏的一类 |
| `aiGenerated` **只用于标识与合规溯源，排序模块不得读取** | 禁用特征 `X13` | ✅ 一致。出图链路读它**不违反 X13**——X13 禁的是排序读取，不是标识链路读取 |
| 显式标识文案「**该内容由 AI 生成**」 | `COPY-GUIDE §2.4` | ✅ 一致。🔴 **预览图上的文案与前端角标共用同一份文案常量**（`§3.12.4`），不另起一套，否则合规核查会查出两个口径 |

**结论：阻塞。** 推导如下，不是就"重要性"打分：

| # | 推导 |
|---|---|
| 1 | 分享是**获客主路径之一**（`OPERATION-GTM-*`），所以「不做分享」不是可选项 |
| 2 | AI 标识是**合规硬要求**（《标识办法》2025-09-01 已施行），所以「分享但不带标识」不是可选项 |
| 3 | 1 与 2 叠加：**「能分享但不合规」和「合规但不能分享」都不可接受**，两者必须同时成立 |
| 4 | 而当前状态是**两个交付物都没有**、且此前**没有 owner** ——即默认滑向 1 或 2 中的某一个不可接受态 |

**唯一允许的降级路径**（若排期确实来不及）：**关闭含 AI 成分内容的站外分享入口**（= `TECH-DESIGN §7 Q15` 的选项 C，作为**临时降级**、非常态）。🔴 **绝不允许"先上线分享、标识后补"**——那正是第 3 条排除掉的第一种不可接受态。

🔴 **但必须知道这条降级路径在商业上近似等于关掉分享**：`aiGenerated` 与 `originType` 正交，覆盖面极广——唤醒视频、宠物回声、AI 生成的封面图是 MVP 的主力内容形态，且**种子内容封面全部 `aiGenerated=true`**。真正可分享的将只剩「用户手写文字 + 未经 AI 处理的原图」这一小类。**所以降级不是一条真的退路，只是一个应急阀门。**

→ **排期结论：D1 + D2 + `API-CONTRACT §16` 契约，与「站外分享」功能同批列入 P0，标 Blocker。**

## CM-G2 · AI 内容标识 + 溯源（合规硬要求）

### 目标
公开发布的 AI 生成/编辑内容**可识别、可追溯**，满足《标识办法》显式+隐式双标识。

### P0 范围
1. **显式标识**（已有文案基础 CR2）：C 端可见"基于你记忆的温柔想象"等（措辞见 COPY-GUIDE §2.4）。**站内**由前端左下角角标承担（DOM 渲染、不烧进图片）；**站外分享**是此前的缺口，见下方第 4 项。
2. 🔄 **隐式标识**（缺口）：AI 生成/编辑的图片、音视频**在文件元数据中写入 GB 45438—2025 附录 E 的七要素**；文本按办法要求做隐式标记（元数据/附加信息）。**发布到公开层前必做**。**要素集、取值域、字符集限制、QA 检出命令、派生图覆盖要求见 §CM-G0S S-8**（🔴 **该节已于 2026-08-25 按国标整体重写，原「四项必含字段」已作废**）。

   > 🔄 🔴 **本条 2026-08-25 修订：拆开「元数据水印」与「数字水印」，🔴 后者不是强制项。**
   >
   > **原写法把两者并列**（「写入**元数据水印/数字水印**」），🔴 **容易被读成两个都是 P0 硬要求。不是。**
   >
   > | | 是不是硬要求 | 依据 |
   > |---|---|---|
   > | **文件元数据隐式标识** | 🔴 **是。强制。** | 《标识办法》**第 5 条** + **GB 45438—2025**（**强制性**国标）**附录 E**（规范性附录）|
   > | **数字水印**（内容隐式标识，嵌在像素/音频信号里）| 🟢 **否。非强制。** | 🔴 **GB 45438 附录 A.2 明写内容隐式标识「在本文件中<u>不做要求</u>」**；**§6.2 用的是「准许」**；《标识办法》**第 5 条用的是「鼓励」** —— **三处措辞一致地落在「可以做」而不是「应当做」** |
   >
   > 🟢 **数字水印仍是有价值的加强项**（它能扛住元数据被剥离），🔴 **但不得作为 P0 阻断项，也不得写进任何「缺一 Fail」的判据。**
   > ⚠️ 🔴 **为什么这个区分重要**：数字水印的实现成本与元数据写入**不在一个量级**（前者要动图像/音频信号处理与检出模型，后者是写一个字段）。**把非强制项当强制项排进 P0，会挤掉真正强制的那一项的排期** —— 而真正会 Fail 国标的恰恰是后者。
3. **溯源账本 `t_ai_provenance`**：每条 AI 产物记录 `{ contentId, capability(vision/imagegen/echo/…), provider, model, promptRef, sourceMaterialRefs, consentRef, createdAt, hash }`，可回答"这条是谁、用什么、基于哪些素材、经谁授权生成的"。
   - `hash` = 对**产出物文件字节**的 **SHA-256**；`promptRef` = **存引用不存原文**；撤回状态**不加冗余列**，经 `consentRef` join 实时判定（三条均定死于 §CM-G0S S-5）。
   - `sourceMaterialRefs` 为多值，**须可 join 回 `t_material`**（G0-10 ① 第 4 行）。
4. 🆕 **站外分享的显式标识**（v0.4 补，此前无 owner 的缺口）：内容分享到站外时，标识必须**跟着内容走出产品**。需两个交付物——**分享落地页按窗渲染 meta**（让爬虫抓得到每扇窗各自的 `og:image`）+ **服务端合成分享预览图并把标识叠进图里**（站外只有静态图，DOM 角标在那里等于不存在）。🔴 **边界：只有分享预览图叠标识，站内原图与用户素材一律不动。** 方案倾向、微信生态约束、判定口径核对、职责矩阵与阻塞判定全部落 **§CM-G0S S-11**；接口契约落 **`API-CONTRACT §16`**；部署形态落 **`DEPLOY §1.5`**。

### 字段 / 接入点
- 生成侧（回声/定妆/近况）在产出时**同步写** `t_ai_provenance` + 给媒体打隐式水印。
- **派生管线（缩放 / 转码 / 加水印）不得丢弃元数据，派生后须重新写入标识字段**（S-8 ④）——公开层用户看到的正是缩略图与水印图，派生时丢标识则合规当场失效。
- `t_ai_provenance` 与 CM-G3 授权账本、CM-G1 导出联动。

## CM-G3 · AI 授权账本（Consent Ledger）

### 目标
把"哪些素材、允许给哪种 AI 能力、**是否已撤回、何时撤回**"变成**可查、可撤、可留痕**的账本，而不是一个笼统开关。

> **v0.3 措辞回改（G0-8）**：取代 v0.2 原文「用到**何时**」。该措辞会被读成存在一个"授权期限"，而 `t_ai_consent` 里没有任何期限字段——按 G0-8，本期**不设期限概念**，账本回答的是「**撤回前 / 撤回后**」，不是「用到哪一天」。

### P0 范围
- 授权**按能力分项**：`识别 / 定妆生成 / 近况生成 / 向量检索 / 训练`。三种呈现分组（G0-7 B-2 / `CM-D7` / `CM-D10`）：

  | 分组 | 含哪些 | 呈现与默认值 |
  |---|---|---|
  | `usage` 使用类 | 识别 / 定妆生成 / 近况生成 | **打包明示告知、一次同意**（服务所必需），三项同进同出 |
  | `vector` 向量检索 | 向量检索 | **单列一行**，随使用类一并明示（说明"内容会被处理为特征向量并**长期留存**"），但**「我」页可单独关闭**。不并入打包三项、**不归训练** |
  | `training` 训练 | 训练 | **独立 opt-in、默认关**，与使用类**视觉分块、不同勾选框**，=AI-CAPABILITIES §7 PIPL 红线 |

- 每次 AI 使用素材前**校验账本**；未授权则不用于该能力。**五个校验点必须走 G0-10 ③ 的统一门控入口**（见下方字段表）。
- 用户可**随时撤回**任一分项；**撤回处置按 G0-4**：自撤回起停止使用与辅助生成、后续不再进入训练集；**撤回前已产生的产物不清除、已训练进权重的不回滚**（PIPL 15）。`t_ai_provenance` 经 `consentRef` join **实时判定**撤回状态（不加冗余列，S-5）。
- 全程留痕（授权/撤回时间、范围）。
- 「我」页的查看 / 撤回入口契约见 `API-CONTRACT §15.3`；未授权时的 C 端行为见 §CM-G0S **S-6**。

### 字段

`t_ai_consent { id, ownerId, materialRef, capability, granted(bool), grantedAt, revokedAt, source(建档/设置页/补传), version }`

> **本期不设期限字段**（无 `expiresAt`）——按 G0-8，「授权期内」全文已改「**撤回前**」，不引入过期机制。

#### 派生物外键口径（G0-10 ① 落到本节）

凡由用户素材派生出来的东西，其表**必须带 `materialRef` + `consentRef` 两列外键**。本期必须补齐的表：**拆解产物表**、**向量库行**（pgvector）、**`t_train_sample`**、**`t_ai_provenance`**（已有 `consentRef`，需补 `materialRef` 可 join 口径）。**没有这两列的派生物表一律不合格，CR 直接打回。**

#### `IConsentGate` 校验点清单（G0-10 ③ 落到本节，解 QA U-5.7）

| # | 校验点 | capability | 调用入口 |
|---|---|---|---|
| 1 | 肖像识别 | `识别` | `IConsentGate.assertUsable(materialRef, capability)` |
| 2 | 定妆生成 | `定妆生成` | 同上 |
| 3 | 近况 / 回声生成 | `近况生成` | 同上 |
| 4 | 向量检索（含 embedding 入库与检索取用） | `向量检索` | 同上 |
| 5 | 训练语料写入与训练 | `训练` | 同上 |

- **五处必须全部经由该入口**；任何一处自己写 join、自己判 `granted`，**CR 直接打回**。
- 依赖规则（ArchUnit 或等价）：AI 能力模块**不得直接查询 `t_ai_consent`** —— 把"漏一处"从靠人眼发现变成**构建失败**。散着写必漏一处，**漏的那处就是法律风险点**。
- 校验的四条件与"不通过则该素材及其全部派生物退出本次操作"的语义见 **G0-10 ②**。

> · 「拟人化互动服务提供者……应当**及时识别用户面临的安全风险**，并采取相应的应急处置措施。」
> · 「发现用户出现**极端情绪**的，应当**及时生成情绪安抚和鼓励寻求帮助等相关内容**」
> · 「发现用户……**明确表示实施自残自杀**等威胁生命健康的极端情境的，应当**采取提供相应援助等必要措施予以干预**，并**及时联络用户监护人或者紧急联系人**。」
>
> 🔴 **冲突点（说清楚，别抽象化）**：**若 Echo 适用该办法，这是产品功能义务，运营补不了。** 两处具体不可补：
> ① 「**及时生成**情绪安抚……内容」要的是**生成链路上的能力**——那是研发的活，内容治理岗事后看不到、也接不上。
> ② 「及时**联络用户监护人或者紧急联系人**」要求注册环节就采集这些字段（同办法**第 12 条**：应要求用户提供「年龄、监护人或者紧急联系人等必要信息」）——🔴 **没采集就永远联络不到**，这是一个**上线时点就已经错过**的义务。
>
> 🔴 **本节现行 `G7-1` 与第 13 条的方向差**：`G7-1` 做的是**被动展示资源**（不判定、不跟进、不联络），第 13 条要的是**主动识别 + 生成安抚 + 必要时联络第三人**。两者不是程度差，是**动作类型不同**。
>
> **罚则**：第 30 条责令停止提供相关服务，可并处 1 万~10 万元罚款；🔴 **「涉及危害公民生命健康安全且有危害后果的」，并处 10 万~20 万元**（加重档）。
>
> ⚠️ **前置问题**：**Echo 是否构成「拟人化互动服务」**（争点：第 2 条「模拟**自然人**人格特征、思维模式和沟通风格」是否涵盖**宠物**）。🔴 **这一条同时决定危机干预、依赖护栏、上线安全评估三件事**，已置顶登记为 **`§CM-G8.3 LW-0a`**。

> 🔴 **`G7-2` 的「准入 vs 分发」边界不随移交失效**（`G7-3`）：它约束的是**排序侧不得拿情绪标记打分**——🔴 **那是一条禁令，禁令不需要有人去实现，只需要没有人去违反。** 红线汇总第 9 条继续有效。

### G7-1 · 危机词 → 兜底提示，不做干预

**裁定原文**：识别到自伤/自杀类表述时，🔴 **仅展示官方援助资源**（如心理援助热线）即可。

**做什么（穷举，此外一概不做）**

| # | 动作 | 说明 |
|---|---|---|
| 1 | 命中危机词表 → 在当前上下文**就地展示官方援助资源卡片** | 内容 = 官方公布的心理援助热线等公开资源。文案走 `COPY-GUIDE`，🔴 **不评判、不劝阻、不追问、不要求用户确认「我没事」** |
| 2 | 展示后**原样放行用户的操作** | 🔴 **不阻断保存、不阻断发布、不进审核队列、不改变内容状态**。提示是**并行的**，不是一道闸 |

🔴 **明确不做（写成禁止项，防止后人以「兜底」为名扩权）**

| # | 🔴 禁止 | 为什么 |
|---|---|---|
| N1 | **不做人工干预** | 不派单、不由客服/运营联系用户 |
| N2 | **不做主动介入** | 不弹强制确认、不设冷静期、不中断使用 |
| N3 | **不做用户状态判定** | 🔴 **不得存在任何「风险等级 / 危机分 / 心理状态」的用户侧字段、标签、画像或打分**。命中是**一次性的展示触发**，🔴 **不落用户档案** |
| N4 | **不做后续跟进** | 不回访、不复查、不建跟进流程、不进运营看板作为跟进对象 |

**实现约束**

- 🔴 **词表与判定只服务于「要不要展示这张卡」这一个用途**，判定结果**不写库、不产出可被其他模块读取的字段**。这条是 `N3` 的工程保证——没有字段就没法被别处消费。
- 复用既有内容安全能力的**危机词分类**（`AI-CAPABILITIES` 能力 K：规则 + 云内容安全 API 的「心理危机词」类目），🔴 **不新建情绪/心理模型**（与 `SPEC-recommendation-ranking §9 红线四`「不建立情绪强度模型」同向）。
- ⚠️ **与 `SPEC-admin-console §1.4 T4` 的关系**：后台已有的「自伤/自杀等紧急风险信号可先看后批」是**审计与执法配合通道**（有三人审批、事后追责），🔴 **那是既有能力、本节不扩不缩，也不得被 `G7-1` 引用为「可以主动介入」的依据**。

**与 `DP1` 的关系（🔴 同向但不同因，不要互相援引）**

| | `DP1`（`DECISIONS §G⁗⁗′`） | `G7-1` / `CS1`（本条） |
|---|---|---|
| 管什么 | 依赖识别与使用强度干预 | 自伤自杀风险兜底 |
| 结论 | **不做**——不把用户的使用强度当问题 | **只做最小动作**——展示官方援助资源 |
| 为什么 | 成年人自负其责，平台无权评价「用得多是好是坏」 | 风险兜底的最小动作，不做提示不可接受 |

🔴 两条**各自独立成立**。不得用 `DP1` 论证「危机词也不该提示」，也不得用 `G7-1` 论证「所以依赖也可以介入」。

### G7-2 · 公开层消极内容属内容审核范畴

🔴 **这是内容审核规则，不是心理判断。** 判的是**内容合不合适公开**，不是**用户心理状态如何**。

| 层 | 规则 |
|---|---|
| **公开发布的内容** | 情绪表达过于消极的，🔴 **可被审核处理**（限制公开等），走既有审核流程与申诉通道（`SPEC-publish-and-ops §2`） |
| **私域内容**（用户自己的窗、私密可见） | 🔴 **一律不管，情绪表达不设限。** 不扫描判负、不限制、不提示「你是不是太消极了」 |

> 🟢 **`G7-1` 在两层都成立**：私域不管的是「消极内容的可见性」，不是「危机词提示」。用户在私密内容里写下自伤表述，仍然展示援助资源卡片——那是 `G7-1` 的一次性展示，不是审核动作。

### 🔴 G7-3 · 准入 vs 分发（本节最重要的一条边界，写死）

🔴 **`G7-2` 与既有的「悲伤强度不得作为排序特征」是两件不同的事，不得混同。**

| | 管什么 | 出处 | 动作 |
|---|---|---|---|
| **`G7-2`（准入）** | **能不能公开** | 本节 · `DECISIONS §G⁗⁗⁗ CS2` | 二元：过审公开 / 限制公开 |
| **排序禁令（分发）** | **推多少量** | `SPEC-recommendation-ranking §9 红线四` · `X1` 情绪强度禁用特征 · `DECISIONS AD2` | 🔴 **不存在任何基于情绪强度的量级调节——连负向都不许** |

🔴 **把两者混在一起会得到「越难过的内容越少人看见」——那既不是 `CS2` 的意思，也直接违反既有排序禁令。**

**由此推出的硬约束（构建期可查）**

| # | 🔴 约束 |
|---|---|
| G7-3a | 审核侧产生的**任何消极度/情绪相关标记**，🔴 **不得作为排序特征、不得进打分函数、不得作为降权依据**。审核结论对分发的唯一合法影响是：**限制公开的内容根本不进候选集**——那是准入结果，不是排序权重 |
| G7-3b | 🔴 **不得因为「内容偏消极」而给它更低的分发权重**。过了审的内容，在排序侧与其他内容**一视同仁** |
| G7-3c | ⚠️ **一处既有的合法用法不要误伤**：`SPEC-recommendation-ranking §9 红线四` 允许**复用审核侧既有敏感标记做偏斜观测的代理**（用于发现「消费悲伤」）。🔴 **那是观测与告警，不是排序输入**；`G7-3a` 禁的是进打分函数，两者不冲突 |

> 📌 **需在排序侧补一条反向交叉引用**（`SPEC-recommendation-ranking.md` 本轮被其他线占用，未改）：文本已随裁定回执转交 PM，落点建议 §9 红线四。

## CM-G8 · 用户协议的法定硬边界（v0.6 新增）

> **本节登记的是「协议约不掉」的事项** —— 无论用户协议怎么写、用户是否点了同意，下面这些都不因约定而消失。每条注明法条出处。
> **裁定源**：`DECISIONS.md §G⁗⁗⁗⁗ CM-D18~CM-D23 / MOD4 / OM1` + `§G⁗ CR-M②′`。
> 🔴 **本节不是法律意见，是产品与工程侧的边界登记。** 需要律师定论的部分统一进 §CM-G8.3 待律师清单，🔴 **不在本节自行拍板**。

### CM-G8.0 🔴 先澄清一条（否则下面全部会被误读）

🔴 **`PIPL` 第 47 条第 1 款第（二）项的触发条件是「个人信息处理者停止提供产品或者服务」——指的是「平台这一侧停止提供」，不是「用户停止付费」。**

由此得出两句必须一起记住的话：

1. 🔴 **Echo 的「降档不减少」承诺（`CR-M②′`），在服务存续期间根本不触发该条。** 用户从付费档掉回免费档，Echo 仍在向他提供服务，处理目的并未终止。把这条读成「用户不付费了就得删」，是把主体读反了。
2. 🔴 **真正需要处理的只有一个窄口：Echo 自己停止运营。** 那一种情形已由 `CM-D20`（停服条款按高强度写）覆盖 —— 90 日公告 + 导出期按量分档 + 按剩余天数比例退款。

⚠️ **顺带更正一类表述**：若文档中出现「**永久保存承诺与停服即删相冲突**」一类说法，🔴 **该冲突不存在**——一个说的是服务存续期间不因档位减少（`CR-M②′`），一个说的是平台停止服务时的处置（`CM-D20`），两者的触发条件互斥。
✅ **本轮已全库检索，未发现该表述的既有实例**，因此无需回改；本条正面写入，是为了堵住它日后被写出来。

### CM-G8.1 逐条法定硬边界

| # | 法条 | 硬边界内容 | 对 Echo 的具体约束 |
|---|---|---|---|
| **L-1** | 《个人信息保护法》**第 45 条**（查阅、复制权） | 🔴 **无条件**，且须「**及时提供**」 | 🔴 **素材导出不得做成付费功能**，不得设档位门槛、不得排队降速给免费用户。这是 `CR-M②′` 第①层「用户素材完全不受档位影响」的法律来源。<br>⚠️ **第 3 款「可携带权」有前置条件——「符合国家网信部门规定条件的」，而该配套规定至今未出台。** 🔴 **因此导出功能应建立在第 1、2 款（查阅、复制）之上，不要在协议或对外文案里援引可携带权** —— 援引一个尚无生效条件的权利，等于给自己设一个无法验收的标准。 |
| **L-2** | 《个人信息保护法》**第 47 条**（删除权） | 五种法定情形下应主动删除；个人请求删除的应当删除 | 与既有 `CM-D3`（彻底删除本期不实现、暴露面已知悉并接受）**同一条法条的两侧**，本条不改变该裁定。<br>🔴 **兜底句要照写不要略**：「**删除技术上难以实现的，个人信息处理者应当停止除存储和采取必要安全保护措施之外的处理。**」<br>**为什么不能略**：这句话正是 `CM-D3` 现行做法（软删 + 停止一切使用 + 保留存储）的**法定落点**。略掉它，协议里就只剩「你可以要求删除」这半句，而我们实际做的是另一半，两边对不上。 |
| **L-3** | 《著作权法》**第 29 条** | 🔴 **合同中未明确许可的权利，不得行使** | 🔴 **许可用途必须逐项列明，凡未列明者一律不得行使——尤其是模型训练。** 兜底语（「以及其他必要用途」）在这一条下**换不来任何实际权利**，只会让用户看见「他们想拿走一切」。<br>落点：`CM-D23` 明确排除**再许可 / 宣传推广 / 模型训练**三类；训练另有 `CM-D7` 的单独 opt-in 要求。 |
| **L-4** | 《民法典》**第 496–498 条** | 格式条款的提示说明义务（496）、无效情形（497）、🔴 **解释规则（498）** | 见下方 **CM-G8.1a**，🔴 **这三条对 Echo 是当下的具体风险，不是背景知识**。 |
| **L-5** | 《消费者权益保护法》**第 26 条** | 显著提示义务；🔴 **不得利用格式条款并借助技术手段强制交易** | 「借助技术手段强制交易」直接对应一类具体做法：**用弹窗遮挡内容逼付费、用降速/拦截逼续费**。🔴 **这与 `ACCEPTANCE TC-EXP-09`（降档路径不得存在任何读取阻断）是同一条约束的法律面与工程面。** |
| **L-6** | 《消费者权益保护法实施条例》**第 21、22 条** | 停业须**提前 30 日**公告（带罚则：最高违法所得 **10 倍**或 **50 万元**）；🔴 **不得降低商品或者服务质量**；🔴 消费者**有权要求退还未消费的预付款余额** | 🔴 **任何「已收取费用一律不退」的条款，在停服场景下可能无效** —— 不要写。<br>`CM-D20` 已按高于底线的 **90 日**写。<br>🔴 **「不得降低商品或者服务质量」是第二个落点**：它意味着服务期内单方缩水已购档位的权益（少发、降规格、砍功能）本身就有问题，与 `CR-M②′` 第②层同向。<br>⚠️ **第 21 条的字面是「停业或者迁移服务场所」，对纯线上 App 下线的适用性需律师确认** —— 它决定 90 日是**法定义务**还是**自愿承诺**。 |
| **L-7** | 《人工智能生成合成内容标识办法》**第 4 条末款、第 5 条** | 🔴 **导出文件必须带显式标识 + 元数据隐式标识** | ⚠️ 🔴 **这一条直接约束「永久可导出」承诺**：**不能承诺导出无水印的干净文件。**<br>🔴 **建议在条款里写明「该标识为法定要求，不因服务档位或付费状态而增减」** —— 目的是提前挡住「**付费去水印**」这个几乎一定会被问到的误解。一旦让用户以为水印是可以花钱去掉的，我们就同时违反了标识办法和 `CR-M②′`（把法定标识做成档位差异）。<br>实现侧对应 `CM-G2` 显隐双标识与 `§CM-G0S S-8`。 |
| **L-8** | 《互联网信息服务深度合成管理规定》**第 14 条** + 《民法典》**第 994、1019 条** | 深度合成他人肖像/声音须取得**单独同意**；逝者人格利益保护 | 🔴 **这是「扩展到人」时的硬关口，协议约不掉。** 见下方 **CM-G8.1b**。 |

#### CM-G8.1a 《民法典》496–498 对 Echo 的具体风险（🔴 当下，不是将来）

**第 498 条的解释规则**：格式条款「**有两种以上解释的，应当作出不利于提供格式条款一方的解释**」。

🔴 **具体风险场景，写清楚，别抽象化**：

> 对外宣传若说「**绝不设悲伤付费墙**」，而协议里的档位条款含糊，🔴 **用户可以主张：免费档也应当获得与付费档相同的产出量。**
> 在第 498 条下，这个主张**不需要证明我们承诺过**，只需要证明**这句话可以这样理解**。

🔴 **因此：宣传语与协议口径必须严格对齐。这是合同解释问题，不是公关问题。**
—— 这也正是 `CR-M②′` 把「档位差异只体现在**尚未生成**的服务产出上」写死在同一句话里的原因：**把第二种解释消灭在措辞里**，而不是留给事后解释。

🔴 **另一条必须内部约束的**：第 498 条末句——「**格式条款和非格式条款不一致的，应当采用非格式条款。**」

> 🔴 **客服的个别承诺、活动页文案，效力可能高于协议。**
> 一个客服为了安抚用户说的「您的内容我们会永久保存」，是**非格式条款**；协议里写得再严谨，在这一句面前可能让位。
> **需要的内部约束**：客服话术、活动页、投放物料的对外承诺**必须与协议同源**，不得由个人临场发挥。🔴 **落点在 `COPY-GUIDE`，本轮未写，已登记。**

#### CM-G8.1b 扩展到「人」时的硬关口（🔴 协议约不掉，只能靠产品设计缓释）

三个事实叠在一起，构成一个**协议无法解决**的关口：

1. 🔴 **逝者无法给出《深度合成管理规定》第 14 条要求的「单独同意」。** 这不是流程问题，是**主体已不存在**——没有任何补签、追认、代签的路径。
2. 🔴 **《民法典》第 994 条给近亲属的是「请求权」，不是「授权权」。** 近亲属**有权要求他人停止侵害**，但**不因此获得代逝者授权他人使用其肖像的权利**。「家属同意了」在法律上并不等于「取得了授权」。
3. 🔴 **配偶、子女、父母各自独立行使。** 于是：**一个子女上传母亲照片生成回声，另一个子女可以独立起诉。** 平台拿到的第一个人的同意，挡不住第二个人。

🔴 **结论：协议约不掉，只能靠产品设计缓释，且须在扩展到「人」之前做专项论证。**
⚠️ 该论证是 §CM-G8.3 待律师清单的**第 1 项**，也是 🔴 **唯一一条可能推翻现有产品设想的**。

### CM-G8.2 账号归属与许可范围（裁定落点）

> 裁定源 `DECISIONS §G⁗⁗⁗⁗ CM-D22 / CM-D23`。本节只写协议起草时的可执行要点。

#### ① 账号归属 —— 采用「第二代写法」（`CM-D22`）

| 写法 | 代表 | 内容 | Echo |
|---|---|---|---|
| 第一代 | 微信、快手 | 明写「**账号所有权归平台**」 | ❌ **不采用** |
| **第二代** | **抖音现行版、小红书现行版** | 🔴 **已删除所有权声明**，只保留「仅限本人使用 + 不得转让 + 平台可依约处置」 | ✅ **采用** |

> 🔴 经全文检索确认，现行抖音协议「**所有权归**」**零命中**。这不是疏漏，是一次有意的换代。

**三条理由（记录下来，避免日后被当成疏漏补回去）：**
① 🔴 **司法上换不来额外权利** —— 该有的处置权，「不得转让 + 平台可处置」已经写全。
② 🔴 **反而制造风险** —— 北京石景山法院游戏账号继承案中，这句话是**法院论证的起点**：「用户协议**亦仅约定所有权归属运营商，并未排除继承人继承账号使用权的权利**」。
③ 🔴 **对 Echo 尤其致命** —— 纪念类产品的用户高度在意「这些东西是我的」。🔴 **在协议第一屏写「账号所有权归平台」，是用一句法律上无用的话，换取产品调性上的重大损失。**

**连带**：账号继承的处理方式见 `CM-D18` —— 🔴 **不继承账号，提供近亲属导出通道；平台不裁判谁是合法继承人，只负责把内容交出去。**

#### ② 许可范围 —— 收紧到「可撤销」并逐项排除三类用途（`CM-D23`）

- 🔴 **写「可撤销」，反业界通行做法**（小红书 4.2、网易 Filmly 第十五条均写「不可撤销」）。
  **理由**：🔴 **Echo 不需要传播用户内容**——不做内容分发生意、不靠 UGC 换流量。「不可撤销」对我们**没有商业价值，只有舆论成本**。
- 🔴 **明确排除三类用途**（逐项列明，🔴 **不用兜底语**，依据 `L-3` 著作权法第 29 条）：

| 排除项 | 含义 |
|---|---|
| **再许可** | 不得转授权给任何第三方 |
| **宣传推广** | 不得用于对外宣传物料、案例展示、广告素材 |
| **模型训练** | 🔴 **与既有裁定 `CM-D7` 方向一致，不是新增约束** |

> 🔴 **关于第三项的一致性说明（必须写，否则会被误读成两套要求）**：
> `CM-D7` 定的是「训练授权**单独 opt-in、默认关**，是 PIPL 红线、不让步」；`CM-D23` 定的是「**基础许可里不含训练**」。
> 🔴 **两者是同一件事的两个位置** —— 正因基础许可不含它，才需要单独授权。不是两套约束，更不冲突。

## CM-G9 · 私域内容治理 · 调研结论登记（v0.7 新增）

> **来源**：同一主题的**两次独立调研**，报告原样归档在 `docs/RESEARCH-private-content-governance.md`（987 行）与 `docs/RESEARCH-private-content-governance-2.md`（674 行）。🔴 **两份互补，不可只读其一**；🔴 **本节只做结论登记，两个报告文件本身由恢复线持有，本节不改动它们。**
>
> 🔴 **本节的效力边界，先写死：**
> ① **调研不是法律意见。** 全文结论**不得直接当作合规依据**，须由执业律师出具正式意见后方可采信。
> ② 🔴 **本轮不据调研改动任何已定裁定** —— 制作人已裁定**等律师**（`DECISIONS §G⁗⁗⁗⁗′ CS3`）。

### CM-G9.0 🔴 调研推翻的那个内部假设（先记这一条）

**被检验的内部假设**：「**私域是用户自己的地方，平台不该拦也不必拦**」。

🔴 **两份调研的一致结论：这个假设在 Echo 的具体业态下不成立**，理由不是「私域也要管」，而是 —— **义务的锚点根本不在「传播」上**：

| 规章 | 条文 | 义务锚点 |
|---|---|---|
| 《互联网信息服务深度合成管理规定》第 10 条 | 对使用者的**输入数据和合成结果**进行审核 | **输入 / 生成**（🔴 无传播限定）|
| 《生成式人工智能服务管理暂行办法》第 14 条 | 发现违法内容应**停止生成**、停止传输、消除 | **生成** |
| 《人工智能拟人化互动服务管理暂行办法》第 13 条 | 及时识别用户安全风险、发现极端情绪应干预 | **互动过程**（要求主动识别）|

⚠️ **假设成立的那一半也要记住**：以「传播 / 发布」为锚点的法条（《生态治理规定》平台定义限于「传播服务」、网安法第 49 条限于「发布」）**确实不覆盖纯私密内容** —— 🔴 **所以正确的结论不是「假设全错」，是「假设用错了地方」**：它在通用内容平台语境下成立，在深度合成 + 拟人化互动服务语境下不成立。

🔴 **旧结论留痕**：「私域不审」这条内部假设**保留、标注**（推翻时间 2026-08-25，原因如上），🔴 **不删除** —— 删掉它，后人会以为从来没有人这样想过，从而在下一次讨论里原样重提。

### CM-G9.1 🔴 三类私域内容的判定（🔴 三类分开写，结论方向不同，合并就废了）

> 🔴 **不要一刀切。** 三类的结论分别是「取决于是否入模」「可以不审但有一个例外」「必须审且责任最重」—— **合并成一条之后，无论合成哪一条都会同时冤枉两类。**

#### ① 上传但未公开的素材（照片 / 视频 / 音频）

🔴 **结论：分两种情况，界限在「是否送入模型」。**

| | 判定 | 依据 |
|---|---|---|
| **A. 已送入 AI 生成流程的素材** | 🔴 **必须审核** | 《深度合成规定》第 10 条第 1 款「**输入数据**」，无传播限定，义务动词是「**应当**」。⚠️ **这是 Echo 的主用例** —— 所以**实际上绝大部分上传素材都落入必审范围** |
| **B. 纯存储、从未送入模型、无任何分享入口** | ⚠️ **法定强制审核义务不明确** | 网安法第 49 条限于「发布」；《生态治理规定》平台定义限于「传播服务」；阿里云盘协议 5.5 把审查权明确限定在「**传输、分享**」，不含存储 |

**B 类的两条正面支撑（这是调研中证明力最强的一组）：**
- **[司法]** 北京焦点公司诉北京百度公司案裁判要旨：「**网盘用户所拥有的账号下的存储空间，可以视为用户个人电脑、手机等硬件物理设备存储空间在网络环境中的延伸**」。⚠️ 🔴 **射程限制必须一并记**：该案是**著作权侵权**案件，**不能直接推及内容安全（涉黄涉恐涉政）领域** —— 著作权是私权，内容安全是公法义务，注意义务标准不同。能否跨领域援引，**须律师确认**。
- **[官方口径]** 国家版权局就《关于规范网盘服务版权秩序的通知》答问：「**如果网盘用户只是单纯上传、存储一些信息或作品，没有向公众分享、传播，那么网盘服务商不会对用户的私人网盘进行筛查，不会侵犯用户的隐私。**」🔴 **这是主管部门口径，不是企业实践，可借鉴程度高。**

⚠️ 🔴 **即使是 B 类，也有两条不可豁免的底线**：
1. **CSAM（儿童性虐待材料）零容忍** —— 刑事风险，**与是否传播无关**。
2. 《深度合成规定》第 10 条第 2 款要求「建立健全用于识别违法和不良信息的**特征库**」—— 🔴 **这是体系建设义务，不因某批内容未传播而免除**。

> 🆕 🔴 **`①A` 的一个具体审核维度已成规格（2026-08-25）**：`SPEC-subject-recognition-and-degradation.md` —— 从素材内容判定**主体类型**（是宠物、是人、还是物），据此**分级收缩生成能力**。🔴 **它不是新机制，是本行「入模必审」的一个维度的落地**；本节是它的义务来源，两处须互引，否则会各自演化。
>
> ⚠️ 🔴 **同时登记一条实质冲突（规格 `X-2`，🔴 不粉饰）**：该规格按制作人裁定 `SR-D2` **只管新上传、存量素材不重扫**；而本行说的是**已送入 AI 生成流程的素材必须审核**。
> 🔴 **冲突点**：一份**存量**素材被用于一次**新的**生成任务时，它已经「送入 AI 生成流程」，按本行必须审核，但按 `SR-D2` 不被扫描。
> 🔴 **这条冲突的性质是「法定义务 vs 产品承诺」**，不是两条产品口径打架 —— 🔴 **这使它比一般的口径分歧更硬。**
> ⚠️ **但范围是窄的**：只发生在「**存量素材 + 新生成任务**」这一个交叉点。存量素材**只被浏览、不入模**时两条并不冲突（那一类正是下面的 `①B`）。
> 🟢 🔄 🔴 **2026-08-25 晚：`X-2` 已由 `SR-D3` 化解（🔴 上方双方原文照旧保留，不删）**
>
> **裁定 `SR-D3`（`DECISIONS §G⁗⁗⁗⁗″`）**：存量素材**在<u>入模的那一刻</u>即时判定**；只读取、只浏览、**已交付的产出完全不动**；🔴 **不做任何回溯扫描。**
>
> 🟢 **为什么这正好解掉本行的冲突**：冲突范围本就只在「**存量素材 + 新生成任务**」这一个交叉点上，而**即时判定发生的位置就是这个交叉点** —— 存量素材在真正「送入 AI 生成流程」的那一刻被审核，🔴 **与本行的「入模必审」对齐，且不需要任何回溯扫描**。
>
> 🔴 **裁定为什么否掉另外两条路，一并记住**：
> · **全量扫描** —— 🔴 **扫描本身就是对全部存量素材做一次生物识别处理**，`PIPL` 第 28 条的必要性论证过不去。⚠️ **它听起来是「更严格因而更安全」的选项，实际上是为了合规而制造一个新的合规问题。**
> · **完全豁免** —— 🔴 **「知道了却没处置」可能比不知道更糟**；素材一旦入模，平台已处在「把它送进生成链路」的位置上，此时主张「没扫所以不知道」没有说服力。
>
> ⚠️ 🔴 **实现上有一处不得挪动**：判定**必须发生在入模那一刻**。🔴 **不得为了性能把它挪到上传时、或改成异步事后补判** —— **它的位置就是它化解本冲突的全部理由**；挪走之后「入模必审」立刻重新落空，而代码看起来只是做了一次正常的性能优化。
>
> ⚠️ **已知代价（`SR-D3` 已明确接受）**：老用户可能遇到「这张老照片以前能做定妆、现在入口没了」。**呈现照 `COPY-GUIDE §2.9`：表现为「这里没有这个入口」，不是「你被拒绝了」。**

**审核到什么程度**：机器哈希比对 + 高置信度模型筛查即可，🔴 **不做人工浏览、不做语义或情绪判读**。
🔴 **哈希比对在法律上是最优方案的理由（值得单独记）**：它使平台在**技术上无法知道**未命中文件的内容 —— 这**不是承诺，是能力边界**。「**我做不到**」比「**我承诺不做**」在合规上强得多，且同时消灭了「审核人员泄露内容」这一风险点。

#### ② 记录页「给自己」的纯私密文字

🔴 **结论：不做内容合规审核。这是三类中唯一可以坚持原假设的一类。但有一个例外。**

**支持不审的依据（法条级）**：网安法第 49 条（「发布」不成立，「停止传输」「防止扩散」无适用对象）· 《生态治理规定》第 41 条（此功能上不提供「传播服务」）与第 18 条（列举的「发帖、回复、留言、弹幕」均不涵盖）· 《互联网信息服务管理办法》第 2/3 条（「公开性、共享性」的定性不指向此场景）。

🔴 **一道必须守住的产品设计的墙**：上述结论的**前提是这些文字不进入模型**。
> **同一句话，不进 AI 是第二类，进 AI 就是第三类，义务强度完全不同。**
🔴 **如果 Echo 把「给自己」的文字作为上下文喂给 AI 以生成回应，它立刻变成《深度合成规定》第 10 条的「输入数据」，性质翻转。**
⚠️ **技术实现须专门确认这一点**，🔴 **本轮未核**（不在文档线边界内）。这与既有裁定 `D17`（给「自己」的记录默认纯私密不喂光谱、opt-in 才喂）方向一致，但 `D17` 管的是**光谱**，本条管的是**生成链路**，🔴 **两者不能互相代替**。

🔴 **唯一的例外 —— 《拟人化互动办法》第 13 条**：若 Echo 落入该办法，第 13 条要求「及时识别用户面临的**安全风险**」。⚠️ **这不是内容审核，是安全监测**，且法条明写「**在保护用户隐私权和个人信息的前提下**」。
📌 **该例外的处置已有裁定**：归 `CS1`/`CS3` —— **移交运营 · 研发期不实现 · 待律师确认适用性**。🔴 **本节不改变该裁定。**

**业界可直接借鉴的成文范式（印象笔记《隐私条款》，🔴 调研认为是最有价值的一条）：**
> 「当您向……联系人**分享**您的印象笔记帐户中的笔记时，**您明确同意**我们通过**系统自动审核及必要的人工复核**来审查您**分享的**笔记内容……」

🔴 **它的结构价值在于：把审核的触发点绑定在「分享」这个用户动作上，并写进隐私政策。** 对私密内容则用**风险告知**而非审核声明。

#### ③ 与 AI 的交互内容

🔴 **必须把「用户输入」与「AI 输出」彻底分开判断，两侧的结论都比预期更严。**

**③-a 用户输入（对着宠物形象说的话）—— 🔴 必须审核，无回旋余地**

依据三重，任一独立成立：《深度合成规定》第 10 条第 1 款「输入数据」· 《生成式 AI 办法》第 14 条第 2 款（要求「发现」，就要求有发现能力）· 《拟人化互动办法》第 13 条。

🔴 **审核到什么程度 —— 这是能否保住调性的关键，两类信号绝不可共用一套阈值：**

| 信号类型 | 处置 | 🔴 关键约束 |
|---|---|---|
| **合规类**（涉政 / 涉恐 / 涉黄 / 教唆犯罪 / 越狱注入）| 拦截 | 🔴 **拦截的是 AI 的回应，不是用户的表达。** 用户已经打出的字**不删除、不报错、不弹「内容违规」** —— 让宠物形象自然地不接这个话题即可 |
| **情绪 / 安全类**（自伤 / 自杀 / 极端悲痛）| 🔴 **绝对禁止拦截** | 用内容安全模型拦截一个丧亲者说「我不想活了」，**既造成二次伤害，又同时违反第 13 条** —— 因为你本该干预而没有干预 |

⚠️ 🔴 **这是最容易做错的地方**：市面上通用内容安全 API 会把「自杀」相关表达**一律判为违规并拦截**。🔴 **Echo 绝不能直接套用通用审核策略。**
🟢 **这一条与既有的生成侧安全闸方向一致**：`S9`（第四关不得在通用位置替用户断言丧失、`deceased` 下 B 组放行）与 `SPEC-security §4.3.2` 的 A/B 组分组，正是为了避免把哀伤语境当成违规语境。🔴 **不是新增要求，是同一件事的法律侧依据。**

#### 🆕 🔴 `CM-G9.1 ③-a′` 提炼为通用纪律：**不同治理目的的信号，一律不得共用阈值或复用判定结果**

> 🔄 **2026-08-25 提炼。** 🔴 **上面那条不是一个具体场景的结论，它是同一条纪律的第三次出现** —— 每一次都在不同规格里被从头论证了一遍。**提炼之后，下一次出现时引用即可。**
> ⚠️ 🔴 **更重要的理由不是省事，是覆盖**：**不提炼，下一处就会漏。** 前三处能被发现，是因为每次都恰好有人在那个上下文里想到了；**第四处不会有人替我们想。**

🔴 **纪律原文**：

> **两条治理链路的目的不同时，它们不得共用阈值，也不得复用彼此的判定结果 —— 即使被判定的是同一段文本、用的是同一个模型。**

🔴 **判准**：问「**这两条链路命中之后，各自要对用户做什么**」。**两个答案不一样，就必须是两条管线。**

**已知的三处实例（🔴 全部是实例，不是三条独立规则）：**

| # | 两条链路 | 共用会怎样 | 落点 |
|---|---|---|---|
| 1 | **合规审核** vs **情绪安全照护** | 🔴 **「我不想活了」会同时触发拦截与关怀，而拦截先发生** —— **用户看到的是「内容违规」**，那正是两份调研都判为最严重的体验伤害 | 本节 ③-a · `§CM-G10` |
| 2 | **依赖判断** vs **危机判断** | 🔴 **两者的处置方向相反**：依赖判断指向「减少介入」，危机判断指向「立即介入」。共用信号会让**一个高频使用的用户被当成危机个案**，或反过来**一个真正的危机被当成依赖信号处理** | `SPEC-intervention-levels.md §2.3` |
| 3 | **分发信号** vs **干涉判据** | 🔴 **投入度既被用来增加触达、又被用来判断依赖** —— **同一个数一边推着用户多用、一边判他用得多**。这不只是逻辑矛盾，🔴 **它使「我们没有用投入度做画像」这句话在举证上无法成立** | `SPEC-intervention-levels.md IL-8` |

⚠️ 🔴 **实现层面的具体形态**：**不得只做一个"打分服务"然后在调用处用不同阈值切**。🔴 **那仍然是共用** —— 共用的是判定结果本身。**必须是两套判据、两套阈值、两条落库路径。**

**③-b AI 输出 —— 🔴 必须审核 + 必须标识，且责任最重**

依据：《生成式 AI 办法》第 9 条（🔴 **法律直接把 Echo 定性为「网络信息内容生产者」**）· 《生态治理规定》第 6 条（生产者不得「**制作**」违法信息，「制作」独立于「发布」）· 《生成式 AI 办法》第 14 条第 1 款「**停止生成**」· 《深度合成规定》第 10 条「合成结果」与第 16 条（标识 + 保存日志）· 《标识办法》第 5 条（元数据隐式标识）· 《拟人化互动办法》第 8 条第（二）（五）（六）项。

🔴 **隐式标识的射程要特别注意**：《标识办法》第 5 条的义务**附着于「生成」动作**。🔴 **即使内容永远停留在私域、永不公开，Echo 也必须在生成的每一份影像 / 音频里写入隐式标识。** 与 `CM-G2` / `§CM-G0S S-8` 同源，🔴 **本条不新增要求，只补法律依据的射程说明**。

📌 **第 8 条第（五）项（诱导情感依赖）已有裁定**：`DECISIONS §G⁗⁗⁗⁗′ DP6` —— **改措辞不改产品**，「加深情感依赖」改写为「长期陪伴与情感连结」，`DP1` 保留为内部态度但不写进对外目标陈述。

### CM-G9.2 🔴 上线前置：安全评估与算法备案（🔴 与用户规模门槛无关）

> 🔴 **这是本节最需要显著登记的一条，因为市面解读普遍把它读错了。**

《人工智能拟人化互动服务管理暂行办法》**第 22 条**原文是「**具有下列情形之一的**」，五项**并列**：

> （一）**上线拟人化互动服务，或者增设拟人化互动服务相关功能的**；
> （二）使用新技术、新应用，导致拟人化互动服务发生重大变化的；
> （三）注册用户 100 万以上或者月活跃用户 10 万以上的；
> （四）存在可能影响国家安全、公共利益等安全风险的；

🔴 **第（一）项就是「上线即触发」。用户规模门槛是第（三）项，是另一个独立的触发情形，不是前置条件。**
⚠️ 🔴 **普遍的误读是把第（三）项当成门槛**（「注册 100 万 / 月活 10 万才需要评估」）—— **调研明确指出这是误读**，且这个误读**恰好会让小产品以为自己不用做**。

**触发后的动作**：开展**安全评估**，并向**所在地省级网信部门提交评估报告**。
**评估重点（第 23 条，等于监管的检查清单）**：安全保障措施建设 · 训练数据处理 · 🔴 **用户极端情境的识别、应急处置、干预管理情况** · 用户规模/时长/年龄结构 · 未成年人与老年人保护 · 申诉与举报处置。
**另有第 26 条**：**算法备案 + 网信部门年度核验**。
**罚则**：第 27 条责令限期重新评估、现场检查；第 30 条责令停止提供服务 + 罚款。

⚠️ 🔴 **归属与阻塞关系（按既定口径写清楚，防止两头落空）**：
- **备案与评估类事项归运营，🔴 不阻塞开发** —— 这是既定口径，本节不改。
- 🔴 **但必须登记为「上线前置」，不能因为归运营就从文档里消失。** 「不阻塞开发」说的是**研发排期**，不是**上线闸门**；🔴 **两者混淆的后果是：开发一路顺利，上线那天才发现少一份省级网信部门的评估报告，而那时补办来不及。**
- ⚠️ **前提仍是「Echo 是否适用该办法」**（`LW-0a`）—— 🔴 **若不适用，本节整条不成立；若适用，它是硬前置。这就是为什么 `LW-0a` 必须尽快定。**

📌 **另一条独立成立、不依赖 `LW-0a` 的评估义务**：《深度合成规定》第 20 条（具有舆论属性或社会动员能力的新产品、新应用、新功能须开展安全评估）与第 19 条（算法备案）。🔴 **Echo 是否构成「深度合成服务」争议远小于拟人化互动**（`LW-0b`），且既有 `F3` 已把「AI 算法备案」列入合规清单。

#### 🆕 🔴🔴 CM-G9.2a 优先级裁定（2026-08-25 制作人）：`§22` 安全评估与显著标识**升为最高优先**

**裁定：**

| | 🔄 |
|---|---|
| **`§22` 上线前安全评估报告 + 显著标识** | 🔴 **最高优先** |
| **主体识别**（`SPEC-subject-recognition-and-degradation.md`）| 🔄 🔴 **降为 P1** |

🔴 **依据是执法事实，不是风险偏好**（`RESEARCH-third-party-likeness-industry-practice.md`，🟢 **一手**）：

- **网信办实际的执法抓手是「未落实<u>安全评估</u>」+「未作<u>显著标识</u>」。**
- 两轮「清朗」专项行动处置 AI 产品 **3500 余款（2025）** 与 **1.4 万余款（2026）**，🔴 **公布的整治重点全部集中在<u>备案、安全评估、标识、训练语料、数据投毒</u> —— 没有一项是「上传端肖像授权核验不到位」。**

⚠️ 🔴 **两条限定，缺一会被读错：**

1. 🔴 **这是<u>顺序</u>裁定，不是<u>取舍</u>裁定。** 主体识别规格的结论**一条都没有被推翻**，敞口也**一处都没有消失**；**P1 的意思是「它排在后面」，不是「它不疼了」。**
2. ⚠️ 🔴 **「未找到」不等于「不会查」。** 调研只是**未找到**要求平台对肖像做事前核验的条文，🔴 **这是未找到反证，不是找到否证**（调研自己把这一条列在了「未解决问题」里）。**据此排序可以，据此认为没有风险不行。**

🟢 **一条与执法无关的独立理由**：安全评估与标识**是我们自己就能做完的事**；🔴 **而主体识别里判定能力最强的一类（涉政）现已改为<u>采购</u>，是外部依赖、有自己的周期。** ⚠️ **把自己能做完的事排在等外部依赖的事后面，是排期上的浪费。**

#### 🆕 🔴🔴 CM-G9.2b 风险登记：殷某桢案 —— **Echo 结构上占的是要赔钱的那个位置**

> 🔴 **本条是风险登记，不是法律意见。** 来源：`RESEARCH-third-party-likeness-industry-practice.md`（🟢 **一手判决**，全国首例 AI 声音侵权案）。

| 谁 | 结果 |
|---|---|

| **做 AI 化处理的技术方** | 🔴 **赔** |

🔴 **因为「平台一般不担责」这个印象的来源，正是本案里免责的那两方（云服务商、采购中介）** —— **他们免责恰恰是因为<u>他们不做生成</u>。** ⚠️ **Echo 做生成。援引他们的免责来给自己壮胆，是把判决读反了。**

### CM-G10.1 分歧一：《拟人化办法》第 13 条的定位 —— **审核义务** vs **照护义务**

| | 报告一的立场 | 报告二的立场 |
|---|---|---|
| **定位** | 把第 13 条列入**第三类（AI 交互）的法定义务清单**，与「对用户输入与生成结果**双侧**做机器审核」「建立识别违法和不良信息的**特征库**」「留存网络日志」**同列一张清单**（第 6 项：「落实极端情绪识别与干预、紧急联系人联络」）| 🔴 **明确否定审核定位**：「**第 13 条不是「审查」义务，而是「照护」义务**……这条极大地改变了「私域该不该看」的性质」；「**这不是内容审核，是安全监测**」|
| **落地形态** | 与其余合规义务一并落地，未单独区分管线 | 🔴 **要求拆成两条独立管线，绝不共用阈值**：合规过滤作用于 **AI 的输出侧**（用户侧无感知）；安全照护作用于**用户的输入侧**，但**输出的不是拦截，而是关怀**。命中后**不删除、不拦截、不上报内容**，而是温和呈现心理援助资源 |
| **一句可直接引用的原文** | （报告一 §3.5）「用 **内容审核** 的工具去处理一个 **危机干预** 的问题，两边都做不好」| （报告二）「**同一句「我想去陪它」，在合规管线里应当完全静默，在照护管线里应当被温柔接住。**」|

⚠️ 🔴 **必须公平指出：两份报告在「不该拿通用违规词表去拦丧亲表达」这一点上是<u>一致</u>的。** 报告一同样写了「自杀自伤内容**不是「违法信息」**……它是**产品伦理与民事风险问题，不是内容治理义务问题**」。
🔴 **真正的分歧不在定性，在<u>落地形态</u>**：报告一把第 13 条放进同一张义务清单，报告二要求它**必须是一条与合规审核物理分开、阈值分开的管线**。
🔴 **这个分歧有实际后果**：若两条管线共用一套模型与阈值，🔴 **「我不想活了」这句话会同时触发拦截与关怀**，而拦截先发生 —— **用户看到的是「内容违规」**，那正是两份报告都判为最严重的体验伤害。

### CM-G10.2 分歧二：用户写给自己的文字**要不要扫**

| | 报告一的立场 | 报告二的立场 |
|---|---|---|
| **结论** | 🔴 **不扫。** 「对私密文字做全量关键词过滤」**不仅没有法律义务，而且是主动制造风险**」| ⚠️ **大体不扫，但有一处例外必须扫**：「🔴 **唯一的例外——《拟人化互动办法》第 13 条**」，要求做**自伤 / 自杀风险的关键词与模型信号识别** |
| **理由** | 这一类**连「潜在受众」都不存在**，是三类中平台义务**最弱**的一类；且行业普遍做全量过滤是「**成本低所以顺手做了，不是法律要求做**」。对 Echo 而言代价与普通产品完全不同：**大面积误判**（死、走了、想陪你……在通用词库里全是高危词）· **对用户的二次伤害** · 🔴 **反向的法律风险**（因误判而删除用户写给亡亲的文字，可能构成违约与人格利益侵害）| 第 13 条要求「及时识别用户面临的安全风险」，且法条明写「**在保护用户隐私权和个人信息的前提下**」。🔴 **扫的是安全信号，不是违规内容**；「这是「照护」，不是「审查」，与产品调性完全一致 —— 对丧亲者产品而言，这甚至是加分项」|

🟢 **两份报告在一个关键边界上完全一致，这一点不要漏读**：**同一句话，不进 AI 与进 AI 是两回事。**
· 报告一：「**同一句话，不进 AI 是第二类，进 AI 就是第三类，义务强度完全不同**」；
· 报告二：「🔴 **如果 Echo 把「给自己」的文字作为上下文喂给 AI 以生成回应，它立刻变成「输入数据」，性质翻转。这是产品设计上必须守住的一道墙，请务必确认技术实现。**」

🔴 **由此得出一条<u>无争议</u>的工程动作，可以先做**：**把「给自己的文字是否进入模型上下文」这件事在实现层确认清楚并写死。** ⚠️ **两份报告的分歧全部发生在「不进 AI」这个分支上；一旦它其实进了 AI，分歧自动消失、两方都指向要处理。** 🔴 **所以这个事实必须先查清，它比分歧本身更前置。**

### CM-G10.4 分歧四：《拟人化办法》的适用对象 —— **模拟人** vs **模拟宠物**

### CM-G10.5 🔴 一处必须纠正的前提错误：第 14 条「虚拟亲属」条款

> ⚠️ 🔴 **本节不是分歧登记，是纠错。这条结论不得照抄进任何合规清单。**

**报告一的原文结论**：

> 「🔴 **『虚拟亲属』这四个字就是 Echo 的核心产品形态。** 一个让用户与已故亲人的 AI 化身对话的功能，就是『虚拟亲属』。该办法对未成年人是绝对禁止（『不得』），没有例外、没有同意豁免。」

🔴 **该结论建立在「Echo 模拟逝去的<u>人</u>」这个前提上，而该前提与既有裁定不符**：

- **`A6`** —— 对逝者（人）极慎重，需专门伦理 + 法务框架后再评估；
- **`A7`** —— **P0 仍只做宠物**，「人」品类**未立项**。

🔴 **正确的写法（照这个写，不要照抄原结论）：**

> **若 Echo 未来开放「人」品类，此条命中；在 P0 只做宠物的前提下，该条不适用。但其适用性与 `LW-0a`（「模拟自然人」是否涵盖宠物）绑定。**

⚠️ 🔴 **末句那个绑定不能省。** 这里有一个容易被忽略的连锁：**若 `LW-0a` 被认定为「宠物也算模拟自然人」，那么「虚拟亲属」的射程是否也随之扩张到「虚拟宠物伴侣」，就成了一个真问题** —— 🔴 **不能一边主张「宠物也算拟人化服务」，一边主张「宠物不算虚拟亲属」**，两个主张用的是同一个「像不像人」的尺子。📌 已登记 `LW-14`。

🔴 **登记它而不是删掉它的理由**：这条结论**在「人」品类那一天是正确的**，而 `A7` 已明确定位放宽是「兼容更多情形」。⚠️ **删掉它，等到真要开「人」品类时，没人记得曾经查到过这一条；照抄它，则现在就会有人按一个不存在的风险去加未成年人年龄识别。** 🔴 **两种错法都要避免，所以是「登记 + 标注前提不成立」。**
